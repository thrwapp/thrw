# 234 — claim state in the UI is local-only, never reconciled with the relay

Also closes **#265** (a handover mute is invisible on macOS). The two were
done together because both are "the menu doesn't say what this device is
actually doing" and both land in the same files; splitting them would have
meant touching `Status/` and the menu construction twice.

## The root cause, and why the fix removes code rather than adding it

All three symptoms in the issue came from one thing: `ManualClaim` kept its
own `held` boolean, written in exactly one place — `toggle()`. So it
answered *"did the user tap Claim on this device?"*, never *"does this
device hold the headset?"*

The tempting fix is to keep the boolean and add writes to it from the
release path. That would have left two records of one fact, which is what
caused this, so instead `isHeld()` now **derives** from the node's existing
`activeEvents` — the set every registration already carries so the relay can
reconcile (#178):

- `packages/adapter-mac/.../ManualClaim/ManualClaim.swift:63`
- `packages/adapter-android/.../claim/ManualClaim.kt:67`

The local boolean and its lock are gone from both. The stale-in-both-
directions bug cannot return in a new form because there is no second copy
left to go stale.

## Criterion 1 — both adapters read the retained state topic

`listenForState()` subscribes to `thrw/{account}/state/{resource}`, decodes
`StatePayload`, and feeds a `HolderState`:

- `MacNode.swift:400`, exposed at `:62` (`holdsClaim()`)
- `AndroidNode.kt:368`, exposed at `:169`

Wired into both runtimes as their own task/coroutine — `NodeRuntime.swift`
and `NodeRuntime.kt` — so one subscription ending cannot take the other
down. A menu that has stopped updating is a much smaller failure than a node
that has stopped hearing commands.

**No topic builder or `NodeInterface` was touched**, per the issue. This is
a read of a topic that already existed.

### Three states, not two

`holdsClaim()` returns `Bool?`. `nil` means *we have not heard* and is
deliberately distinct from "somebody else holds it":

- no retained message yet, or
- the transport is down, so what we last heard is a stale belief.

`{"holder": null}` is a **real** answer (nobody holds it) and reads as
`false`. Collapsing the two would make the UI assert something it does not
know — the failure `NodeStatus.unknown` already exists to avoid.

### One thing I had to add that isn't a mirror

`TopicQos.stateSubscribeQos` / `STATE_SUBSCRIBE_QOS` = 0. `packages/protocol`
specifies only `{ retained: true }` for state and `relay-core`'s
`publishState` passes no QoS, so there was nothing to mirror. Subscribing at
1 would buy nothing (delivery is the lower of the two) while implying a
guarantee the publisher does not make. Documented as a local decision that
becomes a mirror if protocol ever pins one.

## Criterion 2 — the label is derived from holder state

Extracted as a pure function, the same treatment `nodeStatus(...)` gets:
`ClaimAction.swift:55` / `ClaimAction.kt`. The rule:

1. **Manual claim held** → "Release Headset", enabled. Regardless of holder:
   a claim published but not yet granted is still the user's to cancel.
2. **Holds the headset, no manual claim** → a **disabled readout** naming
   why ("Holding — playing media").
3. **Otherwise** → "Claim Headset", enabled. Including unknown holder —
   claiming is always safe and meaningful, so it degrades to the useful
   control rather than to a readout that might be wrong.

Case 2 is a product decision, taken with Tom: a node can only end its *own*
triggers, so when the hold comes from `media`/`voip`/`call` there is
genuinely no action a tap could perform. Offering "Release Headset" would be
a control that visibly does nothing; offering "Claim Headset" was the
original bug. Applied at `AppDelegate.swift:180` and via `setSubText` at
`AdapterForegroundService.kt:346`.

`because` is the **most recently started** trigger, not the highest-ranked
one — adapters do not rank triggers (architecture.md), so it reads the
insertion order both active-event sets already preserve.

## Criterion 3 — a relay RELEASE clears the flag

`MacNode.swift:226` / `AndroidNode.kt:294`, both calling
`endManualClaimIfHeld()` (`:368` / `:339`).

## Criterion 5 — the ambiguous one: ended, not suspended

**Decision (Tom's): a call that outranks a manual claim ENDS it.** The
headset does not return to that device when the call finishes; it follows
the remaining triggers.

Rejected alternative: resume afterwards. A headset that silently reappears
on a device minutes after an unrelated call ended is indistinguishable, from
the user's side, from the oscillation bugs (#236, #251) this project spent
weeks removing.

### The part that is easy to get wrong

Forgetting the claim locally **silently implements the opposite decision.**
The relay keeps its own per-node record of active triggers; if it is never
told the claim ended, it still has `manual_claim` active for that node, and
the moment the outranking call finishes `computeActiveHolder` hands the
headset straight back. The claim would be suspended, not ended, and nothing
in the adapter would look wrong.

So the end is **published**, not merely forgotten — and that is what
`testTheEndOfARevokedManualClaimIsPublishedToTheRelay` /
`the end of a revoked manual claim is published to the relay` pin down.

A failed publish is logged and swallowed rather than failing the release:
`endEvent` removes the local entry *before* publishing (#183), so the next
periodic registration reconciles within one interval. Letting it propagate
would fail the release itself — the headset would stay connected here while
the relay believed it had moved.

## Criterion 4 — the Android notification refreshes on holder change

**Event-driven, not a timer**, via a `StateFlow` on `HolderState` collected
at `AdapterForegroundService.kt:315`.

The kdoc at that file rejected a *timer* on battery grounds, and that
reasoning is untouched and still correct. A subscription does not reopen it:
it rides a topic the node already subscribes to, costs nothing while nothing
is happening, and fires exactly when the displayed text has stopped being
true — which no polling interval can offer. Before this, the Pixel's status
line and action label did not update on a handover the user did not initiate
from that device.

The Mac keeps refreshing in `menuWillOpen` — nobody reads a closed menu.
Same behaviour, different idiom, which is what criterion 6 asks for.

## Criterion 6 — the two adapters mirror each other

`HolderState`, `ClaimAction`, `StatePayload`, the `EventLifecycle`
extension, the derived `isHeld()`, and `endManualClaimIfHeld()` all exist on
both sides with the same semantics, and `ClaimActionTests` /
`ClaimActionTest` are test-for-test identical.

## #265 — the mute is no longer invisible

`HandoverAudioGate.isSuppressing()`, defaulted to `false` in a protocol
extension so `NoOpHandoverAudioGate` needs no code and a node that never
suppresses shows no indicator (criterion 4). `MutingHandoverAudioGate`
implements it at `:135` by reading the store live — holding a record *is*
being muted, so it cannot drift from the real state the way a separate flag
would, and the indicator clears by itself however the mute is undone
(criterion 3).

The menu item (`AppDelegate.swift:127`, refreshed at `:194`) is hidden
unless this Mac is actually muted, and un-muting calls the gate's
`restore()` so the volume **and** the stored record are both cleared
(criterion 2) — clearing only the volume would let the next claim's restore
overwrite whatever the user chose.

## A fixture bug this exposed (not caused)

Both `FakeMqttTransport`s returned **one shared stream for every topic**.
That worked only while the node subscribed to exactly one. With two, an
`AsyncStream`'s elements are *split* between consumers, and Kotlin's
`Channel.consumeAsFlow()` can be consumed only once. The first symptom was
`listenForCommands` tests timing out waiting for a release that had been
delivered to the state listener instead.

Both fakes now route by topic shape. The Kotlin `runTest` cases also needed
`closeAllSubscriptions()` — a flow that never completes keeps a child
coroutine alive, so `advanceUntilIdle()` hung rather than failing usefully.
Worth knowing before the next subscription is added.

## What is uncertain

- **`setSubText` for the disabled-readout case on Android** is my choice,
  not something the issue specified. A `Notification.Action` cannot be
  rendered disabled, so the readout had to go somewhere else in the
  notification. It may read poorly on a real device; that is a
  by-eye check, and it is easy to move.
- **Peer session note (#263):** that change moves the retained state topic
  to `{"holder": null}` after 300s of node silence rather than 90s. The UI
  reads that value, so "nobody holds it" now appears ~3.5 minutes later than
  it used to. Correct, but worth knowing before anyone calibrates timing
  against observed behaviour.
