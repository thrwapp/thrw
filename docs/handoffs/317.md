# 317 — the payload wire contract, pinned as a shared fixture

`topics.json` (#171) pinned the **topic** contract as data because three
hand-written topic builders had nothing asserting they agreed. This does
the same for the **payloads** on those topics, which had the same
exposure and no fixture.

The gap was not inferred. Three separate production files document it in
their own comments:

- `Payloads.swift` — "three hand-written implementations of one wire
  format, and nothing else catches them drifting"
- `CommandTimeout.swift` — "There are three hand-written declarations of
  one number and nothing else catches them drifting"
- `BluetoothConnectionManager.kt:13` — the mirror of that warning

## What landed

- **`packages/protocol/fixtures/wire.json`** — the contract as data:
  three shared constants, six closed vocabularies, the three `kind`
  discriminators, and thirteen canonical wire messages.
- **Four conformance suites reading that one file**, none of them with a
  copy of it: `packages/protocol` (the constants, vocabularies and
  `CommandOutcomePayload`), `packages/relay-core` (the four payloads it
  declares), `adapter-mac`'s `WireFixtureTests`, `adapter-android`'s
  `WireFixtureTest`.
- **A production fix on Android**, below — the fixture found a real wire
  divergence on its first run.

Loaders follow `TopicsFixtureTests.swift` / `TopicsFixtureTest.kt`
exactly: walked up from the source file, never copied into a platform's
test resources, because a copy is the second source of truth the whole
mechanism exists to prevent.

## The bug the fixture found

Kotlin's `CommandOutcomePayload` was publishing **explicit nulls** where
Swift and TypeScript omit the key. `ProtocolJson` sets
`encodeDefaults = true` — which is what puts `kind` on the wire at all —
and that also serialised every nullable field's `null` default.

Three messages diverged:

| Message | Android emitted, extra |
| --- | --- |
| `commandOutcomeSucceeded` | `reason: null` |
| `commandOutcomeTimedOut` | `reason: null` |
| `commandOutcomeUnsequenced` | `epoch: null, seq: null, reason: null` |

**The third one was rejected by the relay.**
`relay-service.ts`'s `isCommandOutcomePayload` accepts an *absent*
`epoch` and rejects a *null* one:

```ts
if (p.epoch !== undefined && typeof p.epoch !== "string") return false;
```

`null !== undefined` is true and `typeof null` is `"object"`, so the
guard fires and the whole outcome is discarded as malformed. That is the
one case those fields are optional in order to support — a command from a
relay that stamped nothing, which is real rather than hypothetical
because the relay half of #210 shipped before the adapter half. ADR
0019's premise is that every command produces a recorded outcome; this
silently dropped one.

**Latent, not live, and worth being precise about:** the current relay
always stamps `epoch` and `seq`, so `commandOutcomeUnsequenced` does not
arise against production today. It arises against an older relay, or any
future path that stops stamping.

The first two were accepted by the relay — the validator only checks
`reason` when the outcome is `failed` — but propagated `reason: null`
rather than `undefined` into `CommandOutcomeReported`. That is the object
#207 is about to persist, and the v1 exit criterion is a switch-success
rate computed from that persisted data. Two shapes for one meaning in the
rows a product decision gets made from. #206 criterion 5 made exactly
this argument about `superseded_by_newer_command`: get the shape right
before data is collected, not after.

Fixed with `@EncodeDefault(EncodeDefault.Mode.NEVER)` on `epoch`, `seq`
and `reason` — targeted, because `encodeDefaults` must stay on globally:
`RegistrationPayload`'s `kind`, and its empty `activeEvents`, have to
stay on the wire (#178 depends on the empty list being sent).

## Design decisions worth knowing about

**`directions`, and why the fixture has it.** Messages are split into
`nodeToRelay` and `relayToNode`, and the two get different assertions: a
sender must *encode* to exactly the fixture object, a receiver must
*decode* it without loss.

This is load-bearing rather than bookkeeping. `stateNoHolder` is
`{"holder": null}`, and Swift's synthesised encoder omits a nil
`Optional`, so re-encoding it produces `{}`. Holding the Mac to that
encode would have failed falsely — adapters never publish state, only
read it — and the obvious "fix" would have been an explicit-null
workaround in an adapter with no reason to serialise the type at all.
Note this cuts the opposite way from the Android bug above: there, an
explicit null was wrong because the adapter *is* the sender.

**The priority order is deliberately not asserted in either adapter.**
`vocabularies.eventKinds` is in priority order because the relay needs
it, but `EventKind`'s own doc comment and architecture.md both require
priority rules to live server-side, "never duplicated in adapters". Both
adapter suites compare the **set** and say nothing about order.
Asserting the order there would be a test enforcing the opposite of the
architecture.

**`CaseIterable` added to six Swift enums.** Without it a Swift test can
check that every fixture spelling decodes, but not that every case
appears in the fixture — so the adapter could grow a kind the relay has
never heard of and nothing would notice. Kotlin enums give this for free
via `entries`; this makes Swift's half of the conformance symmetric.
Zero runtime cost, no behaviour change.

**Runtime assertions only, on the TypeScript side.** Both tsconfigs are
`"include": ["src"]`, so `pnpm turbo typecheck` never sees a test file
and Vitest transpiles without type-checking. A `satisfies` clause in a
test would look like a conformance assertion and be checked by nothing.
See "Uncertain / follow-ups".

## Uncertain / follow-ups

- **`adapter-linux` has no conformance test**, deliberately — it has no
  node interface yet (#271). The fixture is shaped for it to adopt on
  arrival, which was the timing argument for doing this now: the Rust
  mirror is the fourth copy and is cheaper to write against a fixture
  than to reconcile afterwards.
- **`cargo` is not installed on this machine**, so `packages/adapter-linux`'s
  11 tests could not be run locally at all and `pnpm turbo test` from the
  repo root fails there. CI is unaffected (`ubuntu-latest` ships Rust).
  Unverified by me either way.
- **Test files are never type-checked** (`"include": ["src"]` in every
  tsconfig). Worth fixing, deliberately not done here: widening `include`
  may surface existing errors across every package's tests, which is its
  own PR rather than a rider on this one.
- **`heartbeatTimeoutMs` is asserted only as a relationship** (an exact
  3× multiple of the beat interval), not against the relay's own
  constant. `DEFAULT_HEARTBEAT_TIMEOUT_MS` is module-local in
  `relay-service.ts`, and exporting it would touch `services/**`
  (human-merge, FSL) for a test's convenience. The two adapter-side
  interval declarations *are* asserted directly.
- **Nothing here tests behaviour**, only wire shape. A node can be
  perfectly conformant and still decide the wrong thing — that is
  `docs/spec/testing-framework.md`'s job, and this fixture is a
  deliberately smaller, lower-risk instance of the same
  language-neutral-fixture pattern its scenario traces will use.
