# 222 — the relay now publishes the state topic

`architecture.md`'s topic table and ADR 0001 have always specified
`thrw/{account}/state/{resource}`, retained, carrying the current
holder. `RelayMqttClient.publishState` existed and set the retained flag
correctly. **Nothing ever called it.**

Found while running #171's cutover, looking for a stale retained message
that turned out never to have existed.

## The decision, and the argument against it

The spec attaches a specific job to the retained flag:

> a reconnecting node (phone regains signal, laptop wakes up)
> immediately knows who currently holds the connection without waiting
> for the next event — this is what makes recovery from a mobile network
> dropout work smoothly.

**That justification has been superseded.** Recovery is handled by
#178 (periodic re-registration carrying current state), #173 (the relay
re-asserts a claim to a node that registers while still the holder) and
#182 (re-register on reconnect). The reconnecting phone is told what to
do; it does not need to read shared state to find out.

So the honest framing is that this is **observability, not a broken
guarantee**. What still wants it:

- **#213's status surface** can say whether *this* node holds the
  headset, but not which other device does.
- **Diagnosis.** Every investigation during this week's work meant
  subscribing to raw topics and reconstructing holder state by hand from
  the command stream.
- **#206 / ADR 0019** wants somewhere observable for switch outcomes.

Publishing was chosen over deleting the topic from the spec. Deleting
would have been defensible — and it is a frozen-contract change
requiring an ADR — but the value is already computed at exactly the
right moment, and two open issues want to read it.

## The part that was not a few lines

**A retained message outlives the process that wrote it, and this relay
holds all its state in memory** (the premise of #178). After a restart
the broker keeps serving the previous process's answer while the new one
believes nothing — so every node connecting in that window is handed an
authoritative-looking statement the relay would disown. That is #210's
epoch problem in a new place.

Worse, `syncHolder` returns early when the holder has not changed, so it
would never correct it. A relay that restarted during a quiet period
would leave a confident, wrong, retained answer standing indefinitely.

The fix is `ResourceState.publishedHolder`'s **third state**. It is
`string | null | undefined`, and `undefined` is the load-bearing one: it
means *this process has published nothing*, which is not the same as
having published "nobody holds it". `lastHolder` being `null` on both
sides would otherwise look like agreement.

So the publish happens from two places, and both are needed:

- `syncHolder`, on a real holder change — the obvious one.
- **Registration**, which is the only thing that runs after a restart
  with no holder change to trigger it. The first call always publishes,
  because `undefined !== null`, overwriting the stale message. After
  that only a genuine change publishes, so the steady state is silent —
  which matters, since #178 re-registers every node every two minutes
  forever.

A failed publish rolls `publishedHolder` back to `undefined`, so the
next opportunity retries rather than believing it has already announced
that holder.

## Two tests that were wrong first

Both are worth recording, because in each case the failure taught
something about the system rather than about the test.

**`holder: null` when a call ends — wrong.** `currentHolder()` is
`computeActiveHolder() ?? lastClaimed`, so when the last trigger ends
the holder does *not* become nobody: the last claimer keeps it until
something outranks it. That is rule 5, and it is why a call ending does
not fling the headset back to a device nobody is using. The test now
asserts that, and a separate one gets `holder: null` the way it really
happens — the node goes silent and the heartbeat sweep forgets it.

Kept as an assertion rather than a comment: the state topic is the
surface a reader forms their mental model from, so if it ever did report
`null` there, the readout and the arbitration would disagree.

**Counting publishes — wrong.** The "is it quiet?" test subscribed with
`rh: 2` (MQTT 5's "don't send retained on subscribe") on a client that
connects as MQTT 3.1.1, where that option does not exist. The existing
retained message arrived on subscribe and was counted as a new publish.
It now settles and discards once before counting, with a comment saying
why.

## Verification

- `relay-hosted` **23 tests**, green, against a real Mosquitto broker.
  Every state-topic test reads through a **fresh client subscribing
  after the fact**, because a late subscription is the only thing that
  proves retention rather than mere delivery.
- Mutation-tested, five mutations, all killed:
  - drop the publish from `syncHolder` → 6 tests;
  - drop the publish from registration → the stale-overwrite test;
  - `publishedHolder` starts `null` instead of `undefined` → the
    stale-overwrite test (this is the mutation that proves the third
    state earns its place);
  - publish without the retained flag → 7 tests;
  - drop the unchanged-holder guard → the quiet test.

### A methodology note, twice in one day

The retained-flag mutation **survived on the first attempt**, and the
result was meaningless: `relay-hosted` resolves `@thrw/relay-core` to
`dist/`, so editing `src` and re-running the tests exercised the
unmutated build. Rebuilt, the same mutation kills 7 tests.

This is the second time today a mutation result was a lie because a
build artifact was stale — the first was Gradle serving a previous run's
test-results XML during #210. Different tool, identical shape. **When
mutation-testing across a package boundary, prove the mutation reached
the code under test before believing a survivor.**
