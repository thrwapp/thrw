# Handoff: #236 — the holder oscillates Mac/Pixel every ~2 minutes

## What this was

The production relay logged the headset alternating Mac ↔ Pixel roughly
every 90–120s for nine and a half hours overnight on 2026-09-21, with
nobody using either device: 293 `holder_change` and 200 `route_drift`
lines between 16:00 and 01:20 UTC. Found by reading the structured logs
#207 stage 1 (202b3d0) made survivable, while investigating a much smaller
complaint — that the app still offered "Claim Headset" on a device that
was holding the connection (that part is #234, still open).

## The mechanism

Established by experiment, not inference — acceptance criterion 1.

1. **`HeartbeatPublisher.run()` died permanently on one transient error.**
   Both platforms had `while true { publishHeartbeat(); sleep }`, so a
   single throw exited the loop. `NodeRuntime` catches and logs it, and
   nothing restarts it; `onReconnected` only re-registers. The MQTT
   connection recovering does **not** bring heartbeats back.
2. **The relay seeds liveness from the registration, not from a
   heartbeat.** `handleEvent` → `trackHeartbeat`
   (`services/relay-hosted/src/relay-service.ts:364`, `:455`) does
   `lastHeartbeatAt.set(node, now())`. A node with a dead heartbeat
   publisher still looks alive at the moment it registers.
3. **90s later the sweep reaps it** (`:476-497`). `forgetNode` drops
   *every* signal that node had; `syncHolder` moves the headset away.
4. **30s after that it re-registers** (120s cadence). `reconcileSignals`
   re-adds the signals with fresh `orderCounter` values
   (`packages/relay-core/src/index.ts:198`), so they look
   newly-started, and the node takes the headset back.
5. Go to 2. Two nodes on independently phased timers ping-pong.

**Nothing in the relay is misbehaving.** `reconcileSignals` and
`forgetNode` each do exactly what `packages/relay-core`'s own tests
specify. The oscillation is what those two correct rules produce when fed
a node that registers without beating.

### Why nobody noticed for nine hours

The sweep logs nothing. There is no `node_reaped` event among `logEvent`'s
four types, so each reap surfaces only as a bare `holder_change` with no
recorded cause.

It also explains why all 200 `route_drift` events had the identical shape
(`holds=false, believed=self`, never the inverse): a node that was just
reaped and has just re-registered is believed to hold the route while
holding no Bluetooth connection.

### Direct evidence

On the Mac running the deployed adapter, mid-investigation:

```
2026-09-22 07:42:35.713 E [app.thrw.mac:NodeRuntime] heartbeatPublisher failed: noConnection
```

The only line in twelve hours of its unified log, with PID 39144 still
running and still holding an ESTABLISHED connection to the relay on :443.
Connected, still re-registering, permanently not heartbeating.

`services/relay-hosted/test/relay-service.test.ts:357-361` already
described this precise failure mode as the *pre-#142* behaviour that #142
fixed by adding heartbeats. It returns in full whenever the loop dies.

## What was done

Three commits on `agent/236-holder-oscillation`:

- **`288b450`** `test(relay-core)` — four tests showing that a node whose
  *reported* signal set drops and returns takes the headset, and that two
  nodes doing so produce the observed alternation. No production changes.
- **`6ba773a`** `fix(adapter-mac,adapter-android)` — the root-cause fix. A
  failed publish is caught, logged on transition, and the loop keeps
  beating. Cancellation is re-thrown so it still ends the loop. Adds
  `logAdapterInfo` on the Mac so *recovery* is recorded too.
- **`d1d5aee`** `test(relay-hosted)` — the controlled experiment:
  non-heartbeating nodes oscillate (≥6 handoffs), the same nodes
  heartbeating never move.

### A test was deliberately reversed

`adapter-mac`'s `testAFailedBeatPropagatesRatherThanSpinningSilently`
asserted the old contract — that a failed beat must escape `run()` —
because "a transport that can't publish is worth surfacing, not swallowing
into an invisible retry." The concern was right; the remedy caused this
bug. It is replaced by `testAFailedBeatDoesNotEndTheLoop`, and the
"surfaced" requirement is now met by the transition log line, which costs
nothing and does not stop the node heartbeating. This is a considered
contract change, not a test removed to go green.

## What is NOT done

- **The relay-side half.** `trackHeartbeat` arguably should not treat a
  registration as liveness evidence — that is what turns a dead-heartbeat
  node into an oscillation rather than a single clean drop-out. And the
  sweep should log when it reaps a node. Both are `services/**`, which is
  FSL-licensed and human-merge per AGENTS.md, so they are a separate PR.
  The `d1d5aee` tests keep passing either way and stand as the spec for it.
- **Acceptance criterion 3** — reconciling `relay-service.ts:392-398`'s
  claim that a drifted holder "repairs itself on the next registration"
  with 146 observed drifts that never did. Note the re-assert there only
  fires when the holder is *unchanged*, so in the oscillating case it
  never runs at all.
- **Acceptance criterion 4** — verification against the live Mac/Pixel
  pair. The fix is not deployed to either device. Until it is, this is
  green unit tests and a reproduction, not a confirmed field fix.
- **Criterion 5's ADR 0020 question** — whether debouncing belongs here
  at all. Not investigated; the fix above is a correctness fix to a
  retry loop, not a debounce, so I do not believe it conflicts.

## Uncertain / worth a second opinion

- **The Mac's heartbeat died at 07:42 *today*, after the 16:00–01:20
  oscillation window.** So this is the mechanism reproduced and caught in
  the act, but not proof that it was the cause of that specific night. It
  fits every feature of the logged data — the cadence, the drift shape,
  the absence of a logged cause — and I could not construct an
  alternative that does. Treat as very likely, not certain.
- An earlier hypothesis in the issue body — that the self-cooldown /
  `activeEvents` asymmetry (`MacNode.swift:115-118` vs `:135`) was
  producing the gap — is **superseded**, not disproven. It remains a real
  asymmetry that can make a playing node under-report, and could produce
  the same oscillation independently. Worth its own look; not what was
  driving this.
- The `route_drift` volume should fall to near zero once this is
  deployed. If it does not, the cooldown hypothesis above is the next
  thing to examine.
