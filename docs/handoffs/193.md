## The one experiment worth repeating

#303 was diagnosed live rather than from code. The chain:

1. Relay logs showed the Mac registering `activeEvents: ["media"]`,
   `observedRoutes: {}` every 2 minutes for 17 minutes, with
   `reassert_exhausted` alongside.
2. A direct CoreAudio probe measured
   `kAudioDevicePropertyDeviceIsRunningSomewhere = 0` on the only output
   device, and showed the AirPods were not a CoreAudio device at all —
   so the trigger state and the hardware disagreed, measurably.
3. Restarting the adapter, and changing nothing else, cleared **both**
   symptoms in a single registration and the relay logged `route_drift`
   within milliseconds.

Step 3 is what turns a hypothesis into a finding: in-process state was
latched, and both symptoms share one cause. `RouteTransition`'s
unbounded counter is the candidate — `isExecuting()` suppresses the
trigger, `isSettling()` withholds the route — but all three `begin()`
sites are `defer`-balanced, so the mechanism is **not** established and
#303 says so explicitly.

## Tooling added

- **`scripts/qa-capture.sh`** — `start` / `mark` / `status` / `stop` /
  `merge`. One run directory per pass holding the relay's decisions, both
  adapters' logs, and timestamped marks. `merge` interleaves marks with
  relay decisions in time order, which is the view that answers "why did
  it switch then?".
- **`scripts/relay-logs.sh --follow`** — the relay could previously only
  be polled, which either misses lines between polls or reprints the same
  tail.

Both exist because two captures were lost earlier in the week — Swift
`print` block-buffers when stdout is not a terminal, and `adb logcat`
overran the device ring mid-session. A finding you cannot re-observe is
not evidence.

## Verified on this tree

- `bash -n` on both scripts.
- **`qa-capture.sh` was used for the whole pass**, which is the real
  check: every quoted log line above came out of it. Two bugs found and
  fixed while doing so — an ambiguous-redirect line count, and
  `adb logcat -G 16M` never returning on the Pixel 10 Pro (it behaves as
  a follow rather than setting the size and exiting), which killed the
  Android capture on first run.
- No package code changed, so no package test suite applies.

## Not verified

- **`adb logcat -G` is skipped, not replaced.** The device-side ring is
  whatever the Pixel defaults to. Continuous draining from second one is
  the mitigation, and it held for this run; a genuinely multi-day capture
  (issue item 5) may still want a larger ring, set by some other means.
- **The Mac capture produced nothing all session**, and that is expected
  rather than broken: `Triggers/` and `Route/` contain no logging at all.
  It is also why #303's Mac-side behaviour is entirely inferred from
  relay traffic, and why "make those paths log" is an acceptance
  criterion there.
- `.info`-level os_log records are memory-backed and do not survive for a
  later `log show`. Streaming catches them live; retroactive diagnosis
  needs `sudo log config --subsystem app.thrw.mac --mode
  "level:info,persist:info"` first. That needs a password, so it was not
  done — worth doing before any multi-day run.

## Resumed 2026-09-26/27 — items 1 and 2 done

**Item 1 (call trigger and auto-return): passes**, both outgoing and
incoming, verified physically on both devices at each step. Four calls
total, four clean handovers. Timings are in the matrix; the headline is a
**3340ms** claim, the second real measurement against #254's single ~4.9s
sample, both inside the coalescer's 6s window.

Two things it did **not** establish, recorded so nobody reads more into
it than happened:

- **#302's guard never fired.** Every call landed on a node that was not
  the believed holder, so they produced genuine holder changes through
  ordinary arbitration. The shape #302 fixes remains unverified.
- **Auto-return has two modes and both are correct.** Immediate when the
  previous holder still has a live trigger; after `DEFAULT_AUTO_RETURN_MS`
  (90s) when it does not. The 90s case was briefly written up here as
  "the headset does not come back" — it does. That was my error, from
  reading the log before the timer elapsed.

**Item 2 (manual claim): the online half passes, the offline half fails**
as ADR 0020 decision 2 says it must. Details in the matrix. First hardware
verification of #234 criterion 5 (a released node ends its claim rather
than suspending it).

## Two harness failures, both found by using it

Worth more than the features they fixed:

1. **An SSH tunnel to the production relay leaked on every run.**
   `relay-logs.sh --follow` wraps `gcloud compute ssh`, which spawns an
   ssh and an IAP tunnel; killing only the recorded pid orphaned them.
   Two were still connected after the first pass. Fixed with
   `kill_tree`. Nothing failed — found by checking for strays.
2. **`status` reported the relay "capturing" for 35 hours while nothing
   arrived.** The tunnel died and the wrapper survived, so liveness was
   being measured by the pid. That is exactly the failure the harness
   exists to prevent. Now measured by the capture file's mtime against a
   per-source threshold.

**Before item 5 is attempted properly, two things from this session:**

- **gcloud auth expires mid-run** — twice in 36 hours. A multi-day
  capture needs a service account key, or the follower running on the VM
  itself. Otherwise the relay stream reliably dies partway through, and
  until the fix above it did so silently.
- **The Pixel dropped off `adb` twice**, each time needing a replug.
  Losing the phone loses half the evidence.

Item 5 is also better run *after* #307 and #303 are fixed — against a
build that still has #307 it will mostly re-find #307.
