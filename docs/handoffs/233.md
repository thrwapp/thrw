# HANDOFF: deploy-site migrated off the removed cloudflare/pages-action (#233)

## What was done

`.github/workflows/deploy-site.yml` now deploys with
`cloudflare/wrangler-action@v4` running `pages deploy` instead of
`cloudflare/pages-action@v1`, which Cloudflare archived and whose
repository now returns 404.

Nothing else changed. The build steps, the trigger paths, the
concurrency group and the `deployments: write` permission are all
untouched.

## Why it broke without anyone touching it

Action resolution happens during **Set up job**, before the first step
runs, so the failure is total and unrelated to the diff that triggered
it. The workflow last ran green on 18 September and was not edited
since; it failed on #232's merge only because that was the next push
matching `content/site/**`. Any push would have done it.

Run [35701955532](https://github.com/thrwapp/thrw/actions/runs/35701955532):

```
##[error]Unable to resolve action `cloudflare/pages-action`, not found
```

## What had to survive the swap

Both of these already had comments in the workflow explaining what they
cost to learn the first time, and both are preserved:

- **`workingDirectory: content/site`.** Wrangler resolves `functions/`
  against its own cwd, not against the output directory. `dist` in the
  new `command` is relative to `workingDirectory`, so the output
  directory and the functions directory still both resolve inside
  `content/site`. Getting this wrong does not fail the build - it
  silently ships a site with no `/waitlist` endpoint.
- **`gitHubToken` and `deployments: write`.** `wrangler-action` creates
  a GitHub Deployment through the REST API the same way the old action
  did, so the scope is still required. Dropping it would 403.

## Acceptance criteria, with evidence

**1. The workflow file is valid and references the new action.** Parsed
rather than eyeballed:

```
$ ruby -ryaml -e '...' .github/workflows/deploy-site.yml
PARSED OK
uses: cloudflare/wrangler-action@v4
with: {"apiToken":..., "workingDirectory":"content/site",
        "command":"pages deploy dist --project-name=${{ vars.CLOUDFLARE_PAGES_PROJECT }}",
        "gitHubToken":..., "packageManager":"pnpm"}
permissions: {"contents"=>"read", "deployments"=>"write"}
```

**2 and 3 (green run, working `/waitlist`) are NOT verified.** They
cannot be from a branch: `deploy-site` only triggers on pushes to
`main` and `workflow_dispatch`, and a `workflow_dispatch` run replays
the workflow file from the ref it runs on - so this is only testable
once merged. See "What to check after merging".

## What to check after merging

1. `gh workflow run deploy-site.yml` and confirm it completes green.
2. `curl -X POST https://thrw.app/waitlist -H 'content-type: application/json' -d '{}'`
   returns **JSON**, not Cloudflare's default 404 HTML. That is the
   check that proves the Pages Function deployed, and it is the failure
   this workflow has already shipped once.
3. Confirm the site serves #232's changes, which are built but
   unpublished until this lands.

## Known gaps / judgment calls

- **`packageManager: pnpm` is the one unverified choice.** AGENTS.md
  says pnpm, never npm, and this input is what fetches wrangler - but
  the action's default is npm and pnpm is the less-trodden path here.
  If the deploy fails inside the action's own setup rather than in
  `pages deploy`, drop the input first; it is not load-bearing.
- **`wranglerVersion` is deliberately unpinned.** Pinning would trade
  this class of surprise for manual bumps. Worth reconsidering if a
  wrangler major ever breaks the deploy - but note that pinning would
  not have prevented *this* outage, which was the action being deleted,
  not a version changing under us.
- **The site itself was never down.** The last successful deploy stayed
  live throughout; only publishing new changes was blocked.
