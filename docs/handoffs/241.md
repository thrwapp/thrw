# 241 — relay log archives nobody could read

#207 built the writing half of log archiving and none of the reading
half. The archives were real, the deploy output announced them, and no
human could open them:

```
2026-09-22T08:42:42Z Archived relay logs to /root/thrw-logs/relay-20260922T084241Z.log (79 lines)
```

Confirmed live on the relay VM before changing anything, which is worth
recording because it is the whole bug in three lines:

```
$ gcloud compute ssh thrw-relay --tunnel-through-iap --command='id -un; ls -la /var/log/thrw; ls -la /root/thrw-logs'
tmiller
ls: cannot access '/var/log/thrw': No such file or directory
ls: cannot access '/root/thrw-logs': Permission denied
```

An interactive session lands as `tmiller`. `/root` is mode 0700. The
evidence existed and was unreachable — the failure mode #207 set out to
remove, wearing a different coat.

## The comment was wrong, not just the path

`relay-redeploy.sh` recorded a false premise as settled reasoning, which
is why criterion 2 asks for the comment and not only the path:

> Under `$HOME`, not `/var/log`: nothing in this script uses sudo (docker
> runs via the SSH user's docker group), so `/var/log/thrw` would not be
> writable …

`deploy.yml:140` invokes it as `sudo bash ~/relay-redeploy.sh`. The
script runs as **root**, `$HOME` is `/root`, and `/var/log/thrw` was
writable the entire time. The reasoning did not just pick the wrong
path — it picked the wrong path *because* it believed it had no
privileges it in fact had. The replacement comment
(`scripts/relay-redeploy.sh:53-81`) says that, so the next person does
not re-derive the same false conclusion.

## What changed

**`scripts/relay-redeploy.sh`**

- `:82` — `LOG_ARCHIVE_DIR` defaults to `/var/log/thrw`, not
  `$HOME/thrw-logs`. `THRW_LOG_ARCHIVE_DIR` still overrides it, for a
  by-hand recovery run without root.
- `:88-95` — `ensure_archive_dir` chmods the directory to 0755
  explicitly. `mkdir -p` honours umask, so root's umask would otherwise
  get to decide who can reach the archive, which is precisely the bug.
  Archive files are chmodded 0644 at `:156`.
- `:107-112` — `readable_without_sudo` probes by *reading the file as
  `nobody`*, not by inspecting mode bits. Readability depends on
  traversal permission on every ancestor directory; a single `stat`
  cannot see that, and an unreadable ancestor is exactly how #241
  happened. It returns 2 ("cannot tell") when the run is not root,
  reported as such rather than as a warning it has no evidence for.
- `:158-166` — the deploy output now states, per archive, whether it is
  readable without sudo (criterion 3). "Wrote the file" and "a human can
  read the file" are different claims and only the second is the point.
- `:119-144` — `migrate_legacy_archives` moves pre-#241 archives out of
  `/root/thrw-logs` (and `$HOME/thrw-logs`) into the new location, once,
  on the next redeploy (criterion 4). Moved rather than copied: a second
  unreadable copy left behind is how this stayed invisible. `mv -n`, so
  a collision can never silently discard a distinct archive.

**`scripts/relay-logs.sh` (new)** — criterion 5 names
`./scripts/relay-logs.sh --archives`. **That script did not exist** —
not in `scripts/`, not anywhere in git history. #207 shipped the write
side and nothing to read it with, which is a fair part of why the
archives could sit unreachable for two weeks without anyone noticing.
Added here: `--archives` lists them, `--cat <file>` prints one,
`--live [container]` tails a running container.

`--archives` deliberately uses **no sudo**, and exits non-zero if the
directory is unlistable or any file is unreadable. It is a regression
test for this bug that a human can run in one command, not just a
convenience.

## Verification

Criterion 5 asks for a real redeploy, because a green workflow does not
prove a human can read the result. See the PR description for exactly
what was and was not run against the live VM — if it says the redeploy
is still pending, then it is pending, and nothing here should be read as
claiming otherwise.

What was verified locally, in a `debian:bookworm-slim` container running
as root (the same shape as the real run — the archive block extracted
and `eval`'d verbatim from the script, with a stubbed `docker`):

```

  Readable without sudo: yes - verified by reading it as an unprivileged user

  (nobody read it)

=== CASE B: the pre-fix location, to prove the check catches it ===

WARNING: /root/thrw-logs/relay-20260923T202329Z.log is NOT readable without sudo - an interactive SSH user cannot read this archive (#241)
```

Case B is the important one: pointed at the old path, the new check
fails loudly instead of reporting success. Migration was exercised
separately against a stubbed `/root/thrw-logs` holding a 1-line and a
496-line archive (the shape of the real pair): both moved, mode 600 →
644, empty directory removed, and the fresh archive written alongside.

`pnpm turbo test --filter=@thrw/relay-hosted` — 23 tests pass, including
the real-broker integration suite. Unaffected by this change, as the
issue predicted; run rather than assumed.

## Uncertain, and one thing a reader should know

**A `scripts/` change does not trigger a deploy.** `deploy.yml`'s `paths`
filter is `packages/relay-core/**`, `services/relay-hosted/**`,
`services/licensing/**`. `scripts/relay-redeploy.sh` is not in it, so
**merging this PR will not put it on the VM** — it reaches the VM on the
next deploy triggered by something else, or via `workflow_dispatch`.

That is its own instance of this issue's pattern: a fix that merges,
reports green, and silently does not take effect. Worth adding `scripts/
relay-redeploy.sh` to that `paths` list, but `.github/**` is human-merge
per AGENTS.md, so it is a separate PR and is deliberately not in this
one.

**World-readable was chosen over root:adm 0640.** GCE's guest agent does
add SSH users to `adm`, so 0640 would probably also have worked and
would be the more conventional `/var/log` posture. 0755/0644 was chosen
because criterion 1 explicitly allows it, it does not depend on guest-
agent group behaviour staying true, and the probe verifies the actual
guarantee rather than assuming it. What lands in these files is
operational events — holder changes, route drift, account and node ids.
The EMQX credential is not among them: the entrypoint writes it to a
mode-0600 file inside the container, and the script passes it via a
mode-0600 env file rather than argv. If the account id is ever treated
as sensitive (#207 raises exactly that question for telemetry), this
choice should be revisited.

**Retention interacts with migration.** The prune keeps the newest 20
per container and migrated files keep their mtimes, so migrating more
than 20 older archives at once would delete the oldest. There are only
a handful on the VM today, so this is theoretical — noting it because
the first run is the only one where it could bite.
