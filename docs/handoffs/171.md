# 171 — resource-type segment in the MQTT topics (ADR 0015)

The flag day. `packages/protocol`, `relay-core`, `relay-hosted` and both
adapters change together, because old and new topic structures are
mutually incompatible — a node on one is invisible to a relay on the
other, with no overlap window.

## One PR, deliberately

The scope comment proposed one PR per lane, merged back-to-back. That was
wrong: any window with half of it merged is a broken `main`. The lanes
govern *review requirements*, not PR boundaries, and a change touching
`packages/protocol` (frozen contract) and `services/**` is human-merge
either way — so splitting buys nothing and costs a broken-main window.

## The three decisions

**(b) Per-resource priority engine — done now.** `AccountState` split in
two: the registry and liveness stay per-account, because they are facts
about *nodes* (a manifest describes one device; a heartbeat says its
process is running). A new `ResourceState` holds the engine and
`lastHolder` per resource type, because ADR 0015 makes priority rules
resource-specific — "a call is ringing" has no sensible mapping onto
"should the keyboard switch".

With one resource type this is a pure re-key with no behaviour change,
which is exactly why it was worth doing now: it stops being mechanical
the moment `hid` exists.

**(c) A missed heartbeat forgets the node from every resource's engine.**
Liveness is evidence about the node, not about one resource — a phone
that has gone silent has gone silent for audio and HID alike. Leaving it
as the holder of one resource while forgetting it from another would
strand exactly the stale-winner bug #130 closed. The alternative,
per-resource liveness, would need per-resource heartbeats, which ADR 0015
does not specify.

**(d) Cross-platform topic fixture — included, and it earns its place.**
`packages/protocol/fixtures/topics.json` pins every topic string, and all
three implementations assert against it: TypeScript, Swift and Kotlin.
They are hand-written mirrors and *nothing* previously checked they
agreed, so a typo in one would surface only as a node going quiet on real
hardware — the same failure shape as #174, #175 and #182, and the risk
peaks here because all three move at once.

Proven rather than asserted: swapping two segments in the Kotlin mirror
fails the Kotlin fixture test, and the same mutation in Swift fails the
Swift one.

## What did *not* change, and why

**Heartbeat keeps no resource segment.** ADR 0015 lists exactly three
topics that gain one. Liveness is per-node. Adding a segment here would
also mean per-resource heartbeats, multiplying traffic for no signal —
and it is precisely the kind of thing that gets "helpfully" made
consistent during a migration and then silently breaks the reaper.

**Sequence numbers are not in this PR.** ADR 0018's sequencing paragraph
says they should ride this flag day; that is wrong and is corrected in
#210 — adding fields to a command payload is additive and ignorable
(both adapters already tolerate unknown keys, with tests), so it has none
of the all-at-once character the topic change has.

## The parser is the only guard

`nodeFromEventsTopic` now returns `{ node, resource }` and **validates**
the resource segment rather than casting it. It is the only thing between
a topic off the wire and the priority engine, and the resource type now
selects *which engine* a message reaches — so an unrecognised one is
dropped rather than quietly creating state for a resource nothing
manages.

## Verification

All five suites: protocol 35, relay-core 43, relay-hosted 16,
adapter-mac 152, adapter-android green. The real-broker integration tests
in `relay-core` and `relay-hosted` are the closest thing to a contract
test between relay and adapters, and they pass on the new structure.

## NOT DONE — the cutover itself

**This PR is the code change only.** Merging it does not complete the
migration:

1. **Redeploy the relay.** Until then the deployed relay speaks the old
   structure and the new adapters are invisible to it.
2. **Clear the stale retained message** on the old `thrw/{account}/state`
   topic. It is retained, so it outlives the redeploy and will mislead
   anyone inspecting the broker; publish an empty retained payload to it.
3. **Rebuild and reinstall both adapters.** #188/#189 now produce
   installable artifacts, so this no longer needs local builds with a
   hand-written credential overlay.
4. **Verify on hardware** (criterion 6): both nodes register, heartbeat,
   and complete a real handoff. Anything less has not proved the
   migration.

Between steps 1 and 3 the system is down by construction. That is what a
flag day means here, and with two devices and no customers it is minutes.
