# HANDOFF: composition root for packages/adapter-android (#96)

## What was done

This issue turned out to require a prerequisite that no earlier issue
delivered: `packages/adapter-android` was still a plain Kotlin/JVM Gradle
module, not the Android Gradle Plugin (AGP) — no `android.jar` on the
compile classpath, no `AndroidManifest.xml` at all. Every real
`android.bluetooth`/`android.telephony`/`NotificationListenerService`-backed
implementation this issue's wiring depends on had been deliberately
deferred behind interfaces with that exact justification ("lands once the
module moves to AGP") since #66, and #66's own handoff explicitly flagged
this and punted: "Flagging this for human judgment rather than guessing
whether to do the AGP swap in this PR." That flag was never acted on
before #96 was filed, so #96's acceptance criteria (a real `Service`,
`AndroidManifest.xml`, a `NotificationListenerService`) assumed a
precondition that didn't actually hold. I raised this with Tom directly
mid-session; he asked me to do the AGP migration as part of this PR, and
then — once it was clear the composition root would otherwise be wired to
literally nothing (no real gateway/call-state/notification
implementations existed either) — also asked me to write those real
implementations rather than stub ones. Both decisions are his, not
something I inferred from the issue text alone.

So this PR is larger than #96's own text describes. In order:

**AGP migration** (not in #96's acceptance criteria, but a hard
prerequisite):
- `packages/adapter-android/settings.gradle.kts` — added `pluginManagement`
  with `google()`/`mavenCentral()`/`gradlePluginPortal()`.
- `packages/adapter-android/build.gradle.kts` — declares
  `com.android.application` 8.7.3, `kotlin("android")` 2.1.0,
  `kotlin("plugin.serialization")` 2.1.0 (all `apply false`).
- `packages/adapter-android/app/build.gradle.kts` — switched from
  `kotlin("jvm")` to `id("com.android.application")` + `kotlin("android")`;
  added the `android {}` block (`namespace`, `compileSdk 35`, `minSdk 31`,
  `targetSdk 35`, `versionName "0.1.0"`, `buildFeatures.buildConfig = true`,
  `testOptions.unitTests.isReturnDefaultValues = true`). The existing
  `generateAdapterBuildConfig` task (ADR 0005) needed an explicit
  `tasks.withType<KotlinCompile>().configureEach { dependsOn(...) }` —
  wiring a generated dir into `android.sourceSets` doesn't add a task
  dependency the way it did under the plain Kotlin/JVM plugin's
  `kotlin.sourceSets`, and the generated file was silently stale/missing
  without this.
- `packages/adapter-android/app/src/main/AndroidManifest.xml` — new.
  Permissions: `INTERNET`, `BLUETOOTH_CONNECT`, `READ_PHONE_STATE`,
  `POST_NOTIFICATIONS`, `FOREGROUND_SERVICE`,
  `FOREGROUND_SERVICE_CONNECTED_DEVICE`, `RECEIVE_BOOT_COMPLETED`.
  Declares `AdapterForegroundService`
  (`foregroundServiceType="connectedDevice"`),
  `triggers.AndroidNotificationListenerService`
  (`BIND_NOTIFICATION_LISTENER_SERVICE`), and `BootCompletedReceiver`.
- `packages/adapter-android/app/src/main/res/values/strings.xml` — new,
  the foreground notification's text plus its channel name.
- `packages/adapter-android/local.properties` — new, gitignored
  (`.gitignore` already excluded it before this PR), points at this
  machine's SDK.
- `.github/workflows/ci.yml`'s `android` job — added an "Install Android
  SDK" step (Google's own `cmdline-tools` archive, no third-party Action):
  `platform-tools`, `platforms;android-35`, `build-tools;35.0.1`, matching
  `compileSdk`/`build-tools` above exactly. Previously the job only set up
  Java. **This file is always human-merge per AGENTS.md regardless of
  directory — flagging clearly that this PR touches it, not routing
  around that.**

**Real seam implementations** (also not in #96's text; see above for why
they're here):
- `bluetooth/AndroidBluetoothClassicGateway.kt` — real
  `BluetoothClassicGateway`, `BluetoothAdapter.getRemoteDevice` +
  `createRfcommSocketToServiceRecord`(SPP UUID) + `socket.connect()`/`close()`,
  the concrete implementation `BluetoothClassicGateway`'s own kdoc
  anticipated since #66.
- `triggers/AndroidCallStateSource.kt` — real `CallStateSource`,
  `TelephonyManager.registerTelephonyCallback` +
  `TelephonyCallback.CallStateListener` (API 31+ only — no
  `PhoneStateListener` fallback; see "Judgment calls" below).
- `triggers/AndroidNotificationListenerService.kt` — real
  `NotificationListenerService` subclass, bridging its instance callbacks
  to a companion-object `MutableSharedFlow`, replaying
  `activeNotifications` on `onListenerConnected` (`NotificationSource`'s
  kdoc explicitly calls for this replay). `AndroidNotificationSource`
  (same file) is the tiny `NotificationSource` that collects it, since
  `VoipTriggerMonitor` is constructed in a different component
  (`AdapterForegroundService`) with a different, system-independent
  lifecycle from the listener service itself.

**The composition root itself** (#96's actual text):
- `identity/DeviceIdentity.kt` — generates and persists a stable
  per-install `nodeId` (`UUID`, `SharedPreferences`) and builds the
  `NodeManifest` `register()` sends. `supportedEventKinds` only lists
  `CALL`/`VOIP` — the two triggers this adapter has a real monitor for —
  not `MEDIA` (no detector exists anywhere in this codebase) or
  `MANUAL_CLAIM` (nothing here emits it).
- `identity/AdapterProvisioning.kt` — reads `accountId`/`headsetAddress`
  from `SharedPreferences`; see "Known gaps" below, there's no UI that
  writes them yet.
- `NodeRuntime.kt:22,34` — the testable half: plain Kotlin, no
  `android.*` imports, launches `register`, `listenForCommands`, and both
  monitors each as their own coroutine in a caller-supplied
  `CoroutineScope`.
- `AdapterForegroundService.kt:44` — the untestable half: a real
  `Service`. `onCreate` (`:51`) creates the notification channel.
  `onStartCommand` (`:56`) calls `startForeground` first and
  unconditionally (`:60`, before any suspending work, per Android's
  few-seconds requirement), then checks `AdapterProvisioning` and either
  `stopSelf`s with a clear log line or launches a coroutine (`:73`) that
  connects `HiveMqttTransport`, constructs the real `AndroidNode` and both
  monitors, and hands them to `NodeRuntime` (`:87`).
- `BootCompletedReceiver.kt:18` — starts the service on
  `ACTION_BOOT_COMPLETED`.

## Acceptance criteria, with evidence

**1. Foreground `Service` that constructs a real `BluetoothConnectionManager`,
`HiveMqttTransport` (via `RelayConfig`), and `AndroidNode`; calls
`register(manifest)`; launches `listenForCommands()` in a scoped
coroutine; wires `CallTriggerMonitor`/`VoipTriggerMonitor` to the same
node.** `AdapterForegroundService.kt:73-88` does all of this inside one
`scope.launch` block: `HiveMqttTransport.connect(relayConfig, clientId =
nodeId)` (`:80`), `BluetoothConnectionManager(AndroidBluetoothClassicGateway(...))`
(`:82`), `AndroidNode(accountId, nodeId, headsetAddress, hiveTransport,
bluetooth)` (`:83`), both monitors (`:85-86`), then
`NodeRuntime(...).start(scope, manifest)` (`:87`), which itself calls
`register`/`listenForCommands`/both monitors' `run()` (`NodeRuntime.kt:35-38`).

**2. Lifecycle: starts on boot or launch (documented), survives config
changes, cancels/disconnects on stop.** Starts on boot —
`BootCompletedReceiver.kt:18-21` — documented judgment call in that file's
own kdoc (no launcher `Activity` exists for "app launch" to mean anything
yet). Configuration changes: a `Service` (unlike an `Activity`) is not
restarted on a config change by default, so nothing extra was needed — a
real gap this criterion's phrasing anticipates but genuinely doesn't apply
to a `Service`, noted here rather than adding dead code to address it.
`onDestroy` (`AdapterForegroundService.kt:96-104`) cancels the
`SupervisorJob` and best-effort closes the transport — see "Known gaps"
below for the one real caveat on this.

**3. `AndroidManifest.xml` with the service declaration and genuinely
required permissions; confirm `VoipTriggerMonitor`'s
`NotificationListenerService` manifest entry is present and correct.**
`AndroidManifest.xml:32-49` declares `AdapterForegroundService`
(`foregroundServiceType="connectedDevice"`, requiring the
`FOREGROUND_SERVICE_CONNECTED_DEVICE` permission at `:22`) and
`triggers.AndroidNotificationListenerService` with
`BIND_NOTIFICATION_LISTENER_SERVICE` (`:45`) and the required
`intent-filter` action (`:47`). Per #86, this entry did not previously
exist at all (no manifest existed) — confirmed by `find` for
`AndroidManifest.xml` before this PR, empty result.

**4. Tests cover the wiring/construction logic via a testable seam, not
the entire `Service` lifecycle.** `NodeRuntime.kt` is that seam — plain
Kotlin, zero `android.*` imports. `NodeRuntimeTest.kt` (5 tests): manifest
registration (`:78`), commands-topic subscription (`:98`), the call
monitor wired through to a fake transport (`:115`), the VoIP monitor wired
through (`:139`), and that all four launched coroutines run independently
rather than sequentially (`:169` — this one would hang and time out if
`NodeRuntime.start` awaited each `launch` in turn instead of firing all
four). `AdapterForegroundService`/`BootCompletedReceiver`/
`AndroidNotificationListenerService`/`AndroidBluetoothClassicGateway`/
`AndroidCallStateSource` are **not** unit tested — each extends or calls
real `android.*` framework classes that only run under
Robolectric/instrumentation, neither of which this PR adds (no
justification for a new dependency beyond what this one composition-root
issue needs). This matches every prior seam in this codebase
(`BluetoothClassicGateway`, `CallStateSource`, `NotificationSource`): the
interface/testable half is tested against fakes, the framework-backed
half is not.

**5. No connection state machine.** Grepped the full diff for
`pre-claim`/`preclaim`/`cooldown`/state-machine-shaped enums beyond the
pre-existing `BluetoothConnectionState` — no matches. `AndroidNode`
(untouched) still only exposes the plain `onClaim`/`onRelease` hooks.

**6. No new dependency beyond what's in this module, unless justified.**
No new Gradle *library* dependency — `hivemq-mqtt-client`,
`kotlinx-coroutines-core`, `kotlinx-serialization-json`,
`kotlinx-coroutines-test`, `moquette-broker` are all pre-existing and
unchanged. The AGP/Kotlin-Android *plugin* additions
(`com.android.application`, `kotlin("android")`) are the prerequisite
covered above, not an app dependency in the usual sense; no androidx
artifact was added anywhere (`AndroidCallStateSource`'s kdoc notes
explicitly avoiding `ContextCompat.getMainExecutor` for exactly this
reason).

## Known gaps / judgment calls

- **No provisioning UI.** `AdapterProvisioning.accountId`/`headsetAddress`
  read `SharedPreferences` keys nothing in this codebase writes yet — no
  pairing/settings `Activity` exists (out of scope for a composition-root
  issue). `AdapterForegroundService` treats both being unset as "not
  provisioned" and `stopSelf()`s with a clear log line rather than
  connecting a half-configured node. This is the biggest real gap: the
  service compiles, tests, and is wired correctly, but **cannot do
  anything on a real device today** without something (adb, or a future
  settings screen) writing those two `SharedPreferences` keys by hand
  first.
- **minSdk 31**, chosen so `TelephonyCallback`
  (`AndroidCallStateSource`) and `CallStyle`'s `EXTRA_CALL_TYPE`
  (`AndroidNotificationListenerService`) both work without a legacy
  `PhoneStateListener` fallback path. Matches the reference hardware
  (Pixel 10 Pro, architecture.md) but is a real floor above whatever the
  product's actual minimum-supported-Android-version decision turns out
  to be — that decision doesn't exist anywhere in this codebase yet
  either, so I picked the value that let the real implementations stay
  simple rather than guessing at a lower one.
- **Runtime permissions.** `BLUETOOTH_CONNECT`, `READ_PHONE_STATE`, and
  `POST_NOTIFICATIONS` are all dangerous/runtime permissions declared in
  the manifest but never requested — there's no `Activity` in this PR to
  host that dialog, and `NotificationListenerService` access specifically
  has no dialog at all (Settings-only, user-granted). Every real
  implementation that needs one is `@SuppressLint("MissingPermission")`'d
  at the call site rather than silently ungated.
- **`onDestroy`'s transport close is best-effort.** A plain `Service` has
  no `goAsync()`-style mechanism to block teardown for async cleanup;
  `HiveMqttTransport.close()` is launched on a fresh, uncancelled
  `CoroutineScope(Job())` so it isn't immediately cancelled by `job.cancel()`
  right after, but if the process dies immediately, that close may never
  complete. Not fixed here — flagging rather than guessing at a bigger
  fix (e.g. a foreground-service-specific extended teardown window) that
  wasn't asked for.
- **Configuration-change survival** (criterion 2) doesn't really apply to
  a `Service` the way it does to an `Activity` — noted above, not coded
  around.
- **AGP/build-tools/compileSdk version pinning.** `app/build.gradle.kts`
  and `.github/workflows/ci.yml`'s new SDK-install step have to be kept
  in sync by hand (documented in both places) — there's no single source
  of truth for these version numbers across the two files.
