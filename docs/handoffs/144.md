# #144: adapter-mac launch at login

## What was done

The Mac app can now start itself at login, via `SMAppService.mainApp`
(macOS 13+, which the package already targets). Android has had this
since #96 (`BootCompletedReceiver`); the Mac app previously had to be
launched by hand after every restart — which for a headset-handoff
daemon is worse than useless, because the user only notices when a
handoff silently doesn't happen.

Same split as the rest of the package:

- **Testable** — `Identity/LoginItem.swift`: the state model and every
  decision made about it (checked/unchecked, what a click should do,
  what to explain). 11 tests.
- **Untestable** — `Identity/SMAppServiceLoginItem.swift` (real
  `SMAppService`; every call mutates the user's real Login Items and
  needs a real bundle) and `AppDelegate`'s menu plumbing.

## The research question, answered empirically

The issue insisted this be checked rather than assumed. It was, by
building a throwaway **unsigned** `.app` bundle and calling the real API:

```
bundleID: app.thrw.mac.smtest
bundlePath: /private/tmp/.../SMTest.app
status BEFORE:            notFound
register():               SUCCEEDED
status AFTER register:    enabled
unregister():             SUCCEEDED
status AFTER unregister:  notRegistered
```

**1. `SMAppService.register()` works for an unsigned, un-notarized
bundle** — and from outside `/Applications` (this ran from `/private/tmp`).
So this feature is genuinely usable today and does **not** have to wait
for #132. `codesign -dv` on the test bundle confirmed `Sealed
Resources=none`, i.e. genuinely unsigned.

**2. It corrected a real bug in my first implementation.** A bundle that
has *never* registered reports `.notFound`, not `.notRegistered`. My
first version captioned `.notFound` with "Open at Login is unavailable —
move thrw to your Applications folder and reopen it." That would have
shown to **every first-time user**, describing a working feature as
broken. `.notFound` now carries no message, with a regression test naming
the mistake so it can't come back.

The empirical semantics, now documented on the enum itself:
- `.notFound` → never registered (fresh install)
- `.notRegistered` → registered before, currently off
- both are simply "off" to the user.

## Acceptance criteria

1. **Register/unregister via `SMAppService.mainApp`** —
   `SMAppServiceLoginItem`.
2. **User-facing toggle** — a checkable "Open at Login" item on the
   status menu. #143's provisioning window hasn't merged yet, and the
   issue explicitly allows a menu item in that case. It's also idiomatic:
   a single boolean on a menu-bar app is exactly what a checkable menu
   item is for, so this is not a placeholder to be moved later unless
   #143's window turns out to be a better home.
3. **Reflects actual status, not a remembered flag** — `menuWillOpen`
   re-reads `SMAppService.mainApp.status` every time the menu opens, so
   revoking the login item in System Settings shows up. There is no
   persisted boolean anywhere in this change. Covered by
   `testRevokingOutsideTheAppIsReflectedOnTheNextRead`.
4. **Failures surface** — logged to the same `app.thrw.mac` subsystem,
   and the checkmark is re-read from the system afterwards rather than
   assumed from the attempt, so a failed register leaves it off
   (`testAFailedRegistrationLeavesTheToggleOff`).
5. **Opt-in only** — nothing registers unless the user clicks. No
   registration happens at launch.
6. **Testable seam** — `LoginItemController` protocol, faked in tests.
   The `SMAppService` calls themselves are not unit-tested (they mutate
   real system state); they were verified by the live run above instead.
7. **Research question answered** — above, with observed output rather
   than what the docs imply.

## Test command

`cd packages/adapter-mac && swift test` — **66/66** (was 55 on `main`;
+11 `LoginItemTests`).

Also built the real `.app` and ran it: it launches, and — the point of
the copy fix — logs **no** Open at Login message on a machine where it
has never registered.

## Known gaps / judgment calls

- **The menu item was never clicked.** Same limitation as #143: driving
  the menu bar needs Accessibility permission, which this environment is
  refused (`osascript is not allowed assistive access`). So the toggle's
  *logic* is unit-tested and the underlying API is verified live, but
  nobody has confirmed that clicking the real item registers the real
  app. The one thing that makes this lower-risk than it sounds: the exact
  `register()`/`unregister()`/`status` sequence was exercised for real
  from an equivalent unsigned bundle, so only the AppKit wiring is
  unverified.
- **`requiresApproval` was never observed**, so its copy is written from
  Apple's documented meaning rather than from something seen. It did not
  occur in any of the register/unregister cycles run here. If it shows up
  in practice and the wording is wrong, that's the line to fix.
- **Deliberately not placed in #143's window.** #143 is open but
  unmerged; putting it there would have stacked this branch on that one.
  When #143 lands, moving this into the window is a small follow-up — or
  leaving it on the menu is perfectly defensible, since that is where Mac
  users look for it.
- **Registering from a debug build registers the debug build's path.**
  `SMAppService.mainApp` registers whatever bundle is running, so a login
  item created from `.build/.../AdapterMac.app` points at that path and
  will break when the build directory is cleaned. Fine for development,
  and it resolves itself once there's a real installed app (#132/M10),
  but worth knowing before wondering why a stale login item fails.
