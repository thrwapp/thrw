# #162: move the audio route via A2DP/HFP, not an RFCOMM socket

## What was done

`AndroidBluetoothClassicGateway` now connects and disconnects the
headset's **A2DP (media) and HFP (call)** profiles, instead of opening an
RFCOMM/SPP socket. This is what actually moves an audio route.

**Verified on real hardware, both directions**, driven by real relay
commands against the production relay — see Verification.

## Why the old approach could never work

Two independent reasons, both established against the reference AirPods
Pro 2 on a Pixel 10 Pro rather than reasoned from documentation:

1. **Headphones don't run a Serial Port Profile server.** The AirPods
   advertise exactly `0000110b` (A2DP Sink), `0000110e` (AVRCP) and
   `0000111e` (HFP). There is no `00001101` (SPP), so
   `createRfcommSocketToServiceRecord(SPP_UUID)` asked for a service that
   does not exist and failed with
   `read failed, socket might closed or timeout, read ret: -1`.
2. **An RFCOMM socket does not move an audio route anyway.** Audio lives
   on A2DP/HFP. Opening an unrelated serial channel is a different thing,
   even where one would be accepted.

Same class of mistake `adapter-mac` corrected in #101: CoreBluetooth
could connect a peripheral but not move the route, and `IOBluetooth`'s
baseband connection was the real answer. Android's equivalent is the
profile proxies.

## The hidden-API dependency — the main thing to review

`BluetoothA2dp.connect/disconnect` and `BluetoothHeadset.connect/disconnect`
are **not public API**. The public surface lets an app *observe* a
profile connection (`getConnectionState`) but not *force* one. So these
are invoked reflectively.

Verified permitted on Android 16 / `targetSdk 35`, which logs it:

```
hiddenapi: Accessing hidden method Landroid/bluetooth/BluetoothA2dp;->connect(...)
(runtime_flags=0, domain=platform, api=unsupported) ... using reflection: allowed
```

`api=unsupported` means Google can move these to the blocklist in any
future release, at which point the lookup throws. Mitigations here:

- Every reflective call fails **loudly**, with a message naming the cause
  (`"this Android version has blocked the hidden API thrw relies on"`),
  so a future OS update disabling handoff is obvious rather than
  mysterious.
- #161 already made a thrown Bluetooth failure survivable, so this
  degrades to "handoff stops working, adapter keeps running" rather than
  a crash loop.

**This warrants an ADR** — not for a platform ceiling (there isn't one),
but for a deliberate dependency on an unsupported API in a shipping
product. Not written here; `docs/adr/**` is human-merge and the decision
is Tom's. It also needs a Play Store policy check before public release
(#132/M10).

## Both profiles, not just A2DP

A2DP carries media; HFP carries call audio. architecture.md's **rule 1 is
calls**, so connecting A2DP alone would leave the highest-priority
trigger routing to the wrong device. Both are driven on claim and
release. A device lacking one simply yields no proxy for it and is
skipped; the operation only fails if *no* profile could be driven, so a
call-only or media-only headset still works.

## Verification

All against the production relay, with real relay commands — not
synthetic calls into the gateway.

**Claim (Mac → phone).** With the AirPods connected to the Mac, a CLAIM
published to the phone's commands topic:

```
mActiveDevice: XX:XX:XX:XX:2A:21
Active communication device: role:output type:bt_a2dp addr:...:2A:21 name:AirPods Pro
```

The AirPods became the phone's **active A2DP output**. No crash, no
RFCOMM error, nothing logged as failed.

**Release.** A RELEASE to the same node:

```
mActiveDevice: null
```

The phone let the headset go.

The Mac side was verified in the same session for comparison: a CLAIM
moved the AirPods to the Mac (`system_profiler` showed them under
`Connected:`, RSSI -47) and a RELEASE moved them to `Not Connected`. So
both adapters now do the job on real hardware.

`./gradlew test` passes.

## Known gaps / judgment calls

- **Releasing is not sufficient on its own — the headset reconnects.**
  Observed directly: after a release, AirPods re-associate with the
  device that just let them go, within seconds. ADR 0002's sequential
  handoff assumes disconnect-then-connect-elsewhere, and that assumption
  is incomplete against a headset that auto-reconnects. This is the first
  real evidence that ADR 0010's cooldown window and ADR 0012's proactive
  conflict resolution are load-bearing rather than speculative. **Not
  addressed here** — it's a protocol/behaviour question, not a gateway
  one, and deserves its own issue.
- **No unit test covers the new gateway**, and honestly none usefully
  can: every meaningful line is a framework call or a reflective lookup
  against `android.bluetooth`, which this module's stubbed `android.jar`
  returns defaults for. `BluetoothConnectionManager`'s tests still cover
  the state machine against a fake gateway, which is the part with logic
  in it. The gateway itself is verified by the real-hardware run above.
  Claiming unit coverage here would be theatre.
- **AirPods are multipoint**, so "connected to the phone" and "connected
  to the Mac" can both be true simultaneously. `mActiveDevice` and the
  audio-routing readout are the meaningful signals, not ACL state — worth
  knowing for anyone verifying this again.
- **`getProfileProxy` can silently never call back** (Bluetooth off,
  profile unsupported). Handled by resuming with `null` and treating a
  missing proxy as "profile unavailable", rather than suspending forever
  — the same hang-versus-error lesson #158 taught.
