# HANDOFF: bonded-headset picker for packages/adapter-android (#117)

## What was done

Replaced `ProvisioningActivity`'s free-text headset-address field (#102)
with a picker over `BluetoothAdapter.getBondedDevices()`, so provisioning
no longer depends on the user correctly typing a MAC address they
probably don't know.

- `ui/BondedHeadsets.kt` - pure Kotlin: `BondedDevice` (name + address),
  `BondedHeadsetsState` (`PermissionNotGranted`/`NoDevicesBonded`/`Devices`),
  `BondedHeadsets.state(...)` (`:51-59`) and `.label(...)` (`:63-66`). No
  `android.bluetooth` imports, same testability discipline as
  `AdapterPermissions`/`NotificationAccess`.
- `ui/BondedDeviceSource.kt` - the real `android.bluetooth`-backed source
  (`:20-32`), reading `BluetoothManager.adapter.bondedDevices`. Not unit
  tested, for the same reason `AndroidBluetoothClassicGateway` isn't (real
  Bluetooth calls are stubbed under this module's `android.jar`).
- `ui/ProvisioningActivity.kt` - `headsetPicker: Spinner` +
  `headsetPickerStatus: TextView` replace the old `headsetAddressField:
  EditText`. `renderHeadsetPicker()` (`:194-223`) computes
  `BondedHeadsets.state` and either populates the spinner (placeholder at
  position 0, pre-selecting the persisted address if it's still bonded)
  or shows an explanatory message. `selectedHeadsetAddress()` (`:181-185`)
  maps the spinner's selection back to an address. `save()` (`:137-172`)
  is otherwise unchanged in shape - it still runs the selected value
  through `ProvisioningInput.headsetAddress` before persisting.
- `res/layout/activity_provisioning.xml` - the `EditText` swapped for a
  `Spinner` + status `TextView`, both `gone` until the first render.
- `res/values/strings.xml` - new strings for the two non-list states and
  the picker placeholder; `error_headset_address_blank`'s wording updated
  for a picker context (its `FieldError` case is unchanged).
- `ui/BondedHeadsetsTest.kt` - 7 new tests.

## Acceptance criteria, with evidence

**1. Replace (or offer alongside, judgment call) the free-text field with
a picker over `getBondedDevices()`.** Replaced outright -
`BondedHeadsets.kt`'s own kdoc (`:38-44`) documents why: any address the
picker wouldn't list can't actually be connected to anyway
(`AndroidBluetoothClassicGateway` requires the device to already be
bonded), so a free-text fallback would just reopen the exact
wrong/mistyped-address failure mode this issue exists to close.
`activity_provisioning.xml` no longer declares `@+id/headset_address` at
all - grepped for it, only the unrelated `AdapterProvisioning.KEY_HEADSET_ADDRESS`
SharedPreferences key string remains (unchanged, see criterion 3).
`BondedDeviceSource.bondedDevices` (`:29-32`) is the `getBondedDevices()`
call, gated on `BLUETOOTH_CONNECT` exactly as #102 already declared and
requests.

**2. Explicit handling of "no bonded devices" and "permission not yet
granted" - no empty picker with no explanation.**
`BondedHeadsetsState` (`BondedHeadsets.kt:26-35`) has exactly these two
non-list cases plus `Devices`; `ProvisioningActivity.renderHeadsetPicker`
(`:199-222`) switches on all three, hiding the spinner and showing
`R.string.headset_permission_not_granted` /
`R.string.headset_none_bonded` respectively - never an empty, unexplained
`Spinner`.

**3. Whatever's selected goes through `AdapterProvisioning.setHeadsetAddress`
using the same persisted key/format `AdapterForegroundService` already
reads - no new provisioning keys.** `AdapterProvisioning.kt` is
untouched (`git diff --stat` confirms zero changes to that file);
`ProvisioningActivity.save()` (`:161-162`) still calls
`AdapterProvisioning.setAccountId`/`setHeadsetAddress` with exactly the
same two calls as before, just fed from `selectedHeadsetAddress()`
instead of an `EditText`.

**4. Testable logic (mapping bonded-device results to picker entries,
filtering/handling the empty-list case) unit tested with a fake
bonded-device source, same pattern as `AdapterPermissions`/
`NotificationAccess`; state plainly what still needs a real device.**
`BondedHeadsetsTest.kt` - 7 tests: permission-not-granted takes priority
(twice, including over a non-empty device list, since that precedence is
this type's own decision not an assumption about its caller), empty list
reported as its own state rather than an empty `Devices`, device order
preserved, and `label`'s three cases (named, unnamed, blank-name). All
against `BondedHeadsets.state`/`.label` directly - no `android.bluetooth`
anywhere in the test file. **What's not tested and needs a real
device/instrumentation test**: `BondedDeviceSource.bondedDevices` itself
(the real `BluetoothManager`/`BluetoothAdapter` call), and
`ProvisioningActivity`'s wiring (spinner population, pre-selection,
visibility toggling, the Save-button flow) - neither can run under this
module's stubbed `android.jar`, matching every other `Activity`/real-
Bluetooth-call gap already documented in `docs/handoffs/102.md` and
`docs/handoffs/96.md`.

**5. No new dependency.** `android.bluetooth.BluetoothManager`/
`BluetoothAdapter.getBondedDevices()` are platform SDK, already on the
classpath since #96's AGP migration; `android.widget.Spinner`/`ArrayAdapter`
are also platform SDK, no androidx addition. Grepped `git diff` for
`app/build.gradle.kts` - no changes.

## Incidental finding (not fixed, out of scope)

`./gradlew assembleDebug` fails on a `mergeDebugJavaResource` conflict:
six of `hivemq-mqtt-client`'s Netty dependencies each ship a
`META-INF/INDEX.LIST`, and AGP's resource merger refuses to pick one
without an explicit `packaging` block. **Confirmed pre-existing on clean
`main` before this issue's changes** - not something #117 introduced,
and not exercised by `./gradlew test` (the issue's own test command,
and the only thing CI's `android` job runs) or anything else in this
repo's CI. Worth its own issue: a self-hoster or anyone running
`./gradlew assembleDebug`/`bundleRelease` today hits this immediately.
Not fixed here - `app/build.gradle.kts` packaging rules are unrelated to
headset picking, and this issue's "paths the agent must not touch"
doesn't call out `build.gradle.kts` but silently expanding scope to fix
an unrelated build-packaging bug wasn't asked for either.

## Judgment calls

- **Full replacement, not "offer alongside"** - see acceptance criterion
  1's evidence above and `BondedHeadsets.kt`'s kdoc for the reasoning.
- **A placeholder entry at Spinner position 0** ("Select a headset…")
  rather than letting Android's default first-item auto-selection apply.
  Without it, an unconfigured screen would silently show *some* bonded
  device as if chosen, and a careless Save press would persist whichever
  device the platform happened to list first - the placeholder forces a
  deliberate choice, and gives `save()` a real "nothing selected" case to
  validate against (reusing the pre-existing `FieldError.HEADSET_ADDRESS_BLANK`
  path via an empty string, rather than inventing a new error case
  `ProvisioningInput` would have to grow - which the issue's own "paths
  the agent must not touch" forbids).
- **The picker is refreshed in `onResume`, not just `onCreate`** - the
  bonded-device list can change while this screen is stopped (user goes
  to Bluetooth settings, pairs or unpairs something, comes back), the
  same reasoning `renderPermissionStatus`/`renderNotificationAccessStatus`
  already use for their own OS-boundary state.
- **`headsetPickerStatus` serves the non-list explanations *and* the
  "you didn't pick one" validation error**, but never both confusingly at
  once: `save()` only overwrites it with the validation message when
  `bondedDevices.isNotEmpty()` - in the permission-not-granted/no-devices
  states, that line already explains exactly why nothing could be picked,
  and overwriting it with a generic "select a headset" would erase a more
  useful message.
