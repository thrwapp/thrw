# 203 — the Linux release asset, and why there now isn't one

The issue framed this as a product question before a CI one: **what is
the Linux adapter meant to ship as?** The answer turned out to be
"nothing yet", so this removes the asset rather than repackaging it.

Tom chose option 3 (drop the asset, keep the job as a compile check) when
presented with the evidence below. Recording that the decision was his,
because the issue explicitly reserved it: *"that is a call for Tom rather
than an inference from the Cargo manifest."*

## What `adapter-linux` actually is

Established by reading the crate, not inferred from the manifest:

- **500 lines total**, every one of them under `src/bluetooth/`.
- `src/lib.rs` is, in full: `pub mod bluetooth;` and
  `pub const ADAPTER_NAME: &str = "adapter-linux";`
- No `main`, no `[[bin]]`, no MQTT, no node interface, no config, no
  trigger detection, no heartbeat.
- The crate documents its own boundary —
  `src/bluetooth/connection_manager.rs:14-16`:

  > This is local device control only. It does not talk to a relay, does
  > not implement the node interface, and does not do any trigger
  > detection - see #108 and its handoff doc for scope.

For scale, the two adapters that do work:

| | lines | has |
|---|---|---|
| `adapter-android` | 4773 | `mqtt/`, `config/`, `protocol/`, `registration/`, `heartbeat/`, `claim/`, `triggers/`, `ui/` |
| `adapter-mac` | 5170 | the above plus an app entry point (`AdapterMacApp/AppDelegate.swift`) |
| `adapter-linux` | 500 | `bluetooth/` |

`docs/roadmap.md:338-342` says the same thing independently: *"bootstrap
done - a BlueZ-backed Bluetooth connection seam (#108), the same stage
`packages/adapter-mac` was at after #95, before its own node-interface/
MQTT wiring (#112). Node interface + trigger detection (PulseAudio/
D-Bus) still ahead of it."*

So there is no Linux artifact a user could install, and the `.rlib` was
not a packaging bug — it was the only thing a library crate with no
binary target *can* produce. Option 1 (`[[bin]]`) would not have been a
packaging change; it would have been the M4 adapter epic, and a `[[bin]]`
with an empty `main` would ship something that runs and does nothing.
Option 2 (`cdylib`) has no consumer anywhere in the repo.

I did not verify the `.rlib` by building: there is no `cargo` on this
machine, and `bluer`/`libdbus` would not build on macOS anyway. The claim
rests on the manifest (`[lib]` with no `crate-type` key defaults to
`rlib`) and on the issue's own report, not on an observed artifact.

## What changed

**`.github/workflows/release.yml`**

- `:110-140` — the header now records that Linux ships nothing and why,
  including what an `.rlib` is, that the job was green while the outcome
  was meaningless (the #187 shape), and what would have to be true to
  ship something: **#271**.
- `:158-164` — the `cargo build --release` step stays, with a comment
  aimed at whoever comes here intending to add the upload back: the
  question is not how to package the artifact, it is whether one exists.
- The whole `Attach to GitHub Release` step is gone (43 lines).

**Two knock-on corrections in the same file**, both now false statements
rather than stylistic preferences. Each is a separate hunk and can be
dropped without affecting the fix:

- `:88-89` — `contents: write` → `contents: read`. That permission
  existed to create the Release and upload into it; this workflow no
  longer does either.
- `:144-150` — the "Known race" paragraph described `announce` as a job
  *in this workflow* that might run before `release-android.yml` attached
  its bundle. `announce` moved out to `announce.yml` and triggers on
  `release: published`, which only happens after a human looks at the
  draft. The comment outlived the fix it described.

## Why removing the asset is safe

Checked rather than assumed:

1. **Nothing depends on the job.** `release.yml` contains exactly one
   job, `linux`. `announce` lives in `announce.yml` on a `release:
   published` trigger.
2. **A tag still produces a Release.** Both `release-mac.yml` and
   `release-android.yml` trigger on `v*` with no path filter, and each
   runs the same create-the-draft-if-absent block
   (`release-mac.yml:272-276`, `release-android.yml:296-300`). The draft
   creation that lived in the removed step was redundant with theirs.
3. **The crate keeps compiling regardless.** `ci.yml`'s `lint` job runs
   `pnpm turbo lint typecheck test` filtered only against the three
   adapters with their own runners, so `@thrw/adapter-linux` is in scope
   — confirmed in a real CI run's "Packages in scope" line, which lists
   it. The release-profile build kept here is additional, not the only
   coverage.
4. **Nothing else promises a Linux artifact.** The only other references
   to `libadapter_linux` in the repo are in `docs/handoffs/190.md`, which
   is a historical record and correctly left alone.

## Follow-up filed

**#271** — `packages/adapter-linux`: node interface + MQTT wiring,
mirroring #112's shape. The roadmap called this "unblocked and ready to
scope whenever it's prioritized" but nothing tracked it, so it was the
most likely thing here to rot. Labelled `local-only`, per AGENTS.md's
cost-control default — deliberately **not** `trivial`, which is Tom's
call at creation time.

## Verification, and its limits

- YAML parses clean (`js-yaml`).
- `cargo build --release` / `cargo test` were **not** run locally: no
  cargo toolchain on this machine. CI's `lint` job does run them, and
  this PR triggers it (the filter marks `lint=true` for any changed file
  outside `packages/adapter-(android|mac|ipad)/`).
- **The real check cannot be run without cutting a tag.** No `v*` tag has
  ever been pushed (#190), so this workflow's asset path has never
  executed in production — the `.rlib` was never actually attached to
  anything. That also means this change cannot regress a working release;
  there is no observed behaviour to compare against. The first real tag
  is when the Release's shape gets confirmed for the first time either
  way.

## Uncertainty

`release.yml` is now a single-job workflow that compiles one crate and
attaches nothing. That is defensible — it is a release-profile check and
the obvious home for the Linux lane once #271 lands — but it is also
close to earning nothing, and the alternative (delete the file, let
ci.yml carry the crate) was a real option that was considered and not
taken. If #271 slips indefinitely, deleting it is the better end state.
