# HANDOFF: target API 36 (#237)

## What was done

`packages/adapter-android` now compiles against and targets API 36,
because Play rejects anything lower for a new app - on the internal
testing track, not only on production.

Four files move together, and they have to:

| File | Change |
| --- | --- |
| `build.gradle.kts` | AGP 8.7.3 -> 8.11.1 |
| `app/build.gradle.kts` | `compileSdk`/`targetSdk` 35 -> 36, `buildToolsVersion = "36.0.0"` added |
| `ci.yml` | `platforms;android-36`, `build-tools;36.0.0` |
| `release-android.yml` | same, plus the `apksigner` path |

Bumping `compileSdk` while CI installs only android-35 breaks the
build, so splitting this across the `packages/**` and `.github/**`
lanes the way #153 was split would leave `main` broken in between.
That is why it is one PR.

## Why AGP had to move

`targetSdk` cannot exceed `compileSdk`, and AGP caps `compileSdk`
independently of the SDK you have installed. **AGP 8.9's maximum is API
35**; 8.11 is the lowest that supports 36.

8.11.1 rather than the latest 8.x deliberately - the smallest move that
clears the requirement. It needs Gradle >= 8.13 and the wrapper is
already 8.14.3, so the wrapper does not move.

## Acceptance criteria, with evidence

**1. compileSdk/targetSdk are 36, AGP >= 8.11.** Verified against the
built artifact rather than the source, since the source proves only
what was asked for:

```
$ aapt2 dump badging app/build/outputs/apk/release/app-release-unsigned.apk
package: name='app.thrw.android' versionCode='1' versionName='0.1.0'
  platformBuildVersionName='16' platformBuildVersionCode='36'
  compileSdkVersion='36' compileSdkVersionCodename='16'
targetSdkVersion:'36'
```

Merged manifest agrees: `android:targetSdkVersion="36"`,
`android:minSdkVersion="31"`.

**2. Tests pass.** The repo's own command, run locally:

```
$ pnpm turbo test --filter=@thrw/adapter-android
BUILD SUCCESSFUL in 34s
Tasks:    1 successful, 1 total
```

`./gradlew test assembleDebug` and `bundleRelease assembleRelease` also
succeed against the API 36 platform.

**3. Workflow SDK versions and the apksigner path.** Updated in both
files; no `android-35` / `build-tools;35` / `build-tools/35` reference
remains in `.github/workflows`. The release workflow already fails
loudly if `apksigner` is not at the path it builds, so a green release
run is the proof - see below, it has not run yet.

**4. Play accepts the target API level.** NOT verified - that needs an
upload. This is the criterion the whole issue exists for, and it stays
open until the bundle is actually accepted.

**5. Insets on the Pixel.** NOT verified. See below.

## Verified locally, on JDK 21, not JDK 17

CI uses temurin 17; this machine has only 21 and 24, so the local runs
above used 21. AGP 8.11's floor is JDK 17 and the module compiles to
`jvmTarget 17` either way, so this is very unlikely to differ - but the
authority is CI's `android` job, not these runs.

Local builds also produce `app-release-unsigned.apk` rather than
`app-release.apk`, since no upload key is configured here. That is
`app/build.gradle.kts`'s documented behaviour and is why the release
workflow's asset path is unaffected: CI has the keystore, so it emits
the signed name.

## Runtime exposure that was checked and dismissed

Android 16's targeting changes, against this code:

- **Edge-to-edge**: enforcement began at `targetSdk 35`, which this app
  already was. Android 16 only removes the
  `windowOptOutEdgeToEdgeEnforcement` opt-out, which this app never
  used. So targeting 36 changes nothing here.
- **BOOT_COMPLETED foreground services**: the blocked types are
  dataSync, mediaPlayback, mediaProjection and phoneCall.
  `AdapterForegroundService` is `connectedDevice`, which is not among
  them, and this restriction also already applied at 35.
- **Predictive back**: no `onBackPressed` override exists.
- **Large-screen adaptive layouts**: no `screenOrientation` or
  `resizeableActivity` in the manifest.
- **JobScheduler/WorkManager runtime quotas**: neither is used.

## Known gaps

- **The provisioning screen has never been looked at on hardware.**
  `docs/handoffs/102.md` says so outright: the layout's appearance, the
  `Theme.DeviceDefault.DayNight` choice and "edge-to-edge insets under
  `targetSdk 35`" are all unverified beyond "the manifest merges and
  the resources link". This change does not make that worse - the
  enforcement was already in effect - but it is the obvious thing to
  check on the next install, since the layout relies on
  `fitsSystemWindows="true"` on a `ScrollView` and nothing has ever
  confirmed that renders correctly.
- **Local Network Permission** (Android 16, currently opt-in) will
  matter for a self-hosted relay on a LAN when it becomes mandatory.
  Not a concern for the hosted relay, which is reached over the
  internet. Worth an issue when Google sets a date.
- **A Kotlin warning in `TopicsFixtureTest.kt:28`** ("Java type
  mismatch: inferred type is `String?`") appears in these builds. That
  file is untouched here and the Kotlin version is unchanged, so it is
  near-certainly pre-existing - but I did not find it in an earlier CI
  log to prove that, so it is recorded rather than claimed.
