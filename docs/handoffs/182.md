# 182 — adapters never reconnected

## What was wrong

An adapter that lost its MQTT connection **never reconnected**. It stayed
running, its foreground notification / menu bar item stayed up, and it was
silently useless until the user relaunched it by hand.

Observed for real: deploying the relay restarted the EMQX container, which
dropped every client, and neither adapter came back.

```
$ emqx ctl clients list
Client(observer-…)        <- a test observer
Client(mqttjs_…)          <- relay-service
                          <- no Mac node, no Android node
```

Both node processes were still running.

## Why it was invisible

Android logged this on every subsequent publish, forever:

```
E AdapterForegroundService: Unhandled exception in the node runtime - the adapter stays up
E AdapterForegroundService: com.hivemq.client.mqtt.exceptions.MqttClientStateException: MQTT client is not connected.
```

#161's crash survivability was doing exactly its job — the adapter *does*
stay up — and that is precisely what hid this. Nothing degraded visibly.
From the user's side thrw just stops working and never says why.

The triggers are mundane: a Wi-Fi change, the phone sleeping past the 60s
keepalive, any relay deploy.

## What was done

**Android** — HiveMQ's `automaticReconnectWithDefaultConfig()`, plus
connect/disconnect listeners for observability.

**Mac** — MQTTNIO has no automatic reconnect at all, so the loop is
written here: a close listener starts an exponential backoff (1s
doubling to 30s) with 0-2s jitter, per ADR 0020's reconnect-jitter
decision, so several nodes returning from a shared outage do not all
reconnect on the same tick.

### Reconnect alone is not enough — two further things were needed

**1. Subscriptions must be re-issued.** The session is clean, so
reconnecting restores the *connection*, not the subscriptions. Without
re-subscribing, the client comes back connected and **deaf**: it would
never receive another claim or release while looking perfectly healthy.
That is the same silent-deafness shape as the bug itself, one layer down
— and it is not hypothetical, because the throwaway observer used to
watch the relay during this work hit exactly that failure twice and
reported "nothing is happening" when it was simply not subscribed. Both
transports now keep a registry of live subscriptions and re-issue them.

**2. The node must re-register.** The relay learns of a node *only* from
a registration and holds that in memory, so a node that silently
reconnects is connected but invisible — #178 by another route. Waiting
out #178's 2-minute periodic timer would leave a window where the headset
cannot be arbitrated at all, and reconnect is exactly when the relay's
picture is most likely stale.

This is only safe because #178 made registration a *statement of current
state* rather than an edge: it carries the node's active triggers, so the
relay reconciles instead of being told something just started. Before
#178, re-registering on every reconnect would have wiped the node's live
media/call state.

## Design notes

- `MqttTransport.onReconnected` is added with a **default no-op**
  implementation on both platforms, so every existing fake and any
  transport without a reconnect story needed no change.
- The first CONNECT is deliberately not treated as a reconnect. Without
  that guard the node registers twice at startup — once from
  `NodeRuntime`, once from the connected listener firing on the initial
  connect.
- `close()` sets a shutting-down flag and removes the close listener
  *before* shutting the client down, so an intentional shutdown does not
  start a reconnect loop against a client that is going away.
- The Mac locking is routed through a synchronous `withLock` helper:
  taking an `NSLock` directly inside an `async` function is unavailable
  under the Swift 6 language mode, and AGENTS.md asks for Swift 6
  concurrency. Left as-is it compiles today with warnings and breaks
  later.

## Verification

- `adapter-mac` 127 tests, `adapter-android` green, relay suites
  unaffected (41 / 12).
- Both reconnect paths are mutation-tested: removing the re-registration
  wiring kills `reconnecting re-registers the node` on Android and
  `testReconnectingReRegistersTheNode` on the Mac, and nothing else.

## Hardware verification found a bug the tests could not

Android was tested on a Pixel 10 Pro against the deployed relay by
toggling airplane mode. The first attempt failed, and failed in a way no
unit test could have caught:

```
W HiveMqttTransport: MQTT disconnected (source=SERVER); reconnecting
W HiveMqttTransport: Mqtt3ConnAckException: CONNECT failed as CONNACK
                     contained an Error Code: BAD_USER_NAME_OR_PASSWORD
```

The reconnect fired correctly — and then failed authentication on every
single attempt, forever.

**Cause:** credentials were supplied through
`connectWith().simpleAuth()`, which applies to *that one CONNECT*.
HiveMQ's automatic reconnect sends its own CONNECT, and it sent it
unauthenticated. Against the deployed broker (`allow_anonymous=false`)
every reconnect is rejected, so the adapter retries busily and never
recovers — behaviourally identical to having no reconnect at all, which
is the bug this issue is about.

**Fix:** credentials moved to `Mqtt3ClientBuilder.simpleAuth(...)`, which
is client configuration and therefore rides every CONNECT including the
ones `automaticReconnect` generates.

The unit tests use a fake transport and never touch HiveMQ's CONNECT at
all, so they passed throughout. This is the third time in two days that
a "green tests, broken on device" bug has turned up in adapter code
(#174, #175, this) — all three in the layer where the adapter meets a
real framework or broker.

After the fix, same test, airplane mode off at 11:29:07:

```
12:29:47 I HiveMqttTransport: MQTT reconnected; restoring subscriptions and re-registering
11:29:47 nodes/56479cf1-…/events {"kind":"register",…,"activeEvents":[]}
```

Reconnect, subscription restore and re-registration all confirmed end to
end against the production relay.

## Known gaps — read before trusting this

- **The Mac path is not hardware-verified.** Its credentials go through
  `MQTTClient.Configuration(userName:password:)`, which is
  configuration-level and so should not have the Android bug above — but
  "should not" is exactly what was believed about Android an hour ago.
  The reconnect loop itself is hand-written here and has only ever run
  against a fake.
- **Re-subscription after a real reconnect is only confirmed on
  Android**, via the log line above; nothing yet proves a *command*
  arrives on the restored subscription. A client that returns but is deaf
  looks identical to a healthy one until a claim is missed.
- **Queued commands are not considered.** The session stays clean, so
  commands published while a node was offline are not delivered on
  return. That is deliberate for now: the relay re-asserts the correct
  state on the re-registration (#173/#178), so the backlog is not needed
  and cannot arrive stale. It does mean the recovery path depends on the
  relay behaving correctly, rather than on broker queueing.
- **Backoff numbers are guesses** (1s→30s, 0-2s jitter), not measured.
