# Handoff: #244 — a claim skipped while CONNECTING was dropped forever

## What was wrong

`BluetoothConnectionManager.connect()` set `states[device] = CONNECTING`,
called the gateway, and resolved to CONNECTED on success or DISCONNECTED
on throw. If the gateway call **never returned**, neither path ran and the
state stayed at CONNECTING.

That matters because the CONNECTING branch returns early *without* the
route second-guess ADR 0018 decision 3 added. The second-guess only
rescues a stale CONNECTED. So a state stuck at CONNECTING meant every
subsequent claim for that device was skipped — silently, with no log, no
retry and no audio — for the life of the process.

Both platforms had it. `adapter-mac`'s `case .connecting: return` is the
same shape as `adapter-android`'s early return.

## How it was found

Live on the reference Pixel. It was the relay's holder, connected to the
broker, registering every 120s, and made **no Bluetooth connection
attempt for over half an hour**. `dumpsys bluetooth_manager` showed no new
records for the headset while the relay logged a `route_drift` every two
minutes with no reason attached — indistinguishable from half a dozen
other failures, and attributed to three different wrong causes before the
real one surfaced.

The experiment that settled it: force-stopping the app clears the
in-memory `states` map and nothing else, and claims started working
immediately.

## The fix, and why this one

Bound the in-flight attempt with a timeout rather than add a staleness
threshold to CONNECTING.

A timeout guarantees the state machine resolves — CONNECTED, or
DISCONNECTED with an error thrown. It also **cancels** the hung call. A
staleness threshold would let a later claim through but leave the
original call running unattended, still able to mutate the Bluetooth
stack after the manager had given up on it.

The bound is ADR 0019's 8 seconds. That number already had to exist for
#206, so no adapter invents its own — `packages/protocol`'s
`COMMAND_OUTCOME_TIMEOUT_MS`, `adapter-mac`'s `commandOutcomeTimeout` and
`adapter-android`'s `COMMAND_OUTCOME_TIMEOUT_MS` are three hand-written
copies of one value, each asserted in its own suite. It guarantees
termination, not latency; ADR 0007 owns latency.

Skipped claims are now logged with their reason. Skipping a genuinely
concurrent claim is correct; doing it silently is what made the stuck case
undiagnosable.

## What is NOT established

**The cause of the hang.** `awaitProxy`'s kdoc claimed it resumes with
null "rather than suspending forever" — true only for the
`getProfileProxy` returning `false` path. If it returns `true` and
`onServiceConnected` is never called, it suspends indefinitely. That is
the most plausible candidate and the kdoc is corrected to say so, **but it
was not proven**: the state was cleared by a restart before it could be
instrumented.

The fix is deliberately not at that site. The outer bound covers a hang
wherever it originates, including one nobody has thought of — which is the
right shape given the cause is unproven.

**Not verified on hardware.** The adapter tests are mocked at the gateway
boundary and cannot prove the bound behaves against a real headset. #244
criterion 5's check still stands: force a hang (headset off mid-connect,
Bluetooth disabled) and confirm later claims still fire rather than being
skipped.

## A trade-off worth knowing

A connect that would legitimately have succeeded at 9 seconds is now
aborted at 8. On the reference hardware a claim settles in 3-5s, so this
is roughly 2x headroom and ADR 0019 already fixed the number — but if
switch failures appear on slower hardware, this is the first thing to
suspect. The previous behaviour was strictly worse: it hung forever and
disabled the device.

## Verification

- `pnpm turbo test --filter=@thrw/adapter-mac` — 194 tests, 0 failures
  (191 before).
- `pnpm turbo test --filter=@thrw/adapter-android` — BUILD SUCCESSFUL;
  `BluetoothConnectionManagerTest` 16 tests, 0 failures (13 before).

Six new tests, three per platform: a connect that never resolves times out
rather than sticking at CONNECTING; a claim after a hung one is still
attempted; and the 8s constant matches `packages/protocol`.

A fresh worktree needs `packages/adapter-android/local.properties`
(gitignored, machine-local) copied in before the Android suite will run.
