# #129: deploy relay-service to the real relay VM

## What was done

`services/relay-hosted/src/relay-service.ts` (#118) is now running for
real as a third long-lived container on the `thrw-relay` VM, alongside
`relay` (EMQX) and `caddy` (#119). Same pattern #119 established:
`scripts/relay-redeploy.sh` manages it idempotently, `deploy.yml` builds
and pushes its image, and everything was verified live against the real
VM and the real `relay.thrw.app` domain - not a local substitute.

## Acceptance criteria

1. **`deploy.yml` builds and pushes a `Dockerfile.relay-service` image.**
   New "Build and push relay-service image" step,
   `.github/workflows/deploy.yml:63-69`, built from the repo root (needed
   for `turbo prune`'s full-workspace context, see
   `Dockerfile.relay-service`'s own comment) and pushed to
   `.../thrw/relay-service:{sha,latest}`. **Flagged as required**: this
   is `.github/**`, always human-merge per AGENTS.md - this PR does not
   merge itself.

2. **`relay-redeploy.sh` pulls and runs it as a third container.**
   `scripts/relay-redeploy.sh:30,44,121-140` - pulls
   `RELAY_SERVICE_IMAGE_REF`, tears down/recreates `relay-service` (not
   idempotent, same as `relay`; unlike `caddy` this *is* the thing being
   versioned by each deploy), passes `THRW_RELAY_ACCOUNTS` via env file.
   **Account id**: no `services/accounts` exists yet (confirmed - no
   real user has signed up per roadmap.md M7), so per this issue's own
   "stop and ask" instruction, I asked Tom directly rather than
   inventing a placeholder. He confirmed `tom-personal` - the same value
   `ProvisioningInput`'s hint text on the Android provisioning screen
   already suggests (`account_id_hint`). Wired as
   `deploy.yml:106`'s `THRW_RELAY_ACCOUNTS` repo variable (default
   `tom-personal`, overridable without a code change once a real account
   system exists).

3. **MQTT credential: documented choice.** `relay-service` reuses the
   same shared `EMQX_RELAY_USERNAME`/`PASSWORD` credential `relay`
   itself authenticates with (`scripts/relay-redeploy.sh:113-120`
   comment has the full reasoning) - `acl.conf`'s ACL is currently
   `{allow, all, ...}` per the single-shared-credential interim model
   from #80, so a second credential would be functionally identical
   right now, and per-service credential management before
   `services/accounts` exists is premature. Documented as a judgment
   call, not the more elaborate option, per this criterion's own
   framing.

4. **Health/observability.** Confirmed via `docker ps` on the real VM:
   `relay-service   Up 13 seconds   .../thrw/relay-service:latest`, and
   its own startup log line (`src/index.ts:44`) observed for real:
   `relay-hosted: watching 1 account(s) on ws://localhost:8083/mqtt`.
   No dedicated health-check endpoint added, per this criterion's own
   scope limit (`relay-service` has no HTTP server; adding one is a
   bigger change than "deploy what already exists").

5. **Real end-to-end verification against the deployed VM.** A real
   `mqtt` client connected to `wss://relay.thrw.app/mqtt`, authenticated
   with the real shared relay credential (read live from the running
   `relay` container, never committed - same discipline as
   `docs/handoffs/119.md`), published a registration then a `call` event
   for a throwaway node (`e2e-verify-node`) under account `tom-personal`,
   and received a real `{"type":"claim"}` command back on that node's
   commands topic. Observed output:
   ```
   connected to wss://relay.thrw.app/mqtt
   subscribed to thrw/tom-personal/commands/e2e-verify-node
   published registration
   published call event
   received command: { type: 'claim' }
   SUCCESS: real CLAIM command received end-to-end
   ```
   The verification script and its credentials file were both temporary,
   never committed, and deleted immediately after this run.

6. **No changes to `relay-service.ts`.** Confirmed - `git diff` for this
   branch touches only `.github/workflows/deploy.yml` and
   `scripts/relay-redeploy.sh`; no bug was found while deploying it.

## Known gaps / judgment calls

- **`deploy.yml` had already auto-run once before I started**,
  discovered mid-troubleshooting: `/tmp/relay-redeploy.sh` on the VM was
  owned by `runner:runner`, not `tmiller`, meaning a prior merge
  touching `services/relay-hosted/**` (almost certainly #119's) already
  triggered `deploy.yml`'s `on: push: paths:` watch and ran the
  then-current (pre-#129) `relay-redeploy.sh` for real. Not a problem -
  the VM's `relay`/`caddy` containers were healthy when I checked - but
  worth recording since it means this VM has had more automatic
  deploys than any single handoff doc so far has narrated.
- **Docker image was initially built for arm64** (Apple Silicon default)
  and failed to pull on the amd64 VM (`no matching manifest for
  linux/amd64`). Rebuilt with `docker build --platform linux/amd64`
  (buildx cross-compilation) for the manual verification build; the
  `deploy.yml` step itself runs on `ubuntu-latest` (amd64 GitHub-hosted
  runners), so this platform mismatch is specific to building locally
  from an Apple Silicon machine and does not affect the actual CI path.
- **Account id is a single hardcoded default (`tom-personal`) in a repo
  variable**, not a real multi-account mechanism - expected, since
  `services/accounts` doesn't exist yet (this is the same interim state
  #118's own handoff already flagged, now just wired into the real
  deploy path instead of sitting unused).
- **`relay-service`'s own credential is the same one `relay` uses** -
  see criterion 3 above; revisit once `services/accounts` exists and a
  real per-service ACL is worth the complexity.
