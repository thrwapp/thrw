# HANDOFF: AVAudioSession + process-watching trigger detection for packages/adapter-mac (#127)

## The issue's own premise was wrong - found and corrected before writing code

The issue (and `docs/spec/architecture.md`'s own "System components"
line) named `AVAudioSession` as one of Mac's trigger APIs. **Verified
against Apple's own documentation and developer forums before writing
any Swift: `AVAudioSession` doesn't exist on macOS at all** - it's an
iOS/tvOS/watchOS-only framework. This is the same class of mistake #101
found and corrected at the Bluetooth-framework layer (`CoreBluetooth` is
BLE-only on Mac). Raised with Tom directly mid-session rather than
guessed past; he confirmed the scope this handoff and the code below
actually implement: **VoIP-only trigger detection via process watching,
with architecture.md corrected** (not "also add Core Audio route-change
observation" - investigated and rejected, see below).

Further research, all cited in `docs/spec/architecture.md`'s new "Mac's
trigger-detection gap" section:
- macOS's real audio-route API is Core Audio
  (`kAudioHardwarePropertyDefaultOutputDevice`), but it only reports
  *what* the current output device is, not *why* it changed - no
  "a call started" semantic like iOS's route-change-reason enum, so it
  isn't used as a trigger signal here at all.
- No public macOS API exists for "is the microphone in use by another
  app" - confirmed via search; Apple doesn't expose this to third
  parties (same limitation iOS has).
- CallKit has only just begun shipping on macOS, in beta, as of very
  recent Xcode 26.x releases (one incremental `CXProvider` method as of
  this research) - too new/undocumented to build on.
- **Conclusion**: Mac has no viable API for architecture.md's rule 1
  ("phone call - always wins") at all - not a temporary gap, a real
  platform ceiling, the same tier of finding #115 made for iPad's
  Bluetooth control. Only rule 3 (VoIP) is detectable, via process
  watching.

## Acceptance criteria, with evidence

Re-scoped per the conversation with Tom above - criteria 1 (an
`AVAudioSession` seam) is **not implemented**, since the API it names
doesn't exist on this platform; everything else is.

macOS. Documented in architecture.md rather than silently dropped.

`VoipTriggerMonitor.swift`'s kdoc - "The heuristic" and "Known

**6. Tested against fakes only.** Grepped the full test target for
`NSWorkspace`/`AppKit` imports - none outside
`NSWorkspaceRunningApplicationSource.swift` itself, which no test file

## Known gaps / judgment calls

- **`defaultVoipBundleIdentifiers`'s exact values are not hardware-
  verified.** Zoom's (`us.zoom.xos`) and FaceTime's (`com.apple.FaceTime`)
  are well-established; Teams/Slack/Discord/WhatsApp/Skype's are best-
  known-current values, not independently confirmed against installed
  apps on real hardware - flagged explicitly in the type's own kdoc, and
  the set is constructor-injectable specifically so this is a config fix
  later, not a re-open-this-issue problem.
- **Google Meet (no native Mac app) and any browser-tab VoIP session are
  invisible to this heuristic** - process watching only sees the browser
  process, which carries no signal about what's happening in a specific
  tab. Named explicitly in "Known limitations" rather than silently
  uncovered.
- **This heuristic has real false positives**: a VoIP app sitting open
  with no active call still counts as "in a session" - there is no
  public API to distinguish "open" from "actively calling." Worse than
  Android's own notification-property-based precision, and documented
  as such rather than implied equivalent.
- **No `CallTriggerMonitor`/call detection exists, and per this handoff's
  research, none is realistically buildable right now** - a real,
  permanent-for-now product gap for Mac specifically, not a follow-up
  issue waiting to be filed. Worth revisiting only if/when macOS's
  nascent CallKit support matures past beta.
- No ADR implications - this corrects a factual claim in
  architecture.md's "System components" section, the same tier #101's
  correction was, not a new architectural decision.
