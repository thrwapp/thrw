# 309 — A manual claim that fails tells the user nothing

## What was wrong

Two paths, both ending in a log line nobody reads.

**A tap that does not publish.** `ManualClaim.toggle()` changes state only
after a successful publish, so with no relay it throws and nothing on
screen changes. Observed on hardware 2026-09-27: airplane mode on, four
taps, four `E AdapterForegroundService: Manual claim failed` lines, route
unmoved. **Four taps is the finding** — that is what someone does when a
control gives no sign of having done anything.

**A command that fails after being accepted.** A claim resolves `failed`
or `timed_out` (ADR 0019), the relay is told, and the person holding the
device is not. This is the worse one: "I pressed claim, the UI accepted
it, and the headset never came".

## Scenario

`scenarios.md` **R3** — *"Headset in its case or out of range when a claim
is made: claim resolves `failed` with `target_device_unreachable`
quickly, **the user is told (#309)**, and the next valid trigger works
normally."* Its hardware column is `—`; it has never passed, and could
not until this.

I first argued this bug was outside the scenario set, on the grounds that
every scenario is a promise about holder and route. That was wrong and is
corrected on the issue: the *must recover* table is broader by
construction, R3's outcome has three clauses, and only the first concerns
holder and route. **No new row was added** — R3 already names this issue
by number.

## What changed

`LastCommandFailure` on both platforms: the last command this node could
not carry out, or nothing since the most recent success.

- **`packages/adapter-mac/Sources/AdapterMac/Status/LastCommandFailure.swift`**
  — `@unchecked Sendable` + `NSLock`, matching `ActiveEventSet` and
  `SelfCooldown`. Read by the menu on open, which is the Mac's existing
  pull model (`menuWillOpen`; nobody reads a closed menu).
- **`packages/adapter-android/.../status/LastCommandFailure.kt`** — a
  `StateFlow`, because the Android notification is permanently on screen
  and a value nothing pushes would sit there stale. Same reasoning as
  `HolderState`'s.

Recorded in each node's command loop on the failure and timeout paths,
cleared on success. Surfaced in the menu status line (Mac) and the
notification text (Android) — deliberately where the tap happened, and
both already refresh immediately after a toggle.

**The precedence is a pure function**, `notificationTextRes` in
`status/`, beside `nodeStatus` and `claimAction` for the same reason
those are: the ordering *is* the decision. Failed tap first (the user
just acted), then failed command (may be a switch they never asked for),
then the ordinary status line — which is still true in both cases, and
saying only it is exactly how both stayed invisible.

## A bug caught while writing it

`SUPERSEDED_BY_NEWER_COMMAND` is reported as a `FAILED` outcome, but it is
idempotency working correctly, not a switch that went wrong — ADR 0019
tracks it separately for that reason. Surfacing it would alarm the user
about normal operation.

Neither adapter records it today: both guards `return`/`continue` before
the record. Both implementations are nonetheless defensive about it —
Kotlin falls through to the status line, `describe` returns `nil` — so if
that ever changes the user is not told that routine deduplication is a
failure.

## What this does not do

**Nothing distinguishes the two causes on the Mac's single status line
beyond wording.** There is one line available and three things competing
for it. If that proves too coarse, the answer is a dedicated menu item,
as #265 did for the mute.

**`target_device_unreachable` is reported as "may be in its case or out of
range".** That is the actionable reading, but the reason code is also what
`#264` records for a device macOS has never paired — a provisioning fault
that will never fix itself. A user with that fault gets advice that will
not help them. Out of scope here; worth its own issue.

## Verified

- **adapter-mac: 330 tests, 0 failures** (was 323 on `45035f5`).
- **adapter-android: 309 tests, 0 failures** (was 298).
- **Disconfirmation.** Removing only the `lastCommandFailure.record(...)`
  call from `MacNode`'s failure path:

      MacNodeTests.swift:512: error: testAFailedCommandIsRecordedForTheUser
      XCTUnwrap failed: expected non-nil value of type "CommandFailure"
      Executed 330 tests, with 1 failure

  Exactly the wiring test, and nothing else. That is the check that
  mattered here: `LastCommandFailureTests` covers the store and would
  keep passing with nothing ever calling it.

## Not verified

**No hardware run.** R3's own situation — headset in its case when a
claim is made — needs the AirPods, and they were not available (Tom
travelling with a different headset). **R3 cannot be marked verified on
the strength of this PR.** The hardware pass is: put the AirPods in their
case, trigger a claim, and confirm the Pixel's notification and the Mac's
menu both say so.

The publish-failure half *was* observed on hardware before the fix (the
four taps); the fix for it has not been re-observed.
