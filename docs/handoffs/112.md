# HANDOFF: node interface + MQTT wiring for packages/adapter-mac (#112)

## Context

An automated `agent-code` run on this issue failed before opening a PR
(turn budget or execution error - see the issue comment linking run
35236601603), and the issue was labeled `needs-human`. Picked up here
directly with Tom rather than re-queued to automation, since the
combination of a brand-new SwiftPM MQTT dependency, a build-time-config
mechanism SwiftPM has no built-in equivalent for, and a full protocol
port is exactly the kind of task likely to blow a turn budget on a first
attempt.

This also landed after #101 (CoreBluetooth → IOBluetooth swap), so
`BluetoothConnectionManager.connect`/`disconnect` take a `UUID`
identifier minted by `BluetoothDeviceIdentifier`, not a raw MAC-address
string like `adapter-android`'s equivalent - `MacNode` (below) is written
against that as it exists today, not against #95's original shape.

## What was done

Ported `adapter-android`'s full node-interface + MQTT layer to Swift,
mirroring it method-for-method rather than reinventing the shape:

- **`Sources/AdapterMac/Protocol/NodeInterface.swift`** - `NodeInterface`
  protocol (`register`/`emitEvent`/`onClaim`/`onRelease`, `:73-81`),
  `EventKind`, `Platform`, `NodeManifest`. Mirror of
  `adapter-android/protocol/NodeInterface.kt`.
- **`Sources/AdapterMac/Protocol/Payloads.swift`** - `EventPayload`,
  `CommandType`/`CommandPayload`, `RegistrationPayload`. Mirror of
  `adapter-android/protocol/Payloads.kt`.
- **`Sources/AdapterMac/Protocol/Topics.swift`** - `Topics`/`TopicQos`
  (`:13-41`). Mirror of `adapter-android/protocol/Topics.kt`.
- **`Sources/AdapterMac/Config/RelayConfig.swift`** - relay URL parsing
  (`ws`/`wss`/`mqtt`/`mqtts`, default ports, WebSocket path,
  `:16-89`). Mirror of `adapter-android/config/RelayConfig.kt`, with one
  deliberate difference documented on the type itself: `webSocketPath`
  keeps its leading `/` (MQTTNIO's convention) rather than stripping it
  (HiveMQ's).
- **`Sources/AdapterMac/Mqtt/MqttTransport.swift`** - the transport
  seam (`publish`/`subscribe`/`close`), `subscribe` returning
  `AsyncStream<String>` as the Swift analogue of Kotlin's cold `Flow`.
- **`Sources/AdapterMac/Mqtt/MQTTNIOTransport.swift`** - the real
  implementation, backed by MQTTNIO (`:44-125`; see "Dependency choice"
  below).
- **`Sources/AdapterMac/MacNode.swift`** - `MacNode`, implementing
  `NodeInterface` against `BluetoothConnectionManager`
  (`:24-101`; `register`/`emitEvent`/`onClaim`/`onRelease` at `:49-67`,
  `listenForCommands` at `:76-89`). Mirror of `AndroidNode.kt:53-87,98-110`.
- **`Plugins/GenerateAdapterConfigPlugin/`** - the build-time-config
  mechanism (see "Build-time config" below), plus
  **`config/adapter.properties`** (adapter-mac's own copy, same three
  keys as adapter-android's).
- **`Package.swift`** - adds the `mqtt-nio` dependency and wires the new
  plugin onto the `AdapterMac` target. **`Package.resolved`** is new
  (this package had zero dependencies before) and is committed, same as
  any other SwiftPM/npm/Cargo lockfile in this repo.
- Tests: `Tests/AdapterMacTests/MacNodeTests.swift` (8 tests, mirroring
  `AndroidNodeTest.kt` test-for-test) and
  `Tests/AdapterMacTests/Config/RelayConfigTests.swift` (8 tests,
  mirroring `RelayConfigTest.kt`), plus
  `Tests/AdapterMacTests/Mqtt/FakeMqttTransport.swift`, the fake the
  issue's acceptance criterion 6 asks for.

## Acceptance criteria, with evidence

**1. A Swift `NodeInterface` mirroring `@thrw/protocol`'s shape, state
machine/priority ranking excluded.** `NodeInterface.swift:73-81` declares
exactly the four methods; grepped the file and `MacNode.swift` for
`preClaim`/`pre-claim`/`ConnectionState`/priority-ordering constructs -
no matches.

**2. A `RelayConfig`-equivalent parsing a relay URL from build-time
configuration, never hardcoded inline.** `RelayConfig.swift:51-77`
parses `ws`/`wss`/`mqtt`/`mqtts`, default ports per scheme, WebSocket
path with `/mqtt` fallback - same branches as the Kotlin version,
verified test-for-test in `RelayConfigTests.swift` (8 tests). Build-time
config: `Plugins/GenerateAdapterConfigPlugin/` + `config/adapter.properties`
(details below); `RelayConfig.fromBuildConfig()` (`:86-88`) is the only
path from a literal URL to a `RelayConfig`, and it reads
`AdapterBuildConfig.relayURL`, generated at build time, never a literal
in `MacNode.swift` or anywhere else that constructs a `RelayConfig` for
real use.

**3. An `MqttTransport` protocol plus a real implementation, dependency
choice justified.** `MqttTransport.swift` (protocol);
`MQTTNIOTransport.swift:44-125` (real implementation). Full justification
is in that file's own doc comment - condensed: native async/await
(matches this package's existing actor-based style and AGENTS.md's Swift
6 concurrency convention), WebSocket+TLS support out of the box (ADR
0001), and - the deciding factor - pure Swift/SwiftNIO, so it compiles on
the Linux runner this repo's `agent-code`/`agent-eval` automation
actually uses (only `ci.yml`'s dedicated `mac-ipad` job is real macOS;
see docs/handoffs/101.md), unlike `IOBluetoothPeripheralGateway`'s
necessarily-macOS-only `#if canImport(IOBluetooth)` code. Confirmed by
`grep -rn "^import"` across every new file (`docs/handoffs/112.md`'s own
evidence-gathering, reproduced above under "What was done") - only
`Foundation`/`MQTTNIO`/`NIOCore`/`NIOPosix`, no platform-specific import
anywhere in the new node/transport/protocol code.

**4. A `MacNode` implementing the protocol against
`BluetoothConnectionManager`, same method bodies as `AndroidNode.kt:53-87`,
ported to Swift concurrency, including the command-listening loop
mirroring `AndroidNode.kt:98-110`.** `MacNode.swift:59-67` -
`onClaim`/`onRelease` call `bluetooth.connect`/`disconnect` with no
try/catch, deliberately matching `AndroidNode.kt`'s own lack of one (a
failed claim/release propagates rather than being silently swallowed -
see "Judgment calls" for why this wasn't "improved"). `listenForCommands`
(`:76-89`) subscribes to the commands topic and dispatches
claim/release, skipping unparseable payloads via `try?` exactly like the
Kotlin `runCatching { ... }.getOrNull()`.

**5. Topic strings and QoS from this adapter's own protocol mirror, not
re-derived ad hoc.** Every topic/QoS reference in `MacNode.swift` and
`MQTTNIOTransport.swift` goes through `Topics.events`/`Topics.commands`/
`TopicQos.eventsQos`/`TopicQos.commandsQos` - grepped both files for a
literal `"thrw/`-prefixed string or a bare integer QoS at a publish/
subscribe call site; none found outside `Topics.swift` itself.

**6. Tested against a fake `MqttTransport` and the existing fake
Bluetooth gateway - no real broker, no real hardware.**
`MacNodeTests.swift` uses `FakeMqttTransport` (new) and
`FakeBluetoothPeripheralGateway` (pre-existing, from #95/#101, reused
unchanged) exclusively - 8 tests: manifest registration, event
publishing (including all four `EventKind` wire spellings), claim/release
connecting/disconnecting through the real `BluetoothConnectionManager`
(so its actual state machine is exercised, not just recorded gateway
calls), claim/release publishing nothing, relay commands driving
claim/release, and an unparseable command not dropping the subscription.
No real broker, no real Bluetooth hardware anywhere in this diff.

## Build-time config: SwiftPM build-tool plugin, not `.xcconfig`

ADR 0005 names "an xcconfig for Swift" as its own illustrative example,
but that mechanism has nowhere to land its values into compiled Swift
constants without an `Info.plist` and a `Bundle` to read it from -
`packages/adapter-mac` is a plain SwiftPM library with no app target or
bundle yet, so the ADR's own example doesn't fit this package's current
shape. Full reasoning (including why a checked-in Swift file with
literal values was also rejected - closer to "hardcoded" than ADR 0005
asks for) is in `GenerateAdapterConfigPlugin.swift`'s doc comment.

What was built instead, mirroring `adapter-android`'s Gradle-task
approach as closely as SwiftPM allows:

- `config/adapter.properties` - same format, same three keys
  (`relay.url`/`licensing.url`/`selfHosted`) as adapter-android's own
  file, a separate copy per ADR 0005 ("a config file per adapter").
- `Plugins/GenerateAdapterConfigPlugin/generate.sh` - a plain POSIX shell
  script (not inline in the plugin's Swift code, since a `BuildToolPlugin`
  only *describes* a command to run, it can't execute arbitrary work
  itself) that parses the properties file and writes
  `AdapterBuildConfig.swift`.
- `Plugins/GenerateAdapterConfigPlugin/GenerateAdapterConfigPlugin.swift`
  - the plugin, registering a `prebuildCommand` that invokes the script.

Verified for real, not assumed: `swift build` runs the plugin, generates
`AdapterBuildConfig.swift` into the plugin's work directory, and compiles
it into the `AdapterMac` module - confirmed by `find .build -name
AdapterBuildConfig.swift -exec cat {} \;` after a real build, and again
after `rm -rf .build` (full clean re-resolve + re-run of the plugin from
nothing).

## Judgment calls

- **`onClaim`/`onRelease` have no try/catch**, matching `AndroidNode.kt`
  exactly rather than "fixing" what could be read as fragility (a failed
  Bluetooth connect during `listenForCommands` propagates out of the
  whole loop, ending it). The issue asks for "same method bodies... ported
  to Swift concurrency" - not asked to change the error-handling shape,
  and doing so unasked would be exactly the kind of silent scope
  expansion the project's own conventions warn against. Whoever adds
  real trigger detection (the follow-up this issue itself names) is the
  natural place to reconsider this, the same way `adapter-android`'s own
  error handling here hasn't been revisited since #67.
- **MQTTNIO over CocoaMQTT** - see `MQTTNIOTransport.swift`'s doc comment
  for the full three-point justification; the SwiftNIO dependency tree
  (`swift-nio`, `swift-nio-ssl`, `swift-nio-transport-services`,
  `swift-log`, `swift-atomics`) is heavier than CocoaMQTT's, named as a
  real trade-off rather than hidden.
- **A SwiftPM build-tool plugin over `.xcconfig`** - see the dedicated
  section above.
- **`AsyncStream` as the Swift analogue of Kotlin's cold `Flow`** for
  `MqttTransport.subscribe` - a fresh MQTT `SUBSCRIBE` happens on each
  call, not lazily on first stream iteration, matching Kotlin's own
  documented semantics on the same method.
- **`webSocketPath` keeps its leading `/`**, the opposite of
  `adapter-android`'s stripped convention - each MQTT client library
  gets to define its own expected shape (MQTTNIO's `WebSocketConfiguration.urlPath`
  is a literal HTTP request-line URI, which needs the slash; HiveMQ's
  `MqttWebSocketConfig.serverPath` explicitly doesn't want one). Not a
  bug relative to the Kotlin version - a genuine difference between the
  two libraries, documented on the property itself.
- **`headsetIdentifier: UUID`, not a MAC-address `String`** - `MacNode`'s
  initializer takes what `BluetoothConnectionManager` already requires
  post-#101, via `BluetoothDeviceIdentifier`. There's still no
  composition root anywhere in this package (no equivalent of
  `adapter-android`'s `AdapterForegroundService`/`NodeRuntime`, #96) -
  constructing a real `MacNode` with a real device identifier, a real
  account id, and a real `MQTTNIOTransport.connect(config:clientId:)` call
  is still nobody's job yet. That composition-root issue is the natural
  next step after this one, mirroring how #96 followed #66/#67/#68/#83
  on the Android side.
