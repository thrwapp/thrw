# 210 — command sequencing

ADR 0018 decision 1, as amended by #186. Shipped in two halves:

- **Relay half** (#211, merged 2026-09-20) — commands carry `seq` and
  `epoch`; nothing enforces them. That half of this document is kept
  below, under *Relay half*.
- **Adapter half** (this branch) — both adapters now enforce them.

## Adapter half

### What enforcement is

One small type per platform, mirrored line for line:

- `packages/adapter-android/.../protocol/CommandSequenceGate.kt`
- `packages/adapter-mac/Sources/AdapterMac/Protocol/CommandSequenceGate.swift`

Two rules:

1. Within one epoch, act on a command only if its `seq` is **strictly
   greater** than the last one acted on. Equal means a duplicate
   delivery of something already done.
2. A **different epoch resets the mark entirely**, before rule 1 is
   consulted at all.

Rule 2 is the one that is not optional. The relay holds its counters in
memory, so a restart takes them to zero while the adapter still holds a
persisted mark — and without the reset, every subsequent command is
discarded as stale, permanently, curable only by clearing adapter state
by hand. That is the "restart every adapter manually" failure #178
exists to remove, reintroduced by the mechanism meant to harden things.

### Three decisions worth arguing with

**An unsequenced command is accepted, and records nothing.** A command
with no `seq` can only come from a relay older than ADR 0018 — which is
not hypothetical, since the relay half shipped first and this adapter
has already run against a relay that stamped nothing. A node that
discarded those would be completely deaf rather than merely
unprotected. The mark exists to prevent a *wrong* switch, not to
prevent switching, so refusing to act is the more dangerous failure.

**The mark moves after the command executes, not before.** A claim that
throws — headset off, out of range, busy — has not happened, and
leaving the mark behind is what lets the broker's QoS 1 redelivery
retry it. The cost is that a crash between executing and recording
allows one repeat; a repeated claim or release is idempotent at the
Bluetooth layer, whereas a *lost* one leaves the user with no audio.
That trade is deliberate, and `a command that failed is retried when it
is redelivered` pins it on both platforms.

**`accepts` is a pure query; `record` is the only writer.** Folding the
epoch reset into `accepts` would have been shorter, but then asking
twice would give different answers, and a command that failed to
execute would already have been marked done. `record` also refuses to
move the mark backwards, which nothing today needs — `accepts` guards
the call site — but a mark that could be dragged back by a mis-ordered
caller would reopen the whole hole.

### Acceptance criterion 4 — #173 is not broken by this

Criterion 4 says #173's re-asserted claim must still be accepted, and
that if sequencing discards it #173 regresses *silently*: a device that
restarts while holding the headset goes back to being permanently
stuck, with nothing on the wire to show why.

It holds by construction, in both directions:

- **The node restarted.** The relay is the same process, so its counter
  kept climbing while the node was away. The re-asserted claim carries
  a higher `seq` than the persisted mark, and rule 1 accepts it.
- **The relay restarted.** New process, new epoch, so rule 2 clears the
  mark before rule 1 is ever consulted.

Both are named tests on both platforms (`173's re-asserted claim is
accepted after the node restarts` / `after the relay restarts`), so the
regression would fail a build rather than fail on hardware.

Two facts in `relay-core` are what make that true, and they are worth
knowing if either is ever changed:

- Every command publish goes through `RelayMqttClient.publishCommand`,
  which stamps from one monotonic counter — there is no second publish
  path that could emit an unstamped or re-used `seq`.
- Nothing clears `sequences`. `forgetNode` does not touch it, so a node
  being swept and re-registering does not rewind its counter.

### Persistence

Criterion 3 asks that the store survive an adapter restart, because the
broker may redeliver a QoS 1 command to the node that comes back.

- Android: `SharedPreferencesSequenceStore`, one `apply()` for the pair
  — a mark whose epoch and seq came from different commands would not
  be a partial write, it would be a wrong one.
- macOS: `UserDefaultsSequenceStore`, reading through `object(forKey:)`
  rather than `integer(forKey:)` so a stored `0` is not
  indistinguishable from a missing key. Same reason Android's sentinel
  is `-1`.

Both are wired at the composition root (`AdapterForegroundService`,
`AppDelegate`); the in-memory store stays the default inside the node
so tests and a node built without persistence still work.

### Verification

- `adapter-android` 204 tests, `adapter-mac` 178 tests, both green via
  `pnpm turbo test`. Clean `swift build`, no warnings.
- **Mutation-tested, four mutations per platform, all killed:**
  - `seq > mark.seq` → `>=` — killed by `discards an exact duplicate`
    and the two restart tests.
  - epoch reset deleted — killed by `a new epoch resets the mark` and,
    pointedly, by `173's re-asserted claim is accepted after the relay
    restarts`.
  - mark recorded *before* executing — killed only by `a command that
    failed is retried when it is redelivered`, which is exactly the
    test written to pin that decision.
  - `accepts` always true — killed by seven tests, including the
    node-level redelivery test.
- One methodological note. The first run of the last two Android
  mutations reported a single kill each, which was wrong: the mutated
  source had not compiled, and the runner read **stale** result XML
  from the previous run. The harness now deletes the results directory
  first and fails loudly if no XML appears. Worth repeating for anyone
  mutation-testing through Gradle — a failed build looks exactly like a
  passing one if you only read the report.

### Criterion 5, and what the hardware has now shown

Criterion 5 required step 1 to be proven on hardware against deployed
adapters *before* this was written. The relay-half handoff recorded
that as partly owed: the fields were seen on the wire, but the headset
was powered off, so no adapter reaction was observable.

That debt is settled. During #171's cutover on 2026-09-20, with the
headset live, stamped commands drove real switches in both directions:

    commands/…mac/audio    {"type":"claim","seq":1,"epoch":"ea6807e9-…"}
    commands/…mac/audio    {"type":"release","seq":2,"epoch":"ea6807e9-…"}
    commands/…pixel/audio  {"type":"claim","seq":1,"epoch":"ea6807e9-…"}

The route moved on the devices each time. That run also showed the
epoch changing across a relay redeploy (`9a9a2af6-…` → `ea6807e9-…`)
with sequence numbers restarting at 1 — rule 2's exact scenario,
observed in the wild before anything depended on it.

**Still owed on hardware for this half**: the adapters that performed
those switches did not yet enforce. Enforcement needs its own run — see
*Not done*.

### Found on the way, filed not fixed

**#223: one failed claim makes the Mac permanently deaf.**
`MacNode.listenForCommands` lets a throwing claim out of its `for await`
loop, and `NodeRuntime` logs it and lets the task end — nothing
resubscribes, and `onReconnected` only re-registers. So a headset that
is off when a claim arrives silently costs the Mac every subsequent
command until the app is relaunched.

This is #161, which was only ever fixed on Android. It predates #210
and is out of scope here, but #210 makes it sharper: the
retry-on-redelivery path this branch adds is unreachable on macOS,
which is why `testACommandThatFailedIsRetriedWhenItIsRedelivered` has
to call `listenForCommands` twice where its Android twin does not.

### Not done

**Hardware verification of enforcement.** Everything above is tests.
The pattern this project has been bitten by six times — #174, #175 and
three bugs in #182 — is adapter code that passes every test and fails
against a real framework or broker, so this is not a formality. What to
do once both adapters carrying this branch are installed:

1. Watch a normal handoff still work in both directions. Enforcement
   must be invisible when nothing is out of order.
2. Restart the relay and confirm both nodes keep responding. This is
   rule 2 under real conditions, and its failure mode is total: every
   command discarded, forever, with nothing in the relay's logs to
   suggest why.
3. Restart one adapter while it holds the headset and confirm #173's
   re-asserted claim still lands — criterion 4 against the real relay
   rather than against a test's idea of it.

Publishing a deliberately stale command by hand would exercise the
discard directly, but is awkward to do safely against the live account,
and it is covered by the node-level tests on both platforms.

## Relay half

*(Unchanged from #211. Kept because the reasoning about why the two
halves were separable is the thing most likely to be re-litigated.)*

### The sequencing claim in ADR 0018 is wrong, and that is the point

ADR 0018 says decision 1 "changes the same command payloads, in the
same packages, with the same all-at-once character" as the ADR 0015
topic migration, and that the two **should land as one flag day**. I
repeated that when scoping #171.

Checking the adapters rather than trusting the ADR shows otherwise:

- **Android** — `ProtocolJson` is built with `ignoreUnknownKeys = true`,
  and its comment says exactly why: *"Lenient on decode so a relay that
  grows extra command fields later doesn't break older adapters
  mid-rollout."*
- **Mac** — `CommandPayload` was a plain `Codable` with no `CodingKeys`
  and no custom decoder, so Swift's synthesised decoding ignored
  unknown keys.

The topic migration is mutually incompatible — a node on the old shape
is invisible to a relay on the new one, with no overlap window.
**Adding fields to a command payload is neither.** The relay could emit
them against the adapters deployed at the time, and nothing broke.

That claim was not left as an argument: both adapters have tests that
decode the **exact bytes a real relay emitted**, captured from the
wire, and the mutation that sets `ignoreUnknownKeys = false` fails
them. Those tests survive the adapter half — the fields are known now,
so they assert the decoded values too, alongside the pre-#210 shape
with both absent.

### What the relay does

`RelayMqttClient.publishCommand` stamps every command. Callers still
pass a plain `CommandPayload`; the wire type is
`SequencedCommandPayload`.

That is deliberate. There are three call sites and counting, and a
sequence number any of them can forget to set is **worse than none** —
the adapter would discard whatever arrived without one as stale.

- **`seq`** is monotonic per `(account, node, resource_type)`. The key
  joins on a NUL byte rather than `/` or `:` — account and node ids are
  user- and platform-supplied, and a separator either could contain
  would let two different pairs share one counter.
- **`epoch`** is generated once per process. A reconnect does not change
  it and must not: the counters survive a reconnect, so telling
  adapters to reset would be a lie. Only a new process is a new epoch.

Counters are in-memory, and that is correct rather than a shortcut —
durability is what the epoch provides instead. Persisting them would
mean giving the relay durable state it has nowhere to put, to solve a
problem a single random string already solves.
