# 210 — command sequencing, relay half

ADR 0018 decision 1, as amended by #186. **Relay half only**: commands
now carry `seq` and `epoch`; nothing enforces them yet.

## The sequencing claim in ADR 0018 is wrong, and that is the point

ADR 0018 says decision 1 "changes the same command payloads, in the same
packages, with the same all-at-once character" as the ADR 0015 topic
migration, and that the two **should land as one flag day**. I repeated
that when scoping #171.

Checking the adapters rather than trusting the ADR shows otherwise:

- **Android** — `ProtocolJson` is built with `ignoreUnknownKeys = true`,
  and its comment says exactly why: *"Lenient on decode so a relay that
  grows extra command fields later doesn't break older adapters
  mid-rollout."*
- **Mac** — `CommandPayload` is a plain `Codable` with no `CodingKeys`
  and no custom decoder, so Swift's synthesised decoding ignores unknown
  keys.

The topic migration is mutually incompatible — a node on the old shape is
invisible to a relay on the new one, with no overlap window. **Adding
fields to a command payload is neither.** The relay can emit them today,
against the adapters currently deployed, and nothing breaks.

So this does not need #171's flag day, and bundling it would have made
that flag day larger and riskier for nothing.

That claim is not left as an argument: both adapters now have tests that
decode the **exact bytes a real relay emitted**, captured from the wire,
and the mutation that sets `ignoreUnknownKeys = false` fails them. The
assumption this whole approach rests on is now something that breaks
loudly if it stops being true.

## What the relay does

`RelayMqttClient.publishCommand` stamps every command. Callers still pass
a plain `CommandPayload`; the wire type is `SequencedCommandPayload`.

That is deliberate. There are three call sites and counting, and a
sequence number any of them can forget to set is **worse than none** —
the adapter would discard whatever arrived without one as stale.

- **`seq`** is monotonic per `(account, node)`. ADR 0018 specifies per
  `(account, node, resource_type)`; there is exactly one resource type
  today, so the two are identical, and it gains the segment with #171.
  The key joins on a NUL byte (`\u0000`) rather than `/` or `:` — account
  and node ids are user- and platform-supplied, and a separator either
  could contain would let two different pairs share one counter.
- **`epoch`** is generated once per process. A reconnect does not change
  it and must not: the counters survive a reconnect, so telling adapters
  to reset would be a lie. Only a new process is a new epoch.

Counters are in-memory, and that is correct rather than a shortcut —
durability is what the epoch provides instead. Persisting them would mean
giving the relay durable state it has nowhere to put, to solve a problem
a single random string already solves.

## Why the epoch is not optional

Without it the scheme deadlocks the whole system, which is why #186 added
it. The relay holds all state in memory (the premise of #178), so a
restart resets the counters to zero while adapters still hold persisted
high-water marks — and every subsequent command is discarded as stale,
permanently, until adapter state is cleared by hand. That is exactly the
"restart every adapter manually" failure #178 removed, reintroduced by
the mechanism meant to harden things. The relay restarts routinely: three
times in one day of work on it.

## Verification

- `relay-core` 43, `relay-hosted` 16, `adapter-mac` 134,
  `adapter-android` green.
- Mutation-tested: a single global counter kills
  `sequences each node independently`; an epoch regenerated per command
  kills `stamps every command with a sequence number and an epoch`. The
  second matters most — a per-command epoch would make adapters reset
  their high-water mark constantly, silently disabling the mechanism
  while appearing to work.
- Both adapters' forward-compatibility tests assert on real captured
  wire bytes, and the `ignoreUnknownKeys = false` mutation fails them.
- **On the wire, against the deployed relay's broker**: a real command
  arrived as
  `{"type":"claim","seq":1,"epoch":"2174ac4b-0ab7-4cff-967e-8a352e3bd7c8"}`.

### What the hardware run did *not* prove

The plan was to watch a current-build adapter act on a stamped command.
The command was delivered with the fields, but the **headset was powered
off** (`Not Connected` on the Mac, `mActiveDevice: null` on the phone),
so there was nothing to connect and the adapter's reaction was not
observable.

That is why the decode tests exist: for this particular question they are
better evidence than the hardware run would have been — deterministic,
permanent, and they fail if the guarantee is ever removed. But the
end-to-end observation is still owed, and is cheap to do next time the
headset is out: play media, watch the route move, confirm a stamped
command drove it.

## Not done

Everything adapter-side. The adapters ignore `seq` and `epoch` entirely —
they do not store a high-water mark, do not discard anything, and do not
reset on an epoch change. That is #210's remaining work and is per
platform, independent, and safe to do one at a time.

One constraint for whoever writes it: **#173's re-asserted claim must
still be accepted.** It is published on every registration from the
holder, and if sequencing discards it, #173 regresses silently — a node
that restarts while holding would go back to being permanently stuck.
