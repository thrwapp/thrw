# 307 — The relay never stops believing

## What was wrong

The relay could hold a belief that **both nodes explicitly contradicted**,
log the contradiction from each of them, and do nothing.

Observed on the reference pair on 2026-09-26, from the most ordinary
action there is — taking the AirPods out of their case, which connects
them to whichever device they favour with no involvement from thrw:

```
08:04:19  route_drift         node=mac      nodeHoldsRoute=False  believedHolder=mac
08:04:19  reassert_exhausted  node=mac      attempts=2
08:04:41  route_drift         node=android  nodeHoldsRoute=True   believedHolder=mac
08:04:46  node_event          node=mac      type=media  holderBefore=mac  holderAfter=mac
```

The Mac says it has no route. The Pixel says it has one. Neither has an
active trigger, so `computeActiveHolder()` is null and `currentHolder()`
falls through to rule 5's `lastClaimed`, which still says "mac". Playing
something on the Mac then recomputes, finds the Mac *already* the holder,
and issues no command — so the audio came out of the laptop speakers and
nothing the user could do would move it.

Two mechanisms, each defensible, combining into a dead end: arbitration
acts on holder **changes**, and the only thing that repairs a false belief
is re-assertion, which #289 bounds at two attempts per tenure for good
reason.

## What changed

**`PriorityEngine.releaseStaleFallback(nodeId)`** (`packages/relay-core/src/index.ts:232`)
— clears `lastClaimed` when that node is the believed holder, and returns
whether anything changed.

**Called from the registration handler** (`services/relay-hosted/src/relay-service.ts:777`),
deliberately *before* the re-assert: having stopped believing, there is
nothing left to re-assert, and `syncHolder` is what turns the cleared
fallback into a real transition.

Three constraints, each with a reason rather than a preference:

1. **`holdsRoute === false`, never `!holdsRoute`.** `undefined` means the
   node could not answer, which is #303's permanent state. Reading it as
   a denial would let one stuck node continuously reassign the headset.
2. **Only the believed holder's own report counts.** A *different* node
   claiming the route is still not acted on — under multipoint two hosts
   hold a Bluetooth link at once (`compatibility-matrix.md`), so that
   signal is not trustworthy alone. A node reporting it does **not** have
   the route is the one report only that node can make.
3. **Nothing is cleared while any node has an active trigger.** Then
   `computeActiveHolder()` already decides and the fallback is not in
   play; clearing it would change rule 5's meaning for a case that is not
   broken. A holder *with* live triggers denying the route is what the
   bounded re-assert is for.

## Scope correction from the issue

#307 proposed transferring belief to whichever node reports
`nodeHoldsRoute: true`. **That is not what this does**, and the narrower
version is better: acting only on the first-hand denial avoids trusting
the multipoint-unreliable positive signal entirely, and it produces the
same outcome on the observed trace. Belief goes to null, the Mac's next
`media` event is then a real transition, and a normal CLAIM follows
through the ordinary path.

## The one deviation from the issue's criteria

The issue said belief transfer should publish nothing by itself. It
publishes a **RELEASE**, because clearing the belief takes the holder to
null and `syncHolder` releases the outgoing holder.

Kept rather than suppressed, for a reason: the node has just said it has
no route, but its own connection state may still think otherwise — that
is exactly #303's shape, and `BluetoothConnectionManager` caches
`.connected`. A release is how the relay says "agreed, you don't have
it", and it is the cheap idempotent direction (`CommandCoalescer`'s kdoc
on why a release is never the expensive one). Suppressing it would leave
the two sides disagreeing silently.

## Two things the tests taught me

Recorded because in both cases my expectation was wrong, not the code:

- **The reclaim is not immediate.** Clearing the belief publishes a
  release, and the coalescer then holds any claim arriving inside
  `DEFAULT_RELEASE_WINDOW_MS`. Correct — the route is still settling —
  but it means the test has to fire the scheduler rather than wait.
- **A registration from the holder with no route reading already
  re-asserts.** `reassertHolderClaim` treats `undefined` as "cannot tell"
  on purpose (rule 1), so a node with no route observer still gets the
  restart repair. That command is pre-existing and is now asserted, so a
  regression in either mechanism is visible.

## Not verified

**Nothing here has been seen on hardware.** The wedge was observed live
and is reproduced in tests; the fix has only been observed in tests. After
deploy, the line to watch for is `fallback_released` appearing when a node
reports `observedRoutes: {audio: false}` while believed to be the holder,
followed by the route actually moving on the next trigger.

## Still open

This does not explain **why** the Mac's belief and the hardware diverged
in the first place. It makes the divergence recoverable. #303 is the
other half — a node whose route reading never resolves is still invisible
to reconciliation, and this change deliberately does not act on it.
