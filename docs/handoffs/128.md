# #128: adapter-mac composition root wiring MacNode into a running menu-bar app

## What was done

`packages/adapter-mac` now has a real, running composition root: a
menu-bar `NSApplication` (`AdapterMacApp`) that constructs a real
`MacNode` wired to a real `MQTTNIOTransport` and
`IOBluetoothPeripheralGateway`, plus a real `VoipTriggerMonitor`, and
hands them to a testable `NodeRuntime` seam. This is the gap
`docs/handoffs/112.md` flagged: "constructing a real MacNode with a real
device identifier, a real account id, and a real
MQTTNIOTransport.connect(config:clientId:) call is still nobody's job
yet." It is now `AppDelegate`'s job.

Split the same way `adapter-android`'s #96 split it:
- **`Sources/AdapterMac/NodeRuntime.swift:34`** — the testable half.
  Plain Swift, zero AppKit imports.
- **`Sources/AdapterMacApp/AppDelegate.swift:27`** — the untestable half.
  Real `NSApplication`, real transport, real Bluetooth gateway.

## Acceptance criteria

1. **A real, running menu-bar `NSApplication` per ADR 0004.** Built as a
   new `AdapterMacApp` executable target.
   `AppDelegate.swift:34` (`main()`) constructs `NSApplication.shared`,
   sets the delegate and calls `app.run()` — a real main run loop, which
   `IOBluetoothPeripheralGateway` requires (`docs/handoffs/101.md`; the
   issue explicitly called out that this has to actually satisfy that, not
   just compile). `setUpStatusItem()` (`:50`) creates the
   `NSStatusItem` with a "headphones" SF Symbol and a Quit menu item.
   `Info.plist`'s `LSUIElement` is `true`, so it is menu-bar-only with no
   Dock icon — the declarative form of ADR 0004's "a menu bar icon […]
   and a background process".

   No alternative was proposed: ADR 0004 already commits to this, and
   the research question the issue raised (does something else fit
   better?) resolved *toward* the ADR — a `launchd` LaunchAgent with no
   UI would leave no way to quit or see status, and `IOBluetooth`'s main
   run loop requirement rules out a bare headless binary anyway.

2. **Real `BluetoothConnectionManager`, real `MQTTNIOTransport` via
   `RelayConfig.fromBuildConfig()`, real `MacNode` from both.**
   `AppDelegate.swift:85-93`: `MQTTNIOTransport.connect(config:clientId:)`
   with `RelayConfig.fromBuildConfig()` (ADR 0005 — build-time config, not
   a hardcoded endpoint), `BluetoothConnectionManager(gateway:
   IOBluetoothPeripheralGateway())`, and `MacNode` built from both.

3. **`register(manifest:)`, `listenForCommands()` in a lifetime-scoped
   task, and the trigger monitor wired to the same `MacNode`.**
   `AppDelegate.swift:95-96` constructs
   `VoipTriggerMonitor(source: NSWorkspaceRunningApplicationSource(), node: node)`
   — the *same* `node` instance, which is what makes `MacNode`'s
   `EventLifecycle` conformance (#127) the path triggers take.
   `NodeRuntime.start(manifest:)` (`NodeRuntime.swift:56`) launches all
   three as independent `Task`s; `applicationWillTerminate`
   (`AppDelegate.swift:46`) cancels them via the returned handle — the
   equivalent of Android's `SupervisorJob.cancel()` in `onDestroy()`.

   **One trigger monitor, not two.** The issue said "both trigger
   monitors"; #127 only produced one (`VoipTriggerMonitor`). That is not
   an omission here — #127's own research established macOS has no
   call-detection API at all (`AVAudioSession` is iOS/tvOS/watchOS-only),
   a permanent platform gap documented in `docs/spec/architecture.md`'s
   "Mac's trigger-detection gap" section. There is no second monitor to
   wire.

4. **Device/account identity mirroring `DeviceIdentity`/`AdapterProvisioning`.**
   `Identity/DeviceIdentity.swift:23` generates a UUID node id once and
   persists it in `UserDefaults` (stable across restarts — the broker's
   ACLs key off the connecting client id). `:44` builds the
   `NodeManifest`. `Identity/AdapterProvisioning.swift:25` reads/writes
   the account id and headset address.

   **No provisioning UI**, per this criterion's own scope boundary.
   Stated plainly: nothing in this codebase writes those two
   `UserDefaults` keys today, so the app **cannot do anything on a real
   Mac** without `defaults write` by hand first. Exactly the gap
   `docs/handoffs/96.md` documented for Android before #102. `AppDelegate`
   treats either being unset as "not provisioned" and logs a clear error
   instead of connecting a half-configured node (`:66-82`) — verified
   live, see Verification below.

5. **Testable seam separate from the untestable glue.** `NodeRuntime` is
   that seam: plain Swift, no AppKit. `NodeRuntimeTests.swift` (6 tests)
   covers manifest registration, commands-topic subscription at QoS 1,
   the VoIP monitor wired through to the transport, relay commands
   driving the Bluetooth gateway, all three tasks running independently,
   and handle cancellation stopping the monitor. `IdentityTests.swift`
   (5 tests) covers node-id generation/persistence, the manifest's
   contents, and provisioning round-tripping — against a throwaway
   `UserDefaults` suite, never the real user's defaults.

   **Not covered by tests**, stated plainly: everything in
   `AppDelegate.swift` — the `NSStatusItem`, the real
   `MQTTNIOTransport.connect` call, the real `IOBluetoothPeripheralGateway`,
   and the not-provisioned branches. Same boundary #96 drew. These were
   verified by running the app for real instead (below).

6. **No connection state machine.** Not implemented. `NodeRuntime` and
   `AppDelegate` call `register`/`listenForCommands`/`onClaim`/`onRelease`
   as the plain hooks the protocol declares; nothing tracks or
   transitions a node state. Frozen contract per ADR 0010/0011/0013.

7. **No new dependencies.** `Package.swift` gained a target, not a
   dependency — `AdapterMacApp` uses only `AdapterMac`, `AppKit` and
   `os` (all already available). MQTTNIO remains the only external
   package.

## Test command

`cd packages/adapter-mac && swift test` — **55/55 tests passed**
(44 pre-existing + 6 `NodeRuntimeTests` + 5 `IdentityTests`). Clean
build, zero warnings.

Also run **on Linux**, in a `swift:5.10-jammy` container, since that is
where this repo's `agent-code`/`agent-eval` automation runs `swift test`
(only `ci.yml`'s `mac-ipad` job uses real macOS): `swift build` and
`swift test` both pass there too, 55/55. The build log confirms only
`AdapterMac` compiles and `AdapterMacApp` does not — i.e. the
`#if os(macOS)` manifest guard does what it claims.

**This check caught a real bug that the macOS build and all of CI
missed.** `NodeRuntime.swift` originally did a plain `import os`, and
`os`/`os.Logger` is an Apple-platform module that does not exist on
Linux. Unlike AppKit — confined to the macOS-only `AdapterMacApp` target
— `NodeRuntime` is part of the `AdapterMac` *library* target, which does
build on Linux, so this broke the agent container build outright
(`error: no such module 'os'`, repeated across every file in the
target). Fixed with a `#if canImport(os)` guard plus a real stderr
fallback (`NodeRuntime.swift`'s `logError`), not an empty one — silently
dropping the error on the non-Apple path would make a failing node look
like an idle one. Worth recording because nothing in CI would have
caught it: `mac-ipad` is macOS, and `evaluate` passes in ~6s without
compiling Swift at all.

## Verification (beyond the test suite)

The app was built and actually run, not just compiled:

- `./Scripts/build-app-bundle.sh` produced a well-formed
  `AdapterMac.app`; confirmed `CFBundleIdentifier=app.thrw.mac`,
  `LSUIElement=true`, and `NSBluetoothAlwaysUsageDescription` present via
  `PlistBuddy`.
- Launched it with `open`. The process stayed alive as a real
  `NSApplication` accessory app (confirmed running via `pgrep`, and
  registered with the window server via System Events).
- Its real `os_log` output, captured live:
  ```
  AdapterMacApp[96668] [app.thrw.mac:AppDelegate] Not provisioned (no account id) - not starting a node
  ```
  This is the correct, intended behavior on an unprovisioned machine —
  it refused to start a half-configured node rather than connecting one.
- The status item's SF Symbol was verified to resolve to a real 16×16
  image (`NSImage(systemSymbolName: "headphones",…) != nil`).

**Not verified**: the fully-provisioned happy path — a real MQTT
connection to `relay.thrw.app` plus a real Bluetooth connect/disconnect
against actual headset hardware. Deliberately not run: it would have
meant writing real provisioning values to the developer's own machine
and physically moving a headset's audio route as a side effect of a
build verification. The pieces it composes are individually verified
(`MQTTNIOTransport` by #112, `IOBluetoothPeripheralGateway` by #101,
`MacNode` by `MacNodeTests`), but their real composition on a
provisioned Mac has not been exercised end-to-end and should not be
assumed working.

## Known gaps / judgment calls

- **Bundle identifier `app.thrw.mac` confirmed with Tom directly**, per
  the issue's instruction to ask rather than invent a placeholder (he may
  be mid-Apple-Developer-Program registration, #132). Matches the
  `thrw.app` domain already used across the system.
- **The `.app` bundle is assembled by a shell script, not SwiftPM.**
  `Scripts/build-app-bundle.sh` — plain SwiftPM has no notion of a macOS
  `.app` bundle, and `swift build` alone produces a bare Unix executable
  whose `Bundle.main` has no `Info.plist`, which is not enough for
  `NSBluetoothAlwaysUsageDescription` to be read at all. A real Xcode
  project would be the heavier alternative; this keeps `swift test` (what
  CI and this repo's automation actually run) working unchanged.
- **The bundle is unsigned and un-notarized.** That needs a real Apple
  Developer Program team identity, which doesn't exist yet (#132). The
  unsigned bundle runs locally via "Open Anyway"; it is not
  distributable.
- **`Package.swift` guards the app target behind `#if os(macOS)`.**
  `AdapterMacApp` imports AppKit, which doesn't exist on Linux, and this
  repo's `agent-code`/`agent-eval` automation runs `swift test` on a
  Linux container — where `swift build` compiles *every* target in the
  manifest, not just what the test target depends on. The usual
  `#if canImport(AppKit)`-inside-the-source pattern (what
  `IOBluetoothPeripheralGateway.swift` uses) can't work for an
  `executableTarget`: it needs a real `@main` entry point on every
  platform it's compiled for, and a fully-conditioned-away file leaves
  none. Guarding at the manifest level is the only option. Verified
  against a real Linux container, not assumed — see "Test command".
- **Nothing in CI builds this package on Linux**, which is how the
  `import os` bug above survived a fully green CI run. The Linux check
  that caught it was run by hand in Docker. Worth considering whether
  `ci.yml` should gain a Linux `swift build` job for `packages/adapter-mac`
  — noted, not implemented, since `.github/**` is always human-merge per
  AGENTS.md (same reasoning #131 used for its own CI recommendation).
- **`NodeRuntime` is `@MainActor`, not `Sendable`.** `VoipTriggerMonitor`
  (#127) is a plain class with mutable state and genuinely isn't
  `Sendable`, so a `Sendable` `NodeRuntime` holding one is an error in
  the Swift 6 language mode (it was a live warning before this change).
  Main-actor isolation protects that state instead — and is what this
  composition root wants anyway, since `IOBluetoothPeripheralGateway`
  already requires the main run loop. `@MainActor` is plain Swift
  concurrency, not an AppKit type, so `NodeRuntime` still tests without a
  host app. No change was made to #127's own code.
- **`DeviceIdentity.adapterVersion` is a hardcoded `"0.1.0"`.**
  `adapter-android` reads `BuildConfig.VERSION_NAME`, which Gradle
  derives; SwiftPM has no equivalent for a plain package target, and the
  `.app` bundle's `CFBundleShortVersionString` isn't readable from the
  library target that builds the manifest. A real fix belongs with
  whatever issue gives this package a versioning scheme.
- **The manifest advertises only `.voip`.** Not `.call` (no macOS API
  exists — #127), not `.media` (no detector in this package), not
  `.manual_claim` (no UI emits it). Mirrors `DeviceIdentity.kt`'s own
  reasoning rather than advertising capabilities nothing produces.
