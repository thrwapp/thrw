# HANDOFF: adapter-android release signing config (#148)

## What was done

Added a release `signingConfig` to
`packages/adapter-android/app/build.gradle.kts` reading upload-key
material from a gitignored `keystore.properties` or, failing that,
environment variables. Before this, `bundleRelease` produced an
unsigned bundle that Play Console would reject - blocking the first
upload now that the Play developer account and app record exist (#132).

## How to configure it locally

Create `packages/adapter-android/keystore.properties` (gitignored - it
sits next to `config/adapter.properties`, matching where this module
already keeps `rootProject`-level config):

```properties
storeFile=/absolute/path/to/thrw-upload.jks
storePassword=...
keyAlias=thrw-upload
keyPassword=...
```

Or set `THRW_PLAY_KEYSTORE_FILE`, `THRW_PLAY_KEYSTORE_PASSWORD`,
`THRW_PLAY_KEY_ALIAS`, `THRW_PLAY_KEY_PASSWORD` instead - the
properties file wins when both are present. The environment-variable
path exists so CI can supply the key from secrets without writing a
file; there is no Android release workflow yet, so nothing uses it in
CI today.

Then:

```
cd packages/adapter-android && ./gradlew bundleRelease
# -> app/build/outputs/bundle/release/app-release.aab, signed
```

## Acceptance criteria, with evidence

**1. Release signingConfig from gitignored file or env vars.** Done -
`keystore.properties` is read first, env vars are the fallback
(`uploadKeyValue`). No key material anywhere in the committed tree.

**2. Unconfigured builds still succeed, unsigned - no debug-key
fallback.** Verified:

```
$ ./gradlew bundleRelease          # no key configured
BUILD SUCCESSFUL in 3s
$ keytool -printcert -jarfile app/build/outputs/bundle/release/app-release.aab
Not a signed jar file
```

Deliberately *not* falling back to `signingConfigs.getByName("debug")`:
a debug-signed AAB looks publishable right up until Play rejects it,
which is a worse failure than an obviously-unsigned one.

**3. Partial configuration fails loudly.** Verified - setting only
`THRW_PLAY_KEYSTORE_FILE`:

```
* What went wrong:
Upload key is partially configured - missing storePassword/THRW_PLAY_KEYSTORE_PASSWORD,
keyAlias/THRW_PLAY_KEY_ALIAS, keyPassword/THRW_PLAY_KEY_PASSWORD. Set all four
(see docs/handoffs/148.md), or none to build unsigned.
```

**4. `.gitignore` covers the key material.** Added `keystore.properties`,
`*.jks`, `*.keystore` at the repo root - deliberately repo-wide rather
than scoped to `packages/adapter-android/`, so a keystore saved
anywhere in the tree can't be committed by accident.

**5. Verified end-to-end against a real keystore.** Generated a
throwaway RSA keystore (in the session scratchpad, never in the repo,
deleted afterwards), built with it, and confirmed the resulting AAB
actually carries that certificate rather than just that the build
succeeded:

```
$ keytool -printcert -jarfile app/build/outputs/bundle/release/app-release.aab
Owner:  CN=Signing Config Test, OU=Test, O=Test, L=Test, ST=Test, C=GB
Issuer: CN=Signing Config Test, OU=Test, O=Test, L=Test, ST=Test, C=GB
Valid from: Fri Sep 18 19:41:56 BST 2026 until: Sun Oct 18 19:41:56 BST 2026
```

`./gradlew test` also still passes, unchanged.

## Known gaps / judgment calls

- **No CI release workflow.** The env-var path is wired up and ready,
  but nothing in `.github/workflows` builds or uploads a release bundle
  yet. Adding one (plus the four secrets, plus a Play Console service
  account for automated upload) is a separate piece of work, and
  `.github/**` is human-merge per AGENTS.md regardless.
- **No `versionCode` automation.** Play rejects re-uploads of the same
  `versionCode`, which is currently the hardcoded `1` in
  `defaultConfig`. The first upload is fine; the second will need this
  bumped, either by hand or by deriving it in the release workflow
  above. Flagged rather than solved, since the right answer depends on
  whether releases end up manual or CI-driven.
- **`minifyEnabled` left off.** R8/ProGuard is untouched - turning it
  on is a real change needing its own keep-rules verification against
  the MQTT/serialization paths, not something to bundle into a signing
  change.
