# 213 — show what thrw thinks is happening (Mac)

## Why

Neither adapter told the user anything. The Mac menu bar had *Set Up…*
and *Quit thrw*; Android has only the provisioning screen. Nothing showed
whether this node held the headset, or whether it was talking to the
relay at all.

That made every failure this week **silent and indistinguishable from
every other**:

- #182 — the adapter lost its MQTT connection and never reconnected. It
  kept running, notification up, looking perfectly healthy, publishing
  nothing.
- #178 — a node reconnected but never re-registered, so it was connected
  and *invisible* to the relay.
- #173 — the relay believed a restarted node still held the headset, so
  it issued no claim and the device sat doing nothing.

From outside, all three look the same: *thrw stopped working and said
nothing.* Telling them apart took subscribing to MQTT by hand and reading
raw payloads — fine for development, impossible mid-meeting.

## What it shows

A disabled first item in the menu, above the manual claim:

| state | text |
|---|---|
| transport down | `Disconnected from relay` |
| connected, holds the route | `Holding headset` |
| connected, does not | `Not holding headset` |
| connected, route unreadable | `Connected — headset state unknown` |

## The two decisions, both tested

**Disconnected outranks everything.** While the transport is down, any
holder state is a stale belief, and a confident wrong answer is worse
than an unhelpful true one. Checking the route first would report a
crisp "Not holding" for a node that is not even talking to the relay —
which is exactly #182's failure, dressed up as information.

**An unreadable route is not "no".** #191's observer returns `nil` when
it genuinely cannot tell, and collapsing that into `notHolding` would
invent an answer. It gets its own wording.

Both are mutation-tested: making the route outrank the connection, and
reporting `nil` as `notHolding`, each fail their own test and nothing
else.

## No polling

Refreshed in `menuWillOpen`, not on a timer. Nobody reads a closed menu,
and a timer would burn battery keeping a string current that nobody is
looking at. Acceptance criterion 4 asked for this explicitly.

The status is asked of the node each time rather than cached — a cached
status is exactly what goes stale during the failures this exists to
expose.

## Reuses what is already there

`MacNode.status()` combines `MqttTransport.isConnected()` with #191's
`AudioRouteObserver`. No new permissions, no new window, no new
observation machinery — #191 already answers "do I hold the route" from
the **actual audio route** rather than a cached belief, which is what
makes this trustworthy rather than another thing that can go stale.

`isConnected()` defaults to `true` on the protocol: a transport that does
not track connection state has no way to be *known* disconnected, and
defaulting to `false` would put every test fake permanently into
"Disconnected from relay".

## Verification

- `adapter-mac` 146 tests.
- Mutation-tested on both precedence decisions.

### Not verified: the menu itself

Same gap as #212, and the same single click closes both. The status logic
is tested; that the item *appears*, is disabled, and refreshes on open is
not — clicking a status-bar item programmatically needs Accessibility
permission `osascript` does not have on this machine.

## Stacked on #212

This branch is built on `agent/212-manual-claim-mac`, not `main`. Both
rewrite the same menu, and attempting them independently produced a
half-applied file — the string anchors for the menu code silently matched
nothing, because the claim item only exists on the other branch. **#214
merges first.**

That near-miss is also why the edits here assert their anchors rather
than relying on `str.replace` quietly doing nothing.
