# 308 — The Pixel's notification contradicts its own button

Stacked on #324 (#309). Review and merge that first.

## What was wrong

The notification read *"Holding headset"* while its own action button
offered *"Claim Headset"* — self-contradictory on its face. Observed with
the Mac demonstrably holding the route and `mActiveDevice: null` on the
phone.

The two halves come from different sources, computed in the same
`refreshNotification()` call:

- **text** ← `AndroidNode.status()` → `bluetooth.isAudioRouteActive()`, the real A2DP route
- **action** ← `claimAction(holdsClaim = …)` → `HolderState`, the relay's retained holder

The action was right. The text was stale.

## The mechanism, and a wrong turn worth recording

My first hypothesis was that the refresh races the disconnect. I then
"disproved" it with a force-stop/relaunch that still showed the old
value, and concluded the fault was in `isAudioRouteActive` returning a
wrong value.

**That disproof was bad evidence**, in two ways: I read `android.subText`
rather than `android.text`, and the service had not finished starting
when I read it. The device then dropped off `adb` and it could not be
repeated. Recorded because it cost a detour, and because "my test said
otherwise" is only worth something if the test was sound.

Reading the code settles it without needing the device.
`isAudioRouteActive` returns:

```kotlin
active?.address?.equals(deviceAddress, ignoreCase = true) ?: false
```

With `mActiveDevice: null` that is `false` → `NOT_HOLDING` → *"Not holding
headset"*. A missing proxy returns `null` → `UNKNOWN` → *"Connected —
headset state unknown"*. **Neither produces "Holding headset."** The only
input that does is `true`, so the displayed value cannot have been
computed from the state it was displayed against. It was computed
earlier, and never recomputed.

So the original hypothesis was right:

1. The Mac claims; the relay's holder changes; the Pixel refreshes.
2. That refresh reads the route **while its own disconnect is still in
   flight** — the observed release took 341ms to resolve — so it
   legitimately still reads `true`.
3. The disconnect completes, **no second holder change ever comes**, and
   the stale line stays on screen indefinitely.

## What changed

The notification refreshed on **holder changes**, but its status line is
about the **route** — and the route settles later than the holder does,
measurably: 341ms for that release, up to 3340ms for a claim (#193 item
1 timings).

`AndroidNode.commandCompletions()` ticks once on every terminal command
outcome, and `AdapterForegroundService` refreshes on it. A command
outcome is precisely when the adapter has finished acting, so the route
it then reads has settled.

Two things this deliberately is **not**:

- **Not `commandFailures()`** (added in #324). That only changes value on
  failure→none and none→failure, so two consecutive successes emit
  nothing — and a release following a claim is exactly two consecutive
  successes, which is the case that produced this bug.
- **Not a timer.** `AdapterForegroundService`'s own note explains why a
  periodic refresh was rejected: it would wake a battery-sensitive
  foreground service to keep a string current that nobody is reading.

Ticked in the command loop's `finally`, beside `routeTransition.end()`
and for the same reason: one site on every terminal path, so a `catch`
added later cannot silently stop the notification updating.

## macOS needs no equivalent — checked, not assumed

`menuWillOpen` calls `refreshStatusItem`, `refreshClaimItem`,
`refreshUnmuteItem` and `refreshPauseItem` on every open, and
`refreshStatusItem` reads `node?.status()` live. The Mac cannot display a
stale route reading, because nobody reads a closed menu.

## Not verified, and what remains

**No hardware run.** The reproduction is: claim on the Mac while the
Pixel holds the route, then read the Pixel's notification once the
release has settled. Needs both devices and the AirPods.

**A route change thrw did not cause still produces no refresh.** The user
taking the headset with the device's own controls, putting it in its
case, or walking out of range generates no command, so nothing ticks.
Closing that needs an observer on the A2DP active-device broadcast —
larger, and filed separately rather than absorbed here.
