# HANDOFF: IOBluetooth (classic Bluetooth) gateway for packages/adapter-mac (#101)

Replaces #95/PR #99's `CoreBluetoothPeripheralGateway` with an
`IOBluetoothDevice`-backed implementation of the same
`BluetoothPeripheralGateway` protocol. CoreBluetooth on macOS is BLE
only, so connecting/cancelling a `CBPeripheral` never moves AirPods'
audio route — the thing ADR 0002's sequential handoff actually depends
on.

## What changed

- **Added** `Sources/AdapterMac/Bluetooth/IOBluetoothPeripheralGateway.swift`
  — the real gateway, `IOBluetoothDevice`-backed, resolving devices from
  `IOBluetoothDevice.pairedDevices()` (never pairing, never running an
  `IOBluetoothDeviceInquiry`).
- **Added** `Sources/AdapterMac/Bluetooth/BluetoothDeviceIdentifier.swift`
  — the address ⇄ `UUID` mapping the protocol seam needs (see "Judgment
  calls" below).
- **Added** `Sources/AdapterMac/Bluetooth/BluetoothGatewayError.swift` —
  the error enum, moved out of the deleted CoreBluetooth file and
  re-cased for classic Bluetooth.
- **Deleted** `Sources/AdapterMac/Bluetooth/CoreBluetoothPeripheralGateway.swift`.
- **Added** `Tests/AdapterMacTests/Bluetooth/BluetoothDeviceIdentifierTests.swift`
  — 7 tests over the one part of this change that is pure logic.
- **Doc-comment-only edits** to `BluetoothPeripheralGateway.swift` and
  `FakeBluetoothPeripheralGateway.swift` (both said "CoreBluetooth",
  which is now wrong). No signatures, no test logic.
- One line in `docs/spec/architecture.md`, which listed CoreBluetooth as
  the Mac adapter's Bluetooth API.

## Acceptance criteria

1. **New type conforming to the existing protocol, backed by
   `IOBluetoothDevice`, same `CheckedContinuation` bridging pattern.**
   `IOBluetoothPeripheralGateway` (`IOBluetoothPeripheralGateway.swift:50`)
   declares `: BluetoothPeripheralGateway`.
   `connect` bridges `openConnection(_:)`'s `connectionComplete:status:`
   callback (`:62-83` calling, `:153-162` receiving);
   `disconnect` bridges `registerForDisconnectNotification(_:selector:)`
   (`:86-114` calling, `:168-171` receiving). Continuation bookkeeping
   lives in a separate `NSObject` callback target (`:130`), the same
   split the CoreBluetooth implementation used.
2. **`BluetoothConnectionManager` and its tests unchanged.** `git diff`
   touches neither `BluetoothConnectionManager.swift` nor
   `BluetoothConnectionManagerTests.swift` — verify with
   `git diff --stat main`. Two things next to them did change, both
   comment-only and both because they named CoreBluetooth explicitly:
   the protocol's own doc comment
   (`BluetoothPeripheralGateway.swift:3-17`) and one line of
   `FakeBluetoothPeripheralGateway.swift:5-6`. The fake's *behaviour* and
   every assertion against it are untouched.
3. **`CoreBluetoothPeripheralGateway` removed, not kept.** Deleted
   outright; nothing in `packages/**` referenced it (it was only ever
   constructed by callers that don't exist yet), so no call sites needed
   updating. Remaining mentions in the tree are historical:
   `docs/handoffs/95.md`, ADR 0004, `docs/roadmap.md`.
4. **No new dependency.** `IOBluetoothPeripheralGateway.swift:3-5`
   imports only `Foundation`, `IOBluetooth` and `IOKit` (for
   `kIOReturnSuccess`), all macOS system frameworks. `Package.swift` is
   unchanged — no `dependencies`, no `linkerSettings`; `import
   IOBluetooth` auto-links the framework.
5. **Real connect/disconnect still not exercised in CI.** Same approach
   as #95: `BluetoothConnectionManagerTests` runs against
   `FakeBluetoothPeripheralGateway` at the protocol boundary
   (`BluetoothConnectionManagerTests.swift:10`), and the new
   `IOBluetooth` type has no test of its own.
6. **Hardware verification.** See the next two sections — yes, there is
   a step outstanding, and it is the only thing that can prove the point
   of this issue.

## Hardware verification still outstanding

**What this PR proves:** the protocol seam holds (the manager and its
tests needed no changes); the address ⇄ identifier mapping is correct and
tested; the code compiles against the macOS SDK (per the `macos-14` CI
job).

**What it does not prove:** that `openConnection()`/`closeConnection()`
actually move AirPods' audio route. Nobody has run this against
hardware. The claim that classic Bluetooth is the right layer is
well-founded (it's where A2DP/HFP live, and it's what `IOBluetooth`
controls), but "well-founded" is not "verified".

Someone with a Mac and real AirPods still needs to, on a machine with the
headset already paired:

1. Get the headset's address (`system_profiler SPBluetoothDataType`, or
   `IOBluetoothDevice.pairedDevices()`), build its identifier with
   `BluetoothDeviceIdentifier.identifier(forAddressString:)`, and call
   `connect`/`disconnect` from a host process that runs its main run loop
   (see the run-loop note below).
2. Confirm the *audio route* moves, not just the connection state:
   macOS's Sound output device should switch to the AirPods on connect
   and away on disconnect. This is exactly the check CoreBluetooth would
   have failed.
3. Confirm the disconnect releases the headset well enough for a second
   host to claim it — the actual ADR 0002 handoff behaviour.

Unknowns that only hardware can settle: whether AirPods need the audio
profile opened explicitly (an SDP query + service-level connect) rather
than just the baseband connection; and whether macOS 14+ prompts for
Bluetooth permission on these `IOBluetooth` calls the way it does for
CoreBluetooth (no `NSBluetoothAlwaysUsageDescription` is declared
anywhere in this package — there's no app bundle yet to declare it in).

## Judgment calls

- **The identifier encoding.** Classic Bluetooth has no per-device UUID;
  `IOBluetoothDevice` is addressed by its 6-byte MAC. The protocol
  signature is `UUID`, and AC2 says the seam must not move, so the
  address is carried losslessly *inside* the identifier:
  `74687277-6274-8000-8000-<6 address bytes>`, a well-formed RFC 9562
  version-8 (vendor-format) UUID whose last field is the address
  (`BluetoothDeviceIdentifier.swift:13-26`). Reversible, so resolving a
  device needs no lookup table or persisted state. The alternatives were
  hashing the address into a v5 UUID (one-way — every call would have to
  enumerate paired devices to find a match) or passing an
  identifier→address map into the gateway's initialiser (a config
  surface, with nothing above this layer existing yet to populate it).
  **Whoever builds the pairing/registration layer needs to know
  identifiers are minted by this helper, not generated.** An arbitrary
  UUID now throws `.unrecognizedDeviceIdentifier` rather than failing
  vaguely.
- **`@MainActor` instead of `NSLock` + `@unchecked Sendable`.** The
  CoreBluetooth version guarded its continuation dictionaries with an
  `NSLock`. `IOBluetooth` delivers its callbacks as *run-loop sources on
  the registering thread*, and Swift concurrency executor threads have no
  run loop — so registering from an arbitrary cooperative thread risks a
  callback that never arrives and a continuation that never resumes.
  Isolating the gateway to the main actor fixes that and makes the lock
  unnecessary (AGENTS.md: "use Swift 6 concurrency features where
  applicable"). The cost is a real constraint on callers, documented on
  the type (`:27-43`, the "Main-actor isolation" doc section): **the
  host process must run its main run loop**
  (`NSApplication`, or `RunLoop.main`/`dispatchMain()` in a CLI). A
  process that only awaits from a top-level task will hang. This is the
  same class of gap #95 flagged for `centralManagerDidUpdateState`, and
  it is not papered over with a timeout that wasn't asked for.
- **`disconnect` awaits the disconnect notification** rather than
  treating `closeConnection()`'s synchronous return as done, so the
  manager's `.disconnected` state means the link is actually down. Both
  paths short-circuit on `isConnected()` (`:66`, `:89`), which also
  keeps `disconnect` from waiting on a notification that can never
  arrive for an already-disconnected device.
- **Disconnect notifications are one-shot** and `IOBluetooth`
  unregisters them after delivery, so `unregister()` is only called on
  the early-failure path (`:107`), not from inside the callback.
- **Status codes are carried, not flattened.**
  `BluetoothGatewayError.connectFailed`/`.disconnectFailed` carry the
  `IOReturn` as a plain `Int32` (`BluetoothGatewayError.swift:24-30`) so
  the enum stays free of macOS-only types and compiles/tests everywhere.
