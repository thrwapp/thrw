# 178 — a relay that loses its state stays blind to every running node

## What was wrong

The relay learns of a node **only** from a registration message, and holds
that entirely in memory. Adapters registered exactly once, at node-runtime
start. So if the relay lost its state — a restart, or merely its MQTT
connection dropping and reconnecting — every already-running node became
invisible to it. They kept heartbeating into a void and were never
arbitrated again. The only cure was restarting each adapter by hand.

This is the mirror image of #173 (a *node* restarting), and it bit during
the very session that found it: the relay's MQTT client reconnected 33s
after the Mac registered and simply missed it, which is what made an
hour's worth of live media events produce no commands at all.

## The design, and the trap in the obvious version

The obvious fix — "have adapters re-register periodically" — is **wrong**,
and would have broken #173.

#173 made a registration mean "this is a fresh process, clear its
signals". Re-sending that same message every two minutes would wipe a
node's *live* media or call state on every interval. That is not a
theoretical risk: `restartNode` exists precisely to clear active signals,
and the test `clears a stale signal the restarted node can never end
itself` passes because it does.

So registration had to stop being an *edge* ("I just started") and become
a *statement of state* ("here is everything I currently have active"):

- `RegistrationPayload` gains `activeEvents` — the triggers the node has
  reported and not yet ended.
- `PriorityEngine.reconcileSignals(nodeId, active)` sets that node's
  signals to exactly `active`. `restartNode` is now simply
  `reconcileSignals(nodeId, [])`, so #173's behaviour is unchanged: a
  fresh process reports nothing.
- Adapters re-register every two minutes, carrying the live set.

That makes the relay's view **converge** on the node's own, rather than
being inferred from a stream of edges it may have missed.

### The ordering subtlety that would have silently stolen the route

Signals present in *both* the old and new sets keep their original
insertion order. That order is the tie-break for "same event kind on more
than one node, most recently started wins". Re-stamping it on every
periodic registration would make whichever node registered most recently
look like the most recent starter — so two devices both playing music
would trade the headset back and forth every two minutes, for as long as
both kept playing. There is a dedicated test for this
(`does not re-stamp the order of a signal the node still reports`), and a
mutation that re-stamps unconditionally kills exactly that test and no
other.

### Why the suppressed-trigger case matters

Both adapters record a trigger in their active set **only after actually
publishing it**. A trigger suppressed by the self-cooldown (#167) was
never told to the relay, so recording it would smuggle it out on the next
periodic registration and undo the suppression entirely. Tested on both
platforms; on Android the mutation that records before the cooldown check
kills exactly that test.

## Scope check (no ADR needed)

`NodeManifest` carries an explicit note in `packages/protocol` — *"New
design decision for this issue — not a frozen contract."* — and this
change touches none of the three frozen things: the MQTT topic structure
is untouched, `NodeInterface` still has exactly its four methods
(`register`'s signature is unchanged; `activeEvents` rides the
registration *envelope*, not the manifest), and the connection state
machine is untouched. Per AGENTS.md that makes this a routine change
rather than ADR territory.

`services/**` still requires human merge — though see #181: that rule is
not currently enforced.

## Interval

Two minutes, on both platforms (`RegistrationPublisher.DEFAULT_INTERVAL_MS`
and `defaultRegistrationInterval`). Deliberately far slower than the 30s
heartbeat: the heartbeat answers "are you still there", which the relay
needs promptly so it does not reap a live node, while this answers "here
is everything about me", which only matters after the rare event of the
relay losing its picture. Two minutes is therefore the worst-case window
of blindness after such an event.

Both publishers **sleep before their first send**, unlike
`HeartbeatPublisher` which beats first — `NodeRuntime` has already
registered once by the time they start.

## A trap worth knowing about, hit again here

Adding the Android runner re-triggered the exact hang
`HeartbeatRunner`'s kdoc warns about: `RegistrationPublisher.run` loops on
`delay` forever, so any `NodeRuntime` test using `advanceUntilIdle()`
under `runTest`'s virtual clock never sees the scheduler go idle and hangs
the whole suite. The fix is the same seam — depend on the
`RegistrationRunner` interface and let tests supply one that terminates.
Two test call sites were missed on the first pass and the suite hung
silently (no failure output, just a timeout), which is worth remembering:
**a hanging Gradle test task produces no test-results XML at all**, so
"no failures reported" is not the same as "nothing failed".

## Side benefit: #183

A `call` that is emitted spuriously and never ended pins the route
permanently, because no `event_end` is ever coming. That was observed for
real (#183, cause still unknown). With this change such a signal clears
itself on the node's next periodic registration, which simply does not
mention it — so the worst consequence of #183 is now bounded at two
minutes instead of indefinite.

## Verification

- `packages/relay-core` — unit tests for reconcile semantics, including
  the ordering rule. Mutation-tested: re-stamping order kills the
  ordering test; never dropping absent signals kills the stale-call and
  tie-break tests.
- `services/relay-hosted` — real-broker integration tests: a relay that
  has never seen a node learns it is playing from a periodic registration
  alone, and a stale signal frees when a later registration stops
  reporting it. Mutation-tested: ignoring `activeEvents` on the wire kills
  the first.
- `packages/adapter-mac` — 126 tests; `packages/adapter-android` — green.
  Both cover the payload carrying the active set, a trigger that ended
  dropping out, and the self-cooldown case.

## Known gaps

- **This does not cover a lost *connection*.** If the adapter's MQTT
  connection drops, nothing here helps, because the adapter never
  reconnects at all — see #182, which is the more serious bug and is
  where re-registration should also be triggered.
- **Two minutes is a guess, not a measurement.** It trades recovery time
  against traffic on a rare event; nothing has been measured to justify
  that particular number.
