# 254 — audio plays out of the speakers during a handover

ADR 0022 and its 2026-09-23 amendment, implemented on both adapters.

## Criterion 1 — where the time actually goes

Measured on the reference pair from the relay log (`scripts/relay-logs.sh`)
against both adapters' `command_outcome` reports, which #206 stage 2 (#255)
added and which is what made this measurable at all:

| leg | duration |
| --- | --- |
| relay decision → command delivered | < 1s |
| Mac release (command → outcome `succeeded`) | ~2.2s |
| Pixel claim (command → outcome `succeeded`) | ~4.9s |
| **total, wall clock** | **~4.9s** |

**The release and the claim run in parallel, not in series.** The relay
publishes both commands at once; it does not wait for the release to be
confirmed before commanding the claim. So the total is the longer of the two,
not their sum.

The window where *neither* device holds the headset is the ~2.7s between the
Mac's release completing and the Pixel's claim completing.

### The ~10s in the issue was not measuring this

The issue's figure came from `holder_change` in the relay log to a Pixel
Bluetooth `CONNECTED` line, read from two different clocks with no common
timebase — and it was taken on v0.1.3, which still had #244 (a hung connect
that silently dropped later claims) and #257 (Android reporting success in
18ms, before the profile had actually attached). Both are fixed. The number
above is from a single source of truth on both legs.

## Criterion 2 — reconciling with ADR 0007 and ADR 0018

Neither document is wrong. ~4.9s is above ADR 0007's **3.5–4s p95** and at the
top of ADR 0018's stated **3–5s**, on a sample of one pair of devices with no
distribution behind it. That is a gap worth watching, not a contradiction worth
amending an ADR over, and `docs/adr/**` is human-merge in any case — raised
here rather than changed, as the issue instructs.

The more important half: **ADR 0019's 8s bound is safe.** A real claim is
~4.9s, so healthy switches are not being reported `timed_out`. The issue's
concern that #206 stage 2 could not be trusted does not hold against the
corrected measurement.

## Criterion 3 — what was done, and why

**There is no avoidable sequencing to remove.** Direction 3 in the issue
("shrink the window") was the one to investigate first, and the measurement
kills it: the two legs already run concurrently, and what remains is ADR 0002's
deliberate consequence — sequential handoff means the old device must let go
before the new one can take hold. The window is Bluetooth, not our scheduling.

So the window gets suppressed rather than shrunk. ADR 0022 chose **pausing**;
the platforms diverge on mechanism, which the ADR's amendment records:

- **Android pauses.** `MediaSessionHandoverAudioGate` pauses only sessions
  actually in `STATE_PLAYING`, records which packages those were, and restores
  only those.
- **macOS mutes.** `MutingHandoverAudioGate` drops the output volume and puts
  it back. Pausing there needs an **Accessibility** grant (synthesising
  `NX_KEYTYPE_PLAY` does nothing from an untrusted process; it works once
  granted). Three things argued against paying that now: Accessibility grants
  control of the whole machine; media keys are a *toggle*, so on the release
  path an already-paused device would start playing; and the app is ad-hoc
  signed, so TCC keys the grant to a cdhash that changes on every build —
  "grant once" would mean "re-grant after every update". Blocked on #132;
  tracked to completion as **#267**.

**The two calls are asymmetric, deliberately.** A release silences and never
restores — the user moved to another device, so continuing to play here is
never what they wanted. A claim silences and restores once the command
resolves.

Evidence:

- `packages/adapter-android/.../AndroidNode.kt:310` — silence before the
  mechanical work; `:321,336,343,347` — restore on claim in the success,
  timeout, cancellation and failure paths.
- `packages/adapter-mac/Sources/AdapterMac/MacNode.swift:255,319` —
  `withHandoverAudioSuppressed`. Swift's `defer` body cannot `await`, so this
  is the closure-scoped equivalent of the `defer` ADR 0022 asks for; every exit
  from the body passes through the restore.
- Composition roots: `AdapterForegroundService.kt:216`,
  `AppDelegate.swift:292`.

## Criterion 4 — failing safe

The criterion the macOS half is mostly *about*, because muting is the riskier
of the two mechanisms: an un-restored pause is self-evident and the user
presses play, while an un-restored mute is just silence with no stated cause.

1. **Restore on every terminal outcome, not only success.** ADR 0019 gives
   exactly three — succeeded, failed, timed_out — and all three restore, plus
   cancellation. Six tests on each platform cover this.
2. **Persist before muting, never after.** A crash between the two writes
   leaves a record and an un-muted device, never the reverse (which would be
   unrecoverable — nothing would know what to restore to).
3. **Never overwrite an existing record.** A second `silence()` without an
   intervening `restore()` would otherwise persist `0` as the "pre-mute" volume
   and restore the user to silence. This is not an edge case: release silences
   without restoring, so the very next claim calls `silence()` on a gate that
   already holds a record. That is the normal handover sequence.
4. **Recover at startup.** `restoreAfterPreviousRun()` runs at adapter launch,
   so a crash inside the window self-heals on the next launch. ADR 0022's
   amendment makes this a *requirement* of choosing to mute, not an optional
   extra, and (2) is worthless without it.
5. **A gate is optional.** Both nodes default to a no-op, so a node built
   without one behaves exactly as it did before ADR 0022 — leaking the audio,
   as it always has — rather than refusing to hand over.

An unreadable volume (a device exposing volume per-channel rather than on the
main element) is **not** muted: leaking 2.7s of audio is the better failure
than muting a device we have no way to un-mute.

## Criterion 5 — by ear on the reference pair

**Not done. This is the one outstanding item.** It cannot be done from here —
it needs the build installed on both devices and someone listening. Everything
above is code and unit tests.

## What is uncertain

- **A released Mac stays muted until it is claimed again**, and nothing on
  screen says so. That is ADR 0022's intended behaviour, and a later claim or a
  relaunch both restore it — but where Android's paused session is visible, a
  mute is not. Filed as **#265** (surface it in the menu bar). I think this is
  the weakest point of the macOS half as shipped.
- **Whether muting is enough on the claiming side.** The claim path silences
  *before* connecting and restores after, so the opening of a track should not
  reach the speakers. Untested by ear, which is criterion 5.
- The ~4.9s is **one measurement on one pair of devices**. It is enough to rule
  out the "something is adding 5s" theory; it is not a distribution.
