# #131: fix gradlew assembleDebug Netty packaging conflict

## What was done

Added an AGP `packaging { resources { ... } }` block to
`packages/adapter-android/app/build.gradle.kts:69-88`, excluding two
`META-INF` files that `hivemq-mqtt-client`'s Netty dependencies each
ship their own copy of, which AGP's resource merger refused to pick one
of without an explicit rule.

## Acceptance criteria

1. **`./gradlew assembleDebug` succeeds.** Verified for real with a
   clean build (`./gradlew clean` first, so no stale task-output cache
   from a prior run could mask a real failure):
   `BUILD SUCCESSFUL in 27s, 67 actionable tasks: 67 executed` -
   `mergeDebugJavaResource` (the task that previously failed) completed
   without conflict.

   The exclude list, `build.gradle.kts:85-86`:
   ```kotlin
   excludes += "META-INF/INDEX.LIST"
   excludes += "META-INF/io.netty.versions.properties"
   ```
   The issue named `META-INF/INDEX.LIST` explicitly; a clean build with
   only that one excluded still failed on a second conflict
   (`io.netty.versions.properties`, the same six `netty-*` jars each
   ship a copy of), so both are excluded.

   **Confirmed neither is read at runtime**, per the issue's own
   instruction not to assume this from the issue text alone:
   - `INDEX.LIST` is a pre-JPMS `java.net.URLClassLoader` "Class-Path"
     lookup-optimization artifact from the JAR-indexing era; the JVM's
     classloader falls back to ordinary classpath scanning when it's
     absent - it was never a functional requirement, only a startup-time
     optimization for a lookup path Android's own `dalvik`/`ART`
     classloading doesn't use in the first place.
   - `io.netty.versions.properties` is read only by
     `io.netty.util.internal.PlatformDependent` / `io.netty.util.Version
     .identify()`, which produces a diagnostic version-banner string
     (e.g. for `-Dio.netty.versions.properties.debug`-style logging).
     Nothing in `adapter-android`'s own source
     (`packages/adapter-android/app/src`) calls `Version.identify()` or
     anything that transitively does - `RelayMqttClient`/`MqttTransport`
     wiring only ever calls hivemq's public MQTT client API, never
     Netty's own internal version-introspection utilities.

   Excluded outright (not `pickFirsts`) for both: keeping one arbitrary
   copy would give no benefit, since each file's content is meaningless
   without the exact jar it was generated for - a `pickFirsts` copy from
   `netty-buffer`'s jar, say, would just be a slightly wrong answer to a
   question nothing in this app actually asks.

2. **`./gradlew bundleRelease` also checked - no additional conflict.**
   Ran for real after the debug-side fix was already in place:
   `BUILD SUCCESSFUL in 6s, 45 actionable tasks: 23 executed, 22
   up-to-date` - `mergeReleaseJavaResource` completed cleanly, no second,
   release-specific packaging conflict to fix.

3. **`./gradlew test` still passes unmodified.** Ran as part of the same
   clean build as criterion 1 (`./gradlew test assembleDebug` together):
   `testDebugUnitTest`/`testReleaseUnitTest`/`test` all completed with no
   failures, same as before this change - the `packaging` block only
   affects resource merging for the assembled artifact, not the unit
   test classpath.

4. **CI documentation (not implementation), per this criterion's own
   instruction.** `.github/**` is always human-merge regardless of
   directory (AGENTS.md) - **not touched by this PR**. Recommendation:
   add `./gradlew assembleDebug` to `ci.yml`'s `android` job alongside
   the existing `test` step, since this exact bug sat undetected since
   whichever PR first pulled in `hivemq-mqtt-client` (#83) purely because
   nothing in CI ever built an APK. `bundleRelease` is a heavier,
   signing-adjacent task with its own concerns (release signing config,
   longer runtime) - `assembleDebug` alone is enough to catch this class
   of packaging-merge conflict in CI without those extra concerns.

## Test command

`cd packages/adapter-android && ./gradlew test assembleDebug` - both
succeeded on a clean build (see criterion 1). `bundleRelease` checked
separately (criterion 2), also succeeded.

## Known gaps / judgment calls

- **This bug was invisible to CI before this fix**, confirmed in the
  issue's own context and re-confirmed here: `ci.yml`'s `android` job
  only ran `./gradlew test`, never `assembleDebug`/`bundleRelease`. See
  criterion 4 above for the recommended (not implemented) fix.
- **No other `META-INF` conflicts were found** in a clean build of
  either `assembleDebug` or `bundleRelease` beyond these two - if a
  future dependency bump reintroduces a similar conflict under a
  different file name, the fix is the same pattern (confirm the file
  isn't read at runtime, then add it to this same `excludes` list).
