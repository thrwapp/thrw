# 183 — a suppressed end strands the relay forever

## The mechanism, finally

#183 recorded a `call` published with no call in progress, never ended,
pinning the route. It was not reproducible and stayed unexplained. The
lead came from an unrelated observation during the call-path test
(#193): the Pixel published an `event_end` for a `voip` event that had no
matching start and that its own `activeEvents` never listed.

That asymmetry is the tell. Both are the self-cooldown, in opposite
directions, and the end-side one is serious:

1. A call starts. `emitEvent(CALL)` publishes; `activeEvents` gains
   `call`.
2. The relay claims. `onClaim()` **arms the 3-second cooldown**.
3. The call ends **within those three seconds**. `endEvent(CALL)`
   returned early - *before* `activeEvents.remove(type)`.
4. `CallTriggerMonitor` had already set `callOpen = false` before making
   that call, so it never retries.

The relay is left holding the highest-priority signal in the system,
forever.

## Why #178 made it worse rather than better

I previously wrote on #183 that the damage was "bounded at ≤2 minutes"
because #178's periodic registration would clear the stale signal. **That
was wrong, and backwards.**

`activeEvents` tracked *what the node published*, not what it believed.
A suppressed end left `call` in that set, so every periodic registration
reported `activeEvents: ["call"]` and the relay kept the signal alive.
The reconciliation intended to repair this was instead the thing keeping
it going.

## The fix

`endEvent` now removes from `activeEvents` **before** the cooldown check,
and regardless of whether it publishes. The trigger really has ended; the
monitor has already forgotten it.

That creates a deliberate, temporary divergence - the relay still
believes the trigger is active, the node says otherwise - and the next
registration settles it in favour of the truth. Within one interval
rather than never, which is what I claimed was already true.

### Why the start side is deliberately left alone

A *suppressed start* is not recorded either, and that is correct: the
relay never heard about it, `activeEvents` says nothing about it, so node
and relay agree. There is no divergence to repair. Suppressing it is
exactly what the cooldown is for (#167), and recording it would
resurrect, two minutes later, the trigger the cooldown just decided to
ignore.

The asymmetry is real and intentional: an unpublished start is a
*decision*, an unpublished end is a *stranding*.

## Verification

Reproduced first on both platforms, as a failing test:

```
a trigger ended inside the cooldown is not left reported as active   (Android)
testATriggerEndedInsideTheCooldownIsNotLeftReportedAsActive          (Mac)
```

Both fail on the pre-fix ordering and pass after. Mutation-tested by
restoring the old remove-after-publish order, which fails exactly those
tests.

Full suites green: `adapter-mac` 147, `adapter-android` green.

## What this does and does not close

It closes the *mechanism* by which a stranded trigger becomes permanent.
Any trigger ended inside a cooldown window now self-heals within one
registration interval.

It does **not** prove this is what happened in the original #183
sighting. That observation was a `call` published while telephony read
idle, and this mechanism requires a real call that ended within three
seconds of the claim - consistent with what was seen (telephony would be
idle by the time it was checked), but not proven, because the event was
never reproduced.

So: the unbounded-damage bug is fixed and tested. Whether a *spurious*
`OFFHOOK` can also occur is still open, and the logging suggestion in the
original issue - record the raw state integer at the point of emission -
is still the thing most likely to catch it.
