# 288 — Android's `media` trigger flaps

Found in the relay log while diagnosing #287: `media` ending and restarting
about a second later, every few minutes, for as long as music played.

## Criterion 1 — the cause, measured

Watched the **system's** view on the reference Pixel via `dumpsys media_session`
polled once a second, so the result is independent of anything the adapter
does. Spotify playing continuously, sounding perfect throughout:

```
14:57:44.350  com.spotify.music: None      -> CONNECTING
14:57:46.701  com.spotify.music: CONNECTING-> PAUSED
14:57:48.846  com.spotify.music: PAUSED    -> PLAYING
14:58:42.159  com.spotify.music: PLAYING   -> BUFFERING
14:58:44.420  com.spotify.music: BUFFERING -> PLAYING     (2.26s)
15:02:42.316  com.spotify.music: PLAYING   -> BUFFERING
15:02:43.386  com.spotify.music: BUFFERING -> PLAYING     (1.07s)
15:06:41.346  com.spotify.music: PLAYING   -> BUFFERING
15:06:42.454  com.spotify.music: BUFFERING -> PLAYING     (1.11s)
```

Three flaps, **exactly four minutes apart**. The session really does leave
`STATE_PLAYING`, into `STATE_BUFFERING`, for one to two seconds.

So the answer to criterion 1 is **"the session really did stop"**, not "the
adapter misread it". Criterion 3 does not apply.

Correlation with the relay is exact: the watcher saw `PLAYING` at
`14:57:48.846` local and the relay logged `media` at `13:57:49.149Z` — 300ms
later, same event.

## What it is not

The tempting theory was that thrw caused this itself: ADR 0022's audio gate
pausing and resuming the session on each redundant claim (#284). It fitted the
~1s gap and the 2-3 minute spacing.

It is wrong, and the data already on hand disproves it. `onClaim` arms the 6s
self-cooldown and `media` does not bypass it, so a restart ~1s later would have
been **suppressed** — yet the log shows it published. Checking directly: **zero
`command_outcome` entries between 14:00 and 16:00** on the day of the original
report. No commands were processed, so no cooldown was armed, so the gate never
ran.

Worth recording because it is where the next person would look first.

## The bug was a comment that reasoned about the wrong case

`MediaTriggerMonitor` already considered buffering and excluded it:

> a track that is loading is on its way to playing, but treating it as playing
> means a skipped track or a momentary network stall can start and stop the
> trigger repeatedly. Buffering resolves to `STATE_PLAYING` within moments when
> it succeeds, so waiting costs very little and avoids the flapping.

That is right for buffering **before playback starts** — `NONE -> BUFFERING ->
PLAYING` — and it is why buffering still must not *start* the trigger.

It is exactly wrong for buffering **during** playback, which is what happens.
There, excluding it *causes* the flapping the comment set out to prevent. The
same `STATE_BUFFERING` means "not yet" before playback and "still playing"
during it; what distinguishes them is what preceded it.

## The fix, and why not a debounce

Criterion 2 offered a time-based debounce. That would work and is the wrong
shape — it papers over a semantic error with a timer, and the threshold would
be another number needing justification against measurement.

Instead, a third state. `MediaSessionState.Playback` is now
`PLAYING` / `TRANSIENT` / `STOPPED`, and `TRANSIENT` is **neither a start nor a
stop**: a tracked session stays tracked, an untracked one stays untracked. Both
intents are preserved and no threshold is invented.

The boundary had been flattening to `isPlaying: Boolean`, which discarded the
distinction before the monitor could act on it. That is why the fix reaches
`MediaSessionSource` and `MediaSessionReconciler` rather than living in the
monitor alone.

### `STATE_CONNECTING` is included, from the same evidence

The capture also caught `CONNECTING` while the session came up. It is the same
class — in flight, says nothing about whether the user's audio stopped — so it
maps to `TRANSIENT` too. Had the fix covered only `BUFFERING`, a session going
`PLAYING -> CONNECTING -> PLAYING` would have reproduced the bug exactly.

## Criterion 4 — a genuine stop still ends the trigger

`PAUSED` / `STOPPED` / `NONE` end `media` immediately, as before. Two tests
cover the paths through a stall: one that resolves to a stop, and a session that
disappears while stalled (#175's failure mode).
