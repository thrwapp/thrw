# HANDOFF: generic events-topic subscription on RelayMqttClient (#97)

## What was done

Added `RelayMqttClient.subscribeAllEvents` — a wildcard subscription
across every registered node's events topic for an account, using MQTT's
`+` single-level wildcard on `@thrw/protocol`'s own `eventsTopic` builder.
Transport only, per the issue's explicit scope: no `PriorityEngine`/
`DeviceRegistry` wiring, no decision logic.

- `packages/relay-core/src/mqtt-client.ts:52` — `NodeEventListener`, a new
  listener type: `(payload: unknown, node: string) => void`.
- `packages/relay-core/src/mqtt-client.ts:140-158` — `subscribeAllEvents(account, onMessage)`.
- `packages/relay-core/src/mqtt-client.ts:195-207` — `nodeFromEventsTopic`,
  a private helper that reverses `eventsTopic(account, node)` by splitting
  on `/` (no regex, nothing to escape for special characters in
  `account`), returning `null` for anything that isn't shaped exactly
  like this account's own events topic.
- `packages/relay-core/src/index.ts` — re-exports `NodeEventListener`
  alongside the package's other public types.
- `packages/relay-core/test/mqtt-client.test.ts` — 2 new tests against
  the real local Mosquitto broker.

## Acceptance criteria, with evidence

**1. A new method subscribing to every node's events topic via MQTT's `+`
wildcard, at `TopicQos.events.qos`, using `@thrw/protocol`'s existing
topic builder.** `subscribeAllEvents` (`mqtt-client.ts:140`) builds the
subscription topic as `eventsTopic(account, "+")` (`:149`) — the same
builder `publishEvent` already uses, just called with `"+"` as the node
argument rather than a real node id, since the builder is a plain
template-literal function with no validation to reject that. Subscribes
at `TopicQos.events.qos` (`:154`), same constant `publishEvent` and
`subscribeHeartbeat` already use.

**2. Listener shape gives both the parsed payload and which node it came
from.** `NodeEventListener = (payload: unknown, node: string) => void`
(`:52`). Documented judgment call (the issue explicitly invited either
following `HeartbeatListener`'s `(payload, topic)` shape or improving on
it): I improved on it — `HeartbeatListener`'s topic is already known to
every caller (fixed per account/node at subscribe time), so handing it
back is mostly a formality, but here the node is exactly the one thing
the wildcard subscription doesn't statically know, so handing back the
already-parsed node directly saves every caller from re-deriving it from
a raw topic string. Reasoning is also in the type's own comment
(`:45-52`).

**3. Tested against a real local broker: publish to multiple different
nodes' events topics, confirm the subscription receives all of them with
the correct node identified for each.** Two new tests in
`mqtt-client.test.ts`, both run against the same real Mosquitto
(`MQTT_BROKER_URL`/`defaultMqttBrokerUrl()`) this package's other
integration tests already use: "subscribes to every node's events topic
for an account at QoS 1, and identifies which node each message came
from" (publishes to 3 distinct random node ids under one account,
confirms all 3 arrive with correct payload+node pairing, and confirms the
broker granted the subscription at `TopicQos.events.qos`), and "does not
mistake a different account's events, or an unrelated topic, for this
account's node events" (publishes to another account's events topic and
to this account's *state* topic first, confirms neither leaks through,
then confirms a genuinely matching publish still arrives).

**4. Transport only — no state machine, no `PriorityEngine`/
`DeviceRegistry` wiring, no decision logic.** Grepped the full diff for
`PriorityEngine`/`DeviceRegistry`/`ConnectionState` — no matches outside
this sentence. `subscribeAllEvents` does nothing beyond subscribe +
hand the caller a parsed payload and node id.

**5. No new dependency.** `mqtt` (already present, added in #61) is the
only import; no `package.json` change in this diff.

## Known gaps / judgment calls

- **Multiple listeners accumulate on the same MQTT client `"message"`
  event**, same pre-existing pattern `subscribeHeartbeat` already uses
  (every call to either method adds another `client.on("message", ...)`
  listener, filtered internally). Calling `subscribeAllEvents` many times
  against one `RelayMqttClient` (e.g. in a test suite, or if a caller
  re-subscribes) could eventually trip Node's default max-listeners
  warning. Not introduced by this PR and not fixed here — it's
  `subscribeHeartbeat`'s existing shape, out of scope for a
  transport-only issue to redesign.
- `nodeFromEventsTopic` assumes a node id never contains `/` (an
  unlikely value given every existing node id in this codebase — UUIDs,
  device names like `pixel-10-pro` — but nothing in `@thrw/protocol`
  actually forbids it). A node id containing `/` would produce more than
  5 segments and simply be treated as "not a match" (returns `null`,
  silently dropped) rather than misattributed to the wrong node — a safe
  failure mode, not a crash, but flagging the assumption rather than
  silently relying on it.
