# 191 — reconcile the audio route, not the Bluetooth link

## What this adds

ADR 0018 decisions 2 and 3, as corrected by #186. #185 landed the
*carrier* — registration re-announces every 2 minutes and is a safe,
repeatable statement of state. This makes it carry the thing decision 2
actually asks for: what the adapter **observes** about its own route.

- `RegistrationPayload.observedRoutes` — `{"audio": true|false}`, keyed by
  ADR 0015's resource vocabulary.
- `AudioRouteObserver` on both platforms, with real implementations.
- `RouteTransition`, which suppresses observations taken mid-switch.
- Relay-side drift detection, surfaced through an injectable
  `onRouteDrift`.
- `BluetoothConnectionManager.connect` now decides its skip from the
  actual route rather than its cached belief (decision 3).

## The signal is the route, not the link

This is the whole correctness of the thing, so it is stated in the code
where an implementer will trip over it rather than only in the ADR.

Multipoint headsets hold links to several hosts at once. Measured with
the **phone** holding the route: the Mac reported the AirPods as
`Connected` while its default output device was `MacBook Air Speakers`,
and the phone reported `mActiveDevice` for the same headset. Under a
link-state reading both adapters answer "I hold it", the relay sees two
holders, and the drift is unresolvable — corrective commands forever.

So: `kAudioHardwarePropertyDefaultOutputDevice` on macOS, A2DP
`mActiveDevice` on Android. Explicitly not `getConnectionState()`.

## Three-valued on purpose

`holdsAudioRoute()` returns `true` / `false` / **`nil`**, and an absent
resource key means the same as `nil`.

`nil` is not a failure to smooth into `false`. `false` is an *assertion*
that this node does not hold the headset, and is grounds for corrective
action; `nil` is "no information" and leaves the relay's record alone.
Collapsing them would hand the relay a fabricated disagreement every time
a node simply could not read its route — and would make every
mid-transition registration look like a bug. There is a test for exactly
this, and the mutation that treats absent as `false` kills it.

## Why decision 3 mattered more than it looked

`BluetoothConnectionManager.connect` skipped when its cached state said
`CONNECTED`. That cache is precisely what multipoint invalidates: the
phone can take the route while this device keeps its link, leaving the
cache saying `CONNECTED` while audio plays elsewhere. A claim arriving
then was **silently dropped** — no log, no retry, no audio.

Only `CONNECTED` is second-guessed. `CONNECTING` means a claim is already
in flight and re-entering would duplicate it, and a `null` route reading
is no reason to override a cache that may well be right.

## What the relay does, and deliberately does not do

It **detects and reports** drift. It does not add a second correction
mechanism, because the one that matters already exists: #173 re-asserts a
claim to the holder on *every* registration, and the adapter now decides
whether to act on it from its real route. A holder whose route has gone
therefore repairs itself on the next registration, without the relay
needing to do anything new.

The opposite direction — a node that is *not* the holder reporting that
it does hold the route — is reported and **not** acted on. ADR 0010's
"local state wins" is about a manual override, which ADR 0014's
`claimMode` covers and is still Proposed; and under multipoint two nodes
can briefly both report `true`. Moving the recorded holder on that basis
would turn a transient into a real switch.

## The one assumption, isolated

`CoreAudioRouteObserver` has to decide whether a CoreAudio device UID
refers to a given Bluetooth headset, and Apple does not document that
string format. That decision is `audioDeviceUID(_:matchesBluetoothAddress:)`
— a pure function with its own tests, rather than an inline comparison,
so the assumption can be corrected in one obvious place and correcting it
is a test change.

It normalises both sides to hex digits, so `74-15-F5-12-2A-21`,
`74:15:f5:12:2a:21` and `7415F5122A21` all compare equal, and it refuses
to match unless the address is a full 12 hex digits — without that guard
a malformed address is a substring of nearly any UID and every device
reads as "this is the headset", which is a false `true` and worse than no
answer.

## Verification

All four suites green: relay-core 41, relay-hosted 16, adapter-mac 131,
adapter-android BUILD SUCCESSFUL.

Mutation-tested where behaviour is subtle:
- Trusting the cached state again (the pre-#191 behaviour) kills
  `a claim is re-issued when the cached state says connected but the
  route is elsewhere`, and nothing else.
- Never detecting drift kills both drift tests.
- Treating an absent observation as `false` kills
  `reports no drift when the node makes no route observation`.

## Known gaps — read before trusting this

- **Not verified on hardware.** The headset was in its case for this
  work, so neither real observer has read a real route. Two specific
  unknowns:
  - **The CoreAudio UID format is unconfirmed.** The matcher accepts
    several plausible spellings, but no Bluetooth device UID has actually
    been observed. The probe to confirm it is three lines: read
    `kAudioDevicePropertyDeviceUID` of the default output device while
    the headset is connected.
  - **`BluetoothA2dp.getActiveDevice()` may be blocked.** It is a hidden
    API reached by reflection, like `connect`/`disconnect` (#162), which
    do work on the reference Pixel. If it is blocked the observer returns
    `null` and reconciliation degrades to nothing, which is the correct
    failure direction — but that is a designed fallback, not an observed
    one.
- Given #174, #175 and #182 were all "passes tests, fails on device",
  **this should be exercised on hardware before it is trusted.**
- **`RouteTransition`'s 6s** is derived from the measured 3-5s settle
  plus margin, not itself measured.
