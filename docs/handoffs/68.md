# HANDOFF: call / VoIP trigger detection for packages/adapter-android (#68)

## What was done

The Android adapter now detects the two triggers M3 cares about and
reports them to the relay through #67's node interface:

- **`call`** — `TelephonyManager` call state, via `CallTriggerMonitor`.
- **`voip`** — an active call notification seen by
  `NotificationListenerService`, via `VoipTriggerMonitor`.

Both report a start *and* a matching end (see "The end signal" below).
Media detection and the connection state machine are untouched, per
acceptance criteria 4 and 5.

New source, all under
`app/src/main/kotlin/com/thrw/adapter/android/triggers/`:

- `EventLifecycle.kt` — the `emitEvent` + `endEvent` pair the monitors
  report to, plus the `UNRANKED_PRIORITY` constant.
- `CallStateSource.kt` — `PhoneCallState` (IDLE/RINGING/OFFHOOK, mirroring
  `TelephonyManager.CALL_STATE_*`) and the `CallStateSource` seam.
- `CallTriggerMonitor.kt` — call state → `call` trigger start/end.
- `NotificationSource.kt` — `PostedNotification` (the notification fields
  the heuristic reads), the `NotificationFlags` / `CallType` /
  `CATEGORY_CALL` / `CALL_STYLE_TEMPLATE` framework-constant mirrors, the
  `NotificationEvent` posted/removed pair, and the `NotificationSource`
  seam.
- `VoipTriggerMonitor.kt` — the VoIP heuristic + session tracking →
  `voip` trigger start/end.

Changed:

- `AndroidNode.kt` — now also implements `EventLifecycle`, adding
  `endEvent(type)`.
- `protocol/Payloads.kt` — new `EventEndPayload`.

## The end signal (acceptance criterion 3)

The issue was right to flag this: #67's interface has **no** end signal.
`protocol/NodeInterface.kt` mirrors `packages/protocol`'s frozen type,
which is `register` / `emitEvent` / `onClaim` / `onRelease` and nothing
else.

What the rest of the system already assumes, though, is that an end
signal exists:

- `packages/relay-core/src/index.ts`'s `PriorityEngine` has
  `endEvent(nodeId, type)` right next to `recordEvent(nodeId, type)`.
- architecture.md's "Priority rules" section hangs auto-return off
  `call_ended`.

So the engine expects it; only the *adapter-side method* and the *wire
shape* were missing. Both were added, and deliberately **not** to
`packages/protocol` or to its Kotlin mirror — growing that type is an ADR
plus human review (AGENTS.md), and the issue explicitly forbids touching
it:

- **Method**: `EventLifecycle` (adapter-only interface) declares
  `emitEvent` + `endEvent`; `AndroidNode` implements it alongside
  `NodeInterface`. Named `endEvent` to match relay-core's method exactly.
  When an ADR blesses this, `NodeInterface` grows `endEvent` and
  `EventLifecycle` can be deleted with no change to either monitor.
- **Wire shape**: `{"kind":"event_end","type":"call"}`, published on the
  node's own events topic at QoS 1, not retained. Same
  `kind`-discriminator approach as #67's `RegistrationPayload`, for the
  same reason (the topic set is a frozen contract, so a node's only
  publish topic has to carry everything). No `priority` field: ending a
  trigger needs only its kind, which is all `PriorityEngine.endEvent`
  takes. **The relay does not consume this yet** — nothing in
  `packages/relay-core` subscribes to the events topic at all today, so
  like the registration envelope it's a proposal the relay side still has
  to be taught to read.

## The `call` mapping, and why ringing reports nothing

`OFFHOOK` → `emitEvent("call", …)`; `IDLE` → `endEvent("call")`;
`RINGING` → nothing.

`OFFHOOK` is the state the platform uses both for an answered incoming
call and for an outgoing call from the moment it's dialed, so it covers
both halves of architecture.md's rule 1 and is the point the headset is
actually needed.

`RINGING` is deliberately dropped. ADR 0011 is explicit that ringing is
the *pre-claim* trigger, and pre-claim is a state in the connection state
machine — a frozen contract per ADR 0010/0011/0013 and out of scope here
(criterion 5). Emitting a full `call` event on ringing would do that
state machine's job badly instead: a declined call would take the headset
(rule 1 beats everything) and immediately hand it back, which is the
visible flicker ADR 0011 exists to avoid. `CallStateSource` still
*surfaces* `RINGING`, so the signal is sitting there for whoever does the
pre-claim work.

Side benefit: because only `IDLE` closes the trigger, call waiting
(`OFFHOOK` → `RINGING` → `OFFHOOK`) neither ends the open trigger nor
starts a second one.

## The VoIP heuristic

`VoipTriggerMonitor.isActiveVoipCall` — a posted notification is an
active VoIP call when all of:

1. **Call-shaped**: `category == "call"` (`CATEGORY_CALL`) **or** style is
   `Notification.CallStyle`.
2. **Ongoing**: `FLAG_ONGOING_EVENT` or `FLAG_FOREGROUND_SERVICE` set.
3. **Not a group summary** (`FLAG_GROUP_SUMMARY`).
4. **Not ringing/screening**: for `CallStyle`, `EXTRA_CALL_TYPE` must be
   `CALL_TYPE_ONGOING`, not `CALL_TYPE_INCOMING` / `CALL_TYPE_SCREENING`.
5. **Not from a dialer/telecom package** (`DEFAULT_TELEPHONY_PACKAGES`,
   constructor-overridable).

Why category/style rather than a package allowlist: it's what makes the
trigger work for a conferencing app nobody has heard of yet, without an
adapter release. Every app architecture.md names (Zoom/Meet/Teams/
WhatsApp) posts one of the two. Condition 2 is what separates an active
call from a *missed*-call or voicemail notification, which are also
`category == "call"`. Condition 4 draws the same line as `RINGING` above,
for the same ADR 0011 reason. Condition 5 exists because the system
dialer posts an ongoing `CATEGORY_CALL` notification for an ordinary
cellular call — without excluding it, one phone call gets reported twice,
once as rule 1 and once as rule 3.

Sessions are counted by `StatusBarNotification.getKey()`, and only 0→1
and 1→0 transitions are reported: a call notification that updates itself
every second (call timer, mute state) emits once, and a Zoom call
overlapping a WhatsApp call is one trigger, not two starts and a
premature end. A notification that stops qualifying while keeping its key
— the usual in-place "Call ended" update — is treated exactly like a
removal, because apps don't reliably remove promptly.

### Known limitations of the heuristic

- **False positive**: an app that posts an ongoing `CATEGORY_CALL`
  notification *without* `CallStyle` while merely ringing looks active —
  there's no `EXTRA_CALL_TYPE` to check, so condition 4 can't fire.
- **False negative**: an app that never marks its in-call notification
  ongoing/foreground-service never triggers.
- **Invisible**: an app whose in-call notification is neither
  `CATEGORY_CALL` nor `CallStyle` (some in-house/enterprise clients).
- `DEFAULT_TELEPHONY_PACKAGES` covers AOSP/Pixel dialers
  (`com.android.dialer`, `com.google.android.dialer`,
  `com.android.phone`, `com.android.server.telecom`). An OEM dialer under
  a different package would double-report; the set is a constructor
  parameter so that's configuration, not a code change.
- Notification access is user-granted and revocable. With it off this
  monitor simply never sees anything, and **cannot tell that apart from
  "no calls are happening"** — no permission-state signal is exposed
  anywhere yet.
- A notification posted *before* the listener connects is only seen if
  the implementation replays `getActiveNotifications()` on connect. The
  seam's kdoc says to; nothing enforces it.

## Priority values

Every event is emitted with `UNRANKED_PRIORITY = 0`. Adapters don't rank
triggers — "Priority rules live server-side in the relay, never
duplicated in adapters" (architecture.md) — and relay-core's
`PriorityEngine` ranks purely by `EventKind` against `PRIORITY_ORDER`,
never reading this field. But `EventPayload.priority` exists on the wire,
so *something* has to go in it. One constant for every kind means no
ranking is implied by, or can silently drift in, this adapter. If the
relay ever starts reading the field, this constant is the one place to
change.

## Verification

`cd packages/adapter-android && ./gradlew test` — **run, passing**: 78
tests, 0 failures, 0 skipped, both incrementally and from a `clean`.
(Mechanically invoked as `pnpm --filter @thrw/adapter-android test`,
which is that package's `test` script and runs exactly `./gradlew test`
in that directory, plus one `… exec ./gradlew clean test` for the clean
run — this session's tool policy allows `pnpm` but not a bare
`./gradlew`.) Up from 45 tests before this change; the 33 new ones are
`CallTriggerMonitorTest` (10), `VoipTriggerMonitorTest` (18),
3 in `AndroidNodeTest`, 2 in `PayloadsTest`.

Per criterion 6, the tests fake `CallStateSource` and
`NotificationSource` — this adapter's own boundaries — rather than
mocking Android framework internals, the same pattern #66 used for
`BluetoothClassicGateway`. There is nothing else available: this Gradle
module is still the plain Kotlin/JVM scaffold rather than the Android
Gradle Plugin, so `android.telephony` / `android.service.notification`
aren't on the classpath, and the Gradle test runner can't raise a real
call state change or post a real notification regardless.

No new dependencies (criterion 7): the framework constants used
(`FLAG_ONGOING_EVENT` = 0x2, `FLAG_FOREGROUND_SERVICE` = 0x40,
`FLAG_GROUP_SUMMARY` = 0x200, `CALL_TYPE_*` = 1/2/3, `CATEGORY_CALL`,
`EXTRA_TEMPLATE`'s `CallStyle` class name) are mirrored as constants in
`NotificationSource.kt`, the same way `Topics.kt` mirrors the topic
strings.

## Uncertain / not verified

- **No `android.telephony` or `android.service.notification`
  implementation exists.** This issue delivers the detection *logic* plus
  its two seams. The `TelephonyManager`-backed `CallStateSource` and the
  `NotificationListenerService`-backed `NotificationSource` land when the
  module moves to the Android Gradle Plugin (same open item as #66's
  `BluetoothClassicGateway`). So "a real call on a real Pixel emits a
  real `call` event" is **unverified end to end** — what's verified is
  that the documented state/notification inputs produce the documented
  emit/end calls, and that those reach MQTT on the right topic at the
  right QoS.
- **The framework constant values are from the Android docs, not from a
  compiled `android.jar`.** Nothing in this module's build can catch a
  typo in them; the first real integration will. They're all long-stable
  public constants, but that's an argument, not a check.
- **`EXTRA_CALL_TYPE` availability.** `CallStyle` is API 31+. On an older
  release, or from an app targeting an older SDK, `callType` is null and
  the heuristic falls back to the flag check — which is the false-positive
  case listed above. The reference device is a Pixel 10 Pro, so this
  mostly matters for apps, not the OS.
- **Nothing starts the monitors.** `CallTriggerMonitor.run()` /
  `VoipTriggerMonitor.run()` are `suspend` collectors; no
  service/`Application` launches them in a scope, because there's no
  Android entry point in this module yet (`Adapter.kt` is still a
  one-constant placeholder). Wiring them to a foreground service belongs
  with the AGP move.
- **Monitor state is not thread-safe.** Each monitor's state (one
  boolean, one `MutableSet`) is confined to whichever coroutine calls
  `run()` / `onNotificationEvent`, which is how flow collection already
  serializes it. If a future implementation calls `onNotificationEvent`
  from `NotificationListenerService`'s binder threads directly instead of
  funnelling through the flow, it needs its own confinement (a single
  dispatcher, or a `Mutex` like `BluetoothConnectionManager`'s).
- **Simultaneous cellular + VoIP.** Both monitors can have a trigger open
  at once; each reports independently and the relay picks the winner
  (rule 1 beats rule 3), which is the intended division of labour. Not
  exercised against a real relay.
