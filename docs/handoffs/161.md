# #161: an uncaught Bluetooth error crashes the whole adapter

## What was done

A failed Bluetooth connect no longer kills the adapter. Two layers:

1. **`AndroidNode.listenForCommands`** catches a failed `onClaim`/
   `onRelease`, logs it, and stays subscribed — the same discipline the
   unparseable-payload case already followed, and for the same reason: a
   node that stops listening is deaf to the *next*, satisfiable claim.
2. **`AdapterForegroundService`'s scope gains a `CoroutineExceptionHandler`**
   so that anything missed anywhere degrades to a log line rather than
   process death.

## Why a SupervisorJob wasn't already enough

Worth stating because it's an easy and common wrong assumption: a
`SupervisorJob` stops a failing child from cancelling its siblings, but
it does **not** handle the exception. Without a `CoroutineExceptionHandler`
the failure still reaches the thread's default uncaught handler, which on
Android kills the process.

Observed for real, during the first genuine cross-device handoff against
the production relay:

```
FATAL EXCEPTION: DefaultDispatcher-worker-2
java.io.IOException: read failed, socket might closed or timeout, read ret: -1
    at android.bluetooth.BluetoothSocket.connect(BluetoothSocket.java:693)
    at AndroidBluetoothClassicGateway$connect$2.invokeSuspend(...:49)
W ActivityManager: Scheduling restart of crashed service ... in 11000ms
```

So the practical failure mode was a crash-and-restart loop, tearing down
and rebuilding the MQTT session every time the headset couldn't be
reached.

## Acceptance criteria

1. **Failures logged, never fatal** — both layers above. The adapter
   stays connected to the relay and keeps serving commands.
2. **What a node does when it can't honour a claim: log and stay idle.**
   Documented rather than invented: the frozen protocol has no
   "claim failed" message, and adding one is ADR-gated (topic set and
   node interface are frozen per AGENTS.md). Retrying was rejected too —
   the relay would have to know the claim hadn't taken effect for a retry
   to mean anything, and it can't. **The real consequence, stated
   plainly: the relay believes this node holds the claim when it does
   not.** That divergence is a genuine gap, not something this issue can
   close, and it needs the protocol change it deserves.
3. **Fixed at the boundary where it's actionable**, not a blanket catch.
   `BluetoothConnectionManager`'s own behaviour is unchanged — it still
   reverts to `disconnected` and rethrows, which is correct; what was
   missing was a handler above it. `CancellationException` is
   deliberately rethrown, so coroutine cancellation still works.
4. **`CoroutineExceptionHandler` added** to the service scope.
5. **Test**: `a failing claim does not tear down the commands subscription`
   — drives a gateway that throws the exact `IOException` seen on
   hardware, sends two claims, asserts both were attempted.
6. **Verified on the real Pixel 10 Pro** — below.

## Verification

Reproduced the exact crash scenario against the production relay, with
the AirPods unreachable so the claim genuinely fails:

```
E AndroidNode: Command CLAIM failed - staying subscribed
E AndroidNode: Command CLAIM failed - staying subscribed
```

- **Same PID (32632) throughout** — previously the process died and
  Android restarted it.
- **Zero `FATAL EXCEPTION`** in logcat.
- **Both claims arrived**, which is the real proof: the second could only
  be delivered because the subscription survived the first failure.

`./gradlew test` passes.

## On the test being real

The test was mutation-checked: with the `catch` replaced by a rethrow it
**fails**; with the fix it passes. Worth recording that the first two
mutation attempts were themselves invalid — one failed to compile, the
other used `--tests` on the aggregate `test` task, which Gradle rejects
(`Unknown command-line option '--tests'`; it needs `testDebugUnitTest`).
Both looked like "the test failed", i.e. like a successful mutation
check, while actually proving nothing. A mutation check that fails for
the wrong reason is worse than none, because it manufactures false
confidence.

## Known gaps / judgment calls

- **The relay still thinks a failed claim succeeded.** See criterion 2.
  This is the most important limitation here and it is protocol-shaped:
  closing it means a node→relay failure message, which is an ADR.
- **`adapter-mac` has the same latent deafness**, though not the same
  crash. `MacNode.listenForCommands` lets a throwing `onClaim` propagate;
  `NodeRuntime` catches and logs it, so the process survives — but that
  task ends and the node stops processing commands. Out of scope here
  (this issue is Android-only by its own path restrictions) and worth its
  own issue.
- **The underlying connect failure is not fixed** — that's #162, and it
  is a much bigger question (an RFCOMM socket cannot move an audio route
  at all). This issue only ensures the failure is survivable, which is
  what makes #162's experiments possible without the process dying
  under them.
