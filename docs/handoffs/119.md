# HANDOFF: TLS (wss) for services/relay-hosted (#119)

## What was done

TLS is live on the real deployed relay VM, end-to-end verified against
production infrastructure - not a local/simulated stand-in, per the
issue's own criterion 4. `relay.thrw.app` now serves a valid Let's
Encrypt certificate and a real MQTT-over-WSS round trip succeeds through
it.

- **Domain**: `relay.thrw.app` (confirmed with Tom directly - already
  the value baked into both adapters' `config/adapter.properties`, not a
  new choice). DNS: a Cloudflare A record, `relay` → `34.10.155.149`
  (`$RELAY_IP`), added by Tom and set to **DNS only** (not proxied) -
  see "A real failure mode, hit and fixed live" below for why that
  distinction mattered in practice, not just in theory.
- **Architecture chosen: Caddy terminates TLS on 443, reverse-proxies to
  EMQX's existing plaintext `ws:8083`** - `services/relay-hosted/Caddyfile`
  (new). Rejected: EMQX-native TLS on its own listener (port 8084,
  `listeners.wss.default`) - despite that being the port both adapter
  config files already (incorrectly) referenced, EMQX-native TLS would
  need an external process to source cert files into EMQX's config *and*
  a reload/restart coordination step on every renewal; Caddy's automatic
  HTTPS is designed for exactly the chosen pattern with zero such
  coordination. Full reasoning in the Caddyfile's own comment.
- **`scripts/relay-redeploy.sh`** (`:61-92`): now also bootstraps/reloads
  Caddy - idempotent (only recreated if not already running; otherwise
  hot-`reload`s its config with zero downtime), using `--network host`
  so it reaches EMQX via `localhost:8083` with no shared Docker network
  needed. Deliberately *not* torn down/recreated on every EMQX image
  roll the way the `relay` container is - see the script's own comment
  for why.
- **`.github/workflows/deploy.yml`** (`:83-88`, flagged prominently per
  the issue's own instruction - `.github/**` is always human-merge
  regardless of directory): one new `gcloud compute scp` line, scp'ing
  `services/relay-hosted/Caddyfile` to `/tmp/Caddyfile` alongside
  `relay-redeploy.sh` itself (same existing pattern), so the automated
  pipeline keeps working going forward without duplicating the
  Caddyfile's content inline in a shell heredoc.
- **Firewall**: `thrw-relay-emqx` updated (not a new rule) to also allow
  `tcp:80` (ACME HTTP-01 challenge) and `tcp:443` (wss) - run for real via
  `gcloud compute firewall-rules update thrw-relay-emqx --allow=tcp:8083,tcp:18083,tcp:80,tcp:443`,
  confirmed via `gcloud compute firewall-rules describe`.
  `docs/ops/prompt-5-gcp-and-branch-protection.md` documents this as a
  follow-up to the original `firewall-rules create` command (not rewriting
  history - the create command's own comment is left as-is, a new comment
  block right after it records the later update).
- **`emqx.conf`**: `listeners.wss.default.enable` stays `false` (comment
  updated to explain why that's correct under the chosen architecture,
  not a leftover gap) - EMQX never sees a TLS handshake at all; Caddy
  does.
- **Adapter config fix**: both `packages/adapter-android/config/adapter.properties`
  and `packages/adapter-mac/config/adapter.properties` updated from
  `wss://relay.thrw.app:8884/mqtt` to `wss://relay.thrw.app/mqtt`
  (port 443, the `wss` default - both adapters' `RelayConfig`/`RelayConfig.fromUrl`
  already fall back to 443 when a wss URL omits a port, confirmed via
  their own test suites below). Two real fixes bundled into this one
  change, both found while researching this issue: the value was already
  a placeholder for infrastructure that didn't exist yet (this issue's
  actual job), *and* `:8884` was a typo for EMQX's real native-TLS port
  8084 - moot either way now, since the chosen architecture doesn't use
  8084 at all, but worth naming so it isn't quietly repeated somewhere
  else later.
- `docs/ops/prompt-5-gcp-and-branch-protection.md`'s "Still deferred"
  list: both the TLS item and the relay-core-live-process item it named
  are stale (the second resolved by #118, merged just before this
  session's work on #119) - moved to a "No longer deferred" note with
  citations, TLS's own entry corrected in place.

## Acceptance criteria, with evidence

**1. Document the domain - the one piece needing a human decision.**
Confirmed directly with Tom in this session: `relay.thrw.app` (he owns
`thrw.app`; no DNS existed for this subdomain beyond the Cloudflare
Pages-hosted marketing site at the apex). Not guessed - asked first,
per AGENTS.md and this issue's own instruction.

**2. TLS-terminating reverse proxy once a domain exists.** Caddy,
`services/relay-hosted/Caddyfile` - justified in its own comment
(condensed above). Confirmed running on the real VM via
`docker logs caddy`: `"certificate obtained successfully","identifier":"relay.thrw.app"`.

**3. `listeners.wss.default.enable` flips to `true`, or the proxy
terminates and forwards to `ws:8083` - document which and why.**
Chose forward-to-`ws:8083` (`emqx.conf`'s updated comment states this
explicitly); `listeners.wss.default.enable` stays `false`, correctly -
grepped `emqx.conf` to confirm no other listener config changed.

**4. Update the firewall rule for whichever port is actually used
(8084 native, or 443 proxied).** 443 (chosen architecture) + 80 (ACME) -
`gcloud compute firewall-rules describe thrw-relay-emqx` confirms
`tcp:8083`, `tcp:18083`, `tcp:80`, `tcp:443` all present post-update, run
for real against the live `thrw-prod` project, not asserted.

**5. Update every adapter's `RelayConfig`-equivalent default/example to
`wss://<domain>`, config files/examples only, no hardcoded production
URL in source.** Both `config/adapter.properties` files updated (listed
above); neither adapter's Swift/Kotlin *source* was touched - confirmed
via `git status` showing only the two `.properties` files, not
`RelayConfig.swift`/`RelayConfig.kt`. `RelayConfigTests`/`RelayConfigTest`
(both adapters, both re-run after the change) confirm `RelayConfig.fromBuildConfig()`/
`.fromUrl()`... correctly resolves the new URL to `tls=true, webSocket=true`,
port 443.

**6. Verify end-to-end against the real deployed VM - not a fake/local
broker.** Done for real, against `thrw-relay` (34.10.155.149,
`thrw-prod`), not simulated:
- `curl --resolve relay.thrw.app:443:34.10.155.149 https://relay.thrw.app/`
  → real TLS 1.3 handshake, `CN=relay.thrw.app`, issued by Let's Encrypt,
  valid Sep 18 - Dec 17 2026.
- A real MQTT client (the `mqtt` npm package, the same library
  `@thrw/relay-core`'s `RelayMqttClient` wraps) connected to
  `wss://relay.thrw.app/mqtt`, authenticated with the real relay
  credential read live from the running container
  (`docker exec relay cat /opt/emqx/data/authn-bootstrap/relay-users.csv`
  - **not** committed anywhere, not printed in this doc, used only for
  this one verification), subscribed to a test account's events topic,
  published to it, and received the message back - a genuine round trip
  through Caddy → EMQX → back out over the same `wss://` connection.

## A real failure mode, hit and fixed live

The DNS record was first added as **Proxied** (Cloudflare's default for
a new record), not DNS-only. Consequence, observed directly rather than
just predicted: Caddy's ACME **HTTP-01** challenge still succeeded
(Cloudflare passes plain port-80 traffic through even when proxied), so
Caddy *did* obtain a real certificate - but actual HTTPS/WSS connections
on 443 were being intercepted by Cloudflare's own edge instead of
reaching Caddy at all (`curl` failed outright; `EHOSTUNREACH` from a real
MQTT client). Diagnosed via `dig @1.1.1.1 relay.thrw.app A` returning
Cloudflare's anycast IPs instead of `$RELAY_IP`, asked Tom to toggle the
record to DNS-only, confirmed the fix the same way once he had. Worth
recording here because it's exactly the kind of thing that looks fine
(cert obtained! logs are happy!) while the actual user-facing path is
still broken - the end-to-end MQTT round trip in criterion 6 is what
actually caught it, not the Caddy logs alone.

## Known gaps / judgment calls

- **Caddy on the live VM was bootstrapped by hand over SSH** (copying
  `Caddyfile` to `/tmp`, then running the same commands
  `scripts/relay-redeploy.sh` now runs) rather than by triggering a real
  `deploy.yml` run, specifically so verification didn't also require an
  unrelated EMQX image rebuild/redeploy just to test Caddy. The *script*
  itself was written to do this automatically on every future deploy and
  its logic was verified by hand-running the equivalent commands - the
  next real `deploy.yml` run (any future push touching
  `services/relay-hosted/**`) will be the first time the automated path
  itself executes, and is worth a human glance at its logs when it does.
- **`docker exec caddy caddy reload`'s "already running" branch is
  untested** on this VM specifically (Caddy was freshly started, not
  already running, during this session's bootstrap) - the `docker run`
  branch is what actually ran and was verified; the `reload` branch
  follows Caddy's own documented zero-downtime reload behavior but
  wasn't separately exercised here.
- **The relay credential used for end-to-end verification** was read
  live from the running container for this session only - not logged,
  not committed, not echoed into any file this PR touches. Anyone
  reviewing this PR who wants to re-verify needs to read it the same way
  (`docker exec relay cat /opt/emqx/data/authn-bootstrap/relay-users.csv`
  over SSH) rather than finding it here.
- **`services/relay-hosted`'s own `package.json`/`vitest` test suite has
  no test for the Caddyfile or the redeploy script** - both are shell/
  config, not TypeScript, and this issue's actual verification (criterion
  6) is explicitly the real-VM check above, not a unit test. Nothing new
  added to `test/`.
- No ADR implications - TLS-over-WebSocket was already ADR 0001's actual
  decision; this issue makes the deployment match the spec, it doesn't
  change the spec.
