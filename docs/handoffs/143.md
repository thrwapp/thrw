# #143: adapter-mac provisioning UI

## What was done

The Mac menu-bar app can now be set up from its own UI, closing the gap
#128 documented: `AdapterProvisioning`'s two `UserDefaults` keys had no
writer, so the app always logged "Not provisioned" and stopped.

Split the same way the rest of this package is: every rule lives in
plain-Swift, unit-tested types in `AdapterMac`; the SwiftUI/AppKit window
in `AdapterMacApp` only renders them.

**Testable (21 new tests):**
- `Identity/ProvisioningInput.swift` — validation/normalization.
- `Identity/PairedHeadsets.swift` — picker state, labels, and which
  devices count as headsets.
- `Identity/ProvisioningState.swift` — the single definition of
  "provisioned", shared by the window and the launch path.

**Untestable (no unit tests, by design):**
- `AdapterMacApp/ProvisioningView.swift`, `ProvisioningViewModel.swift`,
  and `AppDelegate`'s window/menu plumbing.
- `Identity/IOBluetoothPairedDeviceSource.swift` — real `IOBluetooth`.

## Acceptance criteria

1. **Reachable from the status item.** `AppDelegate.setUpStatusItem`
   gains a "Set Up…" item (⌘,) above Quit; `openProvisioning()` creates
   or re-focuses the window. `NSApp.activate(ignoringOtherApps:)` is
   needed because an `LSUIElement` app isn't otherwise activated, so the
   window would open behind whatever the user was doing.
2. **Account id validated and persisted.** `ProvisioningInput.accountId`
   trims whitespace and enforces `[A-Za-z0-9._-]{1,64}` — byte-identical
   to Android's `ProvisioningInput.kt` rule, deliberately, since the same
   value addresses the same MQTT topics from either platform. `/`, `+`,
   `#`, whitespace and non-ASCII are rejected because the value is
   interpolated straight into every topic.
3. **Paired-device picker, not free text.** `IOBluetoothPairedDeviceSource`
   reads `IOBluetoothDevice.pairedDevices()` — the *same* call
   `IOBluetoothPeripheralGateway.resolveDevice` uses, so the picker can't
   offer a device the gateway would then fail to resolve. Each row shows
   name + address.
4. **Saving starts the node without a relaunch.**
   `startNodeRuntimeIfProvisioned` is now re-callable, and
   `restartNodeRuntime()` cancels the old `NodeRuntimeHandle` **and
   closes the old `MQTTNIOTransport`** before reconnecting — without the
   close, every save would leak an MQTT client still subscribed to the
   previous node's commands topic. An `isStarting` guard stops a
   double-click (or Save racing the launch-time start) producing two live
   nodes.
5. **Honest status.** The window shows provisioned/not and
   connected/not, driven by `ProvisioningStatus` rather than a separate
   flag that could disagree. `ProvisioningState.Missing` distinguishes
   "not set yet" from `headsetAddressUnusable` — a stored address that no
   longer parses is *wrong*, not absent, and the user needs telling the
   difference.
6. **Testable seam.** See the split above; 21 new tests, 78 total.
7. **Bluetooth permission.** Investigated rather than assumed — see
   "Known gaps".
8. **No connection state machine.** Untouched; frozen per ADR
   0010/0011/0013.

## Test command

`cd packages/adapter-mac && swift test` — **78/78** (was 55 on `main`).

## Verification against real hardware

Not just compiled. Built the `.app` and ran it:

- **Real paired-device enumeration.** Confirmed against this Mac's 10
  paired devices: `IOBluetoothHostController.default()?.powerState`
  reports ON, and `pairedDevices()` returns real entries with addresses
  in dash-lowercase form (`74-15-f5-12-2a-21`) — which is exactly what
  `ProvisioningInput.headsetAddress` normalizes to, so picker output
  round-trips into the `UUID` `MacNode` needs without conversion.
- **Provisioned for real, and the node started.** With a *throwaway*
  account id and the build pointed at a local broker, the app published a
  genuine registration:
  ```
  thrw/verify-143-throwaway/nodes/20D058CE-.../events
  {"manifest":{"supportedEventKinds":["voip"],"platform":"mac",
   "displayName":"Tom's MacBook Air","nodeId":"20D058CE-..."}}
  ```
  …and then a **real VoIP event**, `{"type":"voip","priority":0}` —
  #127's trigger monitor detecting an actually-running VoIP app on this
  Mac, which had never been exercised outside unit tests before.

A throwaway account id was used deliberately: `relay-service` only
watches `THRW_RELAY_ACCOUNTS` (`tom-personal`), so an unwatched account
makes a CLAIM impossible and guarantees nothing touches the real headset
during verification. The build-config change was temporary and reverted;
the throwaway `UserDefaults` were deleted afterwards.

## The blocker this uncovered — #147

Pointed at the **real** relay, the now-provisioned app fails at connect:

```
Failed to start node runtime: connectionError(...badUserNameOrPassword)
```

That is EMQX behaving correctly (`allow_anonymous = false`, #80/#93) —
but **neither adapter can send credentials at all**:
`MQTTNIOTransport.connect` takes no username/password, `HiveMqttTransport`
has no `simpleAuth`, and neither `adapter.properties` carries a
credential key. Filed as **#147**.

This matters beyond this issue: it means #128's composition root and
#142's heartbeats also cannot be verified against production, because the
connection never establishes. Both were verified against local/anonymous
brokers, and both say so. #147 is what finally unblocks a real
`relay.thrw.app` test.

## Known gaps / judgment calls

- **The picker filters to audio-class devices**, and this was a real
  finding rather than a guess: unfiltered, this Mac's paired list offers
  "Magic Trackpad" and "Magic Keyboard" as headsets. Reading
  `deviceClassMajor` against the real 10 devices showed all four genuine
  headsets (AirPods Pro, AirPods Max, Pixel Buds Pro 2, WH-1000XM6)
  report major class `0x04`, keyboards/trackpads report `0x05`, and a
  mouse and a paired iPad report `0x00`. The rule lives in the testable
  layer (`PairedHeadsets.isSelectableHeadset`). **Trade-off**: a headset
  that misreports its class is hidden entirely — two devices on this very
  Mac do report `0x00` — so that is the first thing to revisit if a real
  headset fails to appear.
- **The window itself was never driven end-to-end.** Clicking "Set Up…",
  typing, picking and pressing Save were not exercised: driving the menu
  bar needs Accessibility permission, which this environment is refused
  (`osascript is not allowed assistive access`). The *logic* behind each
  of those is unit-tested, and the provisioned-start path was verified by
  writing the same `UserDefaults` the window writes — but nobody has yet
  confirmed the window renders correctly or that Save wires through from
  a real click. That needs a human with the app in front of them.
- **Bluetooth permission (criterion 7) did not prompt.** Enumerating
  paired devices via `IOBluetoothDevice.pairedDevices()` returned real
  results with no `NSBluetoothAlwaysUsageDescription` prompt appearing,
  on an unsigned local build. That is consistent with enumeration being
  less privileged than connection, but it is *not* proof the prompt won't
  appear on a signed/distributed build, or on a machine that has never
  granted it. No denied-permission path was written, because none was
  observed — `bluetoothUnavailable` covers Bluetooth being off, which is
  the failure mode that did reproduce (by reading `powerState`). Revisit
  alongside #132/#144.
- **No credential field in the window.** #147 lists "credentials entered
  in the provisioning UI" as one of its options; deliberately not
  pre-empted here, since that decision belongs with #147's wider
  shared-vs-per-device question.
