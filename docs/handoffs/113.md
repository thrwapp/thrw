# HANDOFF: end-to-end handoff cycle test for packages/relay-core (#113)

## What was done

Added `packages/relay-core/test/handoff-integration.test.ts` — an
integration test simulating two independent nodes under one account,
each driven through its own `RelayMqttClient` instance over the real
local Mosquitto broker this package's other tests already use
(`defaultMqttBrokerUrl()` / `MQTT_BROKER_URL`), with a single
`PriorityEngine` observing both via the real `subscribeAllEvents` wire
path (added in #97). No changes to `PriorityEngine`, `DeviceRegistry`,
or `RelayMqttClient` — this issue adds a test, not a feature (acceptance
criterion 4).

## Acceptance criteria, with evidence

**1. Two simulated nodes under one account, registered via
`DeviceRegistry` with distinct `NodeManifest`s, driving a `PriorityEngine`
from events published by each node's own `RelayMqttClient` instance over
the real broker via `subscribeAllEvents` — not `PriorityEngine.recordEvent`
called directly.**
`handoff-integration.test.ts:141-157` registers `nodeA`/`nodeB` manifests,
then `:165-171` subscribes `relayListener.subscribeAllEvents(account, ...)`
with a callback that is the *only* place `engine.recordEvent`/
`engine.endEvent` are called (`:167`, `:169`) — driven by messages that
arrive over the wire from `nodeAClient.publishEvent`/`nodeBClient.publishEvent`
(`:177`, `:184`, `:189`) and a raw-client `publishEventEnd` helper
(`:180`, `:197`, `:205`, see "The event-end wire gap" below), not by
calling the engine's methods from the test body directly.

**2. Scenarios (a)-(d), each asserting `currentHolder()`.**
- (a) `:183-185` — node A publishes `call`; polls
  `engine.currentHolder()` to become `nodeA.nodeId`.
- (b) `:187-191` — node B publishes `media` while A's call is still open;
  asserts `currentHolder()` stays `nodeA.nodeId` (call outranks media per
  `PRIORITY_ORDER`).
- (c) `:201-209` — A's call ends (`publishEventEnd(..., "call")`); asserts
  a timer is now pending on the injected `FakeScheduler`
  (`scheduler.pendingCount()` polls to `1`) and that `currentHolder()`
  is still `nodeA.nodeId` (the grace period — same behaviour
  `index.test.ts`'s own auto-return test documents: the last-claimed node
  keeps it until the timer fires).
- (d) `:211-214` — `scheduler.fire(90_000)` (no real 90s wait); asserts
  `currentHolder()` becomes `nodeB.nodeId`, the pre-call holder.

  To make (c)/(d) actually test the timer's effect (rather than
  incidentally matching because of some other still-active signal), node
  B's media is started and then explicitly ended *before* A's call
  starts (`:177-181`), so that at the moment A's call ends there is no
  other active signal — `currentHolder()` can only be showing the
  grace-period holder (A) via `PriorityEngine`'s last-claimed fallback,
  and only reverts to B once the mocked clock actually fires.

**3. `DeviceRegistry` exercised alongside, without hardcoding
platform-specific behavior.**
`:141-157` registers both manifests (one `platform: "android"`, one
`platform: "mac"` — arbitrary, chosen only to look like the M3.3 pairing
the roadmap describes) and asserts `getById`/`listAll` for both. Nothing
in the test branches on `platform` anywhere — both nodes are driven
through the exact same `RelayMqttClient`/`PriorityEngine` call shapes
regardless of which platform their manifest names, matching the
registry's own design (`device-registry.ts:1-13`'s comment: "never
branches on `platform`").

**4. No changes to `PriorityEngine`/`DeviceRegistry`/`RelayMqttClient`'s
existing logic.** Diff is one new test file plus this handoff; grepped
the diff for edits to `src/index.ts`, `src/device-registry.ts`,
`src/mqtt-client.ts` — none.

**5. No new dependency.** Only imports used: `node:crypto`,
`@thrw/protocol`, `mqtt` (already a `relay-core` dependency), `vitest`,
and this package's own `src/index`.

## The event-end wire gap (not a bug in this package — a pre-existing, documented one)

Criterion 1 requires driving the engine's `endEvent` over the real wire,
not by calling it directly. But `RelayMqttClient` has no method to
publish that: `EventPayload` (`mqtt-client.ts:19-22`) only carries
`{type, priority}` — a "signal is active" shape, with nothing to signal
"this signal just ended."

This gap is already known and documented, not new: `docs/handoffs/68.md`
("The end signal") added the wire shape
`{"kind":"event_end","type":<EventKind>}` on the Android adapter side
(`packages/adapter-android/.../protocol/Payloads.kt`'s `EventEndPayload`)
specifically because `PriorityEngine.endEvent` already existed and needed
a wire signal, and says explicitly: **"The relay does not consume this
yet — nothing in `packages/relay-core` subscribes to the events topic at
all today."** That was true until #97 added `subscribeAllEvents`; even
now, nothing in `relay-core` parses the `kind` discriminator — the
payload is handed back as `unknown` for the caller to interpret.

This test's callback (`:165-171`) is that consumer: `isEventEndPayload`
(`:42-48`) checks for `kind === "event_end"` and calls `engine.endEvent`
if so, else `engine.recordEvent`. Kept local to the test file rather than
added to `RelayMqttClient` (e.g. a `publishEventEnd` method or a
`subscribeAllEvents` that parses this itself), per criterion 4 — this
issue is scoped to a test, and turning this into a first-class
`RelayMqttClient` API is a real, separate improvement that a future issue
should pick up (see "Uncertain / follow-up" below). Correspondingly,
publishing the `event_end` message uses a raw `mqtt` client
(`publishEventEnd`, `:105-117`) rather than a `RelayMqttClient` method,
since none exists yet — mirroring `mqtt-client.test.ts`'s own `verifier`
raw-client pattern for publishing on behalf of arbitrary node ids.

Nothing about this required touching `PriorityEngine`, `DeviceRegistry`,
or `RelayMqttClient` — it's wire-message interpretation the test performs
on the `unknown` payload `subscribeAllEvents` already hands back exactly
as designed.

## Verification

- `pnpm turbo typecheck --filter=@thrw/relay-core` — **ran, passed.**
- `pnpm turbo test --filter=@thrw/relay-core` — **ran, but could not pass
  in this environment.** This sandbox has no reachable MQTT broker and no
  way to start one: `docker run` (the exact command
  `.github/workflows/ci.yml` uses to start `eclipse-mosquitto:2`),
  `sudo apt-get install mosquitto`, and outbound network access
  (`registry.npmjs.org`, to fetch a temporary broker) were all blocked
  by this sandbox's command-approval policy. The result:
  `test/index.test.ts` (12 tests) and `test/device-registry.test.ts`
  (8 tests) pass — neither touches MQTT. `test/mqtt-client.test.ts` (a
  **pre-existing** file, unmodified by this PR) and the new
  `test/handoff-integration.test.ts` both fail identically, with
  `Error: connect ECONNREFUSED 127.0.0.1:1883` / `::1:1883` — i.e. the
  same environment gap affects a test this PR didn't write, confirming
  it's the sandbox missing a broker, not something wrong with the new
  test's logic. This is exactly the broker CI's `ci.yml` starts before
  running this same `pnpm turbo test` command (`.github/workflows/ci.yml:102-108`,
  `MQTT_BROKER_URL: mqtt://localhost:1883` at `:132`), so this should run
  for real there. **I could not personally observe this new test pass
  against a live broker** — flagging this per AGENTS.md's honesty
  requirement rather than asserting it works.
- The new test's control-flow logic (event ordering, what's active when,
  what the auto-return timer should do) was written and hand-traced
  against `PriorityEngine`'s existing behavior as already proven by
  `index.test.ts`'s own passing auto-return tests (particularly "auto-return:
  after a call ends, the previous holder gets the claim back once the
  mocked clock fires the default timeout") — the new test's scenario is
  the same state sequence, just driven over real MQTT messages instead of
  direct method calls.

## Uncertain / follow-up

- **This PR could not be verified end-to-end against a real broker** (see
  above) — CI running it for real is the first real signal.
- **`RelayMqttClient` still has no first-class way to publish or consume
  the `event_end` wire message.** This test works around that with a
  local type guard and a raw `mqtt` client, per criterion 4's instruction
  not to add that as a feature here. A follow-up issue should consider
  promoting `isEventEndPayload`/`publishEventEnd` (or an equivalent) into
  `RelayMqttClient` itself now that both an adapter (#68) and a test
  (this one) independently need it.
