# 190 — one tag, one coherent Release

## What was wrong

Two workflows fire on `push: tags: v*`, and between them a single tag
would have produced a Release containing a real signed Android bundle
sitting next to `thrw-android-<tag>.txt`, a file whose entire contents
were:

    TODO: fastlane android release lane not yet implemented.

with nothing marking which was which.

## Worse than the issue described: the first tag would have hung

`release.yml`'s `mac` job required `[self-hosted, macOS]`, and this
repository has **no self-hosted runners registered at all** (`gh api
repos/thrwapp/thrw/actions/runners` → `total_count: 0`). That job could
never have started. `announce` declared `needs: [mac, android, linux]`,
so it would have waited on a job that never ran, and the whole release
would have sat queued until the job timeout.

This had never been observed because **no `v*` tag has ever been cut** —
`git tag --list 'v*'` is empty and `release.yml` has zero runs in its
history. The bug was latent and waiting for the first real release.

## What was done

- **The `android` job is gone.** `release-android.yml` owns Android and
  produces a real signed bundle.
- **The `mac` job is gone.** It could not run, and removing it is what
  lets a tag complete at all. #189 adds the real lane; per the note left
  there it also needs #187's credential steps, or the artifact will
  install and fail to authenticate.
- **`linux` stays** — a real `cargo build --release` against
  `packages/adapter-linux`, whose crate does produce the
  `libadapter_linux.*` the job attaches.
- **`announce` now needs `[linux]`**, the only job left in this workflow.
- **The Fastlane TODOs went with the jobs.** There is no `Gemfile` or
  `Fastfile` anywhere in the repository, so they described a plan nobody
  took up, and a comment pointing at a project that does not exist is
  worse than no comment. The stale reference in
  `docs/ops/prompt-5-gcp-and-branch-protection.md` was corrected too.

## A second incoherence, found on the way

The two workflows disagreed about whether the Release is a draft.
`release-android.yml` runs `gh release create … --draft`;
`action-gh-release` in `release.yml` **defaults to publishing**. So the
draft state was decided by whichever job finished first — and a tag could
have gone public with only half its artifacts attached, depending on a
race.

Both now create a draft. Publishing stays a deliberate act, once the
assets are actually there.

## Known, and deliberately not solved

- **`announce` can run before the Android bundle is attached.** A job can
  only depend on jobs in its own workflow, and GitHub Actions has no
  cross-workflow dependency. Polling the Release, or merging the two
  workflows, both cost more than the problem is worth while releases are
  hand-cut. Stated in the workflow rather than left to be rediscovered.
- **The linux job attaches an `.rlib`.** `packages/adapter-linux` is a
  library crate with no `crate-type` override, so `cargo build --release`
  produces a Rust intermediate artifact, not anything a user installs.
  That is out of scope here — the issue's criterion 3 is only that the
  job keeps running — but it means the Linux "release asset" is not
  currently useful to anyone. Worth its own issue.

## Verification

This cannot be verified by running it: doing so means cutting a real
`v*` tag and publishing a real Release. What was checked instead:

- The workflow parses, and the job graph is now `linux` → `announce`
  with no dangling `needs`.
- Zero self-hosted runners exist, confirming the `mac` job was
  unrunnable rather than merely a placeholder.
- No `Gemfile`/`Fastfile` exists anywhere, confirming the TODOs were
  describing a plan, not a work-in-progress.
- `packages/adapter-linux/Cargo.toml` declares `name = "adapter_linux"`
  under `[lib]`, so the `libadapter_linux.*` glob does match what the
  build produces.
- Only `release.yml`'s linux job and `release-android.yml` now touch the
  Release.
