# HANDOFF: MQTT client + node interface for packages/adapter-android (#67)

## What was done

Wired `@thrw/adapter-android` into the relay: a Kotlin mirror of
`packages/protocol`'s node interface, published over this device's own
MQTT connection to the relay's broker, with `onClaim`/`onRelease` calling
into #66's `BluetoothConnectionManager`.

New source:

- `app/src/main/kotlin/com/thrw/adapter/android/protocol/Topics.kt` —
  Kotlin mirror of `packages/protocol`'s four topic builders and its
  `TopicQos` constant. Single source of truth: nothing else in the adapter
  contains a topic string or a bare QoS number.
- `app/src/main/kotlin/com/thrw/adapter/android/protocol/NodeInterface.kt` —
  `NodeInterface`, `NodeManifest`, `EventKind`, `Platform`, `Priority`,
  mirroring the TypeScript shapes field-for-field.
- `app/src/main/kotlin/com/thrw/adapter/android/protocol/Payloads.kt` —
  wire payloads: `EventPayload` / `CommandPayload` (exact mirrors of
  `packages/relay-core/src/mqtt-client.ts`'s) plus the new
  `RegistrationPayload`.
- `app/src/main/kotlin/com/thrw/adapter/android/mqtt/MqttTransport.kt` —
  the narrow publish/subscribe/close seam.
- `app/src/main/kotlin/com/thrw/adapter/android/mqtt/HiveMqttTransport.kt` —
  the real HiveMQ-backed implementation (WebSocket + TLS per ADR 0001).
- `app/src/main/kotlin/com/thrw/adapter/android/AndroidNode.kt` —
  `NodeInterface` implementation, plus `listenForCommands()` which routes
  relay claim/release commands to `onClaim`/`onRelease`.
- `app/src/main/kotlin/com/thrw/adapter/android/config/RelayConfig.kt` +
  `config/adapter.properties` + a `generateAdapterBuildConfig` Gradle task —
  ADR 0005 build-time configuration.

New tests (45 total in the module, up from 11): `TopicsTest`,
`PayloadsTest`, `RelayConfigTest`, `AndroidNodeTest`, and
`HiveMqttTransportTest` (against a real embedded broker).

## Design decisions made here (none were pre-decided)

**Registration wire format.** Neither `packages/relay-core`'s MQTT client
nor its device registry implies one: `mqtt-client.ts` publishes only
`EventPayload`/`CommandPayload`/`StatePayload`, and `device-registry.ts`
is pure in-memory storage with no MQTT surface at all. So this was
genuinely undecided, and the choice here is:

```json
{ "kind": "register", "manifest": { ...NodeManifest verbatim... } }
```

published on the node's **own events topic** at QoS 1, not retained.

Why the events topic rather than a new `.../register` topic: the topic
set in architecture.md is a frozen contract (AGENTS.md, ADR 0001), and
adding a fifth topic needs an ADR + human review — out of scope for this
issue. `thrw/{account}/nodes/{node}/events` is the only topic a node
publishes on, so registration has to ride it. The `kind` discriminator
makes the two unambiguous without changing the existing event shape: an
event has no `kind` field, and its `type` is always an `EventKind`, never
`"register"`. **The relay does not consume this yet** — nothing in
`packages/relay-core` subscribes to the events topic at all today, so
this is a proposal the relay side still has to be taught to read. If a
reviewer prefers a dedicated registration topic, that's an ADR, and this
payload moves to it unchanged.

**MQTT 3.1.1, not MQTT 5.** First implemented against MQTT 5; it failed
against a real broker, and MQTT 5 turned out to be the wrong choice
anyway: `packages/relay-core/src/mqtt-client.ts` uses the `mqtt` npm
package, whose default `protocolVersion` is 4 (= MQTT 3.1.1). Matching
the relay is the point. Nothing ADR 0001 specifies (WebSocket/TLS, QoS 1,
retained state) needs MQTT 5.

**`suspend fun`, not `void`.** The Kotlin `NodeInterface` methods are
`suspend` where the TypeScript ones return `void`. Every one does I/O
(an MQTT publish; a Bluetooth connect/disconnect through
`BluetoothConnectionManager`, whose methods are already `suspend` from
#66), and AGENTS.md requires coroutines for async code. Names,
parameters, and semantics are otherwise identical.

**Command subscription.** The issue only required `onClaim`/`onRelease`
to exist and call the connection manager. `AndroidNode.listenForCommands()`
was added on top so something actually calls them: it subscribes to
`thrw/{account}/commands/{node}` at QoS 1 and dispatches relay-issued
`{"type":"claim"}` / `{"type":"release"}`. This is message routing only —
it holds no state and makes no decisions. It is **not** the connection
state machine.

## Verification

`cd packages/adapter-android && ./gradlew test` — **run, passing**: 45
tests, 0 failures, both incrementally and from a `clean`. (Mechanically
it was invoked as `pnpm --filter @thrw/adapter-android test`, which is
that package's `test` script and runs exactly `./gradlew test` in that
directory — this session's tool policy allows `pnpm` but not a bare
`./gradlew`.)

`HiveMqttTransportTest` runs against a **real MQTT broker** — an embedded
Moquette started per test on a free port — not a mock, matching the
spirit of `packages/relay-core`'s real-Mosquitto tests. Moquette is
in-process, so the CI `android` job needs no Docker service container the
way the `lint` job does. It covers: a real WebSocket connect; publish at
QoS 1 received as QoS 1 by a second client; `register()` + `emitEvent()`
landing on `thrw/acct-1/nodes/pixel-10-pro/events`; a relay-published
claim then release actually driving the Bluetooth gateway through the
subscription; and a retained publish reaching a subscriber that connects
afterwards.

## Uncertain / not verified

- **TLS is configured but not exercised by any test.** The embedded
  broker speaks `ws://`; the shipped config is `wss://`. So
  `HiveMqttTransport`'s `sslWithDefaultConfig()` path
  (`HiveMqttTransport.kt:93`) is only covered by `RelayConfigTest`
  asserting that a `wss://` URL resolves to `tls = true` — no test does a
  real TLS handshake. Standing up a self-signed broker keystore was
  judged more test scaffolding than signal; the first real connection to
  EMQX will exercise it.
- **Nothing here has touched a real relay or a real phone.** No EMQX
  broker exists to point at yet, and `BluetoothClassicGateway` still has
  no `android.bluetooth`-backed implementation (see #66's handoff: this
  module is still the plain Kotlin/JVM scaffold, not the Android Gradle
  Plugin). So `onClaim()` provably calls `BluetoothConnectionManager.connect`,
  but "the headset actually switches" is unverified end-to-end.
- **Session persistence / reconnect policy is default.** `client.connect()`
  uses a clean session and no `automaticReconnect`. A QoS 1 command
  published while the node is offline is therefore dropped rather than
  queued — which matters for exactly the mobile-dropout case ADR 0001
  cites. Deliberately left alone: choosing a persistent-session and
  backoff policy affects the relay side too and deserves its own issue.
- **Heartbeat is not published.** `Topics.heartbeat` and
  `TopicQos.HEARTBEAT_QOS` are mirrored (the issue asked for the full
  constant set) and tested, but no ~30s heartbeat loop is started —
  that wasn't in the acceptance criteria. Same for `Topics.state`, which
  the relay publishes, not the node.
- **Moquette doesn't set the RETAIN flag** when replaying from its
  retained store, so the retained test asserts delivery-to-a-late-joiner
  rather than the flag on the delivered message. Against EMQX the flag
  would be set; asserting it here would have been testing the test
  broker.
- The generated `BuildConfig.kt` lands in `app/build/` and is gitignored,
  as intended. If the module later moves to the Android Gradle Plugin,
  the `generateAdapterBuildConfig` task should be replaced by AGP's own
  `buildConfigField` mechanism reading the same
  `config/adapter.properties`.
