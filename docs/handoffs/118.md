# HANDOFF: live process for services/relay-hosted (#118)

## What was done

Replaced `src/index.ts`'s one-line placeholder with the actual long-
running decision service: per-account subscription to every registered
node's events, one `PriorityEngine`/`DeviceRegistry` pair per account,
and CLAIM/RELEASE published back whenever the resulting holder changes.
Not new arbitration logic - `PriorityEngine`/`RelayMqttClient` are used
exactly as #113/#114 already proved they work; this is packaging that
logic as a live subscriber.

- `src/relay-service.ts` - `RelayService` (`:118`), the whole
  implementation. `start()` (`:137`) subscribes every configured
  account; `handleEvent` (`:196`) discriminates registration/event_end/
  event payloads by their wire shape and drives `DeviceRegistry`/
  `PriorityEngine` accordingly; `syncHolder` (`:250`) publishes RELEASE-
  then-CLAIM whenever `currentHolder()` actually changes;
  `observingScheduler` (`:185`) wraps the injected `Scheduler` so
  `PriorityEngine`'s own internal auto-return timer (private, no public
  "holder changed" event) also triggers a holder-change check when it
  fires; `trackHeartbeat`/`sweepHeartbeats` (`:217`, `:229`) are the
  missed-heartbeat "gone" detection acceptance criterion 2 asks for.
- `src/index.ts` - the real entry point: reads `THRW_RELAY_ACCOUNTS`
  (`parseAccounts`, `:65`), connects `RelayMqttClient` (optionally
  authenticating with the same `EMQX_RELAY_USERNAME`/`PASSWORD`
  `docker-entrypoint-relay.sh` already requires, `:37`), starts
  `RelayService`, and installs `SIGTERM`/`SIGINT` handlers for clean
  shutdown. `relayHostedPackageName` is kept as an export (the placeholder
  test still passes unmodified).
- `test/relay-service.test.ts` - 5 new tests against the real local
  Mosquitto broker.
- `Dockerfile.relay-service` - a standalone, `turbo prune`-based image
  for this process, verified with a real `docker build` + `docker run`
  end-to-end smoke test (see "Verification").
- `package.json` - adds `@thrw/protocol`/`@thrw/relay-core` as real
  dependencies (`mqtt` as a devDependency, for the test file's raw
  client), plus a `start` script.
- **One-line fix in `packages/relay-core/src/index.ts`**: see "A real bug
  found while wiring this up" below - the issue's own acceptance
  criterion 6 explicitly allows this.

## Acceptance criteria, with evidence

**1. Real entry point: per account, subscribe via `subscribeAllEvents`,
drive one `PriorityEngine`, publish CLAIM/RELEASE on holder change.**
`relay-service.ts:158-182` (`startAccount`) does exactly this per
account; `syncHolder` (`:250-273`) is the holder-change → command-publish
logic. `index.ts` replaces the placeholder entirely - grepped for
`relayHostedPackageName` to confirm only its export survived, not its
former role as "the whole file".

**2. Node registration via `RegistrationPayload`; documented judgment
call for "gone".** `handleEvent`'s `isRegistrationPayload` branch
(`:196-201`) registers into `DeviceRegistry` and starts heartbeat
tracking. "Gone" = 3 missed ~30s heartbeats (`DEFAULT_HEARTBEAT_TIMEOUT_MS
= 90_000`, `relay-service.ts:70-74`), swept every 15s
(`DEFAULT_HEARTBEAT_SWEEP_INTERVAL_MS`, `:76-77`) by `sweepHeartbeats`
(`:229-248`). Documented judgment call, not derived from any measurement
- the comment on the constant says so plainly.

**3. One `PriorityEngine`/`DeviceRegistry` pair per account, never
global.** `AccountState` (`:107-115`) holds both per account, keyed in
`RelayService.states: Map<string, AccountState>` (`:127`);
`registryFor`/`engineFor` (`:150-156`) expose them per-account for
inspection. The "keeps each account's registry and holder fully
independent" test (`relay-service.test.ts`) proves account isolation
against the real broker, not just by construction.

**4. Tested against a fake/injected MQTT layer or the same local
Mosquitto `relay-core`'s/#114's tests use - no real GCP infra required.**
`test/relay-service.test.ts` - real local Mosquitto
(`defaultMqttBrokerUrl()`, same as `relay-core`'s own tests), same
`RelayMqttClient`/raw-`mqtt`-client pattern `handoff-integration.test.ts`
established. 5 tests: registration, the full CLAIM→RELEASE+CLAIM→
RELEASE+CLAIM handoff sequence over two real nodes and the real broker,
per-account isolation, heartbeat-timeout unregistration (via an injected
`FakeScheduler`+`now`, no real 90s wait), and an unrecognized payload
being dropped rather than thrown or registered. No GCP infra anywhere in
this diff.

**5. Deployment wiring: update the Dockerfile/entrypoint, add a second
container, or explicitly defer with reasons.** Genuinely both, split by
what could safely be verified: `Dockerfile.relay-service` is a real,
tested, standalone image for this process (separate from the existing
EMQX `./Dockerfile`, which is untouched) - built and run for real, see
"Verification". **Actually wiring it into the production deploy pipeline
is deliberately deferred** - see "Deployment wiring, in full" below for
the complete reasoning, condensed here: `deploy.yml` is `.github/**`
(this issue's own "must not touch"), and `scripts/relay-redeploy.sh`
manages exactly one running container today, backed by real, already-
hardened GCP operational history this issue's acceptance criterion 4
explicitly says isn't available to verify against ("no real GCP infra
required" *for tests* - also true in the negative: no real GCP infra
*was* used, so a change to how the VM actually runs containers would be
unverified).

**6. No changes to `PriorityEngine`/`DeviceRegistry`/`RelayMqttClient`'s
existing logic unless a real bug is found.** One line changed,
documented below, with the bug and the reasoning both explained in the
diff itself, not just here.

## A real bug found while wiring this up

`packages/relay-core/src/index.ts` exported `DeviceRegistry` from
`"./device-registry"` - no `.js` extension, unlike the `mqtt-client.js`
export two lines below it. Under `tsc`'s ESM output plus this repo's
`"type": "module"`, that compiles to an equally extensionless import in
`dist/index.js`, which Node's real ESM resolver rejects
(`ERR_MODULE_NOT_FOUND`). This had never surfaced before because nothing
until now actually ran relay-core's *compiled* `dist/` output through
real Node - every previous consumer was either a vitest test (whose
resolver tolerates the missing extension) or another package's own
TypeScript source. `services/relay-hosted`'s `index.ts` is the first
real `node dist/index.js` process in this repo that imports
`@thrw/relay-core` as a published package rather than as TS source -
confirmed the hard way: the standalone Docker image (below) failed at
container start with exactly this `ERR_MODULE_NOT_FOUND` until the
one-line fix landed. Fixed at `packages/relay-core/src/index.ts:5`
(now `"./device-registry.js"`); `pnpm turbo test typecheck --filter=@thrw/relay-core`
still passes in full (27/27 tests) after the fix.

## Deployment wiring, in full

What exists and is real: `Dockerfile.relay-service` builds (via `turbo
prune @thrw/relay-hosted --docker`, keeping the image to just this
package's actual dependency subset - `@thrw/protocol`, `@thrw/relay-core`,
`@thrw/relay-hosted`) and runs correctly - verified with `docker build`
and `docker run` against the real local Mosquitto this issue's tests
already use, including an end-to-end smoke test: a real event published
to the broker was correctly answered with a real CLAIM command from the
running container (see "Verification").

What's deliberately not done: wiring this image into the actual GCP
deployment. `deploy.yml` (`.github/workflows/deploy.yml`) currently
builds *one* image from `services/relay-hosted` (the existing
`Dockerfile`, EMQX) and `scripts/relay-redeploy.sh` stops/starts exactly
one container named `relay` on one VM. Making this process actually run
in production means one of:

1. Extending `relay-redeploy.sh` to pull and run a *second* container
   alongside `relay` on the same VM (the more idiomatic single-
   responsibility-per-container shape, matching how `./Dockerfile`
   stayed EMQX-only rather than growing a bundled Node runtime on top of
   an image that isn't built to carry one).
2. Or building a genuinely combined image/entrypoint that runs both EMQX
   and this Node process as one container (more invasive - process
   supervision, signal forwarding, and abandoning the "one container, one
   job" model #80 established).

Either path touches `deploy.yml` (`.github/**`, this issue's own "paths
the agent must not touch" - not a suggestion to route around) and/or
`scripts/relay-redeploy.sh` (not explicitly listed, but real production
infrastructure with documented hard-won history of its own - the
Container-Optimized-OS discontinuation workaround, the health-check
timing window widening, the credential base64-encoding-for-shell-quoting
- visible directly in that script's and `deploy.yml`'s own comments).
Acceptance criterion 4 already establishes this issue's tests don't need
real GCP infra; the flip side is that nothing in this PR was verified
against real GCP infra either, so a change to how the VM actually starts
containers would be asserted, not proven. Left for a follow-up issue that
can actually exercise a real rollout (or at minimum a deliberate, human-
reviewed decision between the two paths above) rather than guessed at
here.

## Known gaps

- **`PriorityEngine`'s internal signal map for a departed node is not
  cleared by the heartbeat sweep** - `sweepHeartbeats` only calls
  `DeviceRegistry.unregister` (`relay-service.ts:236`), since neither
  `PriorityEngine` nor this issue's acceptance criterion 6 offers a way
  to clear a specific node's active signals without touching
  `packages/relay-core`'s existing logic beyond the one bug fix above.
  Concretely: a node that goes silent mid-call (heartbeat stops while its
  `call` signal is still recorded) is *unregistered* from `DeviceRegistry`
  but its stale `call` signal can still make `PriorityEngine.currentHolder()`
  keep reporting it as the winner indefinitely, since nothing ever calls
  `endEvent` for it. A real correctness gap, not a hypothetical one -
  worth its own follow-up (most likely a small, additive
  `PriorityEngine` method along the lines of `forgetNode(nodeId)`, which
  *would* be a `packages/relay-core` change and so is out of scope here).
- **Accounts are statically configured (`THRW_RELAY_ACCOUNTS`), not
  discovered.** There's no accounts/licensing service yet (`services/licensing`
  doesn't exist) to learn the real account set from, and the broker's
  topic ACL wildcards only the node segment
  (`thrw/{account}/nodes/+/events`), not the account segment - so
  dynamic multi-account discovery isn't possible with today's
  `RelayMqttClient.subscribeAllEvents` shape without adding a new,
  broader-wildcard method (a `packages/relay-core` change, out of scope
  here). A static, operator-provided list is the pragmatic interim,
  named explicitly as such in `index.ts`'s own comment.
- **`syncHolder`/`trackHeartbeat`'s MQTT calls are fire-and-forget** (not
  awaited) - matches this service's overall shape (a message handler
  reacting to a stream of events, not a request/response flow with a
  caller waiting on completion). Each is `.catch`-guarded
  (`relay-service.ts:224-231`, `:274-281`) so a transient publish/
  subscribe failure logs and moves on rather than becoming an unhandled
  rejection that crashes the whole process (Node's default since v15) -
  but there's no retry, so a command genuinely lost mid-flight (broker
  hiccup at the wrong moment) stays lost until the next signal changes
  the holder again. Acceptable for this issue's scope (transport-layer
  retry logic wasn't asked for), flagged rather than silently assumed
  fully robust.
