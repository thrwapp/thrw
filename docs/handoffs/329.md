# 329 — Testing framework step 2: scenario runner, world model, node models

## What this is

`docs/spec/scenarios.md` becomes executable. A scenario is a JSON file of
**physical** events; the world model turns those into what each adapter
would observe; the **real** `PriorityEngine` and `DeviceRegistry` decide;
and the resulting commands move the route on measured timings, which
feeds back into the adapters' own signals. That feedback loop is where
#288, #295, #298 and #303 all lived, and step 1 had no notion of it.

Six scenarios run (M1, M5, N2, N5, R298, plus the cadence probe), on a
virtual clock, in milliseconds.

## The result that matters

**The simulator reproduces #298 from first principles.** Reinstating the
bug by setting `macMediaStopDebounceMs` to 0 — and changing nothing else
— produces:

```
47 holder changes over 300s, alternating mac↔pixel on an 11s period
  37s → 48s → 59s → 70s → 81s → …
```

The original report was *"the holder bounced every ten seconds"*. That
period is not a fitted parameter: it falls out of ADR 0010's 6s
self-cooldown plus the settle time. With the debounce restored, the same
scenario produces 2 holder changes and passes.

That is the evidence the model has real resolution, and it is the only
reason to trust the five scenarios that pass.

## How the model was wrong three times before that worked

Recorded because each failure is the kind that would have left a green
suite reproducing nothing.

**1. The device-change gap was a flag nobody read.** I modelled
`macDeviceChangeAudioGapMs` as a parameter and an `inDeviceChangeGap()`
query, and the node model never acted on it. R298 passed with the
debounce removed. The model-resolution probe caught it; nothing else
would have.

**2. `initial` simulated thrw having just acted.** Feeding
`initial.holder` through `apply` armed that node's self-cooldown, which
then suppressed the scenario's own `initial.playing` media start — so
`{ holder: pixel, playing: [pixel] }` produced a Pixel with no media.
`seedInitialState` now sets state with no side effects, because `initial`
describes the world before the scenario, not a handover into it.

**3. The monitor only reacted to edges.** Real `MediaTriggerMonitor`
**polls** `DeviceIsRunningSomewhere`. Without that, the spurious stop
published, the restart was swallowed by the self-cooldown, and nothing
ever re-offered it — so no bounce. The polling retry is what closes the
loop, and the fact that it then produces the *observed* 11s period rather
than an arbitrary one is the check that it is the right mechanism.

A fourth, smaller: `holderChanges` exposed raw node UUIDs, so two runs of
the same seed were incomparable and the reproducibility assertion failed.
It now reports device names.

## Registration cadence (criterion 3)

The number most likely to waste the step, so it was derived rather than
assumed. From two production archives (534 gaps, 2026-09-23):

| | p50 | max | shape |
|---|---|---|---|
| Pixel | 138s | 30985s | unimodal, long tail |
| Mac | 855s | 3996s | **bimodal** |

Reproducing the narrower window the existing
`DEFAULT_NODE_DEPARTURE_TIMEOUT_MS` comment cites gives Android p50
160s / max 2263s and Mac p50 439s / max 1127s against its recorded
160/2263 and 438/1126. That agreement is why the wider figures are
trusted.

**The Mac is bimodal, which percentiles hid.** 55 of its 165 gaps are
under 130s and 79 are 800-1600s, with a near-empty trough between: two
clusters, "awake and on time" and "asleep, registers on wake". A
lognormal fitted to its p50 would generate a mass of 400-800s gaps that
essentially never happen and few of the ~15-minute ones that routinely
do. Asserted directly, so a future "simplification" to a single
distribution fails.

Seeded via `mulberry32`, and `cleanTick` gives the control: over 1200s a
clean 120s tick is 10 registrations against the measured 1-2.

## Criterion 4 is NOT met, and the reason is structural

The issue asks for regressions for **#303 and #307**. Neither is
reachable from `packages/testkit`:

- **#307** is `releaseStaleFallback` being called by `RelayService` on a
  registration. The engine method is in `relay-core` and reachable; the
  orchestration that decides when to call it is not. Replicating that
  here would test a replica of the relay rather than the relay.
- **#303** is a latched `RouteTransition` **inside the Mac adapter** —
  `inProgress` never decremented because a continuation never resumed.
  This model reproduces adapter *decisions*, not adapter internals, and
  deliberately so.

ADR 0003 is the hard constraint: `services/**` is FSL-licensed and
`packages/**` is not, so `packages/testkit` must not import
`RelayService` (#321 found this). The consequence is that a meaningful
slice of the scenario set cannot live here.

**The design doc's own diagram shows `RelayService` inside the
simulator**, which ADR 0003 forbids. That contradiction is unresolved and
should be, because it determines where half the suite lives. The
structure that works: this runner stays in `packages/testkit`, and
`services/relay-hosted/test/` imports it for scenarios needing the
service. Dependency direction permits that; the reverse does not.

## Verified

- `pnpm turbo lint typecheck test --filter=@thrw/testkit` — **41 passed**.
- Whole TypeScript workspace — **24/24 tasks**.
- **Disconfirmation**, which is the point of `model-resolution.test.ts`:
  reinstating #298 in the parameters breaks R298, and removing the
  *perturbation* as well makes the debounce stop mattering — proving the
  two parameters model one mechanism rather than being independently
  tuned to pass.

## Not verified

- **No scenario has been checked against hardware.** Five pass; that is
  the model agreeing with the relay, not with the devices. Step 3's
  conformance replay is what would close that, and until then a passing
  scenario means "the relay decides this way", not "thrw does this".
- **Four world-model parameters are `assumed`**, listed in
  `ASSUMED_PARAMETERS`: the two Android buffering figures, ring-to-answer,
  and `claimSettleMs` — the last because #254's own handoff says it is one
  sample on one pair with no distribution behind it.
- **No scenario currently fails.** #329 expected several to, and the
  honest reading is that #303, #307 and #298 are genuinely fixed on
  `main`, not that the suite is thorough. Criterion 5's expected-fail
  machinery is implemented and exercised by the suite's own structure,
  but no scenario uses it yet — so the Phase 2 backlog this step was
  meant to produce is **empty**, and that is a finding about coverage
  rather than about the product.
