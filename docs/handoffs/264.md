# 264 — an unreachable headset reports `timed_out`, not `target_device_unreachable`

## Criterion 1 — a headset in its case now reports the right reason

Android's `awaitProfileState` detected a *refusal* (#257) by watching for
`CONNECTING → DISCONNECTED`. A powered-off headset never reaches `CONNECTING`
at all, so that path never fired and the poll ran to #244's 8s bound.

The wait now also concludes **unreachable** when no driven profile has left
`STATE_DISCONNECTED` after `UNREACHABLE_AFTER_MS`, throwing
`BluetoothGatewayException.HeadsetUnreachable`, which maps to
`failed` / `target_device_unreachable`.

The decision lives in a pure function,
`packages/adapter-android/.../bluetooth/ProfileWaitDecision.kt`, because
`AndroidBluetoothClassicGateway` needs real `android.bluetooth` proxies and has
no unit tests at all. Same split `nodeStatus` and `CommandSequenceGate` use.

## Criterion 3 — where the threshold comes from, and why it isn't 8s

**This is the part of the issue that mattered most**, so stating it plainly:
`UNREACHABLE_AFTER_MS = 3000` is a **reasoned margin, not a measurement.**

The reasoning:

- A successful claim measures **~4.9s end to end** on the reference Pixel, of
  which **<1s** is relay→command delivery (#254). So the on-device connect is
  roughly 4s.
- Nearly all of that 4s is spent **after** the profile reaches `CONNECTING`, in
  the handshake with the headset. The `CONNECTING` transition is a *local*
  state change made when the stack accepts our request — it does not wait on
  the remote device, so it should land in milliseconds.
- 3s is therefore ~3x the whole window in which a reachable device could
  plausibly still be at `DISCONNECTED`, and 30x the 100ms poll interval.

Two structural protections against the failure criterion 3 warns about — a
working switch reported as failed:

1. **It only fires when `CONNECTING` was never observed.** A slow-but-working
   connect has reached `CONNECTING`, so it can never take this path however
   long it takes; the 8s bound still owns that case. There is a test for
   exactly this.
2. **The refusal path is checked first**, so #257's behaviour is unchanged and
   needs no timer.

**What would falsify it:** a stack that legitimately leaves a profile at
`DISCONNECTED` for over 3s before starting — a connect queued behind the
headset's own teardown from the *other* device is the candidate, since that is
precisely the handover case. That should surface as `CONNECTING` rather than
`DISCONNECTED`, which is why protection (1) exists. If it is wrong anyway, the
symptom is `target_device_unreachable` appearing on switches that used to
succeed. **Watch that rate rather than trusting this reasoning.**

## Criterion 2 — faster than the bound

Resolves at ~3s instead of ~8s. Saves 5 of the 8 seconds.

## Criterion 4 — both platforms agree, and a second bug found on the way

Both adapters used to flatten **every** non-timeout failure to
`target_device_unreachable`. That is wrong for a whole class of them: a missing
profile proxy, a blocked hidden API (#162), or a device macOS has never paired
says nothing about where the headset is. Worse, those are *permanent* faults
until someone fixes them, while `target_device_unreachable` implies a transient
outage — so they were both mislabelled and misleading about whether to
investigate.

Now split, using only existing ADR 0019 codes:

| failure | reason |
| --- | --- |
| headset off / in case / out of range / refused | `target_device_unreachable` |
| no usable profile proxy, blocked hidden API (Android) | `bluetooth_unavailable` |
| device not paired, unrecognised identifier (macOS) | `bluetooth_unavailable` |

`AndroidNode.failureReasonFor` and `MacNode.failureReason(for:)` mirror each
other. No new reason code was added — the confirmed-outcome pattern is a frozen
contract (AGENTS.md), so that would need an ADR. The default stays
`target_device_unreachable`, since an unrecognised error out of a Bluetooth
call is far more likely to be the headset than the stack, and ADR 0019 has no
code for "not sure".

## Why macOS needs no equivalent of `UNREACHABLE_AFTER_MS`

The platforms differ in what they are *told*. macOS gets an explicit
`connectionComplete` callback with a failing `IOReturn`, which becomes
`BluetoothGatewayError.connectFailed` → `target_device_unreachable`. Android
has no such signal and must infer it from a profile that never moved.

**This is the weakest claim in this PR and it is not verified.** It rests on
IOBluetooth's page timeout landing inside the 8s bound. If it does not, the Mac
will report `timed_out` for an in-case headset and will need its own treatment.
The by-hand check below is what settles it.

## Not done — needs the hardware

**Criterion 1's real check: put the headphones in their case and trigger a
claim on each device.** Everything here is unit tests.

- **Pixel:** expect `failed` / `target_device_unreachable` at roughly 3s, not
  `timed_out` at 8s.
- **Mac:** expect `failed` / `target_device_unreachable`. If it shows
  `timed_out` instead, the paragraph above is wrong and macOS needs its own
  early-unreachable path — file that rather than widening the threshold.

`./scripts/relay-logs.sh relay-service 15m command_outcome` reads both.

Also worth watching after this lands: any *rise* in `target_device_unreachable`
on switches that previously succeeded. That is the signature of the threshold
being too tight, and it is the one failure mode the tests cannot catch.
