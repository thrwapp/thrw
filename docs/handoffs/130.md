# #130: PriorityEngine.forgetNode for stale-signal cleanup

## What was done

Added `PriorityEngine.forgetNode(nodeId)` (`packages/relay-core/src/index.ts:111-159`)
and wired it into `RelayService.sweepHeartbeats` (`services/relay-hosted/src/relay-service.ts:235-259`),
closing the real gap `docs/handoffs/118.md`'s "Known gaps" flagged: a node
that goes silent mid-call could make `currentHolder()` keep reporting it
as the winner indefinitely, since nothing ever called `endEvent` for it.

## Acceptance criteria

1. **New method removing the whole node's entry.** `forgetNode` deletes
   `nodeId`'s entire entry from the internal `signals` map in one call
   (`packages/relay-core/src/index.ts:140`), not per-kind via repeated
   `endEvent` calls - the caller (a heartbeat sweep) doesn't know which
   kinds were active.

2. **Correctly re-syncs `currentHolder()`, reusing existing logic.**
   Calls `this.syncLastClaimed()` (`:150`) and `this.computeActiveHolder()`
   (`:158`) exactly as `recordEvent`/`endEvent` already do - no
   duplicated priority logic. The one piece `forgetNode` adds that
   neither of those has: `syncLastClaimed` only ever *sets* `lastClaimed`
   when there's an active holder, never clears it - so `forgetNode`
   explicitly resets `lastClaimed` to `computeActiveHolder() ??
   immediateFallback` when it still points at the just-forgotten node
   (`:157-159`). Covered by
   `packages/relay-core/test/index.test.ts`'s "changes the holder..."
   and "falls back to null..." tests.

3. **Documented judgment call: no auto-return grace period for a
   forgotten node.** `packages/relay-core/src/index.ts:111-134`'s kdoc has
   the full reasoning: the 90s auto-return grace period exists to avoid
   yanking a claim away right after a *graceful* call end, in case the
   same node reclaims it again almost immediately. A node that's gone
   silent has no session left to protect, so `forgetNode` hands the
   claim back to the previous holder (`previousHolderBeforeCall`)
   **immediately** rather than scheduling a `DEFAULT_AUTO_RETURN_MS`
   timer - deliberately *not* reusing `scheduleReturn`. Covered by the
   two "mid-call" tests in `index.test.ts` (one with a previous holder to
   fall back to, one with none) - both assert `scheduler.pendingCount()
   === 0`, confirming no timer was scheduled.

4. **Unit tests covering all four required scenarios**, plus two
   additional ones the mid-call judgment call needed
   (`packages/relay-core/test/index.test.ts`, `describe("forgetNode
   (#130)")`, 7 tests total):
   - no active signals → no-op
   - forgetting the current holder (via an active signal) → holder
     changes to another active node
   - forgetting the only active holder → falls back to `null`
   - forgetting a node that wasn't the holder → no visible change
   - mid-call with a previous holder → immediate return, no timer
   - mid-call with no previous holder → immediate `null`, no timer
   - mid-call with another node still on the call → not resolved early
     (the overall call session hasn't ended)

5. **`sweepHeartbeats` updated to call it.**
   `services/relay-hosted/src/relay-service.ts:247` now calls
   `state.engine.forgetNode(node)` alongside the existing
   `state.registry.unregister(node)`, and `:258` calls `this.syncHolder`
   once after the sweep if anything was forgotten - `forgetNode` can
   change `currentHolder()` synchronously (no timer involved, per
   criterion 3's judgment call above), unlike a normal
   `recordEvent`/`endEvent` holder change, which already rides
   `observingScheduler`'s wrapped timer callback. Verified for real over
   the broker: `services/relay-hosted/test/relay-service.test.ts`'s new
   "forgets a silent node's PriorityEngine signals too (#130)..." test
   registers a node, gives it an active call, fires the heartbeat sweep
   past the timeout, and asserts a real RELEASE command is published and
   `currentHolder()` immediately becomes `null` - the one call site this
   issue exists to unblock is not left unused.

6. **No change to existing public behavior.** `recordEvent`, `endEvent`,
   and `currentHolder` are untouched (only a new method was added below
   `currentHolder`'s existing implementation). Confirmed: the pre-existing
   `packages/relay-core/test/index.test.ts` suite (27 tests before this
   issue's additions) and `handoff-integration.test.ts`'s real-broker
   integration test both still pass unmodified alongside the new tests.

## Known gaps / judgment calls

- **`forgetNode`'s immediate-return design (criterion 3) is a genuine
  behavioral choice, not the only defensible one.** An alternative
  (mirroring `endEvent`'s grace period exactly, including for a
  forgotten node) was considered and rejected - see the kdoc for the
  reasoning. If product behavior ever wants a brief grace period even
  for silently-departed nodes (e.g., to smooth over a flaky network
  blip that looks identical to "gone" until the heartbeat timeout), this
  is the one piece of criterion 3's design to revisit first.
- **`forgetNode` does not touch `DeviceRegistry`** - `sweepHeartbeats`
  still calls `state.registry.unregister(node)` separately, unchanged.
  This issue only closes the `PriorityEngine` half of the gap, per its
  own scope (`DeviceRegistry`/`RelayMqttClient`'s existing logic was
  explicitly off-limits).
