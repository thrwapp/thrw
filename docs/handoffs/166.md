# #166: Mac media trigger

## What was done

`MediaTriggerMonitor` reports architecture.md's rule 4 (`media`) from
CoreAudio's `kAudioDevicePropertyDeviceIsRunningSomewhere` on the default
output device. **Verified live against `relay.thrw.app`** — see below.

Same split the other Mac monitors use: `AudioPlaybackSource` (pure Swift,
faked in tests), `MediaTriggerMonitor` (the logic, 6 tests),
`CoreAudioPlaybackSource` (the real binding, not unit-tested).

## Public API, deliberately

`kAudioDevicePropertyDeviceIsRunningSomewhere` is public CoreAudio.

The private `MediaRemote.framework` (`MRMediaRemoteGetNowPlayingInfo`)
would give richer per-app now-playing data and is **not** used. Apple has
progressively restricted it, and after #162 already took a considered
hidden-API dependency on Android, adding a private-framework dependency
here — where a public signal exists — would be a poor trade. Noted
explicitly so nobody "improves" this later without weighing that.

## The coarseness trade (criterion 3)

CoreAudio reports that *something* is using the output device. It cannot
say what: a UI click, a notification chime and an album are identical to
it. Of the options the issue listed, this implements a **debounce** —
audio must run continuously for 2s before it counts as media.

- 2s comfortably outlasts every system sound (all well under a second)
  while still feeling immediate on a real press of play.
- The cost, stated plainly in the kdoc: **the Mac takes ~2s longer than
  Android to claim for media**, because Android reads a real per-app
  playback state and this cannot.
- Firing immediately and letting the relay's priority rules sort it out
  was rejected: a notification sound would yank the headset off another
  device, which is exactly the behaviour that makes this kind of tool
  feel hostile.

## The default-device problem (criterion 4)

The device this listens to is not stable — plugging in headphones or
AirPods connecting changes the default output, and a listener bound to
the old device is silently dead, indistinguishable from "no audio".

That matters especially here because **thrw's own claim changes the
output device**: connecting the headset makes it the default, orphaning a
listener on the previous one. `CoreAudioPlaybackSource` therefore also
watches `kAudioHardwarePropertyDefaultOutputDevice` and re-attaches, and
only emits on an actual state *change* so a rebind doesn't restart the
debounce.

## Verification

Live, against production, with the Mac node running:

```
>>> playing ~8s of audio on the Mac
[22:12:42] .../events  {"priority":0,"type":"media"}
>>> audio finished
[22:12:46] .../events  {"type":"media","kind":"event_end"}
```

A real `media` event and its `event_end` reached `relay.thrw.app`, with
the debounce behaving correctly — the event fired once playback was
sustained, not on the first sample.

`swift test` — 111/111.

## Known gaps / judgment calls

- **It cannot name the app.** "Media is playing" is all this knows. The
  kdoc says so, in the same spirit as `VoipTriggerMonitor`'s honesty
  about process-watching being weaker than Android's notification-based
  detection.
- **A long enough notification sound would still trip it.** None of the
  macOS system sounds run past 2s, but a third-party app could.
- **It reports this Mac's default output device**, so audio playing to
  some other device on this machine still counts as media here.
- **The device-change path is not unit-tested** — it lives in the
  CoreAudio binding, which needs a real audio stack. The monitor's
  handling of a duplicate `started` (what a rebind produces) *is* tested.
- **Landing this makes #167 (self-cooldown) load-bearing**, same as
  #165: thrw's own disconnect stops audio, which this observes as "media
  ended".
