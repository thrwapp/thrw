# 263 — "silent" and "gone" are not the same thing

The relay had one rule for node liveness: silent for 90s means gone, drop
everything it had. Neither reference device can meet that — a sleeping Mac
cannot send anything at all, and a dozing Pixel has its timers deferred by
the OS — so the rule fired continuously on live nodes.

This splits it into two thresholds. 90s now means **stale** (stop counting
the node as live) and changes nothing a device can feel; 300s means
**gone** (drop its signals, which can move the route). The 30s/90s pair
both adapters document as a 3:1 contract is untouched.

--archives` / `--cat`, which #241 had just made readable:

| registration gap p50 / max | 160s / 2263s | 438s / 1126s |

Silence episodes: p50 **128s**, p90 940s. So the old rule fired 164 times

least likely to mean anything.

### The predicted disaster cannot currently happen, and the reason is exact

The issue predicts a dozing holder losing the headset mid-playback. That
mechanism is real in code but **gated**, and the gate is
`PriorityEngine.dropSignals` (`packages/relay-core/src/index.ts:221-222`):

```ts
const nodeSignals = this.signals.get(nodeId);
if (!nodeSignals) return;        // <- a node with nothing active: no-op
```

`forgetNode` on a node with no active trigger returns before it can touch
`lastClaimed`, so reaping an **idle** holder does nothing at all. Only a
node with an active trigger loses anything.

Measured against that: of the 164 reaps, **0 hit a node with an active
trigger.** All 164 were idle-node no-ops. Replaying holder state from
`holder_change` shows 24 of them hit a node that was nominally the holder
(the Mac, via the rule-5 fallback, 11:31–16:31) and **not one produced a
`holder_change`** — exactly what the early return predicts. The log
confirms the code rather than the code excusing the log.

So the destructive path needs a node that is *both* silent past the
timeout *and* has an active trigger. Tom's second comment names the
reason that combination is rare — playback holds a wakelock — and the log
contains a clean natural experiment for it:

```
16:41:30  node_reaped  (silent 96.9s)     <- idle, screen off
16:44:00  node_reaped  (silent 98.0s)     <- idle, screen off
16:44:46  registration
16:47:04  node_event   call  + voip       <- 13.5-minute call starts
17:00:41  node_event_end voip + call
                                          <- no reap in between at all
17:05:42  registration
```

Same device, same code, same 30s loop: reaped twice in the three minutes
before the call, then zero reaps across 13.5 minutes of it. When the phone
has something to do, its timers run on time.

**Conclusion on severity:** this is a correctness-and-noise problem, as
Tom re-scoped it, and the re-scoping is now measured rather than reasoned.
The severe scenario is not merely rare — it is structurally anti-correlated
with the conditions that trigger a reap.

## Criterion 1 — doze: strongly supported, NOT confirmed

**I could not run `dumpsys deviceidle`. The Pixel was never on USB during
this work** (`adb devices` empty at four separate checks; the other session
released the device, but it was not plugged in). So the specific Android
mechanism is unconfirmed, and I am not claiming otherwise.

What the log supports indirectly, and how far it goes:

- The registration timer is a fixed 120s, and produced gaps of **28s** and
  **2263s** on the same device. Both compressed *and* stretched is what a
  deferred timer catching up looks like; a mis-set constant would produce
  regular gaps. This rules out "the interval is wrong" but not *which*
  deferral mechanism.
- The 30s heartbeat loop is deferred too (`silentForMs` clusters at
  90–105s, i.e. 3+ consecutive misses) while registrations still arrive.
- The call window above: the same loop keeps time when the device is busy.
  Consistent with doze/App Standby deferral, and inconsistent with a bug
  in `HeartbeatPublisher` itself, which would misbehave identically during
  a call.

**What remains genuinely unknown:** whether this is deep doze, doze-light,
App Standby bucketing, or a manufacturer battery-optimisation layer — and
whether an FGS's coroutine `delay` is deferred *specifically* (criterion 1
asks this outright). Only `dumpsys deviceidle` / `dumpsys battery` can say.

To settle it, with the phone on USB and the adapter running:

```
adb shell dumpsys deviceidle | head -40          # state: ACTIVE/IDLE, step
adb shell dumpsys deviceidle get deep            # deep doze state
adb shell dumpsys deviceidle whitelist           # is thrw exempt?
adb shell dumpsys package com.thrw.adapter.android | grep -A3 standbyBucket
# then force it and watch the beats stop:
adb shell dumpsys deviceidle force-idle
adb logcat -s HeartbeatPublisher:* AdapterForegroundService:*
```

**This does not block the fix, by design.** The relay change tolerates
silence without needing to know why the node is silent — so criterion 1's
answer would not change a line of it. That is deliberate: the one thing
worth avoiding here was a fix shaped around a guessed mechanism.

## Criterion 2 — what "gone" should mean

The decision, and the reasoning:

**A node that is quiet is stale. A node that has been quiet for a long
time is gone.** One threshold cannot separate a sleeping device from a
departed one because the only evidence available — absence of messages —
is identical in both cases. What differs is *duration*: a dozing phone
checks in within minutes (observed p50 128s, p90 940s), a departed one
never does.

- `heartbeatTimeoutMs` 90s (`relay-service.ts:280`) — stale. Stops the node
  counting as live (`registry.unregister`). Deliberately non-destructive.
- `nodeDepartureTimeoutMs` 300s (`relay-service.ts:324`) — gone. Drops
  signals across every resource, may move the route, emits `node_reaped`.

300s is taken from the measurement, not picked as a round number:
replaying the observed silence episodes, it would have reaped **34** times
instead of 164, and it is the knee of the curve (180s → 61, 300s → 34,
420s → 26, 600s → 23).

**Why not the obvious alternatives:**

- *Raise the 90s timeout / lengthen the heartbeat.* Rejected. Both
  adapters' publishers document the 30s/90s pair as a contract that must
  stay 3:1, #236 and #251 are recent expensive lessons in this machinery,
  and no fixed timeout survives a max observed gap of 2263s anyway.
- *Fix the adapters to always beat.* Not possible in the direction that
  matters. A sleeping Mac cannot send, and keeping it awake with an
  `IOPMAssertion` to service a liveness ping is a worse bug than the one
  being fixed. Android could use `AlarmManager.setExactAndAllowWhileIdle`
  or a battery-optimisation exemption, but that spends battery and user
  trust on a problem the relay can absorb for free. **No adapter changes
  in this PR** — that is the argument, not an omission.
- *Real departure evidence instead of a timer.* The principled answer, and
  out of scope here: EMQX publishes client connect/disconnect on `$SYS`
  topics, and MQTT's Last Will and Testament is the protocol's own answer
  to "no explicit goodbye" (which `DEFAULT_HEARTBEAT_TIMEOUT_MS`'s comment
  cites as the reason the heartbeat exists at all). Either would replace
  guessing-by-timeout with knowing. Both change the liveness contract, so
  **this needs an ADR** — see below.

## Criterion 3 — the holding, playing device

Satisfied up to the departure threshold, and I want to be precise rather
than reassuring: a node holding the route keeps it for 300s of silence
instead of 90s. It is not an unconditional guarantee, and cannot be one
while absence-of-message is the only evidence — an unbounded version needs
the `$SYS`/LWT work above.

In practice the guarantee is stronger than 300s sounds, because a device
doing the thing worth protecting stays awake (the call window above).

Tested by `keeps a quiet node's signals and its route until it is really
gone (#263)` (`test/relay-service.test.ts:470`): a node holding the route
via an active `call`, silent across three sweeps spanning 180s, keeps the
route, receives no RELEASE, and produces no `node_reaped`.

## Criterion 4 — the churn

164 `node_reaped` lines over the measured window become ~34 on the same
data. The event also means something again: it now fires only when a node
actually lost its signals, so the pairing #245 added it for — a reap line
immediately ahead of the `holder_change` it caused — still holds, without
160 lines that explain nothing.

The residual ~34 is not zero and is not claimed to be. Those are silences
longer than five minutes, which for a two-device system is worth a log
line.

## What I did not do

- **No adapter changes at all.** Argued above, and it keeps this PR out of
  `AdapterForegroundService.kt`, which #234 is editing in parallel. That
  file's `refreshNotification` kdoc (the timer-vs-battery argument) is
  #234's to own; nothing here touches the timer story it describes.
- **No ADR edits** (`docs/adr/**` is off-limits per the issue). ADR 0020's
  decision 2 is adapter-side offline behaviour — what an adapter does when
  *it* cannot reach the relay. The relay's view of a quiet *node* is not
  covered by it, which is why this landed as a service change. **Raising
  for Tom:** 0020 is the natural home for a "relay-side node liveness"
  decision, either as an amendment or a new ADR, and the `$SYS`/LWT
  question above belongs in whichever it becomes.

## Verification

- `pnpm turbo test --filter=@thrw/relay-hosted --filter=@thrw/adapter-android
  --filter=@thrw/adapter-mac` — see the PR body for the run and its result.
- Four existing tests encoded the old single threshold and were updated,
  each keeping its original intent:
  - `:426` #130's "silent mid-call loses its claim" — still asserted, now
    at 300s, **plus** a new assertion that 90s does nothing. #130's
    guarantee is not weakened, only rescheduled.
  - `:516` #236's oscillation characterisation — still asserted, driven at
    300s. #263 slowed this mechanism and did not fix it; the test says so,
    so nobody mistakes the slower cadence for the relay-side half of #236
    being closed.
  - `:677` `node_reaped` reporting — now asserts *silence* at 90s and the
    event at 300s.
  - `:1124` retained-state-after-sweep — advanced past 300s.
- **Criterion 5 is not done.** No multi-hour soak across a real Mac sleep
  and a screen-off phone has been run against this build. The measurement
  that motivated the change is production data from the *old* behaviour;
  it is evidence for the diagnosis, not verification of the fix.

## Uncertainties

1. **The cost of patience, stated plainly.** A node that genuinely departs
   mid-`call` now pins the route for up to 300s instead of 90s, and `call`
   outranks `media`, so the other device cannot take it with music in that
   window. This is a real regression in that one scenario, accepted
   deliberately: the reverse error (yanking the headset off a device
   still using it) is worse, and the data says the wrongly-declared-gone
   case happens constantly while the actually-gone case was never observed.
   An app restart clears it immediately via `restartNode`.
2. **300s is a knee, not a law.** It came from one 10-hour window on one
   pair of devices. If Mac sleep patterns change it should be re-measured,
   and it is an option (`nodeDepartureTimeoutMs`) precisely so that does
   not need a code change.
3. **`heartbeatSubscribed` now survives a stale episode** (it was deleted
   at 90s, now at 300s). A returning node therefore skips a redundant
   MQTT SUBSCRIBE. Believed strictly better — the broker-side subscription
   was never cancelled — but it is a behaviour change I have not observed
   in production.
4. **The relay-service container was crash-looping on startup** when I
   read the live logs: five consecutive `fatal error starting the relay
   service … ECONNRESET` before a successful start, apparently
   relay-service racing EMQX during a redeploy. `--restart unless-stopped`
   recovers it, so it is self-healing and unrelated to this issue, but it
   is unreported and I have not opened an issue for it.
