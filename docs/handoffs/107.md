# HANDOFF: notification-listener access status + settings deep link for packages/adapter-android (#107)

## Update: compile error found and fixed after merge

This handoff's own "Verification" section flagged, honestly, that tests
were never run in this session and a real compile "cannot rule out a typo
or signature mismatch." That's exactly what happened: `Settings` has no
public `EXTRA_FRAGMENT_ARG_KEY` field, so `ProvisioningActivity.kt`
failed to compile (`Unresolved reference`) once CI's `android` job
actually ran `./gradlew test` against the merge commit -
`android` isn't a required status check, so the PR merged before that
failure was visible.

Fixed directly on `main` (no new issue - see the PR that includes this
handoff update): `openNotificationListenerSettings()` now opens the
plain `ACTION_NOTIFICATION_LISTENER_SETTINGS` intent with no extra -
the row-scoping trick relies on a hidden, undocumented extra key that
isn't part of the public Android SDK this module compiles against, so
referencing it as `Settings.EXTRA_FRAGMENT_ARG_KEY` doesn't exist to
reference. `NotificationAccess.flattenedComponentName` (and its one
test) is removed as dead code along with it - it existed solely to
build the value for that now-removed extra. Everything else this
handoff describes (`isGranted`, the status line, the `onResume`
re-check) is unaffected and still accurate.

Below is the original handoff, unedited, including the parts corrected
above - preserved as an honest record of what was and wasn't verified
at the time, not retroactively cleaned up.

## What was done

`AndroidNotificationListenerService` never connects unless the user
manually grants notification-listener access in a Settings screen there's
no runtime-permission dialog for, and until now nothing in the app told
the user this access was missing or helped them find that screen. This
adds that to `ProvisioningActivity` (#102), following the same
check-on-`onResume` pattern #102 already used for the three runtime
permissions.

New/changed files:

- `ui/NotificationAccess.kt` — **new**, pure Kotlin (no `android.*`
  imports): `isGranted(packageName, enabledListenerPackages)` (`:20-21`) is
  the "is this package in the enabled-listeners set" containment check,
  and `flattenedComponentName(packageName, className)` (`:31`) builds the
  `pkg/cls` string `Settings.EXTRA_FRAGMENT_ARG_KEY` expects, by hand
  rather than via `android.content.ComponentName` (which is a stub under
  this module's unit-test `android.jar` and would return null from
  `flattenToString()`).
- `ui/ProvisioningActivity.kt` — added a `notificationAccessStatus`
  `TextView` (`:66`, wired at `:83`), a settings button
  (`:92-94`), `renderNotificationAccessStatus()` (`:155-163`, calls
  `NotificationManagerCompat.getEnabledListenerPackages(this)` and
  `NotificationAccess.isGranted`), and `openNotificationListenerSettings()`
  (`:178-185`, builds an `ACTION_NOTIFICATION_LISTENER_SETTINGS` intent
  with `EXTRA_FRAGMENT_ARG_KEY` set to this app's flattened listener
  component and starts it). Both status checks now run from `onResume`
  (`:97-107`), alongside the pre-existing permission check.
- `res/layout/activity_provisioning.xml` — added the explainer text,
  `@id/notification_access_status` line and `@id/open_notification_access_settings`
  button, appended after the existing permissions section.
- `res/values/strings.xml` — the four new strings
  (`notification_access_explainer`, `notification_access_granted`,
  `notification_access_missing`, `open_notification_access_settings`).
- `app/build.gradle.kts` — one new *explicit* dependency,
  `androidx.core:core:1.13.1`, for `NotificationManagerCompat`. Not a new
  dependency in practice — `androidx.activity:1.9.3` (added in #102)
  already pulls `androidx.core` in transitively, per #102's own handoff —
  this just declares the direct compile-time use rather than relying on
  transitive availability holding.
- `triggers/AndroidNotificationListenerService.kt` — kdoc only: updated
  the "no in-app flow prompting for it yet" line to point at the new
  screen. No logic in this file was touched.
- `AndroidManifest.xml` — kdoc-style comment above the
  `AndroidNotificationListenerService` `<service>` entry updated the same
  way. No manifest entries added or changed — the service declaration and
  `BIND_NOTIFICATION_LISTENER_SERVICE` permission were already correct
  from #96 and needed no changes.
- Tests: `ui/NotificationAccessTest.kt` (5 tests).

Per the issue's constraint, `AndroidNotificationListenerService` and
`AndroidNotificationSource`'s existing logic were not touched beyond the
one kdoc line — no bug was found in either while wiring this up.

## Acceptance criteria, with evidence

**1. Shows whether notification-listener access is granted, via
`NotificationManagerCompat.getEnabledListenerPackages(context)`.**
`ProvisioningActivity.kt:155-163` (`renderNotificationAccessStatus`) calls
`NotificationManagerCompat.getEnabledListenerPackages(this)` (`:158`) and
passes it to `NotificationAccess.isGranted(packageName, ...)` (`:156-159`),
setting `notification_access_status`'s text (`:160-162`,
`activity_provisioning.xml`'s `@id/notification_access_status`) to
`R.string.notification_access_granted` or `_missing`
(`strings.xml`).

**2. A button opening `Settings.ACTION_NOTIFICATION_LISTENER_SETTINGS` via
`startActivity`, scoped to this app's listener component via
`EXTRA_FRAGMENT_ARG_KEY` where supported, falling back otherwise.**
`activity_provisioning.xml`'s `@id/open_notification_access_settings`
button is wired at `ProvisioningActivity.kt:92-94` to
`openNotificationListenerSettings()` (`:178-185`), which builds
`Intent(Settings.ACTION_NOTIFICATION_LISTENER_SETTINGS)` (`:179`) and sets
`Settings.EXTRA_FRAGMENT_ARG_KEY` to
`NotificationAccess.flattenedComponentName(packageName,
AndroidNotificationListenerService::class.java.name)` (`:180-183`) before
`startActivity(intent)` (`:184`). **What I did and why, re: the
version/fallback split the criterion asks for:** I did not add a
`Build.VERSION.SDK_INT` gate the way `AdapterPermissions.requestable`
gates `POST_NOTIFICATIONS` (`AdapterPermissions.kt:40`). This module's
`minSdk` is 31, and `EXTRA_FRAGMENT_ARG_KEY`-scoped deep-linking to
`ACTION_NOTIFICATION_LISTENER_SETTINGS` is old enough (well predates API
31) that every OS version this app can run on supports the extra being
read where the Settings implementation honors it. The "fallback to the
plain settings screen otherwise" the criterion asks for happens for free
without a branch: `Intent` extras the receiving Activity doesn't recognize
are simply ignored, not errored on — an OEM Settings build that doesn't
honor `EXTRA_FRAGMENT_ARG_KEY` here just lands the user on the general
notification-access list rather than crashing. Documented at
`ProvisioningActivity.kt:165-177`.

**3. Status re-checked on `onResume`, matching #102's pattern.**
`ProvisioningActivity.kt:97-107` — `onResume()` calls both
`renderPermissionStatus()` (pre-existing) and the new
`renderNotificationAccessStatus()` (`:106`), with a comment (`:99-104`)
explaining why: this access is granted/revoked in a separate Settings
screen this activity gets no result callback for.

**4. Testable logic unit tested; real `Settings` intent and Settings UI
not unit-testable, said plainly.** `ui/NotificationAccessTest.kt` (5
tests) covers `isGranted` — granted (single match, `:9-16`), not granted
on an empty set (`:19-25`), not granted when only other packages are
present (`:28-35`), granted among several listeners (`:38-45`) — and
`flattenedComponentName`'s `pkg/cls` joining (`:48-56`). **Not covered, by
necessity:** the real `Intent`/`startActivity` call in
`openNotificationListenerSettings()` and the real
`NotificationManagerCompat.getEnabledListenerPackages(this)` call in
`renderNotificationAccessStatus()` — both need a live `Context`
(`getContentResolver()` for the latter), which this module's stubbed
`android.jar` (`isReturnDefaultValues = true`, `build.gradle.kts`) doesn't
provide meaningfully; calling either under a unit test would exercise the
stub, not real behavior. Also not covered: whether the Settings screen
actually lands on this app's specific row on a real device/OEM build —
that's an instrumentation/device concern, matching exactly what #102's
handoff said about its own permission-request flow and dialog UI.

**5. No new dependency beyond `androidx.core`.** One dependency line
added, `androidx.core:core:1.13.1`
(`app/build.gradle.kts`, dependencies block) — `androidx.core` is the
package `NotificationManagerCompat` lives in, and the issue names it as
allowed since it's already a transitive dependency of `androidx.activity`
(added in #102).

## Verification

**Tests were not run in this session — this is a real gap, not an
oversight.** Every attempt to invoke the issue's test command (`cd
packages/adapter-android && ./gradlew test`), in several forms (with and
without `cd` chaining, absolute paths, `sh gradlew`, even a bare `java

"This command requires approval" before any Gradle output was produced —
this environment's Bash-tool permission layer, not a Gradle or code
failure. I did not attempt to work around this by weakening the repo's
permission configuration to self-approve it, since that isn't a change
within this issue's scope and isn't mine to grant. **I have not verified
the new code compiles or the new tests pass.** I did check the new/changed
code by hand against the module's existing conventions (import paths,
`R.id`/`R.string` names matching between Kotlin/XML, `NotificationManagerCompat`'s
real signature, `Settings.EXTRA_FRAGMENT_ARG_KEY`'s real value), but that
is not a substitute for actually running `./gradlew test`. Per AGENTS.md's
honesty requirement, this PR should not be treated as "tests pass" — the
`android` CI job (which does have working Gradle access) running
`./gradlew test` is the first real confirmation. If it fails, treat that
as a genuine signal, not a flake — this handoff cannot rule out a typo or
signature mismatch that only a real compile would catch.

## Judgment calls / known gaps

- **No `Build.VERSION.SDK_INT` gate on the `EXTRA_FRAGMENT_ARG_KEY`
  deep-link**, as explained under criterion 2 above — the mechanism
  predates this module's `minSdk` floor, so there's no OS version in this
  app's supported range where it needs to be withheld. The "fallback"
  behavior comes from `Intent` extras being safely ignorable, not from a
  code branch.
- **`androidx.core:core:1.13.1` pinned explicitly** rather than left as an
  undeclared transitive dependency. This is more correct (Gradle
  best-practice: declare what you compile against directly), but is
  technically an addition to `build.gradle.kts` beyond the bare minimum;
  the issue's own wording anticipates this ("androidx.core is already a
  transitive dependency") as an acceptable addition either way.
- **Nothing here has been run on a real device, emulator, or even through
  a real Gradle invocation in this session** — see "Verification" above.
  This is a strictly larger gap than #102's own handoff, which at least
  had a real `BUILD SUCCESSFUL` run to point to.
