# 282 — the macOS handover mute targeted the wrong device

Found by Tom testing v0.2.0 on the reference hardware the day it shipped:
*"when I play YouTube it still plays out loud temporarily"* on the Mac, while
the Pixel behaves correctly.

## The measurement that settled it

Probed CoreAudio directly rather than reasoning from the code:

```
default output: Tom's AirPods Pro #2 [82]

Tom's AirPods Pro #2 [82]: volume=UNREADABLE(main element) settable=false  <-- DEFAULT
MacBook Air Speakers [70]: volume=0.250 settable=true
```

That one reading invalidated two things I had asserted in source comments when
implementing ADR 0022's macOS half.

## Fault 1 — I attributed a measurement to the wrong device

`CoreAudioSystemOutputVolume`'s kdoc claimed *"Verified on the reference Mac
reading `0.25` with `settable: true` from an untrusted process."* The `0.25`
was the **built-in speakers**. The headset reports no main-element volume at
all and is not settable.

Consequence: on the **release** path the headset is still the default output,
so `silence()` takes the unreadable branch and suppresses nothing. The release
side of ADR 0022 has never worked on macOS.

The comment is corrected rather than deleted — a wrong "verified" claim in
source is worse than no claim, because the next person trusts it.

## Fault 2 — mute and restore resolved the default device separately

`current()` and `set()` each resolved
`kAudioHardwarePropertyDefaultOutputDevice` independently. During a claim that
is two different devices:

1. `silence()` — default is the **speakers**; reads 0.25, stores it, mutes them.
2. The headset connects and becomes the default output.
3. `restore()` — writes 0.25 to the **headset**, which is unsettable, so the
   write is silently dropped. The record is then cleared.

Net: **speakers left at zero, record gone, startup recovery unable to help.**
That is exactly the "silently muted with no explanation" failure ADR 0022's
amendment makes a hard requirement to prevent, reintroduced by keying the
record on "whatever is default now" rather than on a device identity.

Checked Tom's machine while diagnosing: speakers read `0.250`, so he was not
stranded — but only because the paths that ran happened not to hit it.

## The fix

`SystemOutputVolume` now addresses devices explicitly — `defaultOutputUID()`,
`volume(forUID:)`, `setVolume(_:forUID:)` — so "mute one device, restore
another" is no longer expressible.

The identifier is `kAudioDevicePropertyDeviceUID`, **not** `AudioDeviceID`.
The record must survive a crash and a relaunch, and `AudioDeviceID` is an
ephemeral handle that could by then name a different device; restoring a
stranger's volume would be worse than the bug being fixed. A UID that resolves
to nothing is cleared without writing anywhere.

`MutedVolumeStore` now holds a `MutedOutput { uid, volume }`. The
`UserDefaults` store keeps two keys and requires **both** — a record left by a
v0.2.0 build has no device, cannot be honoured, and reads as absent rather
than sending the restore back to guessing.

## What this does NOT fix

**The symptom Tom reported.** Audio starts when he presses play; the claim
command arrives ~1s later, and `silence()` only runs then. Everything before
that is unmuted speakers, and nothing in this change moves that boundary.

Nor does it fix the release path — the headset's volume is unreadable, so
there is nothing to mute there. That is now explicit and tested rather than
silent.

Both of those are properties of **muting** as a mechanism:

- A pause is restorative. The audio resumes where it stopped, so a late start
  costs nothing and the user hears no gap. That is why the Pixel feels right.
- A mute is lossy. Audio plays on inaudibly, and the window before it starts
  is plainly audible.

**#267 (switch macOS to pausing) is the actual fix**, and this bug is evidence
for pulling it forward rather than leaving it behind #132. Tom has already
said he would accept the Accessibility prompt for better UX; the reason it was
deferred is that ad-hoc signing makes the TCC grant die on every build, which
is a real cost but a smaller one than a suppression mechanism that cannot work
on two of its three paths.

## Tests

`swift test` — **257 tests, 0 failures** (was 253; +4).

The fake is now device-keyed, which is the point: the old single-volume fake
**could not express** muting one device and restoring another, so no test
could have caught the original bug. The new one models the default output
changing mid-window, which is what actually happens.

Not verified on hardware. The device-identity fix is unit-tested; confirming
it end-to-end needs a claim on the Mac with the headset elsewhere, then
checking `defaults read app.thrw.mac` shows a `preMuteDeviceUID` naming the
speakers, and that they return to their prior level afterwards.
