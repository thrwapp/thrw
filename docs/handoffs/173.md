# 173 — the relay never re-claims for a node that restarts while it holds

## What was wrong

A device that restarted while it was the relay's holder was **permanently
stuck**: it never received a `claim`, so it never connected the headset,
and nothing could take the route from it short of outranking it.

That is every app restart and every reboot — the ordinary case, not an
edge case.

## How it surfaced

Found by accident while verifying the media triggers (#165/#166) on real
hardware. Both adapters were registered and heartbeating; the Pixel
emitted a genuine media event and the relay published **nothing**:

```
09:32:12 nodes/56479cf1-.../events {"type":"media","priority":0}
(no command, for seven minutes)
```

It looked like the relay was dead. It was not: `docker ps` showed
`relay-service` up, and EMQX's `subscriptions list` showed its client
holding `thrw/tom-personal/nodes/+/events` with `delivered_msgs=45`. It
was receiving the events and deciding to do nothing.

A synthetic node that registered and emitted `call` proved it and, more
usefully, revealed the state:

```
09:39:05 nodes/probe-a/events  {"type":"call","priority":0}
09:39:05 commands/56479cf1-... {"type":"release"}   <-- the relay thought the phone held it
09:39:05 commands/probe-a      {"type":"claim"}
```

The `release` going to the phone is the whole diagnosis: the relay
already considered it the holder, from a session *before* its app
restarted.

## Mechanism

`PriorityEngine.currentHolder()` is `computeActiveHolder() ?? lastClaimed`.
`lastClaimed` is the rule-5 fallback and is never cleared except by
`forgetNode`. With no active signals anywhere it returns the stale value,
and `RelayService.syncHolder` then short-circuits on
`if (nextHolder === state.lastHolder) return;` — so the restarted node is
never told.

`forgetNode` (#130) does not save this: that fires on missed heartbeats,
and a restarted node heartbeats perfectly well. It restarted; it did not
vanish. That distinction is the fix.

## The fix

Registration is the signal. A node registers once per node-runtime start
(`NodeRuntime.kt:40`, `NodeRuntime.swift:83`) and **never on an MQTT
reconnect** — checked before relying on it — so a registration from a
known node means a fresh process, which holds no connection and has no
active triggers.

1. `PriorityEngine.restartNode(nodeId)` (new) clears the node's signals
   like `forgetNode`, but **preserves `lastClaimed`**. Both methods share
   `dropSignals`; the flag is the only difference and it is the whole
   point. Clearing the fallback would move the headset away from the
   device you are actually using every time its app restarted.
2. `RelayService.handleEvent`'s registration branch calls it, then
   re-asserts the `claim` when the holder is unchanged *and* is this
   node — the case `syncHolder` is designed to say nothing about.

Clearing stale signals matters independently: a node that died mid-call
can never send the matching `event_end`, because the monitor that would
have sent one no longer exists, so the signal would pin the route to it
forever.

## Verification

Unit and integration tests, both written to fail first — confirmed
failing against the unfixed service, then passing:

```
× re-publishes CLAIM to a node that restarts while it is still the holder
× clears a restarted node's stale signals so another node can take the route
```

Mutation-tested, since these guard specific behaviour: making
`restartNode` clear `lastClaimed` (i.e. behave like `forgetNode`) kills
the holder test; making it a no-op kills the stale-signal test. Each
mutation failed the test that is supposed to catch it, and no other.

On hardware, against the real broker on an isolated `tom-test` account so
the deployed relay was never touched — Mac claims, then its app is
restarted while it holds:

```
10:09:41 nodes/57678736-.../events {"kind":"register", ...}
10:09:42 commands/57678736-...     {"type":"claim"}      <-- re-asserted
```

and the AirPods reconnected to the Mac. Before the fix that registration
produced nothing at all.

## Open question for the human merging this

Does this need an ADR? It adds **no state** to the connection state
machine (ADR 0010/0011/0013) — idle / pre-claim / claim / active are
untouched, and no new command type exists. But it does add a
reconciliation rule to when a `claim` is published, which is arguably
protocol surface. Flagged rather than guessed at. `services/**` is
human-merge via CODEOWNERS regardless, so this is a question to settle at
merge, not a blocker to opening the PR.

## Known gap, deliberately not fixed here

The relay learns of a node **only** via a registration message. If the
*relay* restarts, every already-connected node stays invisible to it
until that node's adapter restarts — adapters do not re-register
periodically. Same class of problem in the opposite direction, and it bit
during this very session: the relay's MQTT client reconnected 33s after
the Mac registered and simply missed it. Worth its own issue; the fix is
probably periodic re-registration or a relay-side "who's there" probe,
and that is a design choice rather than a bug fix.
