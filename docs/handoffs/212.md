# 212 — a manual claim the user can actually trigger (Mac)

## What was missing

`manual_claim` is ranked second in `PRIORITY_ORDER` — below a call,
above VoIP and media — exists as an `EventKind` in both adapter
protocols, and **nothing emitted it**. The Mac menu bar offered exactly
*Set Up…* and *Quit thrw*.

ADR 0010's principle is that direct user action always wins. That was
aspirational: there was no action to take. For dogfooding this is the
blocker that matters most, because automation you cannot override is
worse than no automation — when it gets it wrong you cannot recover in
the moment. It also defuses #183: an unexplained spurious `call` stops
being frightening once the headset can be taken back.

## It cannot be one-shot, and that is not obvious

The natural implementation — emit `manual_claim`, let the relay claim,
end it immediately — **does not work**, and it fails quietly enough to
be worth recording.

Ending the event makes the engine recompute the holder from whatever is
*still* active. If the Mac is playing media and you manual-claim on the
phone: the phone wins on rank (2 beats 4), then ends its event, and
`computeActiveHolder` sees the Mac's still-active `media` and hands the
headset straight back. The user's action is undone within a second.

So the claim **persists**, and ends only when released, superseded by
another node's manual claim (both active, most-recently-started wins —
the right answer), or outranked by a call. Media elsewhere deliberately
cannot take it back; that is the entire point of having the control.

Because it persists, the surface has to be a **toggle**: a claim you
cannot see and cannot release is worse than none.

## The self-cooldown had to be exempted, or the button would silently do nothing

`MacNode.emitEvent` returns early while `SelfCooldown` is active. The
cooldown exists so thrw ignores **its own** side effects — connecting the
headset changes this device's audio routing, which the media monitor
would otherwise report as a fresh trigger (#167, ADR 0010 point 1).

A manual claim is not a side effect. Without an exemption the override
would do nothing for three seconds after any switch — intermittently, and
silently, which is precisely when a user reaches for it, because a switch
just happened and it was wrong.

The exemption is `manual_claim` alone. Every other kind is *observed*
rather than requested, so every other kind can legitimately be an echo of
our own action, and suppressing those is what #167 is for. Both
directions are mutation-tested: removing the exemption fails the manual
claim tests, and exempting everything fails #167's suppression tests.

## State is updated only after the publish succeeds

`toggle()` awaits the publish before recording the new state. If the
relay cannot be reached the menu keeps showing the truth rather than a
state the relay never heard about, and the next tap retries instead of
toggling into a local-only lie.

## Verification

- `adapter-mac` 141 tests, including the bounce-back case (a claim is not
  ended immediately after being made) and a failed publish leaving state
  unchanged.
- Mutation-tested in both directions on the cooldown exemption.

### Not verified: the menu wiring itself

The `ManualClaim` logic is tested. The AppDelegate wiring — that the item
appears, the action fires, the title flips between *Claim Headset* and
*Release Headset*, and that it is disabled with no node running — is
**not**, and could not be from here: clicking a status-bar item
programmatically needs Accessibility permission that `osascript` does not
have on this machine.

The app was built, installed and confirmed to register with the live
relay, so the surrounding code path runs. One human click would close
this, and it is worth doing before trusting the feature.

## Not done

- **Android.** Same design, in the foreground-service notification as an
  action. Straightforward once this shape is agreed.
- **ADR 0020 decision 2's offline half** — *"a manual claim initiated
  directly on the device is always honoured locally regardless of relay
  reachability"*. That needs local execution bypassing the relay
  round-trip, and ADR 0020's offline behaviour is not implemented at all.
  Doing half would give a claim that behaves differently depending on
  network state, which is worse than one that consistently needs the
  relay.
- **A status surface** (#213). The toggle shows whether *this node* holds
  a manual claim; it does not show who holds the headset or whether the
  relay is reachable.

## A test-suite observation, not a conclusion

One full-suite run took 901s and reported 1 failure; two subsequent runs
were clean at ~1s. That run was contending with a concurrent build. The
suite contains wall-clock-deadline tests (`MediaTriggerMonitorTests`
waits up to 2s), which would flake under that load. Recorded rather than
dismissed: if those tests start failing in CI, this is the likely reason
and they should be made clock-injected like `HeartbeatPublisher`'s.
