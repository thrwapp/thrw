# HANDOFF: adapter-ipad Bluetooth audio-route research (#115)

## What was done

A research/documentation task, not a code-bootstrap task, per the
issue's own framing - answered whether an iOS/iPadOS app can influence
which device a classic-profile Bluetooth audio accessory (like AirPods)
is connected to, using only public APIs, before any `adapter-ipad`
Swift code gets written. Verified against real, current sources (Apple's
own documentation and Developer Forums, including an official Apple DTS
engineer answer), not asserted from memory - see "Sources" below for
every citation actually fetched/searched during this session.

No Swift code was written or committed, per acceptance criterion 4 -
`packages/adapter-ipad` is untouched (confirmed via `git status`).

## Acceptance criteria, with evidence

**1. Answered, with citations: can an app force a classic-profile
Bluetooth audio route using only public APIs?** No. `docs/spec/architecture.md`'s
new "iPad's Bluetooth audio-route limitation (#115)" section covers all
three candidates the issue named:
- `AVAudioSession` (`availableInputs`/`preferredInput`/
  `overrideOutputAudioPort`): observes and picks among *already-connected*
  routes, or forces a speaker/mic fallback - never initiates a new
  connection to a specific paired-but-not-connected device. Corroborated
  by real forum reports that even the already-connected-route case is
  unreliable on recent iOS (cited thread).
- `MPVolumeView`/`AVRoutePickerView`'s route picker: system UI, user-
  driven only - no programmatic selection path.
- `CoreBluetooth`: GATT-only, confirmed by an Apple DTS engineer's direct
  answer (quoted in full in the doc) that classic-profile (BR/EDR)
  access requires either GATT-over-classic support on the accessory
  (AirPods don't expose this) or MFi Program membership + External
  Accessory framework (AirPods aren't a third-party MFi accessory an
  app can register against). An undocumented iOS 13 "BR/EDR Transport
  Bridging Key" was found and named, but explicitly not relied on -
  Apple has published no documentation for it.

**2. Document the finding in `architecture.md`'s adapter-framework
line.** `docs/spec/architecture.md`'s "System components" line changed
from "CoreBluetooth on iPad" to a pointer at a new dedicated section
("no framework can move it on iPad at all" + "see... #115") - same
correction pattern #101 used for the Mac line (inline note, not a
silent rewrite). The new "iPad's Bluetooth audio-route limitation
(#115)" section (right after "System components", before "Connection
state machine") has the full writeup with every citation.

**3. If no public API can force it, describe the M4 fallback product
behavior.** Stated plainly in the new section's "Conclusion" paragraph:
`adapter-ipad` can *observe* the route and detect priority-trigger
events (matching every other adapter), but cannot execute `on_claim`/
`on_release` automatically - the M4 fallback is prompting the user to
switch manually via Control Center's route picker, and "M4's acceptance
criteria need to be written against 'prompt and observe,' never against
'connect and disconnect.'" This is called out explicitly as a real
product-scope finding, not a footnote, matching the issue's own
framing.

**4. No Swift code changes required; a throwaway spike doesn't need
committing.** None written - the public documentation/forum evidence was
sufficient to answer criterion 1 without one. `packages/adapter-ipad`
is a byte-for-byte empty diff (confirmed via `git status`).

  not quietly omitted.

  which platforms can actually execute it automatically.

  already said so before this issue, and acceptance criterion states
  this issue doesn't need to fix it. Noted, not addressed.
- **No test command applies** - this issue is documentation-only, no
