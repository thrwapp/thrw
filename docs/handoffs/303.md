# 303 — the Mac's phantom media event and withheld route

The wedge: a claim that hung for seventeen minutes with no
`command_outcome` ever published, a `media` trigger stuck on with nothing
playing, and `observedRoutes: {}` on every registration — so the relay
kept a node that could not hold the route as its holder, and
`reassert_exhausted` was all it had left to say. Cleared only by quitting
the app.

## The mechanism, found

Tom's restart experiment on the issue narrowed it to one piece of latched
in-process state, and named `RouteTransition.inProgress` as the only state
both `observedRoutes()` and the trigger path consult. That was right, and
this is *why* it latched — which the issue recorded as not visible by
reading the code, because the code reads as correct:

**`withBluetoothTimeout` could not time out.** It raced `body()` against a
sleep in a `withThrowingTaskGroup`. A task group is guaranteed empty when
it returns, so it awaits every child before propagating anything —
including a child stuck in a suspension that ignores cancellation. The
timeout error was produced on schedule and then queued behind the very
thing it existed to escape.

`IOBluetoothPeripheralGateway.connect` suspends on a
`withCheckedThrowingContinuation` resumed only by IOBluetooth's
`connectionComplete` callback, and a checked continuation is not
cancellation-aware. If that callback never arrives, `cancelAll()` does
nothing, the group never returns, and the frame never unwinds — so:

- no `command_outcome`, ever (ADR 0019's 8s bound never fires) — the
  issue's fact 3;
- `RouteTransition`'s `defer`s never run, so `inProgress` stays raised —
  facts 1 and 2, both of them, from one cause;
- `BluetoothConnectionManager.states` stays `.connecting`, which #244's
  bound was written to prevent and could not.

**Why no test caught it.** #244's own test blocks its fake gateway on an
`AsyncStream`, which *is* cancellation-aware — `cancelAll()` unsticks it
and the group returns. The bound looked bounded in tests and was not in
production. `FakeBluetoothPeripheralGateway.blockNextConnectUncancellably`
now blocks the way IOBluetooth does.

### Three fixes, because one is not enough

1. **The cause** — the bound now fires. Every command resolves to an
   outcome, every `defer` runs, the state machine resolves.
2. **Containment** — the ceiling. If any *other* path ever latches that
   counter, the node goes back to reporting its route and reading its own
   triggers on its own, without a restart. Lazy rather than timer-driven:
   the two questions are asked on the node's own schedule, so it repairs
   itself the next time anything cares, with no task to own or leak. It
   **resets** rather than merely answering "false" — leaving the counter
   raised would mean the next real claim began at 1, never restarted the
   clock, and was treated as already expired, which is ADR 0018 decision
   2 silently switched off.
3. **The stranded trigger** — the phantom `media`, which is the
   user-visible half: it is what kept the Mac winning arbitration. The
   ceiling alone does *not* fix it. `MacNode.endEvent` returns without
   touching anything while a transition executes (#295, so the audio
   gate's own pause leaves no trace), but the monitor has already
   forgotten the trigger by then, so the end is lost with nothing to
   retry it. `isEventActive` immediately after `endEvent` is an exact
   signal for that, not a guess: the route-transition check is the only
   early return that skips the local removal.

## Verification

`swift test`: **302 tests, 0 failures**, three consecutive runs, and via
`pnpm turbo test --filter=@thrw/adapter-mac`. 17 new tests. Nothing
skipped or deleted.

**Every new test was made to fail on purpose**, since a test for a wedge
that passes whether or not the wedge is fixed is worth nothing:

| mutation | result |
| --- | --- |
| `withBluetoothTimeout` back to the task-group race | 5 failures across `BluetoothConnectionManagerRouteTests` and `MacNodeTests` — state stuck at `connecting`/`disconnecting`, command loop never resolves, `observedRoutes` stays `[:]`. **This is the issue's own log, reproduced.** |
| the ceiling never fires | 5 failures in `RouteTransitionTests` |
| the swallowed-end retry removed | 4 failures in `MediaTriggerMonitorTests` — media stays active forever |

Note what the first mutation prints: `("connecting") is not equal to
("disconnected")` and `("[:]") is not equal to ("["audio": false]")`.
That is #303's relay-side evidence, from a unit test.

The new tests run the hung call on their own task behind a 3s deadline
rather than awaiting it, so a bound that cannot fire **fails** the suite
instead of hanging it.

### Acceptance criteria

1. *A route transition cannot hold a node in "no information"
   indefinitely — bound, and crossing it logged.* Done:
   `RouteTransition.swift:30` (the bound, derived not chosen), `:179`
   (the write-off), `:191` (the log).
   `RouteTransitionTests.testATransitionOpenPastTheCeilingIsWrittenOff`.
2. *A claim that never resolves still produces a `command_outcome`.*
   Done: `CommandTimeout.swift:87`, and the release path too.
   `MacNodeTests.testAClaimThatIgnoresCancellationStillReportsAnOutcome`.
3. *The `media` trigger cannot stay active while
   `kAudioDevicePropertyDeviceIsRunningSomewhere` is 0, reconciled at
   least as often as registration.* Done **for this cause** — see the
   limitation below. `MediaTriggerMonitor.swift:195`; retries every
   `stopDebounce` (4s), far more often than the 120s registration.
4. *Reproduction, or an explicit statement of what could not be
   reproduced.* Reproduced at the mechanism level, in a unit test
   (`testAConnectThatIgnoresCancellationStillTimesOut`). **Not**
   reproduced on hardware: see below.
5. *`Triggers/` and `Route/` log their state changes.* Done, for the two
   types this wedge went through.
6. *Recovery does not require a restart.* Done, by 1 and 3 together.

## Not verified / limitations

- **No hardware run.** No Mac with a real IOBluetooth stack, no observed
  relay restart, no repeat of the original 17-minute wedge. What is
  verified is that the mechanism the wedge needs is gone and that its
  exact symptoms are reproducible and now fail. That the *original*
  incident took this path is inference from the restart experiment plus
  this mechanism, not a captured trace of it.
- **Criterion 3 is fixed for the cause, not for every cause.** The retry
  fires when a `stopped` was observed and its end was swallowed. If the
  monitor never sees the `stopped` at all — an orphaned CoreAudio
  listener, say — the node would still over-report `media` and nothing
  here would catch it. A true reconciliation would read
  `kAudioDevicePropertyDeviceIsRunningSomewhere` at registration time and
  compare, which needs a readable "is it playing now" on
  `AudioPlaybackSource` (it only offers `events()`); the instantaneous
  read is also exactly what #298's stop debounce exists to avoid acting
  on, so it needs care rather than a one-liner. Left out deliberately,
  not overlooked.
- **The abandoned task is a real leak.** A `body()` that neither finishes
  nor answers cancellation keeps running after `withBluetoothTimeout`
  returns — one task per stuck command. A continuation nobody resumes can
  never be reclaimed, so the alternative is the adapter wedging instead.
  Documented at the call site.
- **The emit side has the mirror-image hole, unfixed.** A suppressed
  `emitEvent` also leaves the monitor believing it reported something the
  node never recorded, so a genuine `media` start can be lost — the Mac
  would fail to claim rather than fail to release. Not fixed here because
  the signal is ambiguous: `emitEvent` also returns early for an
  arbitration pause (#290) and the self-cooldown, and retrying under a
  pause would be wrong. Unobserved so far; worth its own issue.
- **One unexplained test run.** Mid-work, one `swift test` reported 2
  failures in 11.5s; every run before and after — including three under
  10× CPU load and three at the final tree — was clean in ~1.5s. I could
  not reproduce it and did not identify the two tests. The suite's
  polling helpers use 2s deadlines and fixed 80–120ms sleeps, and this
  repo already has prior art for that class of flake (#299/#300, "stable
  waits"), which is the most likely explanation. Stating it rather than
  leaving it out: it is the one thing here I cannot account for.

## Judgment calls

- **`connectTimeout` → `operationTimeout`.** A rename touching 6 call
  sites, worth it because a reader setting "connectTimeout" would not
  expect it to bound releases, and now it does.
- **The ceiling is 14s, derived** (`commandOutcomeTimeout +
  defaultRouteSettle`) rather than picked: no legitimate transition can
  outlast the bound on the work inside it plus the settle tail that
  follows. Asserted in a test so a change to either constant has to be
  deliberate here too.
- **`settledUntil` is cleared on write-off, not extended.** After 14s the
  route is not still moving; the node's whole problem is that it has been
  saying nothing.
- **The retry is unbounded.** It terminates because the transition is now
  itself bounded, so it is ≤4 attempts in the worst case; a cap would
  mean giving up and leaving the phantom event, which is the thing
  criterion 3 forbids.
