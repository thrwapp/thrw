# HANDOFF: EMQX Dockerfile + config for services/relay-hosted (#80)

## What was done

Added the container that `deploy.yml` already assumed existed (its own
comment above the `docker build` step called this out as missing). This
is scoped to the broker only — EMQX itself, configured per ADR 0001 and
docs/spec/architecture.md's "MQTT topic design" — not to wiring
`packages/relay-core`'s `PriorityEngine`/`DeviceRegistry` into a live
subscriber, per the issue body's explicit exclusion.

New files, all under `services/relay-hosted/`:

- `Dockerfile` — `FROM emqx/emqx:5.8.0`.
- `emqx.conf` — baked-in EMQX configuration (listeners, auth backend
  wiring, ACL source).
- `acl.conf` — topic ACL rules.
- `docker-entrypoint-relay.sh` — turns the runtime credential env vars
  into EMQX's authentication bootstrap file before handing off to
  EMQX's own entrypoint.

The existing `src/index.ts` / `test/index.test.ts` TypeScript scaffold
was left untouched — confirmed still passing (`pnpm --filter
@thrw/relay-hosted test`, 1 passed). Nothing in
`packages/protocol/**`, `packages/relay-core/**`, `.github/**`, or
`deploy.yml` was touched.

## Configuration approach: baked-in file, not EMQX_ env vars

The issue allowed either approach for criterion 1; I chose a baked-in
`emqx.conf` (`Dockerfile:12`) over `EMQX_`-prefixed env vars for the
structural config (listeners, auth backend, ACL wiring), because:

- The ACL source and authentication backend wiring are multi-line
  nested structures (an `authentication` list entry, an `authorization`
  block with a `sources` list) that are awkward and error-prone to
  express as flat `EMQX_FOO__BAR__BAZ` env var assignments, versus
  reading naturally as HOCON.
- It keeps the non-secret configuration in git, reviewable in a normal
  diff, rather than living only in whatever `docker run`/GCE
  `--container-env` invocation eventually starts the container.

The one thing deliberately **not** baked in is the actual relay
credential — see below.

## Criterion-by-criterion evidence

1. **`FROM emqx/emqx:5.8.0`, custom config baked in**:
   `services/relay-hosted/Dockerfile:7` pins the exact tag; `Dockerfile:12-14`
   `COPY`s `emqx.conf`/`acl.conf`/the entrypoint wrapper into the image.
2. **Anonymous access disabled, credential via env var, never
   hardcoded**: `emqx.conf:24` sets `allow_anonymous = false`.
   `docker-entrypoint-relay.sh:10-11` requires `EMQX_RELAY_USERNAME`/
   `EMQX_RELAY_PASSWORD` at container start (fails fast via `: "${VAR:?...}"`
   if unset) and writes them to EMQX's authentication bootstrap file at
   `docker-entrypoint-relay.sh:13-21`; neither variable nor any literal
   credential appears in the image's baked-in files. `emqx.conf:33-44`
   wires the built-in-database authenticator to that bootstrap file
   (`bootstrap_file`, `bootstrap_type = plain`). See "Uncertain" below
   re: `password_hash_algorithm.name = plain`.
3. **Topic ACL scoped to `thrw/#`**: `acl.conf:17-19` allows
   subscribe/publish on `thrw/#` and denies everything else;
   `emqx.conf:49-59`'s `authorization` block wires this file in as the
   only authorization source with `no_match = deny`. Applied to `all`
   rather than a specific username because of the single-shared-credential
   model (next section) — every authenticated client is currently the
   same user, so a username-scoped rule would be equivalent but more
   fragile (it would silently stop matching if the username env var
   changes without a matching ACL edit).
4. **Plaintext WebSocket (8083) kept, TLS not attempted**: no
   listener override for `listeners.ws.default` in `emqx.conf` — it
   keeps the image's default bind, which is `8083`. `emqx.conf:18-20`
   explicitly disables `tcp`, `ssl`, and `wss` listeners rather than
   leaving `wss` reachable with no cert.
5. **Dashboard default credentials overridden via env var**: not
   baked into `emqx.conf` — EMQX's own image natively maps
   `EMQX_DASHBOARD__DEFAULT_USERNAME` / `EMQX_DASHBOARD__DEFAULT_PASSWORD`
   env vars to the dashboard's bootstrap admin account, and
   `docker-entrypoint-relay.sh:23` execs into the image's original
   `docker-entrypoint.sh`, which still applies that mapping. This needs
   to actually be *passed* wherever the container is run (see
   "Uncertain" below — the issue's own test command doesn't pass it,
   and neither does the VM startup script in
   `docs/ops/prompt-5-gcp-and-branch-protection.md`, which is out of
   scope for this issue).
6. **Scope**: only files under `services/relay-hosted/` were added;
   confirmed via `git status`/`git diff` before opening the PR that
   `packages/protocol/**`, `packages/relay-core/**`, `.github/**`, and
   `deploy.yml` are untouched.
7. **TS scaffold left alone**: `src/index.ts` and `test/index.test.ts`
   are unmodified; `pnpm --filter @thrw/relay-hosted test` still passes.

## The single-shared-credential tradeoff (explicit, per the issue)

There is exactly one MQTT username/password for the whole broker right
now, supplied at container start. This is a deliberate interim choice,
not an oversight: `services/accounts` doesn't exist yet, so there is no
real per-tenant identity to authenticate against. Consequences worth
knowing:

- Any adapter that has the shared credential can publish/subscribe to
  *any* account's topics under `thrw/#` — the ACL in this PR narrows
  the namespace from "everything" to "everything under `thrw/#`", but
  it cannot enforce per-account isolation without per-account
  credentials or per-account ACL rules, neither of which exist yet.
- Rotating the credential means redeploying the container with new env
  vars, and updating every adapter build's config simultaneously (per
  ADR 0005, adapters read this from build-time config, not hardcoded).
- `password_hash_algorithm.name = plain` (`emqx.conf:38-40`) stores
  that one credential unhashed in EMQX's built-in database. Acceptable
  here only because it's a single shared operational secret rotated by
  redeploying the container, not a per-user password — this would be
  the wrong choice the moment real per-tenant auth exists.

Real fix is per-tenant auth once `services/accounts` exists — likely an
EMQX HTTP authentication backend calling into that service, plus
per-account ACL rules generated from account prefixes instead of the
current static "all" rule. That's follow-up work, not something to
under-scope into this issue.
