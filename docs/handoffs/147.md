# #147: adapters can authenticate to the relay

## What was done

Both adapters can now present an MQTT username/password, so an adapter
can actually connect to the deployed relay. Before this, neither could —
`MQTTNIOTransport.connect` and `HiveMqttTransport.connect` took no
credentials and neither `adapter.properties` had a key for one, while the
deployed EMQX runs `allow_anonymous = false`. A fully provisioned adapter
failed at connect with `badUserNameOrPassword`.

**This is verified against the real relay, not just locally** — see
"Verification" below. It is the first time any adapter has successfully
talked to `relay.thrw.app`.

## The decision (acceptance criterion 1)

Of the three options the issue laid out, **build-time config with the
value not committed** — confirmed with Tom directly rather than chosen
unilaterally, since it determines what ends up inside a published APK.

- `config/adapter.properties` (committed) ships `relay.username=` and
  `relay.password=` **empty**.
- `config/adapter.local.properties` (gitignored, `**/config/adapter.local.properties`)
  overlays it. Any key there wins.
- Empty means *connect anonymously* — a real, supported configuration for
  a local or self-hosted broker with `allow_anonymous = true`, which is
  how both test suites run. It is not an error state.

**What this costs, stated plainly**: the value is still compiled into the
built app, so anyone who can read the binary can recover it. That is
acceptable while the only users are Tom's own devices sharing one relay
credential (the interim model from #80, `acl.conf` as `{allow, all, ...}`).

**It is not acceptable for public distribution.** Before the app ships to
anyone outside Tom's devices, this needs per-device credentials, which
needs `services/accounts` (M7) to mint them. That constraint is repeated
in both `RelayCredentials` types' docs, both properties files, and should
be treated as a blocker on M10, not a nice-to-have. The rejected
alternatives: committing the value (it would be in git history
permanently) and entering it in the provisioning UI (best security, but
more work and Android's screen would need the field too — still the right
answer if the internal build ever leaves Tom's own devices before M7).

## Acceptance criteria

2. **Both transports accept optional credentials** —
   `MQTTNIOTransport.connect(config:clientId:credentials:)` passes them to
   `MQTTClient.Configuration`'s `userName`/`password`;
   `HiveMqttTransport.connect(config, clientId, credentials)` uses
   HiveMQ's `connectWith().simpleAuth()`. Both default to `nil`/`null`,
   so existing anonymous callers are unaffected.
3. **Never hardcoded** — ADR 0005 upheld: the value comes from build-time
   config, and the committed file carries only an empty key. The
   gitignore entry was added in the same change, so there is no window
   where a real value could be committed by accident.
4. **Unit tests at the seam** — `RelayCredentialsTests.swift` and
   `RelayCredentialsTest.kt`, 7 cases each, mirrored case-for-case:
   complete credential used; both-blank means anonymous; **half-set means
   anonymous** (a username with no password would otherwise produce a
   confusing broker-side rejection); whitespace trimmed; awkward
   characters preserved.
5. **Verified for real against `relay.thrw.app`** — below.
6. **No change to the frozen topic set or `NodeInterface`** — neither was
   touched.

## Verification

A real Mac app, built with the real credential in an untracked overlay,
connected to **production** and published — observed by subscribing to
`relay.thrw.app` from a separate client:

```
watcher connected to production relay
RECEIVED thrw/<account>/nodes/C36CC61B-.../events -> {"kind":"register","manifest":{"platform":"mac",...
RECEIVED thrw/<account>/nodes/C36CC61B-.../events -> {"type":"voip","priority":0}
RECEIVED thrw/<account>/nodes/C36CC61B-.../heartbeat ->
```

All three message types, against the real broker: registration, a real
VoIP event from #127's monitor, and a heartbeat from #142's publisher.
Previously this same path failed at connect.

A **throwaway account id** was used deliberately. `relay-service` only
watches `THRW_RELAY_ACCOUNTS` (`tom-personal`), so an unwatched account
cannot produce a CLAIM — which means nothing could reach
`bluetooth.connect()` and move a real headset's audio route as a side
effect of a verification run. The credential overlay and the throwaway
provisioning were both removed afterwards.

Also verified mechanically:
- The overlay **does** override the committed file, on both platforms.
- The generated `AdapterBuildConfig.swift` / `BuildConfig.kt` contain the
  overlaid values, and empty strings when no overlay exists.
- `git check-ignore` confirms the overlay is ignored, and `git status`
  shows it absent.
- Gradle's `inputs.files` includes the overlay, so a credential change
  isn't cached past.

## Known gaps / judgment calls

- **Backslashes behave differently on the two platforms**, found by
  running both generators rather than by reading the code. Android reads
  the file with Java `Properties.load()`, where `\` is an escape
  character, so a literal backslash must be doubled (`p\\ss` → `p\ss`).
  The Mac generator is a shell script taking raw text and applies no such
  escaping, so the *same file* yields a different password there. The
  real credential is alphanumeric plus dashes, so this does not bite
  today — but a backslash-containing password would silently
  authenticate on one platform and fail on the other. Documented in both
  properties files. Not unified, because doing so means implementing
  `.properties` escaping in shell for a case that currently cannot occur.
- **Still one shared credential for every node.** Nothing here changes
  the #80 interim model; two devices authenticate identically and the ACL
  remains `{allow, all, ...}`. Per-node identity and per-node ACLs are
  M7's job.
- **Android was not run against the real relay.** Its credential path is
  unit-tested and its generator verified, but only the Mac has actually
  connected to production. The Android internal build is the natural next
  test — and it should use account `tom-personal`, or `relay-service`
  won't be watching and no CLAIM will come back.
- **No credential rotation story.** Changing the relay password means
  rebuilding and redistributing every adapter. Acceptable at one user;
  another thing M7 subsumes.
