# HANDOFF: automated release versionCode (#153, part 1 of 2)

## What was done

`versionCode` in `packages/adapter-android/app/build.gradle.kts` now
reads `THRW_VERSION_CODE` from the environment, falling back to `1`.
Previously a hardcoded literal that every release after the first would
have needed a manual bump of - flagged as a known gap when the signing
config landed (`docs/handoffs/148.md`).

This is **part 1 of 2**. The workflow that actually supplies the value
is `.github/**`, which is always human-merge per AGENTS.md, so it ships
as a separate PR rather than being bundled into this `packages/**` one.
Until that lands, nothing sets the variable and every build is
`versionCode 1` exactly as before - this change is inert on its own.

## Why an env var rather than deriving it in Gradle

Deriving the commit count inside `build.gradle.kts` (shelling out to
`git rev-list`) would make every local build depend on git being
present, the checkout being non-shallow, and the build directory being
inside a repo at all - and would silently produce a different
`versionCode` depending on how the source was obtained. Passing it in
keeps the build reproducible: given the same inputs it produces the
same artifact, and CI owns the policy of what the number should be.

## Acceptance criteria, with evidence

**1. Reads `THRW_VERSION_CODE`, falls back to the existing literal.**
Verified against the merged manifest rather than the build log, since
the build succeeding proves nothing about the value that landed:

```
$ ./gradlew assembleDebug                       # no env var
android:versionCode="1"

$ THRW_VERSION_CODE=47 ./gradlew assembleDebug  # override
android:versionCode="47"
```

**Malformed values fail loudly rather than coercing.** Verified:

```
$ THRW_VERSION_CODE="not-a-number" ./gradlew assembleDebug
* What went wrong:
THRW_VERSION_CODE must be an integer, got: 'not-a-number'
```

This matters more than it looks: a silently-coerced `0` or `null` would
produce an artifact whose version ordering is wrong in a way nobody
notices until Play refuses a *later* upload, at which point the bad
value is already burned.

## Known gaps / judgment calls

- **`versionName` is untouched**, still the literal `"0.1.0"`. It's
  user-facing and should be a deliberate human decision per release,
  not derived from commit history - unlike `versionCode`, Play doesn't
  require it to change, and `0.1.0` staying stable across several
  internal-testing builds is correct.
- **Local builds all produce `versionCode 1`.** Intentional: they're
  never uploaded. If one ever is, Play rejecting it as a duplicate is
  the right outcome rather than a local build quietly consuming a
  number the CI sequence expects to use later.
