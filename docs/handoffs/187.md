# 187 — release builds could not authenticate

## What was wrong

`config/adapter.properties` ships `relay.username=` and `relay.password=`
deliberately empty in both adapters, with real values supplied by a
gitignored `config/adapter.local.properties` overlay (#147). That works
for a local build on Tom's machine. It did not work for anything CI
produced.

`release-android.yml` injected the keystore secrets and nothing else, so
`generateAdapterBuildConfig` read the committed file, generated
`RELAY_USERNAME = ""` / `RELAY_PASSWORD = ""`, and the resulting bundle
was rejected at connect with `badUserNameOrPassword` — the deployed
broker runs `allow_anonymous = false` (#80/#93).

That is the worst shape of failure: the release looks successful, the app
installs, and it then silently does nothing — which is exactly what #182
describes from the user's side.

## No new secrets were needed

The issue originally asked for `THRW_RELAY_USERNAME` /
`THRW_RELAY_PASSWORD` to be added. They were not, and should not be.
`EMQX_RELAY_USERNAME` / `EMQX_RELAY_PASSWORD` have existed as repository
secrets since 2026-09-17; `deploy.yml:83` calls them "the shared relay
MQTT credential", and `docker inspect relay-service` on the VM shows the
deployed relay running as that username. Per #147 there is exactly one
shared relay credential and every participant presents it.

Two secrets holding one value drift. Rotating the relay password would
update one and not the other, producing a working relay and newly-built
adapters that all fail auth — a failure that reads as an adapter bug and
is nowhere near its cause. The point to split them is M7
(`services/accounts`, per-device credentials), together with the ACL
change that makes separate identities mean something.

## What was done

In `release-android.yml`, mirroring the discipline the decoded keystore
already had:

1. **Write the overlay before the build**, failing loudly if the secrets
   are absent rather than producing an artifact that cannot
   authenticate. Written with `printf` into a file created by `install -m
   600 /dev/null`, so the value is never echoed and the file is never
   briefly world-readable.
2. **Verify the generated config**, not the workflow. A green build does
   not prove the value landed — the same argument as the existing "Verify
   the bundle is signed" step.
3. **Remove the overlay with `if: always()`**, so a failed build does not
   leave a credential on the runner.

### Why the password is checked for non-emptiness but not compared

The username is compared exactly. The password deliberately is not: the
Android generator escapes for Java `Properties` *and* for a Kotlin string
literal, so a password containing a backslash legitimately differs from
the raw secret. `adapter.properties` documents that asymmetry — the same
overlay line yields different passwords on Android and the Mac, because
the Mac generator is a shell script that takes the raw text.

Comparing the password would therefore fail spuriously the first time the
credential is rotated to something containing a backslash. The non-empty
check is what catches the bug this issue is actually about.

## Verification

The check was exercised both ways locally, against a real
`generateAdapterBuildConfig` run rather than a mock:

- **With an overlay** — generated `RELAY_USERNAME: String = "testuser"`,
  extraction returned `testuser`, username comparison passed.
- **Without an overlay** — generated `RELAY_USERNAME: String = ""`, which
  is precisely the #187 bug, and the check correctly failed.

That second case matters: a verification step whose pattern silently
fails to match is worse than no verification, because it reports success.

## Not done here, and why

**The Mac half.** `release.yml`'s `mac` job is still a placeholder that
writes a text file (`echo "placeholder mac build…" > dist/…txt`) — there
is no build for a credential to reach. Adding credential plumbing to it
would be theatre: it would pass CI, look like the issue was satisfied,
and still ship nothing.

The same three steps belong in the real mac lane when #189 lands, and are
better tracked as an acceptance criterion *there* than left half-applied
here. Flagged on the issue rather than quietly dropped.

## Known and unchanged

The credential is still recoverable from the distributed binary —
`adapter.properties` says so plainly. Acceptable while the only users are
Tom's own devices sharing one relay credential; not acceptable for public
distribution, which needs M7. This issue makes the internal-build case
work; it does not change that tradeoff.
