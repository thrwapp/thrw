# #142: adapters publish heartbeats so nodes stop being reaped after 90s

## What was done

Both adapters now publish a liveness heartbeat every ~30s, so
`services/relay-hosted`'s `sweepHeartbeats` stops reaping live nodes.
`services/relay-hosted` gains a regression test proving the fix.

Before this, neither adapter published a heartbeat at all, while
`relay-service.ts:235` dropped any node whose last beat was older than
90s. The chain:

1. A node registers → `trackHeartbeat` stamps `lastHeartbeatAt` **once**.
2. Nothing ever refreshes it.
3. ~90–105s later the sweep runs `registry.unregister(node)` **and**
   `engine.forgetNode(node)`.
4. `syncHolder` sees the holder change and **publishes a RELEASE** —
   disconnecting the headset.

**This regressed in #130.** Before it, the sweep only cleared
`DeviceRegistry` (quiet bookkeeping drift). #130 added `forgetNode` to the
same path — correct *given* heartbeats exist, but since they didn't, it
turned a silent inconsistency into a mid-call disconnect. It reached
production when #130 merged. Nothing was harmed only because no real
adapter is provisioned against production yet (#143 is the Mac blocker).

## Acceptance criteria

1. **adapter-mac publishes at QoS 0 on ~30s.**
   `Heartbeat/HeartbeatPublisher.swift` (new) with
   `MacNode.publishHeartbeat()` (`MacNode.swift`) publishing to
   `Topics.heartbeat(account:node:)` at `TopicQos.heartbeatQos`. Wired
   into `NodeRuntime.start` as a fourth task, cancelled by the same
   `NodeRuntimeHandle`.
2. **adapter-android does the same.**
   `heartbeat/HeartbeatPublisher.kt` (new) with
   `AndroidNode.publishHeartbeat()`, wired into `NodeRuntime.start` as a
   fifth coroutine in the caller's scope.
3. **Interval is a named constant, with the 3:1 relationship documented.**
   `defaultHeartbeatInterval` (Swift) and
   `HeartbeatPublisher.DEFAULT_INTERVAL_MS` (Kotlin), both 30s, both with
   a kdoc stating that relay-hosted's 90s timeout is deliberately 3× and
   that the two must not drift apart. Each adapter has a test asserting
   the constant's value so a silent change fails loudly.
4. **Neither `NodeInterface` mirror gained a method.** Verified: all
   three (`packages/protocol/src/index.ts`,
   `adapter-android/.../protocol/NodeInterface.kt`,
   `adapter-mac/.../Protocol/NodeInterface.swift`) still declare exactly
   `register`, `emitEvent`, `onClaim`, `onRelease`, and
   `git diff --name-only main` for those three paths is **empty**.
   Capability was added via a separate `HeartbeatSink` seam in each
   language, following the precedent `EventLifecycle` set in #68.
5. **relay-hosted regression test.** `relay-service.test.ts`'s
   "keeps a node that is still heartbeating, even well past the timeout
   (#142)". The existing sweep tests still pass unmodified.
6. **Payload: empty.** architecture.md's topic table specifies
   `QoS 0, ~30s` and says nothing about a body, and `relay-core`'s
   `subscribeHeartbeat` ignores the payload entirely — arrival *is* the
   signal. Publishing an empty string avoids creating something a future
   relay might start parsing.

## Frozen contract

The heartbeat topic and interval were already specified in
`docs/spec/architecture.md:256`, so publishing to them fulfils the frozen
contract rather than changing it (per `docs/roadmap.md`'s own nuance on
this). No ADR needed, and none of the frozen interfaces changed — see
criterion 4.

## Three real problems found while building this — worth reading

**1. Beating immediately was wrong, and the existing tests caught it.**
The first implementation beat as soon as the runtime started. But
`relay-service.ts:199` only calls `trackHeartbeat` (which sets up
`subscribeHeartbeat` for that node) **when it sees that node's
registration** — so any beat published before registering lands on a
topic nobody is subscribed to. Both runtimes now wait for registration to
complete before starting the loop (`registerTask.result` / `Job.join()`).
There are now explicit ordering tests in both adapters, because this is a
correctness property, not a test convenience.

**2. An infinite `delay` loop hung the entire Android suite.**
`HeartbeatPublisher.run()` never returns, unlike the trigger monitors
(whose `run()` ends when their source flow completes). Under
`runTest`'s virtual clock, `advanceUntilIdle()` never goes idle when
there is always another `delay` scheduled — the suite hung past a 600s
timeout and had to be killed. Fixed by having `NodeRuntime` depend on a
`HeartbeatRunner` fun-interface, so tests supply a terminating runner.
**This would have hung CI**, not just local runs.

**3. The regression test initially proved nothing.** The first version
looped 3 × 30s, landing `now` on exactly 90_000. The sweep's check is a
strict `lastSeenAt < cutoff`, so `0 < 0` is false and the node was never
reaped — meaning the test passed *with the heartbeat publish deleted*. It
was caught by mutation-testing it (deleting the publish and re-running),
not by it going green. Now 5 intervals, plus a `settle()` after each beat
because `trackHeartbeat`'s `subscribeHeartbeat` is fire-and-forget and a
QoS 0 beat published before that SUBSCRIBE lands is silently dropped.
Re-verified by mutation: **fails without the publish, passes with it.**

A fourth, smaller one: the Swift test fake was `@unchecked Sendable` with
an unguarded `Int` mutated from a background `Task` — a real data race
that crashed the test binary with signal 11 at teardown. Now lock-guarded.

## Known gaps / judgment calls

- **Not verified against a real relay.** These are unit/integration tests
  against fakes and a local broker. Nothing here has been run against the
  deployed `relay.thrw.app` with a real adapter, because no adapter can
  be provisioned on a real Mac yet (#143). The first real hardware test
  is what will actually confirm this fix end-to-end.
- **The 30s constant is duplicated across three places** (both adapters
  plus relay-hosted's 90s timeout) with no shared source of truth — they
  are in three different languages, and `packages/protocol` exports topic
  builders but not timings. Cross-referencing kdoc in each is the mitigation;
  a genuine shared constant would need the protocol package to start
  exporting timing values, which is a bigger change than this issue.
- **A failed beat propagates and ends the loop**, rather than retrying.
  `NodeRuntime` logs it. A transport that can't publish is worth
  surfacing, but this does mean a transient broker blip stops the
  heartbeat permanently until the runtime restarts — reconnection/retry
  behaviour is not in scope here and doesn't exist anywhere in the
  adapters yet. Worth its own issue.
