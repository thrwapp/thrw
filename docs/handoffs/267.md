# 267 — macOS pauses across the handover window instead of muting

Closes the divergence ADR 0022's 2026-09-23 amendment opened. Android has
always paused; macOS shipped muting as a deliberate temporary compromise.

## Why this was pulled forward rather than waiting on #132

The amendment deferred pausing because macOS keys the Accessibility grant to
the code signature, falling back to the cdhash — which changes on every
ad-hoc-signed build, so "grant once" is really "re-grant after every update".
That cost is real and has **not** changed. What changed is the alternative.

Within hours of v0.2.0 reaching real hardware:

- **#282**: the reference AirPods expose no main-element volume at all
  (`volume=UNREADABLE settable=false`). On the release path the headset is
  still the default output, so muting has nothing it can set. That path has
  never worked.
- **Tom's report**: on a claim, audio is audible for about a second before
  suppression begins, because playback starts when he presses play and the
  claim command arrives later.

Muting therefore fails on two of its three paths. The deeper reason is that
**a pause is restorative and a mute is lossy**: pausing gives back exactly
what it took, so arriving late costs nothing, while muting lets audio play on
inaudibly *and* leaves the pre-window second audible anyway. Tom accepted the
re-grant cost explicitly.

## The toggle problem, which is the design

The media key is `play/pause` — one key that starts what is stopped and stops
what is playing. ADR 0022's amendment named this as a reason to avoid the
approach: on the release path, where the gate wants "pause", an already-paused
Mac would start *playing*.

So the key is never fired blind:

- `silence()` fires it only when `AudioPlaybackState` reports something
  actually playing.
- `restore()` fires it only if this gate is what paused.
- A state that cannot be read is "do nothing", never "probably playing".

Four tests cover exactly this, including the release-then-claim sequence where
a second `silence()` would otherwise resume what the first paused.

## Criterion 3 — no grant

`PausingHandoverAudioGate` delegates the **whole window** to a fallback gate,
recording that it did so, so a grant arriving mid-window cannot leave the
fallback's suppression to be undone by the wrong mechanism. There is a test
for that.

The fallback is `MutingHandoverAudioGate` — partial suppression beats none,
and it is what this Mac did before. The grant is re-read on every call rather
than cached at launch, because it can be given or revoked in System Settings
while the app runs.

## The menu item, which is not in the issue but the feature needs it

The grant is read with the **non-prompting** `AXIsProcessTrusted`, so nothing
raises a permissions dialog during a handover — a moment the user did not
initiate and is not looking at. The consequence is that the app never appears
in System Settings' Accessibility list on its own, so without a deliberate way
to ask, pausing would silently never activate and the Mac would sit on the
muting fallback forever.

"Enable Pause During Handover…" is that deliberate moment. Hidden once
granted. It is the one place that may prompt, and it opens the settings pane
afterwards because a grant given to a *previous build* suppresses the prompt
and would otherwise leave a menu item that appears to do nothing.

## Criterion 4 — partially done, and deliberately

`MutingHandoverAudioGate` and `MutedVolumeStore` are **kept**, because the
fallback needs them. The issue said remove them "if nothing else needs them";
something does.

`restoreAfterPreviousRun()` still runs at launch, now against the muting gate
specifically. That matters beyond the fallback: it is the only thing that
heals a `preMuteVolume` record left behind by v0.2.0.

Pausing itself needs no persistence and none was added. A mute that is never
undone is invisible and unrecoverable, which is why ADR 0022's amendment made
durability a requirement of *muting*; a paused player is self-evident and the
user presses play. That the whole recovery apparatus becomes unnecessary is
the clearest sign pausing is the right mechanism.

## Criterion 5 — not done, cannot be done here

ADR 0022's amendment needs updating to record that the divergence is closed.
`docs/adr/**` is human-merge under AGENTS.md, so this PR does not touch it.
**Someone needs to amend it.**

## Not verified on hardware

All of it is unit tests. What needs a human:

1. Grant via the new menu item; confirm the item then disappears.
2. Play something on the Mac, trigger a handover — expect a pause and a resume,
   matching the Pixel, with no audio from the speakers.
3. **Release with the Mac already paused** — the toggle trap. Nothing should
   start playing.
4. Revoke the grant and confirm the Mac falls back to muting rather than
   half-acting.
