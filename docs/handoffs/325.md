# 325 — the registration interval, and a hole in how Android reads fixtures

Two things, the second larger than the issue asked for.

1. `wire.json` now pins the 120s registration interval, the shared constant #317 missed.
2. **Android's fixture tests could pass without running.** Found while demonstrating this issue's own acceptance criterion 4. Fixed here, and it applies to #171's topic fixture as much as to #317's wire fixture.

## 1. The constant

```
defaultRegistrationInterval  = .seconds(120)   RegistrationPublisher.swift:16
DEFAULT_INTERVAL_MS          = 120_000L        RegistrationPublisher.kt:65
```

Two hand-written declarations with nothing asserting they agreed. #317 caught the 8s outcome bound and the 30s heartbeat interval because those files carry comments complaining about the drift risk; `RegistrationPublisher` carries none, so it was missed.

It matters more than the heartbeat interval. The relay's `DEFAULT_NODE_DEPARTURE_TIMEOUT_MS` (300s) is the knee of the **observed** gap distribution measured against this nominal, so a drift between the two adapter declarations leaves that timer tuned against a distribution describing neither device — silently, with the symptom being a healthy node reaped or a departed one lingering.

TypeScript asserts nothing here, deliberately: `packages/protocol` declares no registration interval, and the relay's 300s is module-local in `services/relay-hosted`. Exporting it to satisfy a test would touch the FSL half for no benefit.

## 2. The hole: a fixture edit did not invalidate the Gradle test task

Both adapter fixture tests read `packages/protocol/fixtures/*.json` **at runtime**, by walking up from the source file (Swift) or `user.dir` (Kotlin). That is deliberate and correct — a copy in a platform's test resources is the second source of truth the mechanism exists to prevent.

The cost is that Gradle cannot see those files. They are outside the module, nothing in the test task's input fingerprint changes when one is edited, so the task is reported `UP-TO-DATE` and **skipped** — printing a pass for an assertion that never ran.

This was observed, not theorised. Demonstrating criterion 4:

```
# fixture edited to a deliberately wrong value
$ ./gradlew testDebugUnitTest --offline -q --tests '*WireFixtureTest*'
  tests=22 failures=0        <-- wrong. The test did not run.
```

Swift failed correctly on the same edit. Swift has no equivalent hole because SwiftPM re-runs tests unconditionally.

It only appeared to work when I changed the `--tests` filter between invocations, because that re-fingerprints the task — which is exactly the kind of accident that makes a hole like this survive.

### The fix

`app/build.gradle.kts` declares the fixture directory as a test input:

```kotlin
inputs.dir(rootProject.layout.projectDirectory.dir("../protocol/fixtures"))
    .withPathSensitivity(PathSensitivity.RELATIVE)
    .withPropertyName("sharedProtocolFixtures")
```

One `..`, not two: this resolves against the Gradle root project (`packages/adapter-android`), whereas the tests' own walk-up starts from `user.dir`, which is `packages/adapter-android/app`. Getting that wrong fails loudly at configuration time ("input file was expected to be present"), which is how I caught it.

It tracks the **directory**, not named files, so #171's `topics.json`, #317's `wire.json` and any future fixture are all covered without further edits.

### Why this is the more important half

#317's whole claim was "a typo in one mirror fails that platform's tests instead of shipping". On Android that was **conditionally false** for as long as the fixture was the only thing edited — which is precisely the change a fixture is for. CI happened to be unaffected (a fresh checkout has no Gradle cache, so the task always ran), so this was a local-development hole that would have made a developer trust a pass that had not happened.

## Verification

Criterion 4 demonstrated properly, in three steps, because a single mutation cannot distinguish "caught it" from "ran anyway":

| Step | State | `./gradlew testDebugUnitTest --offline` |
| --- | --- | --- |
| 1 | correct fixture | `BUILD SUCCESSFUL`, task ran |
| 2 | unchanged, run again | `UP-TO-DATE` — caching is live, so the test is real |
| 3 | **only** the fixture edited | `299 tests completed, 1 failed` |

Step 2 matters: without it, step 3 proves nothing, because a task that always re-runs would also fail.

Swift, same edit: `Executed 22 tests, with 1 failure`.

| Suite | Before | After |
| --- | --- | --- |
| `adapter-mac` — `swift test` | 323 | **324**, 0 failures |
| `adapter-android` — `gradlew testDebugUnitTest` | 298 | **299**, 0 failures |
| TypeScript — `turbo lint typecheck test` | 24/24 | **24/24** |

Fixture reverted; the diff carries no trace of the mutation.

## 3. The fixture now warns that 120s is a nominal

`wire.json`'s `constants` comment carries the measured distribution from `relay-service.ts:300` and says explicitly that the hardware does not honour the nominal:

```
registration gaps   Pixel p50 160s / max 2263s   (1.3x / 18.9x)
                    Mac   p50 438s / max 1126s    (3.7x / 9.4x)
silence episodes    p50 128s, p90 940s
```

That measurement previously existed in exactly one place — a comment on the relay's departure timeout, three packages from either `RegistrationPublisher`. Anyone modelling node behaviour from the adapters would reasonably have taken 120s as the cadence and been wrong by 3.7x at the Mac's median.

The note names the Phase 1 simulator specifically, because that is the consumer most likely to get it wrong and the one where getting it wrong is worst: a node model ticking a clean 120s timer makes every timeout scenario pass in the simulator and fail on hardware — the exact failure the simulator exists to prevent.

Note the counter-intuitive direction, called out in the comment: **the Mac is the worse offender at the median.** You would expect the phone's doze to dominate; at p50 it is the Mac's sleep.

## Uncertain / follow-ups

- **The Gradle input covers `packages/protocol/fixtures/` only.** If a future fixture lands elsewhere, it needs its own `inputs.dir`, and the failure mode is silent again. A single conventional location is the cheap protection; there is nothing enforcing one.
- **I have not audited the rest of the tree for the same shape.** Any Gradle task reading a file outside the module at runtime has this hole. The two fixture tests are the ones I know of.
- **`adapter-linux` will be the third declaration of 120s** (#271) and has no conformance test yet — same note as #317.
- The observed distribution is from **one** 9h49m sample, and nothing in it was overnight. The maxima are sample maxima, not bounds; a longer capture will find worse, particularly for a sleeping Mac.
