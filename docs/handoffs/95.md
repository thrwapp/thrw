# HANDOFF: CoreBluetooth connect/disconnect for packages/adapter-mac (#95)

## What was done

First real piece of the Mac adapter: Bluetooth connection management for a
single paired headset, scoped strictly to local device control (no MQTT,
no `NodeInterface`, no trigger detection), mirroring exactly how
`packages/adapter-android`'s equivalent issue (#66) was structured.

- `Sources/AdapterMac/Bluetooth/BluetoothConnectionState.swift` — a
  4-case enum (`disconnected`/`connecting`/`connected`/`disconnecting`),
  the Swift mirror of `adapter-android`'s
  `BluetoothConnectionState.kt`.
- `Sources/AdapterMac/Bluetooth/BluetoothPeripheralGateway.swift` — a
  thin `protocol` (`connect(deviceIdentifier: UUID) async throws`/
  `disconnect(deviceIdentifier: UUID) async throws`) wrapping
  CoreBluetooth's `CBCentralManager`/`CBPeripheral` connect/disconnect
  calls, the same seam pattern `adapter-android`'s
  `BluetoothClassicGateway` uses for `android.bluetooth`.
- `Sources/AdapterMac/Bluetooth/CoreBluetoothPeripheralGateway.swift` —
  the real implementation: a `CBCentralManagerDelegate` subclass bridging
  CoreBluetooth's callback API (`didConnect`/`didFailToConnect`/
  `didDisconnectPeripheral`) to async/await via `CheckedContinuation`.
  Resolves a `deviceIdentifier` via
  `centralManager.retrievePeripherals(withIdentifiers:)` (an
  already-paired peripheral) rather than scanning.
- `Sources/AdapterMac/Bluetooth/BluetoothConnectionManager.swift` — the
  type the issue asked for: an `actor` (Swift structured concurrency —
  actor isolation is the direct equivalent of `adapter-android`'s
  `Mutex`-guarded state) with `connect(deviceIdentifier:)`,
  `disconnect(deviceIdentifier:)`, and `connectionState(deviceIdentifier:)`.
- `Tests/AdapterMacTests/Bluetooth/FakeBluetoothPeripheralGateway.swift` +
  `BluetoothConnectionManagerTests.swift` — 10 tests against a fake
  `BluetoothPeripheralGateway`, one-for-one the same scenarios
  `adapter-android`'s `BluetoothConnectionManagerTest.kt` covers.

## Acceptance criteria, with evidence

**1. Sequential handoff (ADR 0002), `CBCentralManager`/`CBPeripheral`.**
`CoreBluetoothPeripheralGateway.swift` uses only
`CBCentralManager.connect`/`cancelPeripheralConnection` and
`retrievePeripherals(withIdentifiers:)` — no scanning, no dual-connection
or VendorID-spoofing code anywhere in the diff (grepped for
"multipoint"/"spoof"/"VendorID" — no matches).

**2. A type with `connect(deviceIdentifier:)`, `disconnect(deviceIdentifier:)`,
and a state query.** `BluetoothConnectionManager.swift:27` (`connect`),
`:47` (`disconnect`), `:63` (`connectionState`).

**3. Local device control only — no `NodeInterface`
(`register`/`emitEvent`/`onClaim`/`onRelease`).** Grepped the full diff
for those four names (case-sensitive) — no matches outside this sentence
and this file's own prose.

**4. Tests fake the `CBCentralManager`/`CBPeripheral` boundary via a thin
protocol, not CoreBluetooth's own types.**
`FakeBluetoothPeripheralGateway.swift` conforms to
`BluetoothPeripheralGateway` directly; `CoreBluetoothPeripheralGateway`
(the real implementation) is never imported by any test file. Covered:
unknown device reports disconnected, connect while already connected is a
no-op, a failed connect reverts state and rethrows, retry after a failed
connect, disconnect of a connected device, disconnect of an unknown
device is a no-op that never calls the gateway, disconnect of an
already-disconnected device doesn't call the gateway again, a failed
disconnect still leaves state `.disconnected`, and per-identifier
independence — `BluetoothConnectionManagerTests.swift`, all 9 scenario
tests plus the pre-existing `testAdapterNameIsSet`.

**5. Swift structured concurrency (async/await).**
`BluetoothConnectionManager` is an `actor` (`BluetoothConnectionManager.swift:20`);
all three of its methods are `async` (`connect`/`disconnect` also
`throws`). `CoreBluetoothPeripheralGateway`'s real implementation bridges
CoreBluetooth's delegate callbacks to `async throws` via
`withCheckedThrowingContinuation`. `Package.swift`'s
`swift-tools-version` was **not** bumped above the existing 5.10 —
actors and async/await have been available since Swift 5.5, no newer
language feature was needed.

**6. No new dependency beyond Apple's own SDKs.** `import CoreBluetooth`
and `import Foundation` only, both system frameworks. `Package.swift` is
unchanged (still only declares the `AdapterMac` library/test targets, no
new `dependencies:` entries).

## Known gaps / judgment calls

- **`CoreBluetoothPeripheralGateway` (the real gateway) is not
  exercised by any test** — no Bluetooth hardware exists on CI's
  `mac-ipad` runner (`macos-14`, GitHub-hosted), matching AC4's explicit
  instruction not to mock CoreBluetooth's own types. Only
  `BluetoothConnectionManager`'s own state-tracking logic is tested,
  against the fake.
- **CoreBluetooth is BLE-only on macOS; AirPods' actual audio
  connect/disconnect (HFP) goes through the classic Bluetooth /
  IOBluetooth stack, not `CBCentralManager`/`CBPeripheral`.** The issue's
  acceptance criteria explicitly names `CBCentralManager`/`CBPeripheral`
  as the required API, so that's what's implemented here, but this is a
  real architectural gap worth flagging rather than silently building
  around: a later issue exercising this against real AirPods hardware may
  find `CoreBluetoothPeripheralGateway`'s `connect`/`disconnect` don't
  actually change the audio route the way `IOBluetoothDevice`'s
  classic-Bluetooth API would. Not fixed here — the issue's own words are
  followed as given, and this is flagged for whoever picks up the
  hardware-verification follow-up.
- `CoreBluetoothPeripheralGateway.connect`/`disconnect` don't wait for
  `centralManagerDidUpdateState` to report `.poweredOn` before acting —
  if called before Bluetooth is ready, the pending continuation is simply
  never resolved by CoreBluetooth. Documented in
  `centralManagerDidUpdateState`'s own comment rather than guessed at
  with an unrequested retry/queueing mechanism.
