# 277 (decision 1) — relay-side command coalescing

ADR 0020 decision 1 only. Decisions 2 and 3 are untouched and still open on
#277 — decision 2 remains blocked on ADR 0014 being resolved, decision 3
(reconnect jitter) is adapter-side and self-contained.

## What this is, and what it is not

`superseded_by_newer_command` existed before this and is a **different
mechanism**: ADR 0018's sequence gate, running adapter-side, where the node
receives the stale command and discards it by sequence number. Decision 1 is
the relay not sending it at all. The telemetry being present was never
evidence this decision was done, and both are wanted — the sequence gate is
still the backstop for anything coalescing misses, including a command already
in flight over MQTT.

## The window figures, which are the part a reviewer cannot check by reading

`DEFAULT_RELEASE_WINDOW_MS = 3000` (`command-coalescer.ts:80`) and
`DEFAULT_CLAIM_WINDOW_MS = 6000` (`:89`).

Both come from #254's measurement (`docs/handoffs/254.md`), taken from both
adapters' own `command_outcome` reports rather than from two unsynchronised
clocks — which is what made the issue's earlier ~10s figure wrong:

| leg | measured |
| --- | --- |
| Mac release, command → outcome `succeeded` | **~2.2s** |
| Pixel claim, command → outcome `succeeded` | **~4.9s** |

- Release side stays at the ADR's original ~3s, now with evidence rather than
  inheritance: it covers the measured 2.2s.
- Claim side is 6000, not the 3000 the unamended ADR would have given it and
  not 5000. 5000 would sit ~2% above a single measurement, so any device
  slower than the one sample would fall outside its own window. 6000 is ~22%
  headroom over 4.9s and also covers the +5s media re-fire the ADR's amendment
  recorded.

**What I did not verify:** these are one measurement, on one pair of devices,
with no distribution behind it — #254's own handoff says exactly that. I did
not re-measure. The headroom exists because of that, and both windows are
constructor options (`relay-service.ts:390` area, `claimWindowMs` /
`releaseWindowMs`) so a real distribution can replace a judgement without a
code change.

## A steady single trigger pays nothing

Leading-edge dispatch, not trailing. The first command for an idle key
publishes synchronously; only commands arriving while a previous one is still
settling are held (`command-coalescer.ts:187`). A trailing debounce would have
added the window to every ordinary switch, spending ADR 0007's 3.5–4s p95
claim budget to fix a case that happens rarely.

Evidence it is actually free: `command-coalescer.test.ts:80` asserts a lone
submit dispatches immediately **and** schedules no timer at all, and the
entire pre-existing relay-hosted suite passes unchanged apart from the one
expectation discussed below.

## The design changed mid-implementation, and a test is why

**Only claims are ever held. A release always dispatches at once.**
(`command-coalescer.ts:27`, and the `kind === "release"` branch at `:187`.)

This narrows ADR 0020's "coalesces claim/release commands", and it is the most
important thing in this change to review.

I first implemented it symmetrically, as the ADR is written. That fails
relay-hosted's `publishes CLAIM to the first holder, then RELEASE+CLAIM on a
real handoff` test, and the failure is not a test artefact — it is ADR 0002.
Handoff is **sequential**: the winning device cannot take the route until the
losing device lets go. So a held release does not damp a burst, it stalls the
handoff and the claim queued behind it. A switch that ordinarily takes ~4.9s
would have taken ~11s whenever a second device wanted the headset within 6s of
the first getting it — which is an ordinary thing for a person to do.

It is also right on its own terms: a release means the user has moved on, so
executing it late is never what they wanted (#254's handoff makes the same
argument for why a release silences audio and never restores it), and a
release is cheap and idempotent where a claim is the slow, contended operation
whose repeated execution is the thrash the ADR is about.

**This is a deviation from the ADR's letter and is raised on #277 rather than
amended** — `docs/adr/**` is human-merge.

## The hazard that nearly shipped: the re-assert

`relay-service.ts:735` routes the registration re-assert through
`dispatchImmediately` (`command-coalescer.ts:251`), bypassing coalescing
entirely. This is load-bearing, not a convenience.

That command goes to a node that has **restarted and lost its own state**. Run
through `submit`, a claim to a node the relay had recently claimed would be
dropped as `already_in_target_state`, leaving the relay believing the node
holds the route while the node believed it held nothing — a silent desync
introduced by the very change meant to reduce churn.

**Mutation-checked rather than argued.** Replacing `dispatchImmediately` with
`submit` fails two tests: the new
`still re-asserts a claim to a node that restarts inside the window`
(`relay-service.test.ts:763`) and the **pre-existing**
`re-publishes CLAIM to a node that restarts while it is still the holder`
(#173's behaviour). Without the bypass, coalescing would have silently broken
restart recovery.

## Reporting: superseded, never a failure

`command_coalesced` (`relay-service.ts:554`), via an injectable
`onCommandCoalesced` sink (`:390`), with two reasons:

- `superseded_by_newer_command` — a newer command replaced a queued one. Same
  vocabulary as ADR 0019's reason code, for a relay-side decision.
- `already_in_target_state` — the window closed and the coalesced intent
  matched what the node was last told, so there was nothing to send.

**Deliberately not folded into `command_outcome`.** ADR 0019 defines exactly
three terminal outcomes — succeeded, failed, timed_out — reported by the
*node* about a command it received. A coalesced command was never sent, so no
node can report on it; adding a fourth outcome would change an adapter-facing
contract and double-count against the success rate that enum exists to
measure. `relay-service.test.ts:724` asserts the ADR 0019 stream stays empty
while coalescing is happening.

## #236 and #251

- **#236** (holder oscillation): its two characterisation tests pass unchanged,
  as do relay-core's `holder-oscillation.test.ts`. Coalescing does not touch
  arbitration — it only decides when a command may go out — and the reap
  machinery #263 changed is untouched here.
- **#251** (trigger chatter): this damps the relay-side symptom of exactly that
  pattern. A node bounced claim→release→claim inside the window now gets one
  claim instead of three commands. It does not fix the adapter-side chatter and
  is not a substitute for #251's own fix.

## One behaviour change a reviewer should see

`relay-service.test.ts`'s real-broker handoff test now polls 6s rather than 2s
for one assertion: A's re-claim after an A→B→A bounce inside one second is
**held** until the release window closes. That is the coalescing window doing
its job on the exact pattern the ADR describes, so the expectation moved rather
than the behaviour being wrong — but it is a real, user-visible latency change
on bounce-back, up to 3s, and it is the trade the ADR asks for.

## Uncertain

1. **A better trigger than a timer exists, and I did not build it.** ADR 0019's
   `command_outcome` now tells the relay when a claim actually finished. Flushing
   the pending command on the outcome, with the window only as a fallback for a
   node that never reports, would release a held claim at ~2.2s or ~4.9s instead
   of at a fixed 6s. I kept the fixed window because that is what the ADR
   specifies and because gating solely on outcomes would hang forever on a
   silent node. Worth its own decision.
2. **6000 is a judgement on one sample.** Stated above; repeating it because it
   is the number most likely to be wrong.
3. **A relay restart drops pending commands.** `stop()` clears them
   (`command-coalescer.ts:270`) and there is no persistence, so a command held
   when the process dies is simply lost. ADR 0018's reconciliation on
   re-registration is the backstop, and it already is for everything else this
   process holds in memory.
4. **Coalescing is per-node, so a two-node handoff is two independent keys.**
   Correct for dispatch, but it means nothing coordinates the pair: A's release
   and B's claim can be in different states of held/sent. I believe that is fine
   because a release is never held, so the ordering ADR 0002 needs is preserved
   — but it is an invariant resting on the release rule, not on anything
   structural.
