# 225 — ADR 0018 decision 3 on macOS

Decision 3 says an adapter must decide "am I already in the target
state?" from the **audio route**, not from a cached Bluetooth link
state. Android has done that since #191. macOS never did:

```swift
public func connect(deviceIdentifier: UUID) async throws {
    switch states[deviceIdentifier] {
    case .connected, .connecting:
        return                          // no route check
```

The ADR is unusually blunt about why that matters, and it is the reason
this is not a tidy-up:

> Under the Bluetooth-link reading, a Mac that holds a multipoint link
> but is *not* the audio route would consider itself already claimed and
> **silently skip a claim it genuinely needs to execute** — nothing logs
> it, nothing retries it, and the user simply does not get their audio.

This was almost certainly live. #191 measured exactly that state on this
hardware: the Mac reported the AirPods as `Connected` while its default
output was `MacBook Air Speakers` and the phone held the route.

## The fix

`connect` now splits `.connected` from `.connecting`:

- `.connecting` returns immediately, as before. A claim is already in
  flight and re-entering would issue a duplicate — the route is not even
  consulted.
- `.connected` is second-guessed against the real route, and only a
  definite `false` overrides the skip.
- `nil` ("cannot tell") leaves the cached skip alone. Smoothing it into
  `false` would issue a redundant disconnect/reconnect cycle every time
  CoreAudio was momentarily unreadable.

## The seam, and why it is not just an `AudioRouteObserver`

The issue asked for a choice here, so: the route read stays on
`AudioRouteObserver` and is injected, rather than moving onto
`BluetoothPeripheralGateway` the way Android hangs
`isAudioRouteActive` off its gateway.

On macOS these are genuinely two frameworks reading two different
things — CoreAudio's default output device, and IOBluetooth's
connection control. Merging them to match Android's shape would push a
CoreAudio dependency into the Bluetooth gateway for symmetry's sake.

But an `AudioRouteObserver` could not be passed in directly either: it
answers only about the one headset it was built for, while
`BluetoothConnectionManager` is keyed by device identifier. Handing it
over unguarded would have it answering confidently about the wrong
device the moment a second one existed. So there is a small adapter
between the two:

- `DeviceAudioRouteSource` — "does *this device* hold the route?",
  `nil` for "cannot tell", including "I know nothing about that device".
- `HeadsetAudioRouteSource` — one headset's UUID plus its observer, with
  the identity guard as a tested decision rather than a comment.

The composition root builds it, because `AppDelegate` is the only place
that knows both halves: the headset's UUID and its Bluetooth address
(CoreAudio spells a Bluetooth device's UID with its MAC, and that
mapping is one-way — see #191).

## Backwards compatible by construction

`routeSource` is optional and defaults to `nil`, and a manager built
without one behaves exactly as it did before this change. That is not
hypothetical: `AppDelegate` already logs and continues when no headset
address is provisioned, so the route observer is genuinely absent in
that configuration. There is a test for it.

## Verification

- `adapter-mac` 190 tests, green. Clean `swift build`.
- Mutation-tested, all killed:
  - second-guess `.connecting` as well → kills
    `an in-flight connect is not second guessed`;
  - treat `nil` as "route gone" (`!= true`) → kills the unreadable-route
    test, the no-route-source test, *and* the pre-existing
    `connect while already connected is a no-op`;
  - never second-guess (pre-#225 behaviour) → kills the test that names
    the measured multipoint state;
  - drop the identity guard → kills
    `reports no information for any other device`.

### A note on the in-flight test, which was flaky first

Reaching the `.connecting` branch through the public API needs a
genuinely concurrent second call, since the actor serializes everything
else — so `FakeBluetoothPeripheralGateway` gained the ability to hold a
`connect` open.

The first version used `CheckedContinuation` for the handshake and
**deadlocked about half the time**. A continuation only *signals*: if
`connect` reached the signal before the test reached the wait, it
resumed nobody, and both sides waited forever. It passed on the first
run, which is exactly how this kind of bug gets shipped — it hung on
the second.

Latching a boolean alongside the continuation was the first fix, and it
was also wrong: the flag and the continuation are read from two tasks
with no synchronisation, so it narrowed the window rather than closing
it.

Both signals are now `AsyncStream`s, which **buffer**. The handshake
works in either order, with no shared mutable flag. Confirmed over
eight consecutive runs.

## Not verified on hardware

The check that matters is the state that motivates the whole thing:
phone holding the route, Mac's link still `Connected`, Mac's output
`MacBook Air Speakers` — then trigger a claim on the Mac and confirm it
is **executed** rather than skipped. Shares a hardware run with #223 and
with #210's outstanding enforcement check.

## Why it was missed in the first place

`docs/handoffs/191.md` describes decision 3 in platform-neutral language
("Why decision 3 mattered more than it looked") without recording that
only one platform got it. That is the second macOS-only gap found behind
neutral-sounding prose in a single day — #223 is the other, where #161's
fix is also Android-only.

Worth treating "was this done on both platforms?" as a standing question
rather than something a handoff can be trusted to mention.
