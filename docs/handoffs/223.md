# 223 — a failed command no longer makes the Mac deaf

`MacNode.listenForCommands` let a throwing `onClaim`/`onRelease` out of
its `for await` loop. `NodeRuntime` logged it and let the task finish;
nothing resubscribed, and `onReconnected` only re-registers. So **one**
failed claim — a headset that happened to be off, out of range or busy
— cost this Mac every subsequent relay command until the app was
relaunched, while its menu-bar status still said "Connected".

`adapter-android` has had the fix since #161, where the unhandled
version was louder: it took the whole adapter process down on real
hardware and Android restarted it in a loop. macOS fails quietly, which
is most likely why this went unnoticed for so long.

## The fix

A `do`/`catch` around the dispatch, mirroring Android:

- `CancellationError` is **rethrown**. That is the runtime shutting the
  task down (`NodeRuntimeHandle.cancel()`, or app quit), not a Bluetooth
  failure, and catching it would break cancellation — the node would
  keep running after the app asked it to stop.
- Everything else is logged and the loop continues.
- The sequence mark is deliberately **not** recorded for a command that
  threw, so the broker's QoS 1 redelivery is free to retry it (#210).

## How it was found

Writing #210's adapter half. Its retry-on-redelivery test needed two
`listenForCommands` calls on macOS where the Android twin needed one,
and the reason turned out to be a bug rather than a platform
difference. That test is now one call, which is criterion 4.

## Three tests, and why each is a different question

- `a failing command does not tear down the subscription` — a
  **later** command still lands. Deliberately distinct from #210's
  redelivery test, where the *same* command comes back; only a later
  one proves the loop is still iterating.
- `a failing release does not tear down the subscription` — the rule is
  about commands, not about claims.
- `cancellation is not swallowed as a command failure` — the half that
  must keep throwing, via a gateway that throws `CancellationError`
  rather than a Bluetooth error.

### One test lied before it was fixed

The failing-release test was first written as release-then-claim, and
passed immediately — for the wrong reason. With the manager in
`.disconnected`, `disconnect` short-circuits and never reaches the
gateway, so the release never failed at all. It now claims first, and
asserts the release actually reached the gateway before asserting what
came after it. Worth remembering when testing anything behind
`BluetoothConnectionManager`: its early returns make "the command did
nothing" and "the command was never issued" look identical from
outside.

## Incidental refactor

`NodeRuntime`'s `#if canImport(os)` logging shim moved to
`AdapterLog.swift` as `logAdapterError(category:_:)`, because `MacNode`
now needs the same thing. Two hand-rolled copies would drift, and the
failure mode of drift here is a log line that silently stops appearing
— the exact class of problem this issue is about.

## Verification

- `adapter-mac` 190 tests, green. Clean `swift build`, no new warnings.
- Mutation-tested, all killed:
  - rethrow instead of continue (pre-#223 behaviour) → kills all three
    survival tests;
  - remove the `CancellationError` clause → kills the cancellation
    test;
  - record the sequence mark even on failure → kills #210's retry test.

## Not verified on hardware

The real check is: power the headset off, let a claim arrive and fail,
power it back on, and confirm the next claim is acted on **without
relaunching the app**. Shares a hardware run with #225 and with #210's
outstanding enforcement check.

## Pre-existing, not touched

`Tests/AdapterMacTests/Heartbeat/HeartbeatPublisherTests.swift:24-30`
calls `NSLock.lock()` inside an async context, which the compiler warns
"is an error in the Swift 6 language mode". It is on `main` already and
is unrelated to this change, so it is left alone rather than folded in —
but it will have to be fixed before that mode is enabled.
