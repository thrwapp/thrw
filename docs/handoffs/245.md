# Handoff: #245 — the relay logs its outputs, never its inputs

## Why this existed

The relay had four log events, all of them decisions it made:
`holder_change`, `route_drift`, `publish_failed`,
`heartbeat_subscribe_failed`. Nothing recorded what it was *told*.

Over one day of live debugging on the reference Mac/Pixel pair, that gap
blocked diagnosis four separate times. Each time it produced a plausible,
confidently-argued, wrong hypothesis that had to be disproved by hand:

1. "The Mac holds the Bluetooth link and blocks the Pixel" — the link
   observation was real, but it was not the cause.
2. "WhatsApp's false `voip` outranks the Pixel's `media`" — disproved by
   quitting WhatsApp.
3. "`6B5ED1EE` is the Mac" — it was a stale node id; the live one was
   `57678736`, regenerated during a reinstall. This one silently
   invalidated an hour of analysis.
4. "Stale in-memory `voip` state on the Mac" — inconclusive; nothing was
   playing during the window.

None of those four needed cleverness to resolve. They needed one line
saying what each node had reported.

## What landed

Three events, on the injectable-sink shape `onRouteDrift` already used,
so tests assert structured objects rather than scraping stdout:

- **`registration`** — account, node, resource, platform,
  `adapterVersion`, reported `activeEvents`, reported `observedRoutes`,
  holder before/after. The highest-value line: it says what each node is
  claiming, every 120s.
- **`node_event`** — each trigger start/end, with holder before/after.
- **`node_reaped`** — the node dropped by `sweepHeartbeats` and how long
  it had been silent. Emitted *before* the `syncHolder` that follows, so
  a reader sees the cause immediately ahead of the `holder_change` it
  produces.

`displayName` is deliberately omitted — user-chosen, routinely personal,
and #207's open question about `{account}` already being a user
identifier says to add no more identifying content than every existing
line carries.

## Verification

`pnpm turbo test --filter=@thrw/relay-hosted` — 29 tests, 0 failures (25
before). Four new tests: a registration with active triggers; a
registration reporting nothing active (the case that reads identically to
"never registered" in the old logs, and was exactly the unanswerable
question); trigger start/end; and a reap with its silence duration.

## What is NOT done

- **Not deployed or observed in production.** Merging triggers
  `deploy.yml` (this path is one of its three watched paths), after which
  `./scripts/relay-logs.sh relay-service 30m registration` should show one
  line per node per two minutes. Until that is checked, this is green
  tests, not a working diagnostic.
- **No adapter-side logging.** The Mac adapter logs errors only, and
  suppressed triggers are silent on both platforms. If a question turns
  out to be "did the adapter *emit* this at all", this does not answer it
  — that would need #206 / ADR 0019's confirmed outcomes.
- **Does not fix anything.** This is pure observability. #243 and #244
  remain open and are the actual defects.

## What to do with it first

The open question it was built to answer: **why does playing media on the
Pixel not move the holder?** After deploying, play media on the Pixel and
read the `registration` lines from both nodes. The answer will be in the
`activeEvents` each one reports — specifically whether the Mac is claiming
a trigger it should not be, which is what four hypotheses circled without
resolving.

Second: #243 is currently mis-scoped. It names the link-vs-route gap as
the *cause* of the headset not moving, and that was hypothesis 1 above.
The link-vs-route gap is real and worth fixing, but the issue text should
be corrected once these logs say what the real cause is.
