# 290 — a way to tell thrw to leave the headset alone

#287 criterion 2. #289 bounded the reconciliation loop so thrw no longer takes
the headset back every two minutes; it cannot stop the **first** claim, because
from the relay's point of view nothing else is using the headset.

## What landed

"Pause switching on this device", in the macOS menu (⌘P) and the Android
notification. While paused a node:

1. **Emits no triggers** — nothing to win arbitration with, so the relay has no
   reason to claim it.
2. **Ends the triggers it currently has active**, published, so the relay stops
   counting them immediately rather than at the next reconciliation.
3. **Still honours claim and release commands.**

Per-device rather than account-wide: the simpler primitive, no protocol change,
and it matches the reported situation — the phone was the thing grabbing, so
the phone is the thing to silence.

## Three decisions worth the reader's attention

**The pause check runs before the self-cooldown check, not after.**
`manual_claim` and `call` deliberately bypass the cooldown (ADR 0010, #251), so
testing the cooldown first would have let exactly the two loudest triggers
through a pause. Criterion 4 is a test on each platform.

**Pausing ends active triggers rather than only suppressing future ones.** The
relay counts what it was last told. A paused holder that merely stopped
emitting would keep the headset until something else outranked it — precisely
the situation the user is escaping. The flag is set *before* the ends are
published, so a partial failure leaves the node paused rather than half-paused,
and #178's next registration reconciles.

**Paused outranks disconnected in the status.** While paused, whether the relay
is reachable is not why switching stopped. Reporting "Disconnected from relay"
to someone who paused it themselves would send them to debug a connection that
is fine.

## Why not "ignore commands while paused"

Tempting, and wrong. A node that ignores commands leaves the relay believing it
holds a resource it does not — the drift #287 was about, now bounded but still
not worth manufacturing deliberately. Emitting nothing is sufficient: with no
active triggers the relay has no reason to claim this node.

## One store, not two

Both platforms construct a single store instance and hand it to *both* the node
(which reads it on every emit) and the pause control (which writes it). Two
stores over one key would also work, but sharing the instance makes it
structurally impossible for the node's suppression and the UI's label to
disagree — the class of bug #234 was filed for.

## Deliberately not done

- **A timed pause.** More UI, more state, and a guess at a duration. An explicit
  toggle is honest, and criterion 6's status line stops it being forgotten
  silently.
- **Account-wide pause.** Needs a protocol change and a decision about where the
  state lives.
- **Detecting an unmanaged device.** The open half of #287, and a different
  problem.

## Not verified on hardware

Toggling from each UI, confirming the status line changes, confirming a paused
device stops taking the headset while the other keeps working, and confirming
the pause survives a restart.
