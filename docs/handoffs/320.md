# 320 — a virtual clock and an in-memory bus

Step 1 of the build order in `docs/spec/testing-framework.md`, which is
Phase 1 of the v1 plan. **No behaviour change**: this is a seam, so that
the relay's real decision logic can run without a broker and without real
time.

`packages/testkit` was the 5-line placeholder it had been since it was
created, imported by nothing. It is now the thing it was reserved for.

## What landed

- **`packages/relay-core/src/transport.ts`** — `RelayTransport`, exactly
  the four methods `RelayService` calls: `subscribeAllEvents`,
  `subscribeHeartbeat`, `publishCommand`, `publishState`.
- **`packages/relay-core/src/command-sequencer.ts`** — `CommandSequencer`,
  ADR 0018's epoch and per-node counter, extracted from
  `RelayMqttClient`'s private field and private method.
- **`packages/testkit`** — `VirtualClock` (implements relay-core's
  existing `Scheduler`, plus `now()`) and `InMemoryBus` (implements
  `RelayTransport` over that clock, no broker).
- **`services/relay-hosted`** — `RelayService` now depends on
  `RelayTransport`. That is the whole change there: one import and two
  type annotations.

## The stamping trap, and why I did not take either route the design doc names

`RelayMqttClient.publishCommand` stamped ADR 0018's epoch and sequence
number itself, from an epoch generated once per process and an in-memory
counter map. Two transports cannot both do that independently. The design
doc offers two ways out and prefers the first:

> Either move stamping into `RelayService` or have the in-memory transport
> stamp identically; the first is cleaner and must keep
> `packages/relay-core`'s existing tests green.

Both have a problem:

- **Moving it into `RelayService`** orphans `publishCommand`'s stamping
  and the three tests asserting it, which would then cover a path nothing
  used. It also pushes relay-*process* identity into `services/**`, the
  FSL half, for no reason. And it cannot keep relay-core's tests green —
  those tests assert stamping on `publishCommand`, which would no longer
  stamp.
- **Having `InMemoryBus` stamp identically** is a second hand-written
  implementation of one numbering scheme. That is the exact drift shape
  #317 has just spent a PR pinning down elsewhere, and a simulator whose
  sequence numbers behave subtly differently from production would make
  every ADR 0018 test run against it meaningless.

**Extracting `CommandSequencer` has neither problem.** One implementation,
two transports each holding one. `publishCommand`'s signature is
unchanged, relay-core's tests pass **unedited**, and `services/**` changes
by a type name. The parity test asserts the two produce the same sequence
progression and the same payload keys rather than trusting that they do.

## Interface details that mattered

**`Promise<unknown>`, not `Promise<void>`.** Both subscribe methods return
`Promise<ISubscriptionGrant[]>` on `RelayMqttClient`, so its own tests can
confirm the broker granted the QoS asked for. `RelayService` discards both
return values. `Promise<void>` does **not** work — `Promise<T>` is
covariant, so `Promise<ISubscriptionGrant[]>` is not assignable to it, and
adopting it would have forced the real client to throw away a value its
tests use. `Promise<unknown>` accepts both, and no `mqtt` type reaches
`packages/testkit`.

**`publishEvent` is deliberately not on the interface.** Publishing an
event is what a *node* does. Putting it on `RelayTransport` would let a
test drive the relay through a method the relay never calls. The bus has
separate `node*` methods for that, and they are not part of the interface.

**Delivery is scheduled through the clock**, not held in a queue the
scenario drains separately. That is what makes message delivery and the
relay's own timers — coalescing windows, the heartbeat sweep, the 90s
auto-return — interleave in correct time order under one `advance()`.
Zero-delay delivery still goes through the clock rather than inline,
because a real broker round-trip always yields; calling straight through
would create a reentrancy production does not have.

## A licensing constraint on where tests could go

ADR 0003 licenses `services/**` under the FSL and `packages/**` not, so
**`packages/testkit` must not import `RelayService`.** The dependency only
runs one way: a service may use a package, never the reverse.

That split the test work in two:

- `packages/testkit/test/handoff-scenario.test.ts` — the ported scenario
  at the `PriorityEngine` level, the layer available to it.
- `services/relay-hosted/test/transport-parity.test.ts` — `RelayService`
  itself on the bus, and the two-transport parity check. That package is
  the only place in the tree that may import both `RelayMqttClient` and
  `@thrw/testkit`.

## One bug found in my own work, worth recording

The clock's first spin-guard counted **total** firings per `advance` and
threw above 100,000. A legitimate 14-day soak at `RelayService`'s 15s
heartbeat sweep is ~80,600 firings — under the cap, but only just, and a
30-day advance would have thrown falsely. Since a 14-day soak is one of
v1's own exit criteria, the guard would eventually have rejected the thing
the clock exists for.

Rewritten to count firings **at one instant**, resetting whenever time
moves: non-advancing time is the actual symptom of a spin, and the total
is not. `does not mistake a long soak for a spin` pins it at 30 days.

## Uncertain / follow-ups

- **The three `FakeScheduler` copies still exist.** `VirtualClock` is a
  strict superset of all three, but replacing them means editing tests
  that currently pass, and criterion 4 was explicit that relay-core's
  tests stay unedited as evidence the seam was cut in the right place.
  Worth a follow-up; deliberately not bundled here.
- **`InMemoryBus.publishState` records rather than delivers.** Correct
  today — the state topic is retained and read by adapters, and no
  relay-side code subscribes to it. A node model (step 2) will need
  delivery, and `latestState()` is the seam it should read through.
- **The bus does not model QoS, retention or reconnect.** A scenario about
  message loss or a broker restart cannot be written against it yet.
  #182's reconnect case is the obvious one that will want this.
- **`advanceToNextTimer` is used in two tests to avoid naming the
  coalescing window.** That reads as a virtue but hides a weakness: if the
  coalescer scheduled *no* timer, those tests would silently assert
  against whatever else was pending. Step 2 should give the bus a way to
  wait for a specific expected dispatch instead.
- The `zod-to-ts` peer-dependency warning on `pnpm install` is
  pre-existing (it wants TypeScript 4/5, the repo is on 6+) and unrelated.
