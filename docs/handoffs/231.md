# 231 — marketing site: share cards, crawler metadata, shared shell

Picked up locally in Claude Code (issue filed alongside the work for
traceability, not by the agent pipeline).

## What was done

**Sharing metadata.** `content/site/src/layouts/Base.astro` now emits, for
every page that uses it: a meta description, an absolute canonical, the full
`og:*` set (type, site_name, title, description, url, image + width/height/alt),
`twitter:card=summary_large_image` with title/description/image, both
`theme-color`s, and the icon links. `content/site/astro.config.mjs:9` sets
`site: "https://thrw.app"`, which is where the canonical and the absolute
image URL come from — Open Graph consumers reject relative ones.

**The card image.** `content/site/public/og.png` (1200×630) is rendered from
`content/site/assets/og.html` with headless Chromium; likewise
`public/apple-touch-icon.png` from `assets/apple-touch-icon.html`. The HTML
sources are committed and carry their own regeneration command, so the card
is editable rather than an opaque binary. `public/favicon.svg` reuses the
headset geometry from the landing page diagram.

**Crawler files.** `src/pages/robots.txt.ts` and `src/pages/sitemap.xml.ts`
are endpoints rather than files in `public/`, so the origin is read from
`site` instead of being hardcoded a second and third time. The sitemap
enumerates `src/pages/**/*.astro` (minus `404.astro`), so a new page lists
itself.

**Structured data.** The FAQ is one array in `src/pages/index.astro:22-49`
that generates both the rendered `<details>` markup and `FAQPage` JSON-LD, so
the two cannot drift. The markup uses `set:html` so the rendered text stays
byte-identical to the hand-written markup it replaced — an expression would
have escaped every apostrophe to `&#39;`.

**Shared shell.** Tokens, glow, header and footer moved into `Base.astro`.
Both pages had carried their own copy and had already drifted: `privacy.astro`
made the wordmark a link home with a focus ring, `index.astro` left it an
inert `<p>`. Both now get the link, the same footer (with a Source link) and
a `prefers-reduced-motion` block.

**Accessibility.** The diagram `<section>` was `aria-hidden="true"` around an
`<svg role="img" aria-label="…">`, so the label reached nobody — the section
is exposed now. The waitlist message is tied to its input with
`aria-describedby`, the input gets `aria-invalid` on failure, and
`checkValidity()` catches an empty or malformed address before the round-trip
to `/waitlist` instead of after it. The Pages Function remains the authority
on what Buttondown will accept.

**Open-source section** (`src/pages/index.astro:139-147`) — MIT `packages/`,
source-available `services/`, and ADR 0005's build-time relay configuration,
each checked against the repo rather than asserted. `privacy.astro` now links
the word "public" in its self-hosting paragraph to the repo.

## Two things found live on the deployed site, and fixed here

1. **`/privacy` 308-redirects to `/privacy/`.** Confirmed with
   `curl -sI https://thrw.app/privacy` → `308`, `…/privacy/` → `200`. A
   canonical naming the redirecting form points at the wrong URL, so `path`
   carries a trailing slash on sub-pages and the sitemap emits the same.
2. **Unknown paths were soft-200s.** `https://thrw.app/definitely-not-a-page`
   returned `200 text/html`, not a 404 — Cloudflare Pages was falling back to
   the landing page because the build had no `404.html`, making every typo'd
   URL an indexable duplicate of the homepage. `src/pages/404.astro` fixes
   this; it is `noindex` and deliberately carries no canonical, since it is
   served at whatever path was mistyped.

## What is *not* verified

- **No scraper has seen this.** The card, canonical and JSON-LD are asserted
  against the built HTML only. Facebook's sharing debugger, X's card
  validator, Slack unfurling and Google's Rich Results Test can only be run
  once this is deployed — worth doing on the first `deploy-site` run after
  merge.
- **The 404 status code is Cloudflare behaviour, not something the build can
  prove.** Pages serves `dist/404.html` with a real 404; the test only asserts
  the file is built with the right contents. Re-check
  `curl -sI https://thrw.app/definitely-not-a-page` after deploy.
- **The PNGs were rendered on this machine** with the Playwright-cached
  `chrome-headless-shell` and the macOS system font stack. Regenerating on
  another OS will shift the text rendering slightly. That is fine — it is a
  picture, not a layout — but it means the files are not byte-reproducible.
- **`site` is hardcoded to `https://thrw.app`.** If the Pages custom domain
  ever changes, the canonical, card URLs, `robots.txt` and sitemap all move
  with that one line, but nothing warns you if it drifts from reality.
