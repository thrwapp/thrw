# #167: self-cooldown (ADR 0010 point 1)

## What was done

After thrw initiates a claim or release, each adapter suppresses its own
trigger reporting for ~3s, so it doesn't misread the side effects of its
own action as a new trigger. Implemented in both adapters with matching
behaviour and cross-referencing comments.

## Why it became necessary

Nothing needed this while the only triggers were `call` and `voip`:
telephony state and notification activity are unaffected by thrw's own
Bluetooth actions. The media triggers (#165/#166) break that:

- thrw disconnects the headset to hand it over, so
- audio on that device stops (macOS pauses playback when the output
  device disappears), so
- the media monitor observes "media ended", and
- thrw reports an `event_end` caused entirely by its own action.

## Acceptance criteria

1. **Bounded suppression after claim/release** — `SelfCooldown` armed in
   `onClaim`/`onRelease`, checked in `emitEvent`/`endEvent`. 3s per ADR
   0010.
2. **Applies to trigger observation, not relay commands.** A CLAIM
   arriving inside the window is still honoured — the cooldown exists to
   stop thrw talking to itself, not to make it deaf. Explicitly tested on
   both platforms (`a relay command inside the window is still honoured`
   / `testARelayCommandInsideTheWindowIsStillHonoured`).
3. **Both adapters**, with the window constant documented on each side as
   needing to change together.
4. **Testable without wall-clock waits** — injectable clock, the same
   approach `PriorityEngine` and `HeartbeatPublisher` already use.
5. **Tests**: 6 unit tests per platform on the window itself (inactive
   before arming, active on arming, just inside, just outside, re-arming
   extends, the documented default), plus 3 behavioural tests per
   platform on the node (suppressed inside, reported outside, relay
   command still honoured). **Mutation-checked on both**: forcing "never
   suppress" fails the suite on each.
6. **What it cannot do** — documented on both types, and restated below
   because it is the real limitation.

## The limitation, stated plainly

A time window is a heuristic, not a causal link. Inside the window this
**cannot distinguish** *"audio stopped because we disconnected the
headset"* from *"audio stopped because the user pressed pause at that
exact moment"*. Both are suppressed.

The consequence: a genuine user action landing within ~3s of a claim or
release is silently dropped, and the relay briefly believes a trigger is
still active when it isn't. It corrects on the next real state change.
That is the trade ADR 0010 chose; it is worth knowing rather than
discovering.

## Known gaps / judgment calls

- **Armed even when the Bluetooth call throws.** `onRelease` arms in a
  `finally`/`defer`: the headset may well have gone anyway, and a failed
  release is exactly when a spurious self-triggered event is most likely.
- **This is ADR 0010 point 1 only.** Points 2-5 (manual-override
  detection, scope limitation, known-conflict detection, app-priority
  allowlist) are separate concerns and deliberately untouched.
- **Not a connection state.** Per ADR 0013 this is adapter-local
  bookkeeping layered around `onClaim`/`onRelease`; nothing in the frozen
  state machine changes.
- **Not verified on real hardware.** The unit tests cover the logic and
  both were mutation-checked, but no end-to-end run has exercised the
  cooldown during an actual handoff — and the failure mode it prevents
  (oscillation) only appears with the media triggers also live. That
  combined test is the thing still outstanding before calling the
  experiment "seamless".
- **The window is shared across trigger kinds.** A claim suppresses
  *all* trigger reporting for 3s, not just media. That is what ADR 0010
  specifies, but it means a genuine incoming call within 3s of a handoff
  would also be suppressed. Rule 1 is the highest-priority trigger, so
  this is the most costly instance of the limitation above and the
  likeliest reason to revisit the design.
