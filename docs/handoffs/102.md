# HANDOFF: provisioning/settings screen + runtime permissions for packages/adapter-android (#102)

## What was done

Before this PR `packages/adapter-android` had no `Activity` at all, which
meant two things #96's own handoff already flagged as its biggest gaps:
`AdapterProvisioning`'s two `SharedPreferences` keys had no writer (so
`AdapterForegroundService` correctly `stopSelf()`d on every boot), and the
three runtime-dangerous permissions the manifest declares were never
requested. This adds the launcher screen that closes both.

New/changed files:

- `identity/AdapterProvisioning.kt` — added `setAccountId`/`setHeadsetAddress`
  (`:41`, `:43`) against the pre-existing `PREFS_NAME`/`KEY_ACCOUNT_ID`/
  `KEY_HEADSET_ADDRESS` constants (`:33-35`, unchanged — no new keys). The
  getters and setters each gained an `internal` overload taking a
  `SharedPreferences` directly (`:53-63`), with the public `Context`
  overloads delegating to them; that's purely so the read/write logic is
  reachable from unit tests (a `Context` is all-nulls under
  `isReturnDefaultValues = true`, but `SharedPreferences` is a plain
  interface a fake can implement honestly). Also rewrote the class kdoc,
  which claimed there was no UI writing these values.
- `identity/ProvisioningInput.kt` — **new**, pure Kotlin (no `android.*`
  imports): validates/normalizes the two typed fields and returns a
  `FieldResult.Valid(normalizedValue)` / `FieldResult.Invalid(FieldError)`.
  Account ids are restricted to `[A-Za-z0-9._-]{1,64}` — see "Judgment
  calls" for why that set and not a guessed account-id format. Headset
  addresses are trimmed, upper-cased and matched against
  `^[0-9A-F]{2}(:[0-9A-F]{2}){5}$`.
- `ui/AdapterPermissions.kt` — **new**, the three manifest permissions plus
  `requestable(sdkInt)` / `missing(sdkInt, isGranted)`. Pure enough to test:
  `POST_NOTIFICATIONS` is filtered out below API 33, since `minSdk` is 31
  and requesting a permission the platform doesn't know comes back "denied"
  for something the user was never asked about.
- `ui/ProvisioningActivity.kt` — **new**, the launcher `Activity`. Extends
  `androidx.activity.ComponentActivity` (`:49`), registers a
  `ActivityResultContracts.RequestMultiplePermissions` launcher (`:55`),
  pre-fills both fields from `AdapterProvisioning`, validates on save and
  writes through the new setters (`:98-99`), and shows a live
  granted/not-granted status line that recomputes in `onResume`.
- `res/layout/activity_provisioning.xml` — **new**, plain platform widgets
  (`ScrollView` > `LinearLayout` > labels/`EditText`s/`Button`s).
- `res/values/strings.xml` — the screen's labels, hints and error messages.
- `AndroidManifest.xml` — declares the activity with the `MAIN`/`LAUNCHER`
  intent filter and `@android:style/Theme.DeviceDefault.DayNight`.
- `app/build.gradle.kts` — one new dependency, `androidx.activity:activity:1.9.3`.
- `gradle.properties` — **new**; AGP refuses to build with androidx
  artifacts on the classpath unless `android.useAndroidX=true`. This module
  had no `gradle.properties` at all before.
- Tests: `identity/ProvisioningInputTest.kt` (7),
  `identity/AdapterProvisioningTest.kt` (4) plus its
  `identity/FakeSharedPreferences.kt` fake, `ui/AdapterPermissionsTest.kt` (4).

`AdapterForegroundService` is untouched — its null-check/`stopSelf()`
provisioning logic behaved correctly and I found no bug in it.

## Acceptance criteria, with evidence

**1. Settings/provisioning `Activity` with two text fields and a save
action writing via new `AdapterProvisioning` setters, reusing its existing
keys.** `ui/ProvisioningActivity.kt:49` is the activity;
`res/layout/activity_provisioning.xml:33,49` are the two `EditText`s
(`@id/account_id`, `@id/headset_address`) and `:58` the save `Button`.
`ProvisioningActivity.kt:87-107` (`save()`) validates both, sets a
field-level `error` on each invalid one, and on success calls
`AdapterProvisioning.setAccountId`/`setHeadsetAddress` (`:98-99`). Those
setters (`AdapterProvisioning.kt:41,43` → `:57-63`) write
`KEY_ACCOUNT_ID`/`KEY_HEADSET_ADDRESS` in `PREFS_NAME`
(`AdapterProvisioning.kt:33-35`) — the same three constants
`AdapterForegroundService.kt:62-63` reads through, unchanged and not
renamed.

**2. The three runtime-dangerous permissions requested via the platform's
`RequestMultiplePermissions` contract.**
`ProvisioningActivity.kt:54-60` registers
`ActivityResultContracts.RequestMultiplePermissions()`; `:109-119`
(`requestMissingPermissions()`, wired to the "Grant permissions" button at
`:76`) launches it with whatever `AdapterPermissions.missing(...)` returns.
The permission set is `AdapterPermissions.kt:22,29,35` —
`Manifest.permission.BLUETOOTH_CONNECT`, `READ_PHONE_STATE`,
`POST_NOTIFICATIONS`, i.e. exactly the three dangerous permissions declared
at `AndroidManifest.xml:11,15,18`. No hand-written rationale dialog: the
only UI is a status line (`:121-128`) reporting what's still ungranted.

**3. Launcher activity, wired correctly.** `AndroidManifest.xml:39-48`.
Confirming the issue's premise with a correction: there was no
`MAIN`/`LAUNCHER` intent filter anywhere in the manifest before this PR
(`git show HEAD:packages/adapter-android/app/src/main/AndroidManifest.xml`
contains neither string), so nothing was "detached" — the filter is added
here along with the activity. Verified in the *merged* manifest AGP
produced during the test run, not just the source:
`app/build/intermediates/merged_manifest/debug/processDebugMainManifest/AndroidManifest.xml:64-72`
shows `com.thrw.adapter.android.ui.ProvisioningActivity` with
`android.intent.action.MAIN` + `android.intent.category.LAUNCHER`.

**4. Don't start `AdapterForegroundService` on save.** Not started —
`grep -n "startForegroundService\|startService" ui/ProvisioningActivity.kt`
is empty; `BootCompletedReceiver.kt:21` remains the only start path in the
codebase. Documented both in `ProvisioningActivity`'s kdoc (`:32-40`) and
in the user-visible save confirmation, which says the adapter starts
watching after the next restart (`strings.xml`, `provisioning_saved`)
rather than implying it's live now. See "Judgment calls" for the trade-off
I took and how to reverse it.

**5. Testable logic unit tested.** `ProvisioningInputTest.kt` (7 tests)
covers trimming, blank rejection, MQTT-hostile characters (`/`, `+`, `#`,
space, non-ASCII), the 64-char boundary, lowercase-MAC normalization and
seven malformed-address shapes. `AdapterProvisioningTest.kt` (4 tests)
covers the setters round-tripping through the keys the *getters*
`AdapterForegroundService` calls read — so a setter writing the wrong key
fails the test — plus one-field-at-a-time writes and the explicit
no-validation-in-the-setter contract. `AdapterPermissionsTest.kt` (4 tests)
covers the API-33 `POST_NOTIFICATIONS` gate and `missing()`. What is *not*
covered is stated in "Not covered by tests" below.

**6. No new dependency beyond androidx.activity/androidx.core.** Exactly
one added: `androidx.activity:activity:1.9.3`
(`app/build.gradle.kts:77-85`), needed for `ComponentActivity` +
`registerForActivityResult` — the framework `Activity` only has the
deprecated `onRequestPermissionsResult` callback. No AppCompat, no
Material, no ConstraintLayout, no Robolectric. `androidx.core` comes along
transitively but nothing imports it (permission checks use the
framework's own `Context.checkSelfPermission`, `ProvisioningActivity.kt:130`).

## Not covered by tests

Matching how #96's handoff treated `AdapterForegroundService` (#98's
handoff is referenced by the issue but doesn't exist in this repo — the
only handoffs on `main` are 66-70, 80, 95, 96):

- **`ProvisioningActivity` itself is not unit tested.** It extends a real
  framework/androidx `Activity`; under this module's stubbed `android.jar`
  (`isReturnDefaultValues = true`) `setContentView`/`findViewById`/
  `getString` return nulls and defaults, so any "test" of it would exercise
  the stubs, not the screen. Robolectric or instrumentation would be a new
  dependency this issue explicitly rules out. Everything in the activity is
  therefore deliberately thin glue over `ProvisioningInput`,
  `AdapterPermissions` and `AdapterProvisioning`, which *are* tested.
- **The real permission-request flow is not tested** — the system dialog,
  the "don't ask again" auto-deny path, and what the status line shows
  afterwards all need a device/emulator. Only the pure decision of *which*
  permissions to ask for is covered.
- **The `Context` overloads of `AdapterProvisioning`** (the
  `getSharedPreferences(PREFS_NAME, MODE_PRIVATE)` hop) are untested for
  the same reason; the tests go through the `SharedPreferences` overloads
  they delegate to. That means the `PREFS_NAME` string itself is asserted
  by nothing — it's unchanged from #96, but a typo there would not be
  caught by this suite.
- **Nothing here has been run on a real device or emulator.** The layout's
  appearance, the `Theme.DeviceDefault.DayNight` choice, edge-to-edge
  insets under `targetSdk 35`, and whether the screen actually appears in
  the launcher are all unverified beyond "the manifest merges and the
  resources link".

## Judgment calls / known gaps

- **Not starting the service on save** (criterion 4 allowed either, with
  documentation). I kept `BootCompletedReceiver` as the single start path,
  so there's one answer to "what started this service". The honest cost:
  a user who provisions the app gets nothing until the next reboot, which
  is poor. I chose the issue's stated default over my own preference here
  because the trade-off is a product decision, not a technical one; the
  reversal is one `startForegroundService(Intent(this,
  AdapterForegroundService::class.java))` call in `save()`, and the
  `provisioning_saved` string would need rewording with it.
- **Account-id validation is topic-safety only, not a format check.**
  `services/licensing` — which will actually mint account ids — isn't
  built, and nothing in this repo defines their shape, so inventing e.g. a
  UUID or `acct_` prefix requirement would risk rejecting real ids later.
  The rule only enforces what the MQTT layer genuinely requires: the value
  is interpolated straight into `thrw/{account}/...`
  (`protocol/Topics.kt:15-21`), so `/`, the `+`/`#` wildcards, whitespace
  and non-ASCII are rejected. The 64-character cap is arbitrary-but-sane
  and is the one bit of this a future licensing format could plausibly
  collide with.
- **The headset address is typed in, not picked from a list of bonded
  devices.** A bonded-device picker needs `BluetoothAdapter.bondedDevices`,
  i.e. a granted `BLUETOOTH_CONNECT` before the field can render, and pulls
  real Bluetooth calls into the screen. Out of scope here; the hint shows
  the expected format and validation catches typos.
- **`assembleDebug` fails on a pre-existing packaging conflict, unrelated
  to this PR.** `:app:mergeDebugJavaResource` fails with "6 files found
  with path 'META-INF/INDEX.LIST'" from six netty jars (transitive
  dependencies of `hivemq-mqtt-client`). I confirmed this is pre-existing
  by running `assembleDebug` in a clean `git worktree` at `HEAD`
  (3d3462f, before any of my changes) — same failure. CI only runs
  `./gradlew test`, which passes, so this doesn't block anything here, but
  it does mean **no installable APK can currently be built**, which is
  awkward for a PR whose deliverable is a screen. Not fixed: it's a
  packaging-configuration change (`android { packaging { resources.excludes
  += "META-INF/INDEX.LIST" } }`) unrelated to #102's scope, and worth its
  own issue.
- **`android.useAndroidX=true`** now applies module-wide via the new
  `gradle.properties`. That's the standard AGP default for any modern
  module, but it is a build-level change beyond the screen itself, so
  flagging it explicitly.
- **`ProvisioningInput` returning an enum rather than string-resource
  ids** keeps it `android.*`-free and therefore testable; the cost is a
  `when` mapping in the activity (`ProvisioningActivity.kt:133-138`) that
  has to be kept in step with the enum — the compiler enforces
  exhaustiveness, so a new case can't be silently forgotten.
