# HANDOFF: provisioning/settings screen + runtime permissions for packages/adapter-android (#102)

## What was done

`packages/adapter-android` now has a launcher `Activity`. Before this it
had none at all — no `Activity` class anywhere in the module, and (worth
correcting against #102's own wording) **no `MAIN`/`LAUNCHER` intent filter
in `AndroidManifest.xml` either**. The issue says the filter "currently
isn't attached to anything"; in fact it didn't exist, so criterion 3 meant
adding both the activity and the filter, not re-pointing an orphaned one.
Verified by reading the pre-change manifest (its `<application>` block held
exactly two `<service>`s and one `<receiver>`).

- `identity/ProvisioningInput.kt` — new. Pure-Kotlin validation and
  normalization for the two typed-in values, plus the `ProvisioningField`
  (`Valid`/`Invalid`) and `ProvisioningProblem` types it returns. No
  `android.*` imports, so it's unit-testable — the same seam split as
  `NodeRuntime` vs `AdapterForegroundService` in #96.
- `identity/AdapterProvisioning.kt` — added setters (`setAccountId`,
  `setHeadsetAddress`, and `save` for both keys in one commit) behind a new
  `AdapterProvisioning.Store` seam, with the real `SharedPreferences`-backed
  implementation as a private nested class. Existing getters kept their
  behaviour and keys unchanged; the stale kdoc ("no pairing/settings UI
  anywhere in this codebase") was rewritten.
- `ui/ProvisioningActivity.kt` — new. `ComponentActivity` with two fields, a
  save action, a permission-status line, and a "grant permissions" button.
- `res/layout/activity_provisioning.xml`, `res/values/strings.xml` — new
  layout and its strings. Plain platform views (`ScrollView`/`LinearLayout`/
  `EditText`/`Button`/`TextView`) — no Compose, no Material, no
  ConstraintLayout.
- `app/src/main/AndroidManifest.xml` — declares the activity with
  `MAIN`/`LAUNCHER`, `exported="true"`, and `@android:style/Theme.DeviceDefault.DayNight`.
- `app/build.gradle.kts` — added `androidx.activity:activity:1.9.3` and (see
  "Pre-existing bug found" below) a `packaging.resources.excludes` block.
- `gradle.properties` — new file, `android.useAndroidX=true`. AGP fails the
  build outright (`checkDebugAarMetadata`) with any androidx artifact on the
  classpath without it; this module had no `gradle.properties` before.
- Tests: `identity/ProvisioningInputTest.kt` (10 tests),
  `identity/AdapterProvisioningTest.kt` (6 tests).

## Acceptance criteria, with evidence

**1. Provisioning activity with two fields and a save action that writes via
new `AdapterProvisioning` setters, reusing its existing keys.**
`ui/ProvisioningActivity.kt:44` is the activity; `:64` inflates the layout
whose two fields are `activity_provisioning.xml`'s `@+id/account_id` and
`@+id/headset_address`; `:77` wires the save button to `save()` (`:95`),
which validates then calls `AdapterProvisioning.save` at `:109`. The new
setters are `AdapterProvisioning.kt:57` (`setAccountId`), `:59`
(`setHeadsetAddress`) and `:77` (`save`, both keys). They write through the
pre-existing constants only — `PREFS_NAME`/`KEY_ACCOUNT_ID`/
`KEY_HEADSET_ADDRESS` at `AdapterProvisioning.kt:27-29`, unchanged, used at
`:63`, `:67`, `:83-84` and read by the same file's `SharedPreferencesStore`
(`:102-104`). `AdapterProvisioningTest.kt:88` asserts the literal strings
`account_id`/`headset_address` land in the store, so a rename that broke
`AdapterForegroundService`'s reads fails a test.

**2. The three dangerous permissions are requested via the platform's
`RequestMultiplePermissions` flow.** `ProvisioningActivity.kt:58` —
`registerForActivityResult(ActivityResultContracts.RequestMultiplePermissions())`.
`:164-169` builds the requested set: `BLUETOOTH_CONNECT` (`:165`),
`READ_PHONE_STATE` (`:166`), `POST_NOTIFICATIONS` (`:168`, guarded by
`SDK_INT >= TIRAMISU` — it doesn't exist below API 33 and this module's
`minSdk` is 31, where notifications are install-time granted). `:151-154`
filters to only the not-yet-granted ones via `checkSelfPermission`; `:130`
launches the request, both from the button (`:78`) and once automatically on
first creation (`:83`, `savedInstanceState == null` so rotation doesn't
re-ask). No hand-written rationale dialog exists anywhere in the diff —
`:139-149` only renders the resulting status text.

**3. It is the launcher activity.** `AndroidManifest.xml:42-51`: the
`<activity android:name=".ui.ProvisioningActivity">` with `MAIN` (`:48`) and
`LAUNCHER` (`:49`). `exported="true"` is required — it's the system launcher
that starts it, and API 31+ rejects an unexported activity with an
intent-filter at install time. Confirmed the filter did not previously exist
(see "What was done" above).

**4. Doesn't start `AdapterForegroundService`.** Grep the diff: no
`startForegroundService`/`startService`/`AdapterForegroundService` reference
in `ui/`. I kept #102's default rather than taking the judgment call it
offers, and made the consequence visible in the UI instead:
`R.string.provisioning_restart_note` ("Restart the device to start the
adapter with these settings") is rendered under the save button
(`activity_provisioning.xml`). Reasoning, so the next person can reverse it
cheaply: `BootCompletedReceiver` stays the single start path, the service
re-reads both keys from `SharedPreferences` on *every* `onStartCommand`
(`AdapterForegroundService.kt:62-63`, untouched), and the service would
immediately `stopSelf()` anyway if started before the permissions were
granted — so an auto-start on save would frequently be a start that dies.
The real cost is the reboot, which is a genuinely bad first-run experience;
see "Known gaps" for the follow-up.

**5. Testable logic is unit tested.** `ProvisioningInputTest.kt` — 10 tests:
plain account id accepted, whitespace trimmed, blank distinguished from
invalid, topic separators and MQTT wildcards rejected (`:43`, the one that
matters most — the account id is interpolated into every topic, and a `+`/`#`
in a *subscribe* would cross account boundaries), inner whitespace/non-ASCII
rejected, the length ceiling on both sides, well-formed addresses accepted,
lower-case addresses normalized to upper case (`:94`), blank address, and 7
malformed address shapes. `AdapterProvisioningTest.kt` — 6 tests against an
in-memory fake `Store`: unprovisioned reads as null, each setter round-trips
via its own key, `save` writes both keys in exactly one commit (`:55`),
re-saving replaces, the persisted keys are the service's keys, and the
validate-then-persist path end to end.

**Not covered, plainly:** `ProvisioningActivity` itself and the real
permission dialog. Both need Robolectric or instrumentation, and this module
has neither (`app/build.gradle.kts`'s `testOptions.unitTests.isReturnDefaultValues`
comment already spells out why Robolectric wasn't justified). So untested
here: view inflation and `findViewById` wiring, the `EditText.error`
rendering, the launcher registration, whether the system actually shows the
permission dialog, and the `SharedPreferences`-backed `Store` implementation
(the stubbed framework class returns default values in unit tests, so only
the fake-backed logic is exercised). This is the same split #96 applied to
`AdapterForegroundService` and the `bluetooth`/`triggers` seams: interface
half tested, framework half not.

**6. No new dependency beyond androidx.activity/core.**
`app/build.gradle.kts` adds exactly one coordinate:
`androidx.activity:activity:1.9.3` — the plain artifact, not `-ktx` or
`-compose`, since the screen is XML + platform views. `androidx.core`,
`lifecycle`, `savedstate`, `collection`, `profileinstaller` and `tracing`
arrive transitively as `ComponentActivity`'s own dependencies (full list in
the `checkDebugAarMetadata` output I hit before adding
`android.useAndroidX=true`), not as separate choices.

## Pre-existing bug found (fixed, and outside #102's scope)

`./gradlew build` — this module's own `pnpm build` script — failed before
this issue's changes, in `mergeDebugJavaResource`: *"6 files found with path
'META-INF/INDEX.LIST'"*, one from each `io.netty` jar that
`hivemq-mqtt-client` pulls in. **Confirmed pre-existing** by stashing every
change in this branch and re-running `pnpm turbo build --filter=@thrw/adapter-android --force`
on the otherwise-clean tree: same failure, same task. CI's `android` job only
runs `./gradlew test` (`.github/workflows/ci.yml:172-174`), which never
packages an APK, which is why it went unnoticed since #96.

Fixed in `app/build.gradle.kts`'s new `packaging { resources { excludes … } }`
block (`META-INF/INDEX.LIST`, `META-INF/io.netty.versions.properties`,
`META-INF/DEPENDENCIES` — JAR index/build-metadata files with no meaning
inside an APK). I fixed it rather than only reporting it because #102's whole
point is a screen a human uses on a real device, and until this was fixed the
module could not produce an installable APK at all. Flagging it explicitly
since it's a build-configuration change no acceptance criterion asked for; if
you'd rather it landed as its own PR, it's a self-contained 8-line block.

## Known gaps / judgment calls

- **A freshly provisioned device needs a reboot** before the adapter runs
  (criterion 4, above). The obvious follow-up is either an explicit "start
  adapter now" action on this screen or an auto-start once both provisioning
  and all three permissions are in place — I deliberately didn't invent
  either, since the criterion's default was "don't start it".
- **Account-id format is a guess, by necessity.** Nothing authoritative
  defines it: `services/licensing` (which will eventually issue account ids)
  isn't built, and `config/adapter.properties`'s `licensing.url` is still
  marked unused. So `ProvisioningInput.kt:65` accepts
  `[A-Za-z0-9._:-]{1,128}` — derived from what the value is *used for*
  (interpolated into the frozen topic structure, ADR 0001, and used as the
  broker's ACL key), not from a spec. If licensing later issues ids in some
  other shape (e.g. containing `/`), this validation is what needs relaxing,
  and `ProvisioningInputTest` is where that decision should be re-recorded.
- **Bluetooth address entry is typed by hand, not picked from paired
  devices.** A picker would need `BluetoothAdapter.getBondedDevices()` (and
  so `BLUETOOTH_CONNECT` granted before the field is usable), which is a
  bigger screen than #102 asks for. The upper-casing in
  `ProvisioningInput.headsetAddress` is the load-bearing part:
  `BluetoothAdapter.getRemoteDevice` rejects lower-case hex, so without it a
  reasonable-looking entry would persist fine and then throw inside the
  foreground service where no UI could report it.
- **No validation that the entered address is actually a bonded device.**
  Format only. `AndroidBluetoothClassicGateway`'s kdoc already notes pairing
  is a separate, out-of-scope flow.
- **`NotificationListenerService` access is still not requested here.** It
  has no runtime-permission dialog at all — it's a Settings-only grant — so
  `VoipTriggerMonitor`'s notification source stays dark until the user
  enables it manually. #102's criteria name only the three dangerous
  permissions, so this screen doesn't deep-link into that Settings page; it's
  the natural next addition to it.
- **No app icon.** Lint's pre-existing `MissingApplicationIcon` warning now
  has a visible consequence: the launcher entry this PR creates shows the
  platform's default icon. Adding a real icon is design work, not something
  to guess at here.
- **`AdapterProvisioning`'s getters were left exactly as they were**, so a
  blank string written by something other than this screen (e.g. `adb shell`)
  would still pass `AdapterForegroundService`'s null-check and produce a
  malformed topic. Touching that check was explicitly out of scope for #102
  and it isn't reachable through the new UI, so it's flagged, not changed.
- **`local.properties`** was created locally (gitignored, as before) pointing
  at this runner's Android SDK — not part of the diff.
