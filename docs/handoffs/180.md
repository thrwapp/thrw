# 180 — deploy.yml could be broken permanently by one manual deploy

## What was wrong

`deploy.yml` uploaded two files to **fixed paths under `/tmp`** on the
relay VM:

    /tmp/relay-redeploy.sh
    /tmp/Caddyfile

`/tmp` is sticky (`drwxrwxrwt`), so only the owner may overwrite a file
there. A single manual deploy created both owned by a human, after which
**every** CI deploy — running as `runner` — failed:

    /usr/bin/scp: dest open "/tmp/relay-redeploy.sh": Permission denied
    ERROR: (gcloud.compute.scp) [/usr/bin/scp] exited with return code [1].

The failure was permanent: nothing in the workflow could recover from it,
and it needed a human to delete the files by hand. It also failed **one
file at a time**, so clearing the first just moved the error to the
second.

It ran that way for two days. Merged, CI-green fixes sat undeployed
while the VM kept serving the image from 2026-09-18, and nothing
surfaced it — it was found only by going to look at why a merged fix was
not live.

## The fix

Both files are now uploaded to the **SSH user's home directory**, which
is per-user and always writable by whoever is connecting. CI and a human
deploying by hand can no longer collide, because they no longer write to
the same place.

`relay-redeploy.sh` resolves the Caddyfile **relative to its own
location** rather than a fixed path:

```bash
SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
cp "$SCRIPT_DIR/Caddyfile" "$CADDYFILE_DIR/Caddyfile"
```

That indirection is the point, not a nicety — it is what lets the upload
location change without the script caring, and it keeps the two files
together by construction. `BASH_SOURCE` resolves correctly under `sudo`
because the invoking shell expands `~` before `sudo` runs.

## Second half: a green deploy did not prove anything was deployed

The existing health check asks the relay whether it is up, which it
answers identically whether or not the deploy changed anything. A roll
that silently failed to replace the container would still report success
— the same failure shape as the bug above, and the same shape as #187
(an artifact that builds, installs and cannot authenticate).

This was not hypothetical during this work: after the deploy was
unblocked, confirming that the #173 fix was actually live meant SSHing in
and grepping the deployed bundles by hand.

There is now a step between the roll and the health check that compares
the running containers' images against the ones this run built:

```
running images:
  …/thrw/relay:<sha>
  …/thrw/relay-service:<sha>
```

Exact full-line matching (`grep -qxF`), which matters: `relay` is a
prefix of `relay-service`, and a truncated SHA is a prefix of a full one.

## A bug found in my own verification step, worth recording

The first version of that step declared `RELAY_VM_NAME: ${{
vars.RELAY_VM_NAME || … }}` and omitted `IMAGE` entirely.

Those variables are **step-scoped, not job-scoped**. Omitting them would
have compared against empty strings and failed *every* deploy, and the
wrong `vars.` name (`RELAY_VM_NAME` rather than `GCP_RELAY_VM_NAME`)
would have silently ignored a configured override while appearing to work
via the default. The step's env now mirrors "Roll the relay VM"'s
exactly, and that is asserted rather than eyeballed.

Mentioned because it is the same class of mistake as the issue itself: a
step that looks right, goes green in review, and does the wrong thing
against real infrastructure.

## Verification

This cannot be verified by running it — that means deploying to
production. What was checked instead:

- Both workflow files parse, and the step order is
  `Roll → Verify → Health check`.
- `bash -n scripts/relay-redeploy.sh` passes, and no `/tmp/` path remains
  in either file outside an explanatory comment.
- The verify step's env matches the roll step's for all four variables,
  asserted programmatically.
- **The real output format was checked against the live VM**:
  `docker inspect relay --format '{{.Config.Image}}'` returns
  `us-central1-docker.pkg.dev/thrw-prod/thrw/relay:<sha>`, which is
  exactly the shape the comparison builds.
- The comparison logic was simulated with those real strings: a matching
  SHA passes, a stale container fails, and a truncated SHA is correctly
  rejected rather than matching as a prefix.

## Not done: alerting

The issue also asks for the deploy failure to be *noticed*. That is the
part that turned two days of silent failure into a problem, and it is
**not fixed here**.

Nothing was invented for it because there is no channel to send to: the
repository has no Slack/Discord/webhook secret (`gh secret list` —
`AGENT_APP_*`, `CLOUDFLARE_*`, `EMQX_*`, `GCP_*`, `THRW_PLAY_*`,
`WIF_PROVIDER`). The options each need a decision rather than a guess:

1. **Rely on GitHub's own failure notifications.** Possibly already
   sufficient — worth checking what Tom actually receives for a failed
   `deploy.yml` run before building anything.
2. **Open or update a GitHub issue on failure**, using the built-in
   token. No new secret, and he already watches issues; needs care to
   update one issue rather than file a new one per failure.
3. **A webhook** to wherever he would actually see it, which needs a
   secret he would have to add.

Option 1 should be checked first, because it may make the other two
unnecessary.
