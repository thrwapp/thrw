# #158: Android MQTT connect hangs forever on-device

## Root cause

**`netty-codec-http` was missing from the app's runtime classpath.** That
is where Netty's `WebSocketClientHandshaker` lives, so the app had no
WebSocket implementation at all. `hivemq-mqtt-client` treats WebSocket
support as optional and does not declare it — its POM brings in
`netty-buffer`, `netty-codec`, `netty-handler`, `netty-transport` and
`netty-resolver`, but not `netty-codec-http`.

Without it, a `ws://` or `wss://` connect **hangs forever** rather than
failing: the handshake dies inside Netty's pipeline and the connect
future is never completed. On the device that presented as a perfectly
healthy-looking foreground service — notification showing, TLS socket
established to the relay — with no MQTT session, indefinitely.

## Why no test caught it, and why the tests were actively misleading

`HiveMqttTransportTest` runs against **embedded Moquette**, which depends
on `netty-codec-http` transitively. So the *test* classpath had the
dependency and the *app* classpath never did:

```
debugRuntimeClasspath          -> netty-codec-http ABSENT
debugUnitTestRuntimeClasspath  -> io.netty:netty-codec-http:4.1.93.Final
```

The existing WebSocket test passed **for the wrong reason** — it was
validating a classpath the app never had. This is the most important
thing to take from this issue: a green test suite said the transport
worked, and it had never once been exercised in the configuration that
ships.

## How it was actually diagnosed

Worth recording, because the first approach was wrong and expensive.

**What didn't work:** guess-and-check on the device. TLS on/off, `/mqtt`
vs `mqtt`, explicit `subprotocol("mqtt")`, credentials vs anonymous —
each needed a rebuild, reinstall, unlock, tap and wait, and each ruled
out one hypothesis. That consumed a long real-time debugging session and
found nothing.

**What worked, in about a minute:** reproducing off-device. A throwaway
JUnit probe using the identical client, config and credentials connected
to the real relay from the JVM:

```
PROBE: CONNECTED in 1464ms -> MqttConnAck{returnCode=SUCCESS, sessionPresent=false}
```

Same code, JVM works, Android hangs → the difference is environmental,
not logical. Comparing the two classpaths found it immediately. **Compare
the working and failing environments before theorising about the code.**

## Acceptance criteria

1. **Root cause found and fixed** — `implementation("io.netty:netty-codec-http:4.1.99.Final")`
   in `app/build.gradle.kts`, version pinned to match the other Netty
   modules HiveMQ resolves rather than floating, since mixing Netty
   module versions is its own class of runtime failure. An SLF4J binding
   turned out not to be needed; the classpath diff was decisive.
2. **Connect timeout added** — `CONNECT_TIMEOUT_MS = 20_000`, applied
   with `withTimeout` around the blocking connect, which has no timeout
   of its own. Cancellation can't interrupt the blocking call itself, but
   it frees the caller and surfaces a `TimeoutCancellationException` the
   service logs. Any future variant of this fails loudly instead of
   hanging.
3. **Connect logging kept** (merged from the #159 branch): connection
   parameters up front, then success or failure either way.
4. **A test that would have caught this** — see "Known gaps". Not solved
   here, and I want to be straight about that rather than claim it.
5. **Verified on the real Pixel 10 Pro against `relay.thrw.app`** —
   below.

## Verification

On-device, against production:

```
AdapterForegroundService: Connecting to relay.thrw.app:443 (ws=true, tls=true, path=mqtt) as 56479cf1-... credentials=true
AdapterForegroundService: MQTT connected; registering node 56479cf1-... on account tom-personal
```

**1.6 seconds**, where it previously hung indefinitely. Confirmed from
the broker side by subscribing to `thrw/tom-personal/#` on
`relay.thrw.app` and watching the phone's own traffic arrive:

```
thrw/tom-personal/nodes/56479cf1-.../heartbeat   (empty payload)
thrw/tom-personal/nodes/56479cf1-.../heartbeat   (empty payload)
```

Heartbeats at the 30s interval #142 specified. **This is the first time
`packages/adapter-android` has ever connected to the real relay.**

`./gradlew test` passes.

## Known gaps / judgment calls

- **Criterion 4 is not met.** There is still no automated test that
  would catch this class of bug. The honest problem: the only reliable
  check is "does the *app's* runtime classpath contain what the app
  needs", and the existing unit test actively hides that by supplying the
  dependency itself. Options worth considering, none implemented here: an
  instrumented (on-device/emulator) test; a Gradle check asserting
  `netty-codec-http` is on `debugRuntimeClasspath`; or removing Moquette's
  transitive contribution from the test classpath so the unit test fails
  the same way the app does. The last is probably the most valuable and
  the most fiddly. Filed as a gap rather than guessed at.
- **The timeout can't interrupt the blocking call.** `withTimeout` frees
  the coroutine and reports the failure, but HiveMQ's blocking connect
  keeps its own thread until it returns. Acceptable — the point is
  diagnosability, not thread reclamation — but it means a hung connect
  still costs a thread until the underlying socket gives up.
- **20 seconds is a judgment call**, not a measured value. Real connects
  take ~1.5s over mobile data; 20s is generous enough to absorb a bad
  network without leaving a user staring at nothing indefinitely.
- **adapter-mac is unaffected** — MQTTNIO bundles its own WebSocket
  support, which is why the Mac connected to production before this fix
  existed.
